# 서버 Day 14 - 원자 연산과 메모리 모델

멀티스레드에서는 하나의 값을 안전하게 읽고 쓰는 문제와, 다른 데이터의 변경까지 올바르게 전달하는 문제를 구분해야 한다.

`atomic`은 개별 연산의 원자성을 제공한다. 여기에 메모리 순서 정책을 지정하면 스레드 사이에서 데이터가 전달되는 순서도 표현할 수 있다.

이번에는 **원자성, 같은 객체의 수정 순서, 여러 데이터 사이의 동기화**를 나누어 살펴본다.

## 원자적 연산이란?

원자적 연산은 다른 스레드가 중간에 끼어들어 쪼개진 상태를 관찰할 수 없는 작업이다.

```cpp
std::atomic<int> num{0};

num.store(10);
```

다른 스레드는 원자적 읽기로 변경 전 값이나 변경 후 값을 읽는다. 저장 도중 일부만 바뀐 값을 읽지는 않는다.

증가처럼 여러 단계가 필요한 작업도 원자 연산으로 묶을 수 있다.

```cpp
num.fetch_add(1);
```

이는 읽기, 1 더하기, 저장 전체를 하나의 원자적 연산으로 처리한다.

반면 다음 코드는 다르다.

```cpp
num.store(num.load() + 1);
```

읽기와 저장이 각각 원자적일 뿐, 전체가 하나의 연산은 아니다. 두 스레드가 같은 값을 읽고 같은 결과를 저장하면 증가 하나가 사라질 수 있다.

**원자 타입을 사용한다고 모든 코드 묶음이 자동으로 원자적이 되는 것은 아니다.**

## 동일한 수정 순서를 관찰한다는 의미

원자 객체 하나에 대한 수정들은 하나의 순서로 정해진다. 이를 **수정 순서(Modification Order)**라고 한다.

여러 스레드가 같은 `num`에 각각 `2`, `1`, `5`를 저장한다고 하자. 어느 저장이 먼저인지는 실행에 따라 달라질 수 있다. 한 실행에서 다음 수정 이력이 정해질 수 있다.

```text
초기값 0 → 2 저장 → 1 저장 → 5 저장
```

이것은 숫자 크기순이 아니라 해당 객체에 값을 저장한 순서다.

다만 모든 스레드가 동시에 같은 값을 읽거나, 중간 값을 빠짐없이 관찰한다는 뜻은 아니다. 관찰 시점이 달라 일부 수정을 건너뛸 수 있다.

```text
관찰자 A: 0 → 2 → 5
관찰자 B: 0 → 1 → 5
```

단순히 읽기만 하는 한 관찰자의 연속된 읽기는 정해진 수정 이력을 거슬러 올라가지 않는다. 위 이력에서 `5`를 읽은 다음 이전 수정의 `2`로 돌아가는 식으로 관찰하지 않는다는 뜻이다.

물론 나중에 누군가 `2`를 다시 저장했다면 그것은 새로운 수정이다. 값이 같더라도 수정 이력의 위치는 다를 수 있다.

또한 이 보장은 **원자 객체 하나에 대한 것**이다. `x`와 `y`가 각각 원자적이라고 해서 두 객체의 모든 접근을 묶는 하나의 순서가 자동으로 생기는 것은 아니다. [C++ 수정 순서와 일관성 규칙](https://eel.is/c++draft/intro.races)

## 원자성과 메모리 순서는 다른 질문이다

| 질문 | 관련 개념 |
|---|---|
| 연산 자체가 쪼개지지 않는가? | 원자성 |
| 같은 원자 객체의 수정 이력은 어떤 순서인가? | 수정 순서 |
| 다른 데이터의 변경도 함께 전달되는가? | 메모리 순서와 동기화 |

다음 생산자·소비자 예제는 세 번째 질문을 보여준다.

```cpp
std::atomic<bool> ready{false};
int value = 0;
```

`ready`는 준비 완료를 알리는 원자 변수이고, 실제로 전달할 데이터는 일반 변수인 `value`다.

## seq_cst로 준비한 데이터 전달하기

생산자는 값을 준비한 뒤 준비 완료를 알린다. 소비자는 준비 완료를 확인한 뒤 값을 읽는다.

```cpp
#include <atomic>
#include <iostream>
#include <thread>

std::atomic<bool> ready{false};
int value = 0;

void Producer()
{
    value = 10;

    ready.store(true, std::memory_order_seq_cst);
}

void Consumer()
{
    while (ready.load(std::memory_order_seq_cst) == false)
    {
    }

    std::cout << value << "\n";
}

int main()
{
    std::thread t1(Producer);
    std::thread t2(Consumer);

    t1.join();
    t2.join();
}
```

이 예제에서는 생산자만 `true`를 저장한다. 소비자가 그 `true`를 읽고 반복문을 통과하면 다음 관계가 성립한다.

```text
value에 10 저장
→ ready에 true 저장
→ 소비자가 그 true를 읽음
→ value 읽기
```

**준비 완료 신호를 통해 앞서 작성한 데이터까지 안전하게 전달하는 구조**다. 소비자가 반복문을 통과하면 `10`을 출력한다.

`value` 자체가 원자 변수가 아니어도 쓰기와 읽기 사이에 올바른 동기화 관계가 있으므로 안전하다. 다만 이것은 한 번 값을 준비해 전달하는 예제다. 생산자가 이후 `value`를 다시 수정한다면 별도의 규칙이 필요하다.

이 반복문은 조건 변수처럼 스레드를 재우지는 않는다. 대기 방식보다 메모리 순서를 살펴보기 위한 바쁜 대기 예제다.

## seq_cst: 기본으로 사용하는 강한 순서

다음 두 코드는 같은 기본 정책을 사용한다.

```cpp
ready.store(true);
```

```cpp
ready.store(true, std::memory_order_seq_cst);
```

`seq_cst`는 원자성뿐 아니라 이 정책을 사용하는 연산들에 공통된 전체 순서를 제공한다.

다만 모든 스레드가 한 번에 하나씩만 실행되거나, 프로그램 전체의 명령어 재배치가 금지된다는 뜻은 아니다. 관계없는 일반 변수의 데이터 레이스까지 자동으로 해결하지도 않는다.

처음에는 기본 정책으로 정확한 코드를 작성하고, 명확한 이유가 있을 때 더 약한 정책을 고려하는 편이 이해하기 쉽다.

## acquire-release: 준비한 데이터를 전달하는 연결

같은 예제를 다음과 같이 작성해도 된다.

```cpp
void Producer()
{
    value = 10;

    ready.store(true, std::memory_order_release);
}

void Consumer()
{
    while (ready.load(std::memory_order_acquire) == false)
    {
    }

    std::cout << value << "\n";
}
```

핵심은 다음 조건이다.

> 소비자의 acquire 읽기가 생산자의 release 저장값을 읽으면, 생산자가 그 전에 수행한 쓰기를 소비자의 이후 작업에 전달할 수 있다.

```text
생산자                           소비자
value = 10
    ↓
ready에 true 저장 ───────────→ 그 true를 읽음
       release                    acquire
                                     ↓
                                 value 읽기
```

단순히 같은 변수에 `release`와 `acquire`라는 이름을 붙이는 것만으로 끝나지 않는다. 해당 저장값을 읽는 연결이 필요하다. [C++ 원자 연산의 메모리 순서 규칙](https://eel.is/c++draft/atomics.order)

입문 단계에서는 release 이전 작업이 신호 뒤로 넘어가지 않고, acquire 이후 작업이 신호 확인 앞으로 넘어가지 않도록 한다는 그림으로 이해할 수 있다. 실제 코드를 판단할 때는 어떤 저장과 읽기가 연결되어 데이터를 전달하는지 확인하는 것이 더 정확하다.

`seq_cst`와 달리, acquire-release만으로 서로 다른 모든 원자 객체에 대한 공통의 전체 순서를 제공하는 것은 아니다.

## relaxed: 개별 원자성은 있지만 주변 데이터 전달은 없다

```cpp
ready.store(true, std::memory_order_relaxed);
```

```cpp
ready.load(std::memory_order_relaxed);
```

`relaxed`도 원자 연산이다. `ready` 자체의 원자성과 수정 순서는 유지된다.

하지만 이것만으로 생산자의 일반 변수 `value` 쓰기와 소비자의 읽기를 연결하지는 않는다. **위 생산자·소비자 예제에서 양쪽을 relaxed로 바꾸면 `value`에 데이터 레이스가 생긴다.**

단순히 `0`이나 `10` 중 하나를 출력하는 프로그램으로 해석하면 안 된다. 표준 C++에서 동작이 정의되지 않는다.

반면 다른 데이터를 함께 전달할 필요가 없는 독립적인 집계에는 사용할 수 있다.

```cpp
std::atomic<int> count{0};

count.fetch_add(1, std::memory_order_relaxed);
```

이 경우에도 최종 집계 결과를 언제 읽을지는 `join()` 등으로 별도 관리해야 한다.

| 정책 | 핵심 |
|---|---|
| seq_cst | 강한 순서 보장, 기본 선택 |
| release / acquire | 연결된 저장·읽기를 통해 주변 데이터 전달 |
| relaxed | 개별 원자성과 객체별 수정 순서 유지, 주변 데이터 동기화 없음 |

메모리 순서는 모든 연산에 아무렇게나 지정하는 옵션도 아니다. 예를 들어 `store()`에 `acquire`, `load()`에 `release`를 지정할 수 없다.

`acq_rel`은 `exchange()` 같은 읽기·수정 연산 등에 acquire와 release 양쪽 성질이 필요할 때 사용한다. `consume`은 의존성을 다루는 별도 주제이므로, 처음에는 위 세 흐름에 집중해도 충분하다.

## exchange와 CAS도 원자 연산이다

```cpp
std::atomic<bool> flag{false};
bool previous = flag.exchange(true);
```

`exchange()`는 이전 값을 받으면서 새 값을 저장하는 전체 과정이 하나의 원자 연산이다.

CAS는 비교가 성공했을 때만 값을 바꾸는 조건부 변경이다.

```cpp
bool expected = false;
bool desired = true;

bool success = flag.compare_exchange_strong(expected, desired);
```

현재 값이 예상값과 같으면 변경하고 성공한다. 다르면 실패하고 `expected`에 관찰한 값을 넣는다.

### weak와 strong의 차이

`compare_exchange_weak()`는 비교한 값이 같아도 실패하는 것이 허용된다. 이를 가짜 실패라고 한다.

이것이 반드시 다른 스레드가 방해해서 실패한다는 뜻은 아니다. 하드웨어 구현 방식 등으로 허용되는 실패이므로 보통 재시도 반복문에서 사용한다.

`compare_exchange_strong()`은 이런 가짜 실패 없이 비교 결과에 따라 성공·실패한다. 두 함수 모두 실제 값이 예상과 다르면 실패할 수 있다.

반복할 때는 CAS 실패로 `expected`가 바뀐다는 점도 함께 고려해야 한다.

## atomic이면 내부 잠금이 없을까?

```cpp
bool lockFree = flag.is_lock_free();
```

`is_lock_free()`는 해당 원자 객체의 연산이 잠금 없이 구현되는지 확인하는 함수다.

`atomic`이라는 이유만으로 모든 타입과 환경에서 내부 잠금이 없다고 가정하면 안 된다. 잠금 없이 구현되는지 여부와, 원자성이 보장되는지 여부는 구분해야 한다.

## CPU 차이보다 C++의 보장으로 판단하기

x86 계열과 ARM 계열은 하드웨어의 메모리 순서 규칙이 다를 수 있다. 같은 C++ 원자 연산도 CPU에 따라 다른 명령어로 구현될 수 있다.

하지만 특정 CPU에서는 원래 일관되니 필요한 동기화를 생략해도 된다고 판단하면 안 된다. 컴파일러 최적화와 C++의 메모리 모델까지 함께 적용되기 때문이다.

`atomic_thread_fence()`도 메모리 순서를 조절하는 도구다. 다만 아무 위치에 추가하면 일반 변수의 데이터 레이스를 해결하는 만능 장벽은 아니다. 관련 원자 연산과의 관계를 설계해야 한다.

메모리 모델에서 기억할 핵심은 **원자성은 연산 자체를 보호하고, 메모리 순서는 그 연산을 통해 다른 데이터까지 어떻게 전달할지 정한다는 것**이다.
