# 서버 Day 08 - Sleep과 Yield로 잠금 대기 조절하기

스핀락은 잠금을 얻을 때까지 계속 시도한다. 잠금이 빨리 풀리면 작업을 빠르게 이어갈 수 있지만, 오래 기다리면 CPU 시간을 낭비할 수 있다.

이번에는 CAS로 잠금을 획득하는 방식은 유지하면서, **실패하면 잠시 쉬거나 실행 기회를 양보하도록 대기 정책을 변경하는 방법**을 알아본다.

## 계속 재시도하는 대신 잠시 쉬기

기존 스핀락은 CAS가 실패하면 곧바로 다시 시도한다.

```cpp
while (_locked.compare_exchange_strong(expected, desired) == false)
{
    expected = false;
}
```

잠금을 얻을 때까지 CPU를 사용하며 반복하는 방식이다.

여기에 `sleep_for()`를 추가하면 재시도 사이에 쉬는 시간을 둘 수 있다.

```cpp
while (_locked.compare_exchange_strong(expected, desired) == false)
{
    expected = false;

    std::this_thread::sleep_for(std::chrono::milliseconds(1));
}
```

실행 흐름은 다음과 같다.

```text
CAS로 잠금 획득 시도
→ 실패
→ expected를 false로 초기화
→ 1밀리초 동안 쉬기
→ 다시 CAS 시도
```

`expected`를 초기화하는 이유는 CAS가 실패하면 비교 시 읽은 실제 값으로 바뀌기 때문이다. 다음 시도에서도 풀린 상태인 `false`와 비교해야 한다.

여기서 **잠금의 정확성은 CAS가 담당하고, `sleep_for()`는 재시도 간격을 조절한다.** 잠시 쉰다고 잘못된 잠금 구현이 올바르게 바뀌는 것은 아니다.

## sleep_for()는 현재 스레드를 쉬게 한다

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(1));
```

| 표현 | 의미 |
|---|---|
| this_thread | 이 코드를 실행하는 현재 스레드에 대한 기능 |
| sleep_for() | 지정한 시간 동안 현재 스레드의 실행을 멈춤 |
| milliseconds(1) | 1밀리초, 즉 0.001초 |

쉬는 동안에는 해당 스레드가 CAS를 반복하지 않는다. 그 실행 자원을 다른 준비된 스레드가 사용할 수 있다.

다만 **정확히 1밀리초 뒤에 실행이 재개된다는 보장은 없다.** 스케줄링과 시스템 상황에 따라 더 늦게 실행될 수 있다. [Microsoft의 스레드 함수 문서](https://learn.microsoft.com/en-us/cpp/standard-library/thread-functions?view=msvc-170)

## 준비·실행·대기 상태로 이해하기

스레드 상태를 단순화하면 다음과 같이 구분할 수 있다.

| 상태 | 의미 |
|---|---|
| 실행 | CPU에서 코드를 실행하고 있음 |
| 준비 | 실행할 수 있지만 CPU 차례를 기다림 |
| 대기 | 시간 경과나 입출력 완료 같은 조건을 기다림 |

`sleep_for()`를 호출하는 흐름은 다음과 같이 이해할 수 있다.

```text
실행
→ sleep_for() 호출
→ 대기
→ 지정한 시간 경과
→ 준비
→ 스케줄러가 선택
→ 실행 재개
```

중요한 것은 **시간이 지나면 바로 실행되는 것이 아니라, 실행 가능한 상태가 된다는 점**이다.

CPU에서 다른 스레드로 실행을 전환할 때는 실행 상태를 저장하고 복원하는 문맥 교환이 발생할 수 있다. 따라서 쉬는 동안 CPU 사용을 줄이는 효과와 함께, 대기 및 실행 재개에 드는 비용도 고려해야 한다.

## 잠금이 풀렸다고 깨워 주는 방식은 아니다

`sleep_for()`는 시간을 기준으로 다시 시도하는 방식이다. 잠금 해제 통지를 기다리는 기능이 아니다.

예를 들어 다음 상황이 가능하다.

```text
스레드 B: 잠금 획득 실패 → 1밀리초 쉬기 시작
스레드 A: 잠금 해제
스레드 B: 아직 쉬는 중…
```

A가 잠금을 풀었다고 B의 `sleep_for()`가 끝나지는 않는다. 잠금이 이미 풀려 있어도 B는 쉬는 시간이 끝나고 실행 기회를 얻을 때까지 기다릴 수 있다.

반대로 시간이 지난 뒤에도 A가 잠금을 가지고 있다면, B는 다시 CAS에 실패하고 쉰다.

따라서 식당에 비유하면 **잠시 물러났다가 다시 자리를 확인하는 방식**이다. 직원에게 자리가 나면 알려 달라고 부탁하는 통지 기반 대기와는 구분해야 한다.

## yield()는 실행 기회를 양보한다

시간을 정해서 쉬는 대신, 스케줄러에 실행 기회 양보를 요청할 수도 있다.

```cpp
std::this_thread::yield();
```

이를 적용하면 잠금 획득 실패 후 흐름은 다음과 같다.

```text
CAS 실패
→ 실행 기회 양보 요청
→ 다시 실행되면 CAS 재시도
```

`yield()`를 호출해도 반드시 다른 스레드가 실행되는 것은 아니다. 실행 가능한 스레드와 스케줄링 정책에 따라 같은 스레드가 곧바로 계속 실행될 수도 있다.

| 구분 | sleep_for() | yield() |
|---|---|---|
| 시간 지정 | 있음 | 없음 |
| 목적 | 일정 시간 실행을 멈춤 | 실행 기회 양보 요청 |
| 재개 시점 | 지정 시간 경과 후 스케줄링에 따라 결정 | 스케줄링에 따라 결정 |
| 잠금 해제 통지 | 받지 않음 | 받지 않음 |

두 함수 모두 **호출한 스레드가 이미 보유한 잠금을 자동으로 해제하지 않는다.**

여기서는 CAS에 실패해 잠금을 얻지 못한 스레드가 쉬는 것이다. 잠금을 가진 스레드가 보호 구간 안에서 쉬면 그 잠금은 계속 유지되므로, 다른 스레드의 대기 시간이 길어질 수 있다.

## 잠시 쉬었다가 재시도하는 잠금 구현

다음은 CAS 실패 시 `sleep_for()`를 호출하는 구현이다.

```cpp
#include <atomic>
#include <chrono>
#include <thread>

class SpinLock
{
public:
    void lock()
    {
        bool expected = false;
        bool desired = true;

        while (_locked.compare_exchange_strong(expected, desired) == false)
        {
            expected = false;

            std::this_thread::sleep_for(std::chrono::milliseconds(1));
        }
    }

    void unlock()
    {
        _locked.store(false);
    }

private:
    std::atomic<bool> _locked{false};
};
```

`_locked{false}`는 처음에는 잠금이 풀려 있음을 명시한다.

클래스 이름은 `SpinLock`이지만, 이 구현은 순수하게 계속 도는 스핀 방식에 잠시 쉬었다가 재시도하는 정책을 넣은 형태다.

사용 방법은 기존과 같다. `<mutex>` 헤더의 `lock_guard`로 잠금 획득과 해제를 관리할 수 있다.

```cpp
std::lock_guard<SpinLock> guard(spinlock);
sum++;
```

같은 잠금으로 증가와 감소를 보호하고 두 스레드를 `join()`한 뒤 결과를 읽으면, 같은 횟수만큼 증가·감소한 `sum`은 정상 완료 시 `0`이다. 대기 방식의 변경은 보호 규칙을 바꾸지 않는다.

## 여러 번 시도한 뒤 쉬는 정책도 가능하다

처음부터 매번 쉬는 대신, 일정 횟수 동안 즉시 재시도하다가 계속 실패하면 쉬도록 만들 수도 있다.

```text
몇 번은 즉시 재시도
→ 계속 실패하면 yield 또는 sleep
→ 다시 잠금 획득 시도
```

잠금이 빨리 풀리면 바로 얻고, 오래 기다리게 되면 CPU 낭비를 줄이려는 방식이다.

다만 시도 횟수와 쉬는 시간에 정답이 있는 것은 아니다. 잠금 유지 시간과 경쟁하는 스레드 수, 실행 환경에 따라 효과가 달라진다. `1밀리초` 역시 이 예제의 대기 시간일 뿐, 모든 상황에 적합한 기준은 아니다.

## CPU 사용량과 재시도 지연 사이의 균형

| 방식 | 기대할 수 있는 효과 | 비용·주의점 |
|---|---|---|
| 즉시 재시도 | 잠금이 풀리면 빠르게 획득 시도 | 기다리는 동안 CPU 사용 |
| yield 후 재시도 | 다른 스레드에 실행 기회를 줄 수 있음 | 즉시 같은 스레드가 재실행될 수도 있음 |
| sleep 후 재시도 | 재시도 빈도와 대기 중 CPU 사용 감소 | 잠금이 풀린 뒤에도 늦게 알아차릴 수 있음 |

잠금 획득 실패 후 쉬는 시간을 두면 CPU 낭비를 줄일 수 있지만, 작업을 다시 시작하기까지의 지연이 늘어날 수 있다.

잠금 구현에서는 **CAS로 정확성을 확보하는 것과, 대기 정책으로 성능을 조절하는 것을 구분하는 것**이 중요하다.
