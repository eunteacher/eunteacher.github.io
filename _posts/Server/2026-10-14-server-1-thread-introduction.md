# 서버 Day 01 - 스레드 개론

파일을 저장하는 동안에도 버튼을 누를 수 있고, 게임 서버는 여러 사용자의 요청을 처리한다. 프로그램은 어떻게 여러 일을 함께 진행할 수 있을까?

이를 이해하려면 **프로세스, 스레드, CPU 코어**의 관계부터 살펴봐야 한다.

## 프로그램을 실행하면 프로세스가 된다

프로그램은 디스크에 저장된 명령어와 데이터다. 실행 파일이 저장되어 있다는 것만으로 CPU가 그 명령어를 실행하지는 않는다.

프로그램을 실행하면 운영체제가 메모리와 필요한 자원을 준비하고 실행을 관리한다. 이렇게 **실행 중인 프로그램을 프로세스(Process)**라고 한다.

프로세스는 자신의 가상 메모리 공간을 가지며, 기본적으로 다른 프로세스의 메모리에 직접 접근할 수 없다. 프로세스끼리 데이터를 주고받으려면 운영체제가 제공하는 통신이나 공유 메모리 등의 방법을 사용해야 한다.

그런데 실행 환경이 준비됐다고 코드가 저절로 실행되는 것은 아니다. 프로세스 안에서 명령어를 순서대로 실행하는 흐름이 필요하다. 이것이 **스레드(Thread)**다.

| 개념 | 의미 |
|---|---|
| 프로그램 | 저장된 명령어와 데이터 |
| 프로세스 | 프로그램을 실행하며 자원을 관리하는 단위 |
| 스레드 | 프로세스 안에서 코드를 실행하는 흐름 |
| CPU 코어 | 명령어를 실제로 실행하는 하드웨어 |

하나의 프로세스 안에는 여러 스레드가 존재할 수 있다.

## 스레드 하나는 한 번에 하나의 실행 흐름을 따라간다

하나의 스레드에서 다음 코드를 실행한다고 생각해 보자.

```cpp
void Run()
{
    ReadInput();
    Calculate();
    DrawScreen();
}
```

입력 처리가 끝나면 계산하고, 계산이 끝나면 화면을 갱신한다.

여기서 `Calculate()`에 10초가 걸리면 해당 스레드는 그동안 다음 화면 갱신으로 넘어가지 못한다. 입력 처리도 같은 스레드가 맡는다면 추가 입력에 응답하지 못할 수 있다.

사용자에게는 프로그램이 멈춘 것처럼 보인다.

이때 실행 흐름을 나눌 수 있다.

```text
UI 스레드   : 사용자 입력 처리, 화면 갱신
작업 스레드 : 오래 걸리는 계산
```

이처럼 하나의 프로세스에서 여러 스레드를 사용하는 것을 **멀티스레딩(Multithreading)**이라고 한다.

다만 스레드를 나누는 것만으로 협력이 완성되지는 않는다. 작업 결과를 전달하고, 작업이 끝났다는 사실을 알리는 방법도 필요하다.

## 스레드를 실제로 실행하는 것은 CPU다

스레드는 소프트웨어의 실행 흐름이고, CPU 코어는 명령어를 실행하는 하드웨어다.

따라서 스레드 100개를 만든다고 CPU의 실행 능력이 100배가 되는 것은 아니다. 실행하려는 흐름이 100개 생기는 것이다.

이 중 어떤 스레드에 CPU를 사용할 기회를 줄지는 운영체제의 **스케줄러(Scheduler)**가 결정한다.

스레드의 상태는 크게 다음과 같이 이해할 수 있다.

| 상태 | 의미 |
|---|---|
| 준비 | 실행할 수 있지만 CPU 차례를 기다리는 상태 |
| 실행 | CPU에서 명령어를 실행하는 상태 |
| 대기 | 입출력 완료나 잠금 해제 등을 기다리는 상태 |

실행 가능한 스레드가 많아도 모든 스레드가 한꺼번에 CPU를 사용할 수 있는 것은 아니다.

## 동시성과 병렬성은 다르다

CPU의 실행 자리가 하나라고 단순화하면 여러 스레드는 번갈아 실행된다.

```text
시간 →
[A 실행][B 실행][C 실행][A 실행][B 실행]…
```

운영체제는 현재 스레드의 실행 상태를 저장하고 다음 스레드의 상태를 복원한다. 이를 **문맥 교환(Context Switch)**이라고 한다.

실행 위치와 레지스터 값 등을 저장하기 때문에, 나중에 다시 실행할 때 이전 작업을 이어갈 수 있다.

이처럼 여러 작업을 같은 기간에 진행하는 것을 **동시성(Concurrency)**이라고 한다. 반드시 같은 순간에 실행할 필요는 없다.

반면 여러 코어에서 서로 다른 스레드를 실제로 같은 순간에 실행하는 것은 **병렬성(Parallelism)**이다.

```text
시간 →
코어 1 : [A 실행──────────]
코어 2 : [B 실행──────────]
```

즉, **멀티스레딩은 여러 실행 흐름을 만드는 것이고, 병렬 실행 여부는 CPU 자원과 실행 상황에 달려 있다.**

엄밀하게는 운영체제가 스레드를 배정하는 논리 프로세서를 기준으로 봐야 한다. SMT를 사용하는 CPU에서는 물리 코어 하나가 여러 논리 프로세서를 제공할 수 있다.

## 기다리는 동안에는 다른 일을 할 수 있다

스레드가 항상 계산만 하는 것은 아니다. 네트워크 데이터가 도착하거나 DB 응답이 돌아오기를 기다리기도 한다.

```text
요청 전송 → 응답 대기 → 결과 처리
```

입출력을 기다리며 대기 상태에 들어간 스레드 대신 다른 스레드가 CPU 실행 시간을 사용할 수 있다.

```text
스레드 A : 요청 전송 → 대기………… → 결과 처리
스레드 B :            다른 작업 처리
```

따라서 멀티스레딩은 계산을 나눠 처리할 때뿐 아니라, 한 작업이 기다리는 동안 다른 작업을 진행할 때도 유용하다.

그렇다고 서버에서 접속자마다 스레드를 하나씩 만들어야 하는 것은 아니다. 비동기 입출력과 스레드 풀을 이용하면 제한된 수의 스레드로 많은 요청을 처리할 수도 있다.

## 스레드는 메모리를 공유하지만 실행 상태는 따로 가진다

같은 프로세스의 스레드는 메모리 공간을 공유한다. 따라서 여러 스레드가 같은 객체나 데이터에 접근할 수 있다.

반면 각 스레드는 자신의 스택과 실행 상태를 가진다.

```text
하나의 프로세스
├─ 공유: 코드, 전역·정적 변수, 힙 메모리
├─ 스레드 A: 스택 A, 실행 상태 A
└─ 스레드 B: 스택 B, 실행 상태 B
```

C++의 일반적인 실행 모델에서는 다음과 같이 정리할 수 있다.

| 구분 | 대표적인 내용 | 관계 |
|---|---|---|
| 코드 | 실행할 명령어 | 공유 |
| 전역·정적 저장 영역 | 전역 변수, 일반적인 정적 변수 | 공유 |
| 힙 | 동적으로 할당한 객체 | 같은 객체에 접근 가능 |
| 스택 | 함수 호출 정보, 일반적인 지역 변수 | 스레드마다 별도 |
| 실행 상태 | 실행 위치, 레지스터 값 등 | 스레드마다 별도 |

예를 들어 두 스레드가 같은 함수를 실행하더라도 일반적인 지역 변수는 각 호출에 따로 존재한다.

```cpp
void Work()
{
    int localCount = 0;
}
```

반면 전역 변수는 같은 데이터를 함께 사용한다.

```cpp
int sharedCount = 0;

void Work()
{
    ++sharedCount;
}
```

여기서 주의할 점은 **스택이 별도라는 것이 접근까지 차단한다는 의미는 아니라는 것**이다. 지역 변수의 주소를 다른 스레드에 전달하면 그 스레드도 접근할 수 있다. 이 경우 변수의 수명과 접근 규칙을 관리해야 한다.

또한 `thread_local`로 선언한 변수는 스레드마다 별도로 존재한다.

## 공유 데이터에는 동기화가 필요하다

메모리 공유는 데이터를 전달하기 쉽게 해주지만, 여러 스레드가 같은 값을 수정하면 문제가 생길 수 있다.

플레이어의 골드가 100이고, 두 스레드가 각각 10을 추가한다고 해보자. 기대하는 결과는 120이다.

하지만 증가 작업은 개념적으로 다음 단계로 나눌 수 있다.

```text
현재 값 읽기 → 10 더하기 → 결과 저장
```

실행이 겹치면 다음과 같은 상황을 생각할 수 있다.

| 순서 | 스레드 A | 스레드 B |
|---|---|---|
| 1 | 100 읽기 | |
| 2 | | 100 읽기 |
| 3 | 110 저장 | |
| 4 | | 110 저장 |

두 번 증가시켰지만 한 번의 변경이 사라진 셈이다.

이것은 문제의 원리를 단순화한 예다. **C++에서 일반 변수에 동기화 없이 이런 접근을 하면 데이터 레이스가 발생하며, 프로그램의 동작은 정의되지 않는다.** 단순히 예상 가능한 몇 가지 결과 중 하나가 나온다는 의미가 아니다.

이를 막기 위해 공유 데이터에 접근하는 규칙을 정하는 것이 **동기화(Synchronization)**다.

대표적인 방법이 뮤텍스를 사용하는 것이다.

```cpp
#include <mutex>

int gold = 100;
std::mutex goldMutex;

void AddGold()
{
    std::lock_guard<std::mutex> lock(goldMutex);
    gold += 10;
}
```

같은 데이터를 사용하는 모든 관련 접근이 같은 잠금 규칙을 따른다면, 보호된 구간에 여러 스레드가 동시에 진입하는 것을 막을 수 있다.

## 현실에서는 작업과 데이터를 깔끔하게 나누기 어렵다

이상적으로는 각 스레드가 독립적인 작업만 처리하면 좋다.

```text
스레드 A → 플레이어 A
스레드 B → 플레이어 B
스레드 C → 플레이어 C
```

그러나 게임 서버에서는 플레이어끼리 상호작용한다.

A가 B를 공격하려면 A의 공격력뿐 아니라 B의 체력, 두 플레이어의 위치, 주변에 결과를 전달할 대상 등을 확인해야 한다.

**작업을 나눴다고 필요한 데이터까지 완전히 분리되는 것은 아니다.**

이 때문에 여러 스레드가 같은 데이터로 몰리고, 잠금을 얻기 위해 경쟁할 수 있다. 이를 **잠금 경합(Lock Contention)**이라고 한다.

모든 데이터를 하나의 큰 잠금으로 보호하면 많은 작업이 차례대로 실행될 수 있다.

```text
스레드 A : [잠금 획득 → 처리 → 해제]
스레드 B : [기다림…………………][처리]
스레드 C : [기다림……………………………][처리]
```

반대로 잠금을 지나치게 잘게 나누면 관리가 복잡해진다. 여러 잠금을 서로 다른 순서로 획득하다가 서로의 잠금이 풀리기만 기다리는 **교착 상태(Deadlock)**가 생길 수도 있다.

따라서 멀티스레드 설계에서는 스레드 수뿐 아니라 데이터의 담당 주체와 접근 규칙도 함께 고민해야 한다.

## 스레드는 많을수록 빠를까?

스레드를 늘린다고 항상 성능이 좋아지는 것은 아니다.

CPU 계산이 이미 실행 자원을 충분히 사용하고 있다면, 스레드를 추가해도 기다리는 흐름만 늘어날 수 있다. 문맥 교환, 스택 메모리 사용, 공유 자원 경쟁도 비용이다.

반면 입출력 대기가 많은 작업에서는 다른 일을 함께 진행해 처리량을 높일 여지가 있다.

| 작업 특성 | 설계할 때 살펴볼 점 |
|---|---|
| CPU 계산이 많음 | 병렬화할 수 있는 부분과 사용 가능한 CPU 자원 |
| 입출력 대기가 많음 | 대기 중 다른 작업을 진행하는 방법 |
| 공유 데이터 접근이 많음 | 데이터 소유권, 잠금 범위, 경합 |
| 짧은 작업이 많음 | 스레드 생성 비용과 작업 분배 비용 |

스레드는 여러 일을 함께 진행하기 위한 수단이다. 효과적으로 사용하려면 **나눌 수 있는 작업, 공유하는 데이터, 기다리는 시간**을 함께 살펴봐야 한다.
