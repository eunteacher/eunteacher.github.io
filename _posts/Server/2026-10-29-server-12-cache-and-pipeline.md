# 서버 Day 12 - 캐시와 메모리 접근 순서

같은 배열을 같은 횟수만큼 읽어도 접근 순서에 따라 실행 시간이 달라질 수 있다. 계산 횟수뿐 아니라 **필요한 데이터를 얼마나 효율적으로 가져오는가**도 성능에 영향을 주기 때문이다.

캐시가 필요한 이유와 지역성을 살펴보고, 2차원 배열을 순회하는 두 방법을 비교해 보자.

## 캐시는 왜 필요할까?

CPU의 연산 속도에 비해 RAM에서 데이터를 가져오는 데는 시간이 걸린다. CPU가 계산할 때마다 RAM을 기다리면 연산 능력을 충분히 활용하기 어렵다.

그래서 자주 사용하거나 곧 사용할 가능성이 높은 데이터를 CPU 가까운 **캐시(Cache)**에 보관한다.

```text
CPU 가까이                       상대적으로 멀리
레지스터 → L1 캐시 → L2 캐시 → L3 캐시 → RAM
```

일반적으로 CPU에 가까울수록 빠르고 용량은 작다. 구체적인 계층과 코어 사이의 공유 구조는 CPU마다 다르다.

식당에 비유하면 RAM은 창고이고, 캐시는 작업대 가까이에 둔 재료다. 매번 창고에 다녀오기보다 필요한 재료를 가까이에 두면 빠르게 일할 수 있다.

## 캐시 철학: 최근에 썼거나 근처에 있다면 다시 쓸 가능성이 높다

캐시는 프로그램의 **지역성(Locality)**을 활용한다.

| 지역성 | 의미 | 예시 |
|---|---|---|
| 시간 지역성 | 최근 사용한 데이터를 곧 다시 사용할 가능성이 높음 | 같은 데이터를 반복해서 확인 |
| 공간 지역성 | 사용한 데이터 근처의 데이터를 곧 사용할 가능성이 높음 | 배열 원소를 차례대로 읽기 |

### 시간 지역성

방금 주문한 테이블에서 추가 주문이 들어올 수 있다고 생각해 보자. 최근 주문 정보를 가까이에 보관하면 다시 확인하기 쉽다.

프로그램에서도 최근 사용한 데이터를 가까이에 보관하면 다음 접근을 빠르게 처리할 수 있다.

### 공간 지역성

한 사람이 주문했다면 같은 테이블에 앉은 다른 사람들도 주문할 가능성이 있다. 주변 사람의 주문까지 함께 확인하면 이동을 줄일 수 있다.

배열도 비슷하다. 한 원소를 읽은 다음에는 바로 옆 원소를 읽을 가능성이 높다. 이 성질을 활용하는 것이 공간 지역성이다.

이번 배열 순회 실습은 특히 공간 지역성과 관련이 크다.

## 캐시는 데이터를 묶어서 가져온다

CPU 캐시는 보통 원소 하나씩이 아니라 **캐시 라인(Cache Line)**이라는 일정 크기의 단위로 데이터를 가져온다.

예를 들어 캐시 라인이 64바이트이고 정수 하나가 4바이트라면, 한 라인에 정수 16개가 들어간다.

```text
캐시 라인 하나
[정수][정수][정수] … [정수]
             총 16개
```

한 원소를 읽기 위해 가져온 라인에는 주변 원소도 포함된다. 곧바로 옆 원소를 읽으면 이미 가져온 데이터를 활용할 수 있다.

64바이트는 일반적인 현대 x86 CPU의 예이며, 모든 CPU에 적용되는 고정값은 아니다. [Intel의 지역성과 캐시 라인 설명](https://www.intel.com/content/www/us/en/developer/articles/technical/loop-optimizations-where-blocks-are-required.html)

## 2차원 배열도 메모리에는 순서대로 놓인다

```cpp
int32 buffer[10000][10000];
```

2차원 배열은 표처럼 생각할 수 있지만, C++의 내장 배열은 **행 우선(Row-major)**으로 연속 배치된다.

작은 배열로 보면 이해하기 쉽다.

```cpp
int buffer[2][3];
```

메모리 순서는 다음과 같다.

```text
[0][0] → [0][1] → [0][2] → [1][0] → [1][1] → [1][2]
```

즉, 마지막 인덱스를 증가시키면 바로 다음 원소로 이동한다. [Microsoft C++ 배열 문서](https://learn.microsoft.com/en-us/cpp/cpp/arrays-cpp)

`int32`가 4바이트라면 `buffer[10000][10000]`은 총 1억 개의 원소로, 약 400MB의 공간을 사용한다. 여기서 `int32`는 프로젝트에서 정의한 타입이며, 표준 코드에서는 `<cstdint>`의 `std::int32_t`를 사용할 수 있다.

## 첫 번째 순회: 메모리에 놓인 순서대로 읽기

```cpp
for (int32 i = 0; i < 10000; i++)
{
    for (int32 j = 0; j < 10000; j++)
    {
        sum += buffer[i][j];
    }
}
```

안쪽 반복문에서 마지막 인덱스인 `j`가 증가한다.

```text
[0][0] → [0][1] → [0][2] → …
[1][0] → [1][1] → [1][2] → …
```

같은 행의 원소를 연속해서 읽으므로, 캐시 라인으로 함께 가져온 주변 데이터를 바로 활용하기 좋다.

**공간 지역성이 좋은 접근 방식**이다. 연속적인 접근은 CPU가 데이터를 미리 가져오는 기능에도 유리할 수 있다.

## 두 번째 순회: 행을 건너뛰며 읽기

```cpp
for (int32 i = 0; i < 10000; i++)
{
    for (int32 j = 0; j < 10000; j++)
    {
        sum += buffer[j][i];
    }
}
```

이번에는 안쪽 반복문에서 첫 번째 인덱스가 증가한다.

```text
[0][0] → [1][0] → [2][0] → …
[0][1] → [1][1] → [2][1] → …
```

한 행의 크기는 다음과 같다.

```text
10000개 × 4바이트 = 40000바이트
```

따라서 안쪽 반복문의 연속한 두 접근 사이에 40000바이트씩 건너뛴다.

주변 원소를 함께 가져와도 바로 사용하지 않고 멀리 떨어진 다른 행으로 이동한다. 나중에 주변 원소를 읽으려 할 때는 해당 캐시 라인이 밀려났을 수 있다.

같은 원소를 전부 읽더라도 첫 번째 순회보다 캐시 라인을 효율적으로 활용하기 어렵다.

| 비교 | buffer[i][j] | buffer[j][i] |
|---|---|---|
| 안쪽 반복문에서 바뀌는 인덱스 | 마지막 인덱스 | 첫 번째 인덱스 |
| 접근 간격 | 원소 하나, 4바이트 | 한 행, 40000바이트 |
| 공간 지역성 | 좋음 | 상대적으로 나쁨 |
| 일반적인 실행 경향 | 더 빠름 | 더 느림 |

## 캐시 히트와 캐시 미스

| 구분 | 의미 |
|---|---|
| 캐시 히트 | 확인한 캐시에 필요한 데이터가 있음 |
| 캐시 미스 | 해당 캐시에 없어 더 아래 계층에서 가져와야 함 |

L1에서 미스가 발생했다고 반드시 RAM까지 가는 것은 아니다. L2나 L3에서 찾을 수도 있다.

첫 번째 순회가 일반적으로 빠른 이유는 다음 흐름으로 이해할 수 있다.

```text
연속 접근
→ 가져온 캐시 라인의 주변 원소 활용
→ 데이터 접근 비용 감소
```

다만 첫 번째는 전부 히트하고 두 번째는 전부 미스한다는 뜻은 아니다. 실제 실행 시간에는 CPU의 캐시 구조, 미리 가져오기, 주소 변환 비용, 컴파일러 최적화 등도 영향을 준다.

## 실습 측정 시 주의할 점

### 계산 결과를 실제로 사용한다

합산한 `sum`을 사용하지 않고 시간만 출력하면, 컴파일러가 불필요한 계산이라고 판단해 반복문을 제거할 수 있다.

최소한 측정 종료 뒤에 합산 결과도 출력해 사용해야 한다.

```cpp
uint64 start = GetTickCount64();

int64 sum = 0;

for (int32 i = 0; i < 10000; i++)
{
    for (int32 j = 0; j < 10000; j++)
    {
        sum += buffer[i][j];
    }
}

uint64 end = GetTickCount64();

std::cout << "Sum: " << sum << "\n";
std::cout << "Elapsed: " << (end - start) << " ms\n";
```

`GetTickCount64()`는 Windows API이며 반환 단위는 밀리초다. 출력은 측정 구간이 끝난 뒤 수행하므로 출력 자체의 시간은 위 구간에 포함되지 않는다.

다만 결과를 출력하는 것만으로 모든 최적화 영향을 제거하는 완전한 벤치마크가 되는 것은 아니다. 최적화된 실행 파일에서 의도한 배열 접근이 남아 있는지도 확인할 필요가 있다.

### 한 번의 측정만으로 판단하지 않는다

`memset()`으로 초기화하는 과정과 앞선 순회는 메모리·캐시 상태에 영향을 줄 수 있다. 다른 프로그램의 실행과 CPU 상태에 따라서도 시간이 달라질 수 있다.

실행 순서를 바꾸고 여러 번 측정해 경향을 확인하는 것이 좋다. Debug와 Release의 시간 차이에도 컴파일러 최적화가 영향을 주므로, 측정 조건을 함께 살펴봐야 한다.

캐시 차이를 보기 위해 배열 전체를 `volatile`로 바꾸는 방법은 일반적인 최적화까지 제한해 측정하려는 코드의 성격을 바꿀 수 있다. 또한 `volatile`은 CPU 캐시를 끄는 기능이 아니다.

## 파이프라인과 캐시의 관계

캐시와 함께 알아둘 CPU의 기본 개념으로 **파이프라인(Pipeline)**이 있다.

파이프라인은 명령어를 처리하는 여러 단계를 겹쳐 진행하는 방식이다. 세탁에 비유하면 첫 빨래를 말리는 동안 다음 빨래를 세탁하는 것과 비슷하다.

```text
시간 →
명령어 A: [가져오기][해석][실행]
명령어 B:           [가져오기][해석][실행]
명령어 C:                     [가져오기][해석][실행]
```

위 그림은 원리를 설명하기 위한 단순화다. 실제 CPU의 단계와 실행 방식은 더 복잡하다. 명령어를 가져오고, 해석하고, 실행하고, 결과를 기록하는 단계 등으로 나눠 생각할 수 있다.

명령어 하나가 무조건 빨리 끝난다기보다, 여러 명령어의 처리를 겹쳐 전체 처리량을 높이는 방식으로 이해하면 된다.

| 개념 | 핵심 |
|---|---|
| 캐시 | 필요한 데이터를 가까이에 두어 접근 비용을 줄임 |
| 파이프라인 | 명령어 처리 단계를 겹쳐 실행해 처리량을 높임 |

필요한 데이터를 오래 기다려야 하면 명령어 처리도 지연될 수 있다. 캐시는 이런 데이터 대기 비용을 줄여 CPU가 일을 이어가는 데 도움을 준다.

이번 배열 순회에서 기억할 점은 **반복 횟수가 같아도 메모리 접근 순서에 따라 성능이 달라질 수 있다는 것**이다. C++의 내장 2차원 배열에서는 안쪽 반복문에서 마지막 인덱스를 바꾸면 연속 접근이 된다.

## 멀티스레드에서는 메모리 접근 순서도 중요하다

파이프라인은 여러 명령어의 처리 단계를 겹치는 구조다. 이것만으로 명령어가 임의로 재배치된다는 뜻은 아니다.

실제 CPU는 실행과 메모리 접근의 지연을 줄이기 위해 다양한 기법을 사용한다. 한 스레드가 값을 저장했다고 해서 다른 스레드가 그 값을 즉시 관찰한다고 가정할 수는 없다. 또한 명령어의 결과 기록 단계가 끝났다는 설명과, 저장 결과가 다른 코어에도 관찰된다는 설명은 구분해야 한다.

캐시를 잘 활용하는 문제는 성능과 관련되고, 스레드 사이에서 어떤 순서로 데이터를 전달하는지는 프로그램의 정확성과 관련된다. 이 순서는 뮤텍스나 원자 연산 등의 동기화 규칙과 연결된다.

다음 글에서는 두 스레드가 서로 다른 변수에 저장하고 상대 변수를 읽는 예제를 통해 가시성과 메모리 순서를 살펴본다.
