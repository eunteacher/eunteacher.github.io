# 서버 Day 13 - 가시성과 메모리 접근 순서

CPU는 캐시와 파이프라인 등을 활용해 일을 빠르게 처리한다. 하지만 멀티스레드에서는 성능뿐 아니라, **한 스레드의 작업 결과를 다른 스레드가 어떤 순서로 관찰하는가**도 중요하다.

소스 코드에 적힌 순서대로 모든 작업이 즉시 다른 스레드에 보인다고 가정하면 예상하지 못한 결과를 만날 수 있다.

두 스레드가 서로 다른 변수에 값을 저장한 뒤 상대 변수를 읽는 예제로 이 문제를 살펴보자.

## 두 스레드가 값을 쓰고 상대 변수를 읽는다

처음에는 `x`와 `y`가 모두 `0`이라고 하자.

```cpp
int x = 0;
int y = 0;
int r1 = 0;
int r2 = 0;
```

각 스레드는 다음 작업을 수행한다. 아래 코드는 문제를 살펴보기 위한 것으로, 동기화가 없어 올바른 C++ 멀티스레드 코드는 아니다.

```cpp
void Thread_1()
{
    y = 1;
    r1 = x;
}

void Thread_2()
{
    x = 1;
    r2 = y;
}
```

| 스레드 | 첫 번째 작업 | 두 번째 작업 |
|---|---|---|
| 스레드 1 | y에 1 저장 | x를 읽어 r1에 저장 |
| 스레드 2 | x에 1 저장 | y를 읽어 r2에 저장 |

## 코드 순서대로만 생각하면 둘 다 0이 나오기 어렵다

각 문장이 적힌 순서대로 실행되고, 저장 결과가 즉시 상대방에게 보인다고 가정해 보자.

스레드 1이 먼저 실행되면 다음과 같다.

```text
스레드 1: y = 1
스레드 1: x를 읽음 → 0
스레드 2: x = 1
스레드 2: y를 읽음 → 1
```

반대로 스레드 2가 먼저 실행되면 `r1`은 `1`, `r2`는 `0`이 된다. 두 저장을 먼저 마치고 읽으면 둘 다 `1`이다.

| r1 | r2 |
|---|---|
| 0 | 1 |
| 1 | 0 |
| 1 | 1 |

이 단순한 실행 모델에서는 둘 다 `0`이 되는 순서를 만들 수 없다. 누군가 상대방의 초기값을 먼저 읽었다면, 그 전에 수행한 자신의 저장은 상대방이 읽을 때 보여야 하기 때문이다.

하지만 실제 메모리 접근은 이 모델처럼만 관찰되는 것이 아니다.

## 저장한 값이 다른 코어에 즉시 보이는 것은 아니다

CPU는 저장 작업을 **스토어 버퍼(Store Buffer)**에 임시로 두고 다음 작업을 진행할 수 있다. 저장이 다른 코어에 관찰되기까지 기다리는 비용을 줄이기 위한 구조다.

개념적으로 다음 상황을 생각할 수 있다.

```text
코어 1                           코어 2
y = 1을 저장 버퍼에 보관          x = 1을 저장 버퍼에 보관
x를 읽음 → 아직 0                y를 읽음 → 아직 0

이후 각 저장이 다른 코어에도 관찰됨
```

각 코어가 자신의 저장을 먼저 처리하기 시작했더라도, 상대 코어에 그 저장이 관찰되기 전에 다른 변수의 이전 값을 읽을 수 있다.

**실제로 소스 코드 두 줄을 뒤집어 실행해야만 이런 결과가 나오는 것은 아니다.** 저장이 관찰되는 시점 때문에도 같은 모습을 설명할 수 있다.

Intel의 메모리 순서 모델도 서로 다른 위치에 대해, 앞선 저장보다 뒤의 읽기가 먼저 관찰되는 상황을 허용한다. [Intel 메모리 순서 설명](https://cdrdv2-public.intel.com/835754/253668-sdm-vol-3a.pdf)

이것을 각 코어의 캐시가 제멋대로여서 값이 영원히 달라지는 문제로 이해하면 안 된다. 같은 위치에 대한 캐시 일관성과, 서로 다른 위치에 대한 여러 접근의 관찰 순서는 구분해야 한다.

## C++에서는 데이터 레이스를 먼저 구분해야 한다

스토어 버퍼는 하드웨어 현상을 이해하는 설명이다. 앞의 일반 정수 예제에는 별도로 데이터 레이스가 있다.

`x`는 한 스레드가 쓰고 다른 스레드가 동기화 없이 읽는다. `y`도 마찬가지다. 이런 코드는 표준 C++에서 정의되지 않은 동작이다. 따라서 실제 결과를 CPU의 스토어 버퍼 하나만으로 확정해서 설명할 수 없다. 컴파일러 최적화의 영향도 섞일 수 있다. [C++ 데이터 레이스 규칙](https://eel.is/c++draft/intro.races)

시작 시점을 맞추기 위해 다음 변수를 사용하더라도 이 문제는 해결되지 않는다.

```cpp
volatile bool ready = false;
```

메인 스레드가 `ready`를 쓰는 동안 작업 스레드가 읽으면, `ready`에도 데이터 레이스가 발생한다. 표준 C++의 `volatile`은 원자성이나 스레드 사이의 동기화를 보장하지 않는다.

### join()은 작업 스레드 사이의 충돌을 해결하지 않는다

메인이 두 스레드에 대해 `join()`한 뒤 `r1`과 `r2`를 읽는 것은 정상적인 결과 수신 흐름이다. 각 결과 변수는 작업 스레드 하나만 수정하고, 메인은 그 스레드가 끝난 뒤 읽기 때문이다.

하지만 `join()`이 두 작업 스레드 사이에서 이미 발생한 `x`, `y`의 데이터 레이스까지 해결하는 것은 아니다.

## 가시성과 재배치를 나눠 이해하기

| 개념 | 의미 |
|---|---|
| 가시성 | 한 스레드가 변경한 값을 다른 스레드가 언제, 어떤 규칙 아래에서 볼 수 있는가 |
| 컴파일러 재배치 | 컴파일러가 허용된 범위에서 명령어 배치를 변경하는 것 |
| CPU의 실행·메모리 순서 | 내부 처리와 메모리 접근의 관찰 순서가 소스 코드의 단순한 순서와 다를 수 있는 것 |

컴파일러와 CPU는 성능을 높이기 위해 여러 최적화를 수행한다. 올바른 프로그램에서는 C++과 하드웨어가 정한 규칙을 지켜야 하지만, 동기화가 없는 일반 변수의 데이터 레이스를 프로그래머가 기대하는 순서로 처리해 줄 의무는 없다.

따라서 멀티스레드 코드는 명령어를 눈으로 순서대로 읽는 것만으로 판단하지 않고, 동기화 규칙을 함께 확인해야 한다.

## 원자 변수로 메모리 순서를 살펴보기

데이터 레이스와 메모리 순서를 구분해서 학습하려면 공유 변수를 원자 타입으로 만들 수 있다.

다음은 `x`와 `y`에 약한 순서인 `memory_order_relaxed`를 사용한 예제다. 지금은 이 옵션을 **개별 접근의 원자성은 보장하지만, 두 변수 사이에 전체 순서를 강제하지 않는 설정**으로 이해하면 충분하다.

```cpp
#include <atomic>
#include <iostream>
#include <thread>

std::atomic<bool> ready{false};
std::atomic<int> x{0};
std::atomic<int> y{0};

int r1 = 0;
int r2 = 0;

void Thread_1()
{
    while (ready.load() == false)
    {
        std::this_thread::yield();
    }

    y.store(1, std::memory_order_relaxed);
    r1 = x.load(std::memory_order_relaxed);
}

void Thread_2()
{
    while (ready.load() == false)
    {
        std::this_thread::yield();
    }

    x.store(1, std::memory_order_relaxed);
    r2 = y.load(std::memory_order_relaxed);
}

int main()
{
    std::thread t1(Thread_1);
    std::thread t2(Thread_2);

    ready.store(true);

    t1.join();
    t2.join();

    std::cout << "r1: " << r1 << ", r2: " << r2 << "\n";
}
```

이 예제는 일반 정수와 `volatile`을 사용한 코드와 달리 데이터 레이스가 없다. 하지만 `x`와 `y`의 접근에 `relaxed`를 사용하므로 `r1`과 `r2`가 모두 `0`인 결과가 허용된다.

허용된다는 것은 반드시 관찰된다는 뜻이 아니다. 한 번 실행해서는 다른 결과가 나올 수 있고, 여러 번 반복해도 환경에 따라 쉽게 관찰되지 않을 수 있다. 반복 실험을 한다면 이전 작업 스레드를 모두 `join()`한 뒤 다음 시도의 상태를 초기화해야 한다.

`ready`는 시작 시점을 가깝게 맞추려는 장치다. 두 작업이 정확히 같은 순간에 실행되도록 보장하거나, 시작 이후의 `x`, `y` 접근 사이에 별도의 순서를 정하는 것은 아니다.

### 기본 원자 연산으로 바꾸면?

명시한 `memory_order_relaxed`를 제거하면 기본 메모리 순서인 `memory_order_seq_cst`가 적용된다.

```cpp
// 스레드 1
y.store(1);
r1 = x.load();

// 스레드 2
x.store(1);
r2 = y.load();
```

이 네 연산이 모두 기본 순서를 사용하면, 각 스레드의 순서를 지키는 하나의 전체 순서로 설명되어야 한다. 이 예제에서는 두 읽기가 모두 초기값 `0`을 읽는 결과가 허용되지 않는다.

이것은 모든 작업을 뮤텍스로 직렬화한다는 뜻은 아니다. **원자성뿐 아니라 메모리 순서의 보장 수준도 결과에 영향을 준다**는 점이 핵심이다.

실제 코드에서는 특별한 이유 없이 메모리 순서를 약화하기보다, 기본 원자 연산이나 뮤텍스로 필요한 규칙을 명확히 표현하는 것부터 시작하는 편이 이해하기 쉽다.

## 파이프라인과 메모리 순서는 같은 개념이 아니다

파이프라인은 명령어 처리 단계를 겹쳐 진행하는 구조다.

```text
Fetch      : 명령어 가져오기
Decode     : 명령어 해석
Execute    : 실행
Write-back : 결과 기록
```

명령어 A가 실행되는 동안 명령어 B는 해석되고, 명령어 C는 가져와지는 식으로 작업을 겹친다. 위 단계는 원리를 설명하기 위한 단순한 모델이며, 실제 CPU는 더 복잡하다.

파이프라인 자체가 곧 명령어 재배치를 뜻하지는 않는다. 또한 그림의 결과 기록 단계가 끝났다는 사실이 다른 코어에 저장 결과가 모두 전달되었다는 의미도 아니다.

| Day 12 | Day 13 |
|---|---|
| 캐시와 지역성을 통한 데이터 접근 성능 | 스레드 사이의 가시성과 메모리 접근 순서 |
| 어떤 접근 순서가 캐시를 효율적으로 사용하는가? | 변경한 값을 다른 스레드가 어떤 순서로 관찰하는가? |

CPU의 성능 향상 구조를 이해하는 것과, C++ 프로그램이 올바르게 동기화되었는지 판단하는 것은 함께 필요하다. **소스 코드에 적힌 순서만 믿지 말고, 공유 데이터의 원자성과 스레드 사이의 순서 보장을 구분해야 한다.**
