# 서버 Day 05 - 데드락과 잠금 순서

뮤텍스는 여러 스레드가 공유 데이터를 동시에 수정하지 못하도록 보호한다. 하지만 여러 뮤텍스를 함께 사용하면, 서로의 잠금이 풀리기만 기다리는 문제가 생길 수 있다.

이처럼 **서로가 가진 자원을 기다리며 어느 쪽도 진행하지 못하는 상태**를 데드락(Deadlock), 즉 교착 상태라고 한다.

## 잠금을 얻는 순서가 다르면 문제가 생긴다

계정 정보를 관리하는 `AccountManager`와 유저 정보를 관리하는 `UserManager`가 있다고 하자. 두 매니저는 각각 자신의 데이터를 보호하는 뮤텍스를 가진다.

저장 작업은 유저 잠금을 얻은 뒤 계정 정보를 조회한다.

```cpp
void UserManager::ProcessSave()
{
    std::lock_guard<std::mutex> guard(_mutex);

    Account* account = AccountManager::instance()->GetAccount(100);
}
```

`GetAccount()`도 내부에서 계정 잠금을 얻으므로, 잠금 획득 흐름은 다음과 같다.

```text
유저 잠금 → 계정 잠금
```

반면 로그인 작업은 계정 잠금을 얻은 뒤 유저 정보를 조회한다.

```cpp
void AccountManager::ProcessLogin()
{
    std::lock_guard<std::mutex> guard(_mutex);

    User* user = UserManager::instance()->GetUser(100);
}
```

`GetUser()`는 내부에서 유저 잠금을 얻는다.

```text
계정 잠금 → 유저 잠금
```

두 작업이 **같은 잠금을 서로 반대 순서로 얻으려 한다**는 점이 문제다.

## 데드락이 발생하는 과정

두 스레드가 다음 순서로 실행된다고 생각해 보자.

| 순서 | 저장 스레드 | 로그인 스레드 |
|---|---|---|
| 1 | 유저 잠금 획득 | |
| 2 | | 계정 잠금 획득 |
| 3 | 계정 잠금을 기다림 | |
| 4 | | 유저 잠금을 기다림 |

이제 두 스레드가 서로를 기다린다.

```text
저장 스레드
└─ 유저 잠금을 가진 채 계정 잠금을 기다림

로그인 스레드
└─ 계정 잠금을 가진 채 유저 잠금을 기다림
```

저장 스레드가 진행하려면 로그인 스레드가 계정 잠금을 풀어야 한다. 로그인 스레드가 진행하려면 저장 스레드가 유저 잠금을 풀어야 한다.

어느 쪽도 먼저 진행할 수 없으므로 기다림이 끝나지 않는다.

메인 스레드가 두 작업에 대해 `join()`을 호출했다면, 메인 스레드도 작업 종료를 계속 기다리게 된다.

## 항상 발생하지 않아서 발견하기 어렵다

잠금 순서가 잘못되어 있어도 실행할 때마다 데드락이 발생하는 것은 아니다.

한 스레드가 먼저 두 잠금을 모두 얻고 작업을 마치면 정상적으로 종료할 수 있다. 반대로 두 스레드가 각자 잠금 하나씩을 얻으면 서로 기다리는 상태가 될 수 있다.

실행 타이밍에 따라 결과가 달라지므로, **여러 번 정상 실행되었다는 사실만으로 안전한 코드라고 판단하면 안 된다.**

## lock_guard가 있어도 데드락은 발생한다

`std::lock_guard`는 객체가 소멸할 때 잠금을 자동으로 해제한다.

```cpp
std::lock_guard<std::mutex> guard(_mutex);
```

하지만 다른 잠금을 기다리느라 함수가 진행되지 못하면 블록을 벗어날 수 없다. 따라서 `guard`의 소멸자도 실행되지 않는다.

| 도구·규칙 | 해결하는 문제 |
|---|---|
| `lock_guard` | 잠금 해제를 빠뜨리는 문제 |
| 일관된 잠금 순서 | 서로 반대 순서로 잠금을 기다리는 문제 |

**잠금 해제를 자동화하는 것과 데드락을 예방하는 것은 별개의 문제다.**

## 잠금을 얻는 순서를 통일한다

여러 잠금을 함께 사용해야 한다면, 먼저 획득 순서를 정한다.

```text
항상 계정 잠금 → 유저 잠금 순서로 획득한다.
```

모든 관련 코드가 이 규칙을 지키면, 유저 잠금을 가진 채 계정 잠금을 기다리는 반대 흐름이 사라진다.

한 스레드가 계정 잠금을 먼저 얻었다면, 다른 스레드는 계정 잠금에서 기다린다. 기다리는 스레드가 유저 잠금을 먼저 차지하지 않으므로, 앞선 스레드는 유저 잠금을 얻고 작업을 마칠 수 있다.

이 규칙은 **호출한 함수 안에서 얻는 잠금까지 포함해서** 지켜야 한다. 현재 함수에 보이는 `lock()`만 확인하면, 다른 함수가 내부에서 획득하는 잠금을 놓칠 수 있다.

## 잠금에 ID를 부여하면 순서를 정하기 쉽다

잠금이 많아지면 이름만으로 순서를 기억하기 어렵다. 이때 잠금마다 고정된 순위나 ID를 부여할 수 있다.

| 잠금 | ID |
|---|---|
| 계정 잠금 | 10 |
| 유저 잠금 | 20 |
| 아이템 잠금 | 30 |

그리고 다음 규칙을 적용한다.

> 여러 잠금을 함께 보유해야 한다면, ID가 작은 잠금부터 얻는다.

예를 들어 계정과 아이템 잠금이 필요하면 `10 → 30`, 유저와 아이템 잠금이 필요하면 `20 → 30` 순서로 얻는다.

여기서 ID는 스레드 ID가 아니라 **잠금 획득 순서를 정하기 위한 번호**다. 번호를 붙이는 것만으로 안전해지는 것은 아니며, 모든 관련 코드가 그 순서를 지켜야 한다.

## 잠금을 동시에 보유할 필요가 있는지도 확인한다

데드락을 줄이는 또 다른 방법은 **잠금을 가진 상태에서 다른 잠금을 얻는 상황 자체를 줄이는 것**이다.

예를 들어 계정 조회를 마친 뒤 유저 데이터를 처리할 수 있다면 다음 흐름을 생각할 수 있다.

```text
계정 잠금 획득
→ 필요한 정보 조회
→ 계정 잠금 해제
→ 유저 잠금 획득
→ 유저 데이터 처리
→ 유저 잠금 해제
```

다만 이 흐름은 두 잠금을 동시에 유지하는 방식과 의미가 다르다.

계정 잠금을 해제한 뒤에는 다른 스레드가 계정 정보를 바꿀 수 있다. 따라서 두 데이터가 함께 일관된 상태를 유지해야 하는 작업인지 확인해야 한다.

또한 잠금 안에서 얻은 객체 포인터를 잠금 밖에서 사용한다고 해서, 그 객체의 수명과 접근까지 자동으로 보호되는 것은 아니다.

## 여러 잠금을 함께 다루는 표준 도구

`std::lock()`은 여러 뮤텍스를 데드락을 회피하는 방식으로 잠그는 도구다.

```cpp
std::lock(m1, m2);

std::lock_guard<std::mutex> guard1(m1, std::adopt_lock);
std::lock_guard<std::mutex> guard2(m2, std::adopt_lock);
```

`std::adopt_lock`은 이미 획득한 잠금을 객체가 맡아서 관리하도록 지정한다. 다시 잠그지 않고, 객체가 소멸할 때 해제한다.

두 뮤텍스를 잠갔다면 두 잠금 모두 해제되도록 관리해야 한다.

C++17부터는 `std::scoped_lock`으로 더 간단하게 작성할 수 있다.

```cpp
std::scoped_lock guard(m1, m2);
```

여러 뮤텍스의 잠금과 범위를 벗어날 때의 해제를 함께 관리한다. 여러 뮤텍스를 획득할 때 이러한 도구를 사용하는 방식은 [C++ Core Guidelines](https://microsoft.github.io/OfficeCppGuidelines/CppCoreGuidelines.html#cp21-use-stdlock-or-stdscoped_lock-to-acquire-multiple-mutexes)에서도 안내한다.

다만 다른 위치에서 이미 보유한 잠금이나, 호출한 함수가 추가로 얻는 잠금까지 포함해 프로그램 전체의 데드락을 자동으로 해결하는 것은 아니다.

## 데드락은 주의만으로 예방하기 어렵다

모든 잠금에 일관된 순서를 정하고 예외 없이 지키면, 잠금 순서가 뒤집혀 생기는 데드락을 예방할 수 있다.

하지만 프로그램이 커지면 함수 호출과 잠금 관계가 복잡해진다. 코드가 변경되면서 기존 규칙을 어기는 경로가 추가될 수도 있다.

따라서 “조심해서 사용한다”는 생각에만 의존하지 않고 다음 기준을 코드에 적용해야 한다.

- 여러 잠금을 얻는 순서를 정한다.
- 잠금을 가진 상태에서 호출하는 함수가 어떤 잠금을 얻는지 확인한다.
- 여러 잠금을 동시에 보유하는 구간을 줄인다.
- 잠금 해제는 RAII 객체에 맡긴다.

뮤텍스를 사용할 때는 **어디에서 잠금을 해제하는지뿐 아니라, 어떤 잠금을 가진 상태에서 다음 잠금을 기다리는지**도 함께 살펴봐야 한다.
