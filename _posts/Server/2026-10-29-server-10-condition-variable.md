# 서버 Day 10 - 조건 변수로 작업 기다리기

생산자가 큐에 데이터를 넣고 소비자가 꺼내는 구조에서는, 데이터가 없을 때 소비자를 어떻게 기다리게 할지 결정해야 한다.

계속 큐를 확인하면 CPU를 낭비하고, 일정 시간 쉬었다가 확인하면 데이터가 들어와도 늦게 처리할 수 있다.

**조건 변수(Condition Variable)**를 사용하면 공유 데이터의 조건을 확인하고, 조건이 충족되지 않았을 때 대기하도록 만들 수 있다.

## 조건 변수와 뮤텍스의 역할

```cpp
std::mutex m;
std::queue<int> q;
std::condition_variable cv;
```

소비자가 기다리는 조건은 **큐에 처리할 데이터가 있는가?**다.

```cpp
q.empty() == false
```

조건 변수 자체가 큐를 감시하거나 데이터 개수를 기억하는 것은 아니다. 생산자가 데이터를 넣고 통지하면, 소비자가 조건을 확인한다.

| 구성 요소 | 역할 |
|---|---|
| 큐 | 실제 데이터와 상태 보관 |
| 뮤텍스 | 큐에 대한 동시 접근 방지 |
| 조건 변수 | 조건을 기다리는 스레드의 대기·깨움 지원 |

조건 변수는 표준 헤더 `<condition_variable>`에서 제공한다.

## 생산자: 데이터를 넣고 통지하기

생산자는 잠금을 얻어 데이터를 넣고, 잠금을 해제한 뒤 소비자에게 통지한다.

```cpp
void Producer()
{
    while (true)
    {
        {
            std::unique_lock<std::mutex> lock(m);
            q.push(100);
        }

        cv.notify_one();
    }
}
```

실행 순서는 다음과 같다.

```text
잠금 획득
→ 큐에 데이터 추가
→ 잠금 해제
→ 대기 중인 스레드 하나에 통지
```

`notify_one()`은 해당 조건 변수에서 대기 중인 스레드 하나를 깨운다. 여러 대기 스레드에 통지하려면 `notify_all()`을 사용할 수 있다.

통지는 **조건이 참이 되었는지 확인해 보라는 알림**이다. 데이터를 전달하거나 큐의 소유권을 넘기는 작업은 아니다.

## 소비자: 조건을 확인하고 기다리기

```cpp
void Consumer()
{
    while (true)
    {
        std::unique_lock<std::mutex> lock(m);

        cv.wait(lock, []() { return q.empty() == false; });

        int data = q.front();
        q.pop();

        std::cout << data << "\n";
    }
}
```

`wait()`의 두 번째 인자는 조건을 검사하는 함수다. 여기서는 람다 함수로 큐가 비어 있지 않은지 확인한다.

조건 검사 결과가 `true`면 기다리지 않고 진행한다. `false`면 잠금을 풀고 대기한다.

```text
잠금을 가진 상태에서 조건 확인
├─ 데이터가 있음 → 바로 진행
└─ 데이터가 없음
   → 잠금 해제와 대기 진입
   → 깨어남
   → 잠금 재획득
   → 조건 재확인
```

중요한 점은 **대기하는 동안 뮤텍스를 놓는다는 것**이다. 그래야 생산자가 같은 뮤텍스를 얻어 데이터를 넣을 수 있다.

또한 `wait()`에서 정상적으로 돌아오면 다시 잠금을 가진 상태다. 따라서 큐에 안전하게 접근할 수 있다.

## wait()에 unique_lock을 전달하는 이유

`std::condition_variable::wait()`는 대기하면서 잠금을 풀고, 깨어난 뒤 다시 얻어야 한다.

이를 위해 잠금 해제와 재획득을 지원하는 `std::unique_lock<std::mutex>`를 전달한다.

```cpp
std::unique_lock<std::mutex> lock(m);
cv.wait(lock, []() { return q.empty() == false; });
```

`lock_guard`는 생성과 소멸에 맞춰 잠금을 관리하는 단순한 도구이므로, 이 `wait()`의 인자로 사용할 수 없다.

## 조건식이 있는 wait()는 반복해서 확인한다

다음 코드는:

```cpp
cv.wait(lock, []() { return q.empty() == false; });
```

개념적으로 다음과 같다.

```cpp
while (q.empty())
{
    cv.wait(lock);
}
```

대기에서 깨어날 때마다 잠금을 다시 얻고 조건을 검사한다. 조건이 여전히 거짓이면 다시 기다린다.

따라서 조건식이 있는 `wait()`가 정상적으로 반환했다면, 잠금을 가진 상태에서 큐가 비어 있지 않음을 확인한 것이다. [Microsoft 조건 변수 문서](https://learn.microsoft.com/en-us/cpp/standard-library/condition-variable?view=msvc-170)

이후 원소 하나를 꺼내고 다음 반복으로 돌아갔을 때도 데이터가 남아 있다면, 다음 `wait()`는 잠들지 않고 통과한다.

## 깨어난 뒤에도 조건을 확인해야 하는 이유

### 통지 없이 깨어날 수 있다

조건 변수는 명시적인 통지가 없어도 깨어날 수 있다. 이를 **가짜 기상 또는 허위 기상(Spurious Wakeup)**이라고 한다.

따라서 다음처럼 통지만 기다리고 큐에 바로 접근하면 안전하지 않다.

```cpp
cv.wait(lock);

int data = q.front();
q.pop();
```

대기를 통과했다는 사실만으로 큐에 데이터가 있다고 보장할 수 없기 때문이다.

### 다른 소비자가 먼저 처리할 수 있다

소비자가 여러 개라면, 통지를 받은 스레드가 실제로 잠금을 얻기 전에 다른 소비자가 데이터를 가져갈 수도 있다.

```text
생산자: 데이터 추가 후 통지
소비자 A: 깨어났지만 아직 잠금을 얻지 못함
소비자 B: 먼저 잠금을 얻어 데이터 소비
소비자 A: 잠금 획득 후 확인하니 큐가 비어 있음
```

이 경우에도 조건을 다시 확인하고 기다려야 한다.

**통지를 받았다는 사실과, 지금 작업할 수 있다는 사실은 다르다.**

## notify_one()은 잠금 안에서 호출해도 된다

다음처럼 데이터를 변경한 뒤 잠금 안에서 통지하는 것도 가능하다.

```cpp
{
    std::unique_lock<std::mutex> lock(m);

    q.push(100);
    cv.notify_one();
}
```

다만 깨어난 소비자는 같은 뮤텍스를 얻어야 한다. 생산자가 잠금을 유지하고 있다면 소비자는 잠금 해제를 기다릴 수 있다.

다음처럼 잠금을 해제한 뒤 통지하면 이러한 불필요한 기다림을 줄일 수 있다.

```cpp
{
    std::unique_lock<std::mutex> lock(m);
    q.push(100);
}

cv.notify_one();
```

**잠금 밖에서 통지한다고 가짜 기상이 발생하는 것은 아니다.** 가짜 기상은 조건 변수 사용 시 별도로 고려해야 하는 특성이다. [Windows 조건 변수 문서](https://learn.microsoft.com/en-us/windows/win32/sync/condition-variables)

핵심은 공유 상태의 변경과 조건 확인을 같은 뮤텍스로 보호하는 것이다.

## 조건 확인 직후 통지를 놓치지는 않을까?

소비자가 큐가 비었다고 확인한 직후, 잠들기 전에 생산자가 데이터를 넣고 통지하는 상황을 걱정할 수 있다.

올바른 사용에서는 다음 규칙이 이를 막는다.

1. 소비자는 뮤텍스를 가진 상태에서 조건을 확인한다.
2. 생산자도 같은 뮤텍스를 얻어야 데이터를 변경할 수 있다.
3. `wait()`의 잠금 해제와 대기 진입은 통지와 엇갈리지 않도록 원자적으로 수행된다.

소비자가 조건을 검사하는 동안 생산자는 큐를 바꿀 수 없다. 소비자가 `wait()`로 잠금을 놓고 대기하면, 생산자가 잠금을 얻어 데이터를 추가하고 통지할 수 있다.

따라서 **조건 확인과 상태 변경에 같은 뮤텍스를 사용하는 규칙**이 중요하다.

## 조건 변수는 통지를 저장하지 않는다

대기 중인 스레드가 없을 때 `notify_one()`을 호출하면, 그 통지는 나중을 위해 저장되지 않는다.

하지만 생산자가 넣은 데이터는 큐에 남아 있다.

```text
생산자: 데이터 추가 → 통지
소비자: 나중에 잠금 획득 → 큐 확인 → 데이터가 있으므로 바로 진행
```

소비자는 통지 횟수에 의존하지 않고 실제 상태를 확인하므로, 데이터가 있으면 기다리지 않는다.

| 구분 | Windows 이벤트 | 조건 변수 |
|---|---|---|
| 자체 신호 상태 | Signaled / Non-signaled 상태 보유 | 저장된 신호 상태 없음 |
| 진행 판단 | 이벤트 상태로 대기 통과 | 공유 데이터의 조건을 검사 |
| 통지 후 처리 | 별도로 데이터 상태 확인 필요 | 조건식이 있는 wait로 재확인 |

조건 변수에서는 **공유 데이터가 실제 상태를 보관하고, 통지는 상태를 다시 확인할 기회를 제공한다.**

## 조건 변수를 적용한 전체 코드

다음은 동작 흐름을 확인하기 위한 무한 반복 예제다. 소비자는 데이터를 꺼낸 뒤 잠금을 해제하고 출력한다.

```cpp
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <queue>
#include <thread>

std::mutex m;
std::queue<int> q;
std::condition_variable cv;

void Producer()
{
    while (true)
    {
        {
            std::unique_lock<std::mutex> lock(m);
            q.push(100);
        }

        cv.notify_one();
    }
}

void Consumer()
{
    while (true)
    {
        int data = 0;

        {
            std::unique_lock<std::mutex> lock(m);

            cv.wait(lock, []() { return q.empty() == false; });

            data = q.front();
            q.pop();
        }

        std::cout << data << "\n";
    }
}

int main()
{
    std::thread p(Producer);
    std::thread c(Consumer);

    p.join();
    c.join();
}
```

출력을 잠금 밖으로 옮긴 이유는 큐를 보호하는 시간을 줄이기 위해서다. 소비자가 출력하는 동안에도 생산자는 데이터를 넣을 수 있다.

다만 생산자에 대기나 크기 제한이 없으므로, 소비자가 처리하는 속도보다 생산 속도가 빠르면 큐와 메모리 사용량이 계속 증가할 수 있다.

또한 두 스레드 모두 무한 반복하므로 정상 흐름에서는 `join()`이 끝나지 않는다. 실제 프로그램에서는 종료 여부도 공유 상태에 포함하고, 종료 시 대기 중인 스레드를 깨우는 처리가 필요하다.

## 유저 레벨 객체라는 설명의 의미

Windows 조건 변수는 이벤트처럼 `CreateEvent()`로 핸들을 만들고 `CloseHandle()`로 닫는 형태의 커널 객체가 아니다.

하지만 **대기 과정에서 운영체제의 도움을 전혀 받지 않는다는 뜻은 아니다.** 스레드를 대기시키고 다시 실행하는 과정에는 운영체제 기능이 사용될 수 있다.

`std::condition_variable`의 구체적인 구현은 운영체제와 표준 라이브러리에 따라 달라진다.

조건 변수를 사용할 때 기억할 기본 흐름은 다음과 같다.

> **공유 상태는 뮤텍스로 보호하고, 조건 변수로 기다리며, 깨어난 뒤에는 조건을 다시 확인한다.**
