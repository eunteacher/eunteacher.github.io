# 서버 Day 06 - 잠금 대기 방식과 문맥 교환

다른 스레드가 잠금을 가지고 있다면, 잠금을 얻지 못한 스레드는 기다려야 한다. 이때 계속 잠금 상태를 확인할 수도 있고, 실행 기회를 양보하거나 대기 상태로 들어갈 수도 있다.

어떤 방법을 선택하느냐에 따라 CPU 사용량과 작업을 다시 시작하기까지 걸리는 시간이 달라진다.

이번에는 **잠금을 기다리는 세 가지 방식과 문맥 교환의 비용**을 알아본다.

## 식당에서 자리를 기다리는 세 가지 방법

자리가 가득 찬 식당에 도착했다고 생각해 보자. 손님은 다음과 같은 방법으로 기다릴 수 있다.

| 식당에서의 행동 | 스레드의 대기 방식 |
|---|---|
| 자리가 날 때까지 앞에서 계속 확인한다 | 잠금 획득을 반복해서 시도 |
| 일단 물러났다가 나중에 다시 확인한다 | 실행 기회를 양보하거나 잠시 쉰 뒤 재시도 |
| 직원에게 자리가 나면 알려 달라고 부탁한다 | 대기 상태로 들어갔다가 깨움 |

여기서 손님은 스레드, 자리는 잠금, 자리를 안내하는 직원은 운영체제의 대기·깨움 기능에 대응한다.

## 첫 번째: 잠금을 얻을 때까지 계속 확인한다

자리가 날 때까지 앞에서 계속 살펴보듯, 스레드가 잠금 획득을 반복해서 시도하는 방식이다.

```text
잠금 획득 시도 → 실패 → 다시 시도 → 실패 → 다시 시도…
```

이런 대기를 **바쁜 대기(Busy Waiting)**라고 하며, 이를 사용하는 대표적인 잠금이 **스핀락(Spinlock)**이다.

스레드가 실행을 유지하면서 확인하므로, 잠금이 곧 풀리면 빠르게 작업을 이어갈 수 있다. 기다리기 위해 스스로 대기 상태에 들어갔다가 깨워지는 절차를 거치지 않아도 된다.

반면 오래 기다리면 유용한 작업 없이 CPU 시간을 계속 소비한다. 특히 잠금을 가진 스레드가 실행 기회를 얻지 못하고 있다면, 확인만 반복해도 잠금이 빨리 풀리지 않는다.

따라서 스핀 방식은 **잠금이 매우 짧은 시간 안에 풀릴 가능성이 높은 상황**에서 고려할 수 있다. 스핀 중에도 운영체제에 의해 실행이 중단될 수 있으므로, 문맥 교환이 절대로 발생하지 않는다는 의미는 아니다.

## 두 번째: 실행 기회를 양보하고 다시 시도한다

지금은 자리가 없으니 일단 물러났다가 다시 확인하는 방식이다.

```text
잠금 획득 시도 → 실패 → 실행 기회 양보 → 다시 실행되면 재시도
```

C++에서는 다음과 같이 실행 기회 양보를 요청할 수 있다.

```cpp
std::this_thread::yield();
```

`yield()`는 스케줄러에 다른 스레드가 실행될 기회를 주도록 요청한다. 다만 **반드시 다른 스레드가 실행되거나, 일정 시간 동안 쉬는 것은 아니다.** 실행할 다른 스레드가 없다면 같은 스레드가 곧바로 계속 실행될 수도 있다.

잠금이 풀렸다는 통지를 받는 방식도 아니므로, 다시 실행되면 잠금 획득을 재시도해야 한다.

### 일정 시간 쉬는 방법과는 다르다

다음은 지정한 시간 동안 현재 스레드의 실행을 멈추는 방법이다.

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(1));
```

이 예제에는 `<thread>`와 `<chrono>` 헤더가 필요하다.

`sleep_for()`는 잠금이 풀리는 시점에 맞춰 깨어나는 기능이 아니다. 잠금이 일찍 풀려도 기다릴 수 있으며, 지정한 시간이 지나더라도 스케줄링 상황에 따라 실제 실행 재개는 더 늦어질 수 있다.

`yield()`와 `sleep_for()`는 모두 재시도 사이에 여유를 주는 데 사용할 수 있지만, 동작 방식은 구분해야 한다.

## 세 번째: 대기 상태로 들어갔다가 깨움을 받는다

직원에게 자리가 나면 알려 달라고 부탁하듯, 스레드를 대기 상태로 두고 필요할 때 깨우는 방식이다.

```text
잠금 획득 실패
→ 대기 등록
→ 대기 상태
→ 깨움
→ 실행 기회를 얻음
→ 잠금 획득 시도
```

기다리는 동안 CPU에서 잠금 상태를 반복해서 확인하지 않으므로, 오래 기다리는 상황에서 CPU 낭비를 줄일 수 있다.

대신 대기 상태로 전환하고 다시 깨우는 데 비용이 든다. 잠금이 아주 빨리 풀린다면, 기다리는 시간보다 대기·깨움에 드는 비용이 더 크게 느껴질 수도 있다.

또한 **깨웠다고 즉시 실행되거나 잠금을 반드시 얻는 것은 아니다.** 스케줄러로부터 실행 기회를 받아야 하고, 깨어난 뒤에도 잠금 상태를 다시 확인해야 한다.

실제 대기 등록과 깨움은 통지를 놓치지 않도록 조율되어야 한다. 따라서 단순히 일반 변수를 확인하고 잠드는 코드만으로 올바른 잠금 대기를 구현할 수 있는 것은 아니다.

## 문맥 교환은 실행 상태를 바꾸는 과정이다

CPU에서 실행하던 스레드를 다른 스레드로 바꾸려면, 나중에 기존 작업을 이어갈 수 있도록 실행 상태를 보관해야 한다.

```text
스레드 A의 실행 상태 저장
→ 스레드 B의 실행 상태 복원
→ 스레드 B 실행
```

이 과정을 **문맥 교환(Context Switch)**이라고 한다.

실행 상태에는 다음에 실행할 명령어의 위치와 레지스터 값 등이 포함된다. 이를 저장하고 복원하기 때문에 스레드는 중단됐던 작업을 이어갈 수 있다.

대기 상태로 들어간 스레드 대신 다른 스레드를 실행하거나, 실행 기회를 양보해 다른 스레드가 선택되는 상황에서 이러한 전환이 일어날 수 있다.

## 문맥 교환에는 비용이 든다

문맥 교환에서는 실행 상태를 저장하고 복원하는 작업이 필요하다. 스케줄러가 실행할 스레드를 선택하는 과정에도 비용이 든다.

또한 CPU 캐시의 상태가 성능에 영향을 줄 수 있다.

| 구성 요소 | 역할 |
|---|---|
| 레지스터 | CPU가 명령어를 실행하며 직접 사용하는 값과 상태 보관 |
| 캐시 | 자주 사용하는 데이터 등을 CPU 가까이에 보관 |
| RAM | 프로그램의 코드와 데이터가 올라가는 주기억장치 |

다른 스레드가 실행되면서 기존 작업에 유용했던 데이터가 캐시에서 밀려날 수 있다. 이후 원래 스레드가 다시 실행될 때 필요한 데이터를 가져오느라 추가 시간이 들 수 있다.

다만 **문맥 교환 때 캐시 전체를 RAM으로 복사하고 비우는 것은 아니다.** 실행 상태의 저장·복원과 캐시 상태로 인한 성능 영향은 구분해야 한다.

## 어떤 대기 방식이 더 좋을까?

기다리는 시간과 실행 환경에 따라 달라진다.

| 대기 방식 | 장점 | 비용·주의점 |
|---|---|---|
| 계속 확인 | 잠금이 빨리 풀리면 빠르게 진행 가능 | 기다리는 동안 CPU 사용 |
| 양보 후 재시도 | 다른 스레드에 실행 기회를 줄 수 있음 | 재시도 필요, 다른 스레드 실행 보장 없음 |
| 대기 후 깨움 | 오래 기다릴 때 CPU 낭비 감소 | 대기·깨움과 스케줄링 비용 |

아주 짧게 기다릴 상황이라면 계속 확인하는 편이 유리할 수 있다. 반대로 오래 기다려야 한다면 CPU를 사용하면서 확인하기보다 대기 상태로 들어가는 편이 유리할 수 있다.

실제 잠금 구현은 여러 방법을 섞기도 한다. 짧게 스핀한 뒤에도 잠금을 얻지 못하면 대기 상태로 들어가는 방식이 그 예다. 구체적인 전략은 라이브러리와 운영체제에 따라 달라진다.

잠금 대기를 이해할 때는 **계속 확인하는 비용과 스레드를 쉬게 했다가 다시 실행하는 비용을 비교하는 것**이 중요하다. 어떤 방식이든 항상 빠른 것은 아니며, 잠금 유지 시간과 경쟁하는 스레드 수를 함께 살펴봐야 한다.
