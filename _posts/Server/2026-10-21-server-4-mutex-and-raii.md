# 서버 Day 04 - 뮤텍스와 RAII로 공유 데이터 보호하기

여러 스레드가 같은 자료구조를 수정할 때는 접근 규칙이 필요하다. 정수 하나의 증가·감소는 `atomic`으로 처리할 수 있지만, `vector`에 원소를 추가하는 작업은 내부에서 여러 단계로 이루어진다.

이번에는 **뮤텍스로 공유 데이터를 보호하고, RAII로 잠금 해제를 자동화하는 방법**을 알아본다.

## 여러 스레드가 같은 vector를 수정하면 생기는 문제

```cpp
std::vector<int> v;
```

두 스레드가 같은 `v`에 다음 작업을 수행한다고 생각해 보자.

```cpp
v.push_back(i);
```

`push_back()`은 단순히 숫자 하나를 저장하는 작업으로 끝나지 않는다. 개념적으로 다음 작업이 필요하다.

- 새 원소를 저장한다.
- 원소 개수 등 내부 정보를 변경한다.
- 공간이 부족하면 더 큰 메모리를 확보하고 기존 원소를 옮긴다.

두 스레드가 이 과정을 동시에 수행하면 내부 정보가 서로 어긋나거나, 한쪽이 옮기고 있는 메모리에 다른 쪽이 접근할 수 있다. 동기화 없이 같은 벡터에 `push_back()`하면 데이터 레이스가 발생하며, 동작이 정의되지 않는다.

다만 **자료구조를 멀티스레드에서 사용할 수 없다는 뜻은 아니다.** 같은 벡터를 여러 스레드가 읽기만 하는 경우와, 동시에 구조를 변경하는 경우는 구분해야 한다.

이번처럼 같은 벡터에 원소를 추가하는 작업에는 동기화가 필요하다. 미리 `reserve()`로 공간을 확보하더라도, 원소 개수 등 내부 정보를 함께 변경하므로 동시 `push_back()`이 안전해지는 것은 아니다.

## mutex는 공유 데이터에 접근하는 자물쇠다

```cpp
std::mutex m;
```

뮤텍스(Mutex)는 **상호 배제(Mutual Exclusion)**를 위한 도구다. 같은 뮤텍스로 보호한 코드 구간에 한 번에 하나의 스레드만 들어가도록 한다.

```cpp
m.lock();

v.push_back(i);

m.unlock();
```

동작은 다음과 같다.

```text
스레드 A : 잠금 획득 → vector 수정 → 잠금 해제
스레드 B : 잠금 대기………………… → 잠금 획득 → vector 수정
```

이렇게 공유 자원에 접근해 보호가 필요한 코드 구간을 **임계 구역(Critical Section)**이라고 한다.

뮤텍스가 벡터 자체를 자동으로 잠그는 것은 아니다. **같은 데이터를 다루는 관련 코드가 같은 뮤텍스를 사용하는 규칙을 지켜야 한다.** 수정 중인 벡터를 다른 스레드에서 읽어야 한다면, 그 읽기도 같은 규칙으로 보호해야 한다.

또한 잠금을 얻지 못한 스레드가 기다리는 것이지, 프로그램의 다른 모든 스레드가 멈추는 것은 아니다.

## 수동 잠금은 해제를 빠뜨리기 쉽다

다음은 잠금 해제를 빠뜨릴 수 있는 잘못된 예다.

```cpp
m.lock();

if (i == 5000)
{
    break;
}

v.push_back(i);

m.unlock();
```

`i`가 `5000`이면 `unlock()`에 도달하기 전에 반복문을 빠져나간다. 잠금이 풀리지 않으므로 같은 뮤텍스를 얻으려는 다른 스레드가 계속 기다리는 문제가 생길 수 있다.

`break`뿐 아니라 `return`이나 예외로 코드 실행이 중간에 끝날 때도 해제를 빠뜨릴 수 있다. 예를 들어 `push_back()` 도중 메모리 할당에 실패해 예외가 발생하면, 아래의 `unlock()`은 실행되지 않는다.

이를 방지하기 위해 **잠금의 수명을 객체의 수명에 연결하는 방법**을 사용한다.

## RAII로 잠금 해제 자동화하기

RAII(Resource Acquisition Is Initialization)는 **객체가 생성될 때 자원을 얻고, 소멸할 때 자원을 반납하도록 만드는 방식**이다.

여기서 관리할 자원은 뮤텍스 잠금이다. 원리는 다음과 같은 학습용 클래스로 살펴볼 수 있다.

```cpp
template <typename T>
class LockGuard
{
public:
    LockGuard(T& m)
    {
        _mutex = &m;
        _mutex->lock();
    }

    ~LockGuard()
    {
        _mutex->unlock();
    }

private:
    T* _mutex;
};
```

| 시점 | 수행하는 작업 |
|---|---|
| 생성자 실행 | lock()으로 잠금 획득 |
| 소멸자 실행 | unlock()으로 잠금 해제 |

이를 지역 변수로 사용한다.

```cpp
LockGuard<std::mutex> guard(m);
```

객체가 생성되면 잠금을 얻고, 객체가 속한 블록을 벗어나면 소멸자가 잠금을 해제한다.

```cpp
for (int i = 0; i < 10000; i++)
{
    LockGuard<std::mutex> guard(m);

    if (i == 5000)
    {
        break;
    }

    v.push_back(i);
}
```

일반 반복에서는 반복문 본문의 끝에서 잠금을 해제한다. `break`로 빠져나갈 때도 지역 객체가 소멸하면서 잠금을 해제한다.

`return`이나 예외 처리 과정에서 스택을 정리하며 블록을 벗어날 때도 같은 원리가 적용된다.

직접 만든 클래스는 원리를 보여주기 위한 예제다. 이 상태에서는 복사를 허용하므로 여러 객체가 같은 잠금을 중복으로 해제할 수 있다. 실제 코드에서는 복사를 막는 등 필요한 처리가 갖춰진 표준 라이브러리의 도구를 사용하는 것이 좋다.

## std::lock_guard로 같은 작업 수행하기

C++ 표준 라이브러리에는 `std::lock_guard`가 준비되어 있다.

```cpp
std::lock_guard<std::mutex> guard(m);
```

생성 시 잠그고 소멸 시 해제하는 역할은 학습용 `LockGuard`와 같다.

`guard`가 잠금을 관리하는 동안 별도로 `m.unlock()`을 호출하면 안 된다. 잠금 해제는 객체에 맡긴다.

## 두 스레드가 vector에 원소를 추가하는 전체 코드

다음은 별도 프로젝트 헤더 없이 실행할 수 있도록 표준 헤더와 `int`를 사용한 예제다.

```cpp
#include <iostream>
#include <mutex>
#include <thread>
#include <vector>

std::vector<int> v;
std::mutex m;

void Push()
{
    for (int i = 0; i < 10000; i++)
    {
        std::lock_guard<std::mutex> guard(m);

        if (i == 5000)
        {
            break;
        }

        v.push_back(i);
    }
}

int main()
{
    std::cout << "Hello Main\n";

    std::thread t1(Push);
    std::thread t2(Push);

    t1.join();
    t2.join();

    std::cout << v.size() << "\n";
}
```

반복마다 `guard`를 새로 만들므로, 매번 잠금을 획득하고 해제한다. 두 스레드의 원소 추가가 섞여 실행될 수 있지만, 반드시 번갈아 실행된다는 보장은 없다.

### 최종 vector 크기는 10000이다

각 스레드는 `i`가 `5000`이 되면 원소를 추가하기 전에 반복문을 빠져나간다.

```text
스레드 하나가 추가하는 값: 0, 1, 2, ... , 4999
스레드 하나가 추가하는 개수: 5000개

전체 개수: 5000개 × 2개 스레드 = 10000개
```

두 스레드가 모두 정상적으로 작업을 마치면 최종 크기는 `10000`이다. 두 스레드 모두 같은 범위의 숫자를 넣으므로 각 숫자는 두 번씩 들어간다. 다만 두 스레드의 작업이 섞이는 순서는 보장되지 않는다.

메인 스레드는 두 스레드에 대해 `join()`한 뒤 크기를 읽는다. 이 시점에는 원소 추가가 모두 끝났으므로, 최종 `v.size()`를 읽을 때는 별도로 잠글 필요가 없다.

## unique_lock은 잠금 시점을 더 유연하게 다룬다

```cpp
std::unique_lock<std::mutex> guard(m, std::defer_lock);
guard.lock();
```

`std::defer_lock`을 지정하면 객체를 만들 때 바로 잠그지 않는다. 이후 `guard.lock()`을 호출하는 시점에 잠금을 얻는다.

| 도구 | 특징 |
|---|---|
| lock_guard | 생성할 때 잠그고, 소멸할 때 해제 |
| unique_lock | 잠금을 미루거나, 중간에 해제하고 다시 획득 가능 |

`unique_lock`은 소멸할 때 자신이 잠금을 보유하고 있으면 해제한다. 단순히 블록 전체를 보호하는 상황이라면 `lock_guard`로 충분하다.

## 같은 스레드가 같은 mutex를 다시 잠그면?

일반적인 `std::mutex`는 이미 잠금을 가진 스레드가 다시 잠그는 용도로 사용할 수 없다. 이를 시도하면 동작이 정의되지 않으므로, 다시 잠그면 기다리기만 한다고 가정해서도 안 된다.

예를 들어 잠금을 가진 함수가 다른 함수를 호출하고, 그 함수가 같은 뮤텍스를 다시 잠그려고 하는 경우를 주의해야 한다.

이런 중복 잠금을 허용하는 도구가 `std::recursive_mutex`다. 같은 스레드가 여러 번 잠글 수 있지만, 잠근 횟수만큼 해제해야 다른 스레드가 잠금을 얻을 수 있다.

재귀 뮤텍스를 사용하기 전에는 함수 사이에서 잠금을 중복으로 잡는 구조인지 먼저 살펴보는 것이 좋다.

## 잠금과 대기는 역할이 다르다

| 기능 | 역할 |
|---|---|
| mutex | 벡터 수정이 동시에 일어나지 않도록 보호 |
| lock_guard | 블록을 벗어날 때 잠금 자동 해제 |
| join() | 모든 추가 작업이 끝날 때까지 대기 |

`join()`은 작업 도중의 충돌을 막지 않고, `mutex`는 모든 작업이 끝났다는 것을 알려주지 않는다. 각각 필요한 위치에서 사용해야 한다.

공유 데이터는 같은 뮤텍스를 사용하는 규칙으로 보호하고, 잠금 해제는 객체의 수명에 맡기면 중간에 블록을 빠져나가는 코드도 안전하게 관리할 수 있다.
