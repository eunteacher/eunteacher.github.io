이전 글에서는 `CALL`이 반환 주소를 스택에 저장하고, `RET`이 그 주소를 이용해 호출자에게 돌아가는 과정을 살펴봤다. 하지만 실제 함수는 반환 주소만 사용하는 것이 아니다.

함수는 필요에 따라 호출 전 값을 유지해야 하는 레지스터를 보관하고, 지역 데이터를 위한 공간을 확보하며, 다른 함수를 호출하기 위한 스택 규칙도 지켜야 한다. 함수가 빌린 스택 공간을 정확히 되돌려야 `RET`이 올바른 반환 주소를 찾을 수 있다.

이번 글에서는 **함수가 스택 프레임을 만들고 사용하는 과정**, 그리고 **프롤로그에서 수행한 작업을 에필로그에서 역순으로 복원해야 하는 이유**를 살펴본다.

> 이 글은 Windows x64 호출 규약을 기준으로 설명한다. `io64.inc` 학습 템플릿에서 코드를 실행할 때는 템플릿이 제공하는 `CMAIN` 진입 환경도 함께 고려해야 한다.

## 스택과 RSP

스택(Stack)은 데이터를 마지막에 넣은 순서의 역순으로 꺼내는 LIFO 구조다.

```text
Last In, First Out
마지막에 넣은 값이 가장 먼저 나옴
```

x86-64에서 스택은 일반적으로 높은 주소에서 낮은 주소 방향으로 확장된다. RSP는 현재 사용 중인 스택의 맨 위, 즉 가장 최근에 배치된 데이터가 있는 위치를 가리킨다.

```text
높은 주소
┌─────────────────┐
│ 이전 스택 데이터 │
├─────────────────┤
│ 최근 저장한 값   │ ← RSP
└─────────────────┘
낮은 주소
```

RSP가 메모리 전체에서 가장 낮은 주소를 가리킨다는 뜻은 아니다. 새 데이터를 스택에 놓을 때 RSP가 더 낮은 주소로 이동한다는 의미다.

## `PUSH`와 `POP`

64비트 모드에서 범용 레지스터를 `PUSH`하면 일반적으로 8바이트가 스택에 추가된다.

```nasm
mov rax, 0x1111
push rax
```

개념적인 동작은 다음과 같다.

```text
RSP = RSP - 8
[RSP] = RAX
```

`POP`은 현재 RSP가 가리키는 값을 읽은 뒤 RSP를 원래 방향으로 이동한다.

```nasm
pop rbx
```

```text
RBX = [RSP]
RSP = RSP + 8
```

따라서 다음 코드를 실행하면 RBX에는 `0x1111`이 들어가고 RSP는 처음 위치로 돌아온다.

```nasm
mov rax, 0x1111
push rax
pop rbx
```

`POP`은 스택 메모리의 기존 바이트를 0으로 지우는 명령이 아니다. RSP를 이동해 해당 공간을 더 이상 현재 스택 데이터로 사용하지 않도록 만들 뿐이다. 이후 다른 스택 데이터가 같은 위치를 덮어쓸 수 있다.

## 함수 진입 시 스택에 있는 반환 주소

호출자가 다음 코드를 실행한다고 가정한다.

```nasm
call SOME_FUNCTION
mov ebx, eax
```

`CALL`은 `mov ebx, eax`의 주소를 스택에 저장한 뒤 함수로 이동한다. 따라서 `SOME_FUNCTION`에 진입한 직후 RSP는 반환 주소를 가리킨다.

```text
높은 주소
┌────────────────────┐
│ 호출자가 준비한 공간 │
├────────────────────┤
│ 반환 주소            │ ← RSP
└────────────────────┘
낮은 주소
```

함수가 추가로 스택을 사용하지 않았다면 `RET`은 `[RSP]`의 8바이트 값을 반환 주소로 사용하고 RSP를 8 증가시킨다.

함수가 RSP를 변경했다면 `RET` 전에 반드시 반환 주소가 다시 `[RSP]`에 오도록 복원해야 한다.

## Windows x64의 스택 정렬

Windows x64 호출 규약에서는 호출자가 `CALL`을 실행하기 직전에 RSP를 16바이트 경계에 맞춰야 한다.

```text
CALL 직전      : RSP % 16 = 0
함수 진입 직후 : RSP % 16 = 8
```

`CALL`이 8바이트 반환 주소를 스택에 추가하기 때문에 함수 진입 직후에는 RSP가 16바이트 경계에서 8바이트 어긋난 상태가 된다.

함수가 다시 다른 함수를 호출하려면 그 전에 RSP를 조정해 새로운 `CALL` 직전의 16바이트 정렬을 맞춰야 한다. SIMD 명령이나 외부 함수 호출 등은 ABI가 정한 정렬 상태를 전제로 할 수 있으므로 이 규칙을 임의로 무시하면 안 된다.

## 32바이트 Shadow Space

Windows x64에서 호출자는 함수를 호출하기 전에 32바이트의 shadow space 또는 home space를 준비한다.

이 공간은 첫 네 개의 인자 레지스터 RCX, RDX, R8, R9에 대응하는 슬롯이다. 피호출자가 반드시 사용하는 것은 아니지만 호출자는 항상 사용할 수 있도록 마련해야 한다.

피호출자 진입 직후의 스택을 단순화하면 다음과 같다.

```text
높은 주소
┌────────────────────────┐
│ 네 번째 인자 home slot │ [RSP + 32]
├────────────────────────┤
│ 세 번째 인자 home slot │ [RSP + 24]
├────────────────────────┤
│ 두 번째 인자 home slot │ [RSP + 16]
├────────────────────────┤
│ 첫 번째 인자 home slot │ [RSP + 8]
├────────────────────────┤
│ 반환 주소               │ [RSP + 0] ← RSP
└────────────────────────┘
낮은 주소
```

호출자는 `CALL` 직전 관점에서 `[RSP]`부터 `[RSP + 31]`까지 32바이트를 마련한다. `CALL`이 반환 주소를 추가하면 피호출자 진입 시 각 슬롯은 `[RSP + 8]`부터 보인다.

## 호출자가 준비하는 40바이트

Windows x64 함수에 진입한 직후 RSP가 일반적인 `16n + 8` 상태라고 가정해 보자. 이 함수가 다른 함수를 호출하려면 다음과 같이 40바이트를 확보하는 패턴을 사용할 수 있다.

```nasm
sub rsp, 40
call TARGET
add rsp, 40
```

40바이트는 다음 두 목적을 가진다.

```text
32바이트: TARGET을 위한 shadow space
 8바이트: CALL 직전 16바이트 정렬을 맞추는 보정
```

호출 전과 후에 같은 크기를 빼고 더해야 RSP가 원래 위치로 돌아온다.

```nasm
mov ecx, 10
mov edx, 5

sub rsp, 40
call MAX
add rsp, 40
```

이 패턴은 함수 진입 시 RSP의 정렬 상태가 ABI의 일반 규칙을 만족한다는 전제에서 설명한 것이다. 임의의 코드 위치에서 현재 RSP 상태를 확인하지 않고 항상 40을 빼면 된다고 일반화해서는 안 된다.

## 프롤로그로 스택 프레임 만들기

함수가 지역 공간과 고정된 기준 주소가 필요하다면 프롤로그(Prologue)에서 스택 프레임을 만들 수 있다.

```nasm
push rbp
mov rbp, rsp
sub rsp, 16
```

각 명령의 역할은 다음과 같다.

1. `push rbp`: 호출자가 사용하던 RBP 보존
2. `mov rbp, rsp`: 현재 위치를 함수 프레임의 고정 기준점으로 설정
3. `sub rsp, 16`: 지역 데이터로 사용할 16바이트 공간 확보

프롤로그 직후의 개념적 배치는 다음과 같다.

```text
높은 주소
┌────────────────────┐
│ 호출자가 준비한 공간 │
├────────────────────┤
│ 반환 주소            │ [RBP + 8]
├────────────────────┤
│ 이전 RBP             │ [RBP + 0] ← RBP
├────────────────────┤
│ 지역 공간            │ [RBP - 1] ... [RBP - 16]
└────────────────────┘ ← RSP
낮은 주소
```

RSP는 지역 공간 확보나 임시 데이터 사용에 따라 변할 수 있지만 RBP를 변경하지 않으면 함수 내부에서 고정된 오프셋으로 데이터에 접근할 수 있다.

## 지역 변수 공간 사용하기

두 인자를 더한 결과를 4바이트 지역 슬롯에 저장하는 학습용 함수를 작성한다.

```nasm
; Input : ECX = first, EDX = second
; Return: EAX = first + second
ADD_WITH_LOCAL:
    push rbp
    mov rbp, rsp
    sub rsp, 16

    mov eax, ecx
    add eax, edx
    mov dword [rbp - 4], eax

    mov eax, dword [rbp - 4]

    mov rsp, rbp
    pop rbp
    ret
```

실제로는 계산 결과를 EAX에 그대로 반환하면 되므로 이 지역 변수는 필요하지 않다. 여기서는 `[RBP - 4]` 위치에 4바이트 지역 슬롯을 만들고 접근하는 방법을 관찰하기 위해 일부러 메모리에 저장했다.

`sub rsp, 16`으로 16바이트를 확보했으므로 `[rbp - 4]`는 예약한 범위 안에 있다. 지역 슬롯을 사용할 때는 확보한 범위를 벗어나지 않고 접근 크기도 맞춰야 한다.

## 에필로그에서 프레임 복원하기

프레임 포인터를 사용한 함수는 반환 전에 RSP와 RBP를 복원해야 한다.

```nasm
mov rsp, rbp
pop rbp
ret
```

각 단계는 다음과 같다.

1. `mov rsp, rbp`: 지역 공간을 한 번에 반환하고 저장된 이전 RBP 위치로 복귀
2. `pop rbp`: 호출자의 RBP 복원
3. `ret`: 이제 `[RSP]`에 있는 반환 주소를 사용해 호출자로 복귀

`LEAVE`는 개념적으로 다음 두 명령과 같은 프레임 정리 동작을 수행한다.

```nasm
mov rsp, rbp
pop rbp
```

따라서 단순한 프레임에서는 다음처럼 쓸 수도 있다.

```nasm
leave
ret
```

하지만 함수가 RBP 아래에 다른 nonvolatile 레지스터를 별도로 저장했다면 해당 값의 위치와 복원 순서까지 고려해야 한다.

## Nonvolatile 레지스터 보존하기

Windows x64에서 RBX는 nonvolatile 레지스터다. 함수가 RBX를 변경하면 반환 전에 호출 당시 값으로 복원해야 한다.

```nasm
; Input : ECX
; Return: EAX
USE_RBX:
    push rbp
    mov rbp, rsp
    push rbx
    sub rsp, 8

    mov ebx, ecx
    mov dword [rbp - 16], ebx
    mov eax, dword [rbp - 16]

    add rsp, 8
    pop rbx
    pop rbp
    ret
```

프롤로그 이후의 배치는 다음과 같다.

```text
높은 주소
┌────────────────────┐
│ 반환 주소            │ [RBP + 8]
├────────────────────┤
│ 이전 RBP             │ [RBP + 0] ← RBP
├────────────────────┤
│ 저장된 RBX            │ [RBP - 8]
├────────────────────┤
│ 지역 공간 8바이트     │ [RBP - 16] ... [RBP - 9]
└────────────────────┘ ← RSP
낮은 주소
```

에필로그는 프롤로그에서 수행한 작업을 정확히 역순으로 되돌린다.

```text
프롤로그                      에필로그
push rbp                  ↔   pop rbp
mov rbp, rsp              ↔   기준점 사용 종료
push rbx                  ↔   pop rbx
sub rsp, 8                ↔   add rsp, 8
```

실제 실행 순서로 보면 마지막에 확보한 지역 공간부터 반환한다.

```nasm
add rsp, 8
pop rbx
pop rbp
ret
```

RBX를 복원하기 전에 `mov rsp, rbp`를 실행하면 저장된 RBX 위치를 건너뛰게 된다. 어떤 값을 어떤 순서로 스택에 배치했는지에 맞춰 복원해야 한다.

## RBP는 항상 필요한가

RBP를 고정 기준점으로 사용하면 지역 변수와 저장값의 위치를 `[rbp - offset]`, 반환 주소를 `[rbp + offset]`처럼 관찰하기 쉽다.

하지만 모든 함수에 RBP 기반 프레임이 필수인 것은 아니다.

- 지역 공간이 없는 leaf function은 RSP를 변경하지 않고 끝날 수 있다.
- RSP가 함수 안에서 예측 가능한 방식으로만 변한다면 RSP 기준으로 지역 데이터에 접근할 수 있다.
- 컴파일러는 최적화 설정에 따라 프레임 포인터를 생략하고 RBP를 일반 레지스터로 사용할 수 있다.

이번 글에서는 스택 배치를 눈으로 추적하기 위해 RBP를 고정된 기준점으로 사용한다. 실제 코드에서는 디버깅, unwind 정보, 함수 구조와 최적화 정책을 함께 고려한다.

## 다섯 번째 이후 인자의 위치

Windows x64에서는 처음 네 개의 일반적인 정수·포인터 인자를 RCX, RDX, R8, R9로 전달한다. 다섯 번째 이후 인자는 shadow space 뒤쪽 스택에 배치한다.

호출자는 다음처럼 다섯 번째 값을 준비할 수 있다.

```nasm
sub rsp, 40

mov ecx, 1
mov edx, 2
mov r8d, 3
mov r9d, 4
mov qword [rsp + 32], 5

call SUM_FIVE
add rsp, 40
```

`CALL` 직전의 `[rsp + 0]`부터 `[rsp + 31]`까지는 shadow space이고 `[rsp + 32]`에 다섯 번째 인자가 있다.

`CALL`이 반환 주소 8바이트를 추가하므로 `SUM_FIVE` 진입 직후에는 다섯 번째 인자가 다음 위치에서 보인다.

```nasm
mov eax, dword [rsp + 40]
```

함수가 다시 RBP를 저장하면 기준점이 8바이트 이동한다.

```nasm
SUM_FIVE:
    push rbp
    mov rbp, rsp

    mov eax, dword [rbp + 48]    ; 다섯 번째 인자

    pop rbp
    ret
```

오프셋이 달라지는 이유를 단계별로 보면 다음과 같다.

```text
CALL 직전       : [RSP + 32]
반환 주소 추가 후: [RSP + 40]
PUSH RBP 후     : [RBP + 48]
```

스택 인자의 위치는 “항상 `[RBP + 16]`”처럼 고정된 공식이 아니다. 호출 규약이 정한 기본 배치와 함수 프롤로그가 RSP를 얼마나 이동시켰는지를 함께 계산해야 한다.

## 32비트 `cdecl`, `stdcall`과 구분하기

32비트 x86에서는 `__cdecl`, `__stdcall` 같은 호출 규약에 따라 인자를 스택에 넣는 순서와 정리 책임이 달랐다.

- `__cdecl`: 일반적으로 호출자가 스택 인자 정리
- `__stdcall`: 일반적으로 피호출자가 스택 인자 정리

이 규칙을 Windows x64 코드에 그대로 적용하면 안 된다. Windows x64에서는 대부분 통합된 x64 호출 규약을 사용한다.

- 처음 네 일반 정수·포인터 인자는 RCX, RDX, R8, R9
- 추가 인자는 shadow space 뒤쪽 스택
- 호출자가 shadow space와 호출 시점 정렬 준비
- 피호출자가 변경한 nonvolatile 레지스터 복원

따라서 64비트 예제에서 첫 번째와 두 번째 인자를 무조건 `PUSH`하고 이를 `cdecl` 또는 `stdcall`이라고 설명하는 것은 현재 ABI와 맞지 않는다.

## 스택을 잘못 복원하면 발생하는 문제

프롤로그와 에필로그의 크기 또는 순서가 맞지 않으면 다음 문제가 생길 수 있다.

- 잘못된 값을 nonvolatile 레지스터로 복원
- RSP가 호출 전 위치로 돌아오지 않음
- `RET`이 데이터 값을 반환 주소로 해석
- 후속 함수 호출에서 16바이트 정렬 위반
- 다른 함수의 스택 데이터 또는 호출자 영역 손상

예를 들어 다음 코드는 16바이트를 확보하고 8바이트만 돌려준다.

```nasm
sub rsp, 16

; 함수 작업

add rsp, 8       ; 잘못된 복원
ret
```

`RET` 시점의 RSP가 반환 주소보다 8바이트 아래에 있으므로 지역 데이터 일부를 주소로 해석할 수 있다. Windows에서는 잘못된 주소 실행이나 메모리 접근 예외로 이어질 수 있다.

호출자가 마련한 공간을 호출 후 정리하지 않은 경우에는 피호출자의 `RET`이 먼저 정상 동작할 수도 있다. 그러나 호출자의 RSP가 원래 위치로 돌아오지 않았으므로 이후 호출이나 호출자 자신의 `RET`에서 문제가 드러날 수 있다.

## 전체 실습 코드

다음 코드는 Windows x64의 shadow space와 호출 시점 정렬을 고려해 두 개의 학습용 함수를 호출한다. `CMAIN`이 일반적인 Windows x64 함수 진입 상태인 `RSP % 16 = 8`로 시작한다고 가정한다.

```nasm
%include "io64.inc"

section .text
global CMAIN

CMAIN:
    ; CALL 직전 정렬 + 32바이트 shadow space
    sub rsp, 40

    mov ecx, 10
    mov edx, 5
    call ADD_WITH_LOCAL
    mov r10d, eax             ; R10D = 15

    mov ecx, 42
    call USE_RBX
    mov r11d, eax             ; R11D = 42

    add rsp, 40

    xor rax, rax
    ret

; Input : ECX = first, EDX = second
; Return: EAX = first + second
ADD_WITH_LOCAL:
    push rbp
    mov rbp, rsp
    sub rsp, 16

    mov eax, ecx
    add eax, edx
    mov dword [rbp - 4], eax

    mov eax, dword [rbp - 4]

    mov rsp, rbp
    pop rbp
    ret

; Input : ECX
; Return: EAX = ECX
USE_RBX:
    push rbp
    mov rbp, rsp
    push rbx
    sub rsp, 8

    mov ebx, ecx
    mov dword [rbp - 16], ebx
    mov eax, dword [rbp - 16]

    add rsp, 8
    pop rbx
    pop rbp
    ret
```

두 함수 모두 다른 함수를 호출하지 않는 leaf function이다. 함수 내부에서 외부 함수를 다시 호출한다면 해당 호출을 위한 shadow space와 정렬 상태도 함수 프레임 설계에 포함해야 한다.

R10과 R11은 volatile 레지스터이므로 결과 관찰용으로만 사용했다. 두 번째 함수 호출 후 R10의 값이 반드시 유지된다고 가정해서는 안 된다.

## 디버거에서 확인할 것

1. `PUSH RAX` 실행 후 RSP가 8 감소하고 `[RSP]`에 RAX 값이 저장되는가?
2. `POP RBX` 실행 후 RBX에 값이 들어가고 RSP가 원래 위치로 돌아오는가?
3. `CALL` 직전에 RSP가 16바이트 경계에 맞는가?
4. 함수 진입 직후 `[RSP]`에 반환 주소가 있는가?
5. `push rbp` 후 반환 주소가 `[rbp + 8]`에서 보이는가?
6. `ADD_WITH_LOCAL`의 `[rbp - 4]`에 합계 15가 저장되는가?
7. `USE_RBX` 진입 전후 RBX의 전체 값이 같은가?
8. 각 함수의 `RET` 후 RSP가 해당 `CALL` 직전 상태로 돌아오는가?
9. CMAIN의 `add rsp, 40` 이후 RSP가 함수 시작 시점으로 복원되는가?
10. 다섯 번째 인자가 CALL 전 `[rsp + 32]`, 함수 진입 후 `[rsp + 40]`에 위치하는가?

## Assembly 시리즈 마무리

이번 글에서 확인한 핵심은 다음과 같다.

- 스택은 x86-64에서 일반적으로 낮은 주소 방향으로 확장된다.
- `PUSH`는 RSP를 감소시킨 뒤 값을 저장하고 `POP`은 값을 읽은 뒤 RSP를 증가시킨다.
- 함수 진입 직후 `[RSP]`에는 `CALL`이 저장한 반환 주소가 있다.
- Windows x64 호출자는 32바이트 shadow space를 준비하고 호출 시점의 16바이트 정렬을 맞춘다.
- 프롤로그는 이전 기준점과 보존할 레지스터를 저장하고 지역 공간을 확보한다.
- RBP는 학습하기 좋은 고정 기준점이지만 모든 함수에 필수는 아니다.
- nonvolatile 레지스터는 변경했다면 호출 당시 값으로 복원해야 한다.
- 에필로그는 프롤로그에서 수행한 작업을 정확히 역순으로 되돌려야 한다.
- 추가 인자는 shadow space 뒤쪽 스택에 배치된다.
- 32비트 `cdecl/stdcall` 규칙과 Windows x64 호출 규약을 혼합하면 안 된다.

이번 Assembly 시리즈에서는 소스 파일의 구성에서 시작해 레지스터, 메모리, 엔디안, 산술과 비트 연산, 조건 분기, 반복문, 배열, 함수와 스택 프레임까지 순서대로 살펴봤다.

어셈블리를 직접 작성하는 것만큼 중요한 것은 C++ 코드가 컴파일된 뒤 어떤 레지스터와 메모리 접근, 분기와 호출 구조로 바뀌는지 읽을 수 있는 능력이다. 이후에는 디버거의 Disassembly와 레지스터·메모리 창을 함께 보면서 고수준 코드와 CPU 수준 동작을 연결해 볼 수 있다.
