이전 글에서는 CPU 내부의 레지스터에 값을 저장하고, `RAX`, `EAX`, `AX`, `AL`을 통해 하나의 레지스터를 여러 크기로 접근해 봤다.

하지만 레지스터는 개수가 제한되어 있고 프로그램이 사용하는 모든 데이터를 담을 수 없다. 이번에는 `.data`와 `.bss`에 데이터를 배치하고, **데이터가 놓인 주소**와 **그 주소에 저장된 값**을 구분해 본다.

## 메모리에 데이터 배치하기

NASM에서는 `section` 지시어로 코드와 데이터를 배치할 섹션을 구분한다.

```nasm
section .data
    value8  db 0x11
    value16 dw 0x2222
    value32 dd 0x33333333
    value64 dq 0x4444444444444444

section .bss
    buffer resb 10
```

`.data`에는 실행 전부터 초기값이 정해진 데이터를 배치한다. 위 코드의 초기값은 실행 파일에 함께 기록되고, 프로그램을 실행할 때 메모리로 매핑된다.

`.bss`는 초기값을 별도로 저장할 필요가 없는 공간을 예약할 때 사용한다. `buffer resb 10`은 10바이트의 공간이 필요하다는 정보를 기록하고, 로더는 프로세스를 시작할 때 해당 메모리를 0으로 초기화한다.

`.bss`가 실행 파일에서 아무 공간도 사용하지 않는다는 뜻은 아니다. 섹션의 크기와 배치에 필요한 정보는 기록되지만, 초기값 0을 나타내는 바이트들을 예약한 크기만큼 직접 저장하지 않는다는 의미다.

## `db`, `dw`, `dd`, `dq`로 크기 정하기

데이터 정의 지시어는 메모리에 배치할 데이터의 크기를 결정한다.

| 지시어 | 의미 | 크기 | 예제 |
| :--- | :--- | ---: | :--- |
| `db` | Define Byte | 1바이트 | `value8 db 0x11` |
| `dw` | Define Word | 2바이트 | `value16 dw 0x2222` |
| `dd` | Define Doubleword | 4바이트 | `value32 dd 0x33333333` |
| `dq` | Define Quadword | 8바이트 | `value64 dq 0x4444444444444444` |

이 지시어들은 C++의 자료형처럼 데이터의 의미까지 결정하지 않는다. `dd`는 4바이트를 배치할 뿐, 그 비트가 정수인지 실수인지는 이후 어떤 명령어로 읽고 연산하느냐에 따라 달라진다.

초기값이 없는 공간은 `resb`, `resw`, `resd`, `resq`로 예약할 수 있다.

```nasm
section .bss
    byteBuffer  resb 10    ; 1바이트 공간 10개
    wordBuffer  resw 10    ; 2바이트 공간 10개
    dwordBuffer resd 10    ; 4바이트 공간 10개
    qwordBuffer resq 10    ; 8바이트 공간 10개
```

## 레이블은 메모리 위치에 붙인 이름이다

다음 선언에서 `value8`은 데이터 값 `0x11`의 또 다른 이름이 아니다.

```nasm
value8 db 0x11
```

`value8`은 `0x11`이 배치된 메모리 위치를 나타내는 레이블이다. 소스 코드에서는 숫자로 된 실제 주소 대신 이 이름을 사용하고, 어셈블러와 링커가 최종 주소를 결정할 수 있도록 필요한 정보를 만든다.

현재 학습 환경에서는 다음과 같이 레이블이 나타내는 주소를 레지스터에 넣을 수 있다.

```nasm
mov rax, value8
```

이 명령을 실행하면 RAX에는 `0x11`이 아니라 `value8`이 배치된 주소가 들어간다.

주소 계산에는 `lea` 명령어도 사용할 수 있다.

```nasm
lea rbx, [rel value8]
```

`lea`는 대괄호 안의 메모리를 읽지 않고 유효 주소(Effective Address)를 계산한다. `rel`은 현재 명령어 위치를 기준으로 `value8`의 주소를 계산하도록 NASM에 지시한다.

주소를 표현하는 구체적인 방식은 실행 파일 형식과 링크 설정에 따라 달라질 수 있다. 여기서는 `mov rax, value8`과 `lea rbx, [rel value8]` 모두 **값을 읽는 것이 아니라 주소를 구하는 코드**라는 점에 집중한다.

## 대괄호로 주소에 저장된 값 읽기

레이블을 대괄호로 감싸면 해당 주소의 메모리에 접근한다.

```nasm
mov al, [value8]
```

이 명령은 `value8`의 주소에서 1바이트를 읽어 AL에 저장한다. 목적지가 8비트 레지스터인 AL이므로 읽는 크기도 1바이트다.

주소와 값을 비교하면 다음과 같다.

```nasm
mov rax, value8    ; value8의 주소를 RAX에 저장
mov al, [value8]   ; value8 주소에서 1바이트 값을 읽어 AL에 저장
```

대괄호는 주소에 있는 값을 읽거나 쓴다는 뜻이지만, 몇 바이트를 접근할지까지 자동으로 결정하지는 않는다. 실제 접근 크기는 레지스터 크기 또는 명시한 크기 지정자에 따라 결정된다.

```nasm
mov al, [value8]      ; 1바이트 읽기
mov ax, [value8]      ; value8 주소부터 2바이트 읽기
mov eax, [value8]     ; value8 주소부터 4바이트 읽기
mov rax, [value8]     ; value8 주소부터 8바이트 읽기
```

마지막 세 명령은 `value8`이 `db`로 선언됐다는 사실과 관계없이 그 주소부터 각각 2, 4, 8바이트를 읽는다. 어셈블러는 레이블을 C++ 변수처럼 취급해서 선언 크기 밖의 접근을 막아주지 않는다.

## 작은 값을 큰 레지스터로 읽기

1바이트 값 `value8`을 RAX 계열 전체에서 사용하고 싶다고 해서 다음과 같이 읽으면 안 된다.

```nasm
mov rax, [value8]    ; value8 주소부터 8바이트를 읽음
```

필요한 1바이트만 읽은 뒤 나머지 비트를 0으로 채우려면 `movzx`를 사용할 수 있다.

```nasm
movzx eax, byte [value8]
```

`movzx`는 Move with Zero-Extend의 약자다. 원본의 작은 값을 목적지의 더 큰 크기로 복사하면서 새로 늘어난 상위 비트를 0으로 채운다.

```text
메모리의 value8 : 0x11
EAX 결과         : 0x00000011
RAX 결과         : 0x0000000000000011
```

EAX에 값을 쓰면 RAX의 상위 32비트가 0이 된다는 이전 글의 규칙까지 적용되므로 RAX 전체도 깔끔하게 0 확장된다.

크기에 맞춰 데이터를 읽는 예는 다음과 같다.

```nasm
movzx eax, byte [value8]
movzx eax, word [value16]
mov eax, dword [value32]
mov rax, qword [value64]
```

- 1바이트와 2바이트 값은 `movzx`로 EAX까지 0 확장한다.
- 4바이트 값은 EAX에 직접 읽는다.
- 8바이트 값은 RAX에 직접 읽는다.

## 메모리에 값 쓰기

레지스터 값을 메모리에 쓸 때는 레지스터 크기를 통해 접근 크기를 알 수 있다.

```nasm
mov cl, 0x55
mov [value8], cl
```

CL이 1바이트 레지스터이므로 `value8`에도 1바이트를 쓴다.

반면 상수를 메모리에 직접 쓸 때는 상수 자체만 보고 접근 크기를 하나로 결정할 수 없는 경우가 있다. 이때는 메모리 피연산자 앞에 크기를 명시한다.

```nasm
mov byte [value8], 0x55
mov word [value16], 0x6666
mov dword [value32], 0x77777777
mov qword [value64], 0x11111111
```

크기 지정자는 “이 변수의 자료형”을 선언하는 문법이 아니라, **이번 명령이 해당 주소에서 몇 바이트를 읽거나 쓸지** 지정한다.

## 전체 실습 코드

다음 코드를 디버거에서 한 줄씩 실행하며 주소와 값을 확인한다.

```nasm
%include "io64.inc"

section .text
global CMAIN

CMAIN:
    ; 레이블의 주소 가져오기
    mov rax, value8
    lea rbx, [rel value8]

    ; 메모리에서 크기에 맞춰 값 읽기
    movzx eax, byte [value8]
    movzx eax, word [value16]
    mov eax, dword [value32]
    mov rax, qword [value64]

    ; 메모리에 값 쓰기
    mov byte [value8], 0x55
    mov word [value16], 0x6666
    mov dword [value32], 0x77777777

    xor rax, rax
    ret

section .data
    value8  db 0x11
    value16 dw 0x2222
    value32 dd 0x33333333
    value64 dq 0x4444444444444444

section .bss
    buffer resb 10
```

디버거에서는 다음 내용을 확인한다.

1. `mov rax, value8`을 실행했을 때 RAX에 값이 아닌 주소가 들어가는가?
2. `lea rbx, [rel value8]`의 결과가 같은 메모리 위치를 가리키는가?
3. 각 읽기 명령이 목적지 레지스터 크기만큼 데이터를 가져오는가?
4. `movzx`를 실행했을 때 목적지의 상위 비트가 0으로 채워지는가?
5. 메모리에 값을 쓴 뒤 Memory View의 바이트가 변경되는가?

## 접근 크기가 틀리면 옆 데이터까지 침범한다

다음 코드는 실행을 권장하는 정상 예제가 아니라, 접근 크기를 잘못 지정했을 때의 문제를 설명하기 위한 코드다.

```nasm
section .data
    first  db 0x11
    second db 0x22

; 잘못된 접근: first는 1바이트 위치지만 2바이트를 씀
mov word [first], 0xBBAA
```

`word`는 2바이트를 쓰기 때문에 `first`만 변경하는 것이 아니라 바로 다음 위치의 `second`까지 덮어쓴다. x86-64의 리틀 엔디안 환경에서는 메모리가 다음처럼 바뀐다.

```text
쓰기 전: [11] [22]
          first second

쓰기 후: [AA] [BB]
          first second
```

어셈블리에는 C++ 배열의 범위 검사처럼 잘못된 접근을 자동으로 막아주는 장치가 없다. 레이블이 나타내는 위치, 데이터가 차지하는 크기, 명령어가 접근하는 크기를 프로그래머가 직접 맞춰야 한다.

## 다음 학습: 연속된 바이트를 해석하는 방법

이번 글에서 확인한 핵심은 다음과 같다.

- `.data`에는 초기값이 있는 데이터를 배치한다.
- `.bss`에는 실행 시 0으로 초기화할 공간을 예약한다.
- 레이블은 데이터가 놓인 메모리 위치를 나타낸다.
- 대괄호를 사용하면 해당 주소의 메모리에 접근한다.
- 메모리를 읽고 쓸 때는 접근 크기를 정확히 지정해야 한다.
- 작은 값을 큰 레지스터로 읽을 때는 `movzx`로 0 확장할 수 있다.

다음 글에서는 여러 바이트가 메모리에 연속해서 놓이는 방식을 살펴본다. 이를 바탕으로 배열과 문자열을 구성하고, 2바이트 이상의 값이 어떤 순서로 저장되는지 엔디안 관점에서 확인한다.
