이전 글에서는 레이블이 가리키는 주소에서 원하는 크기만큼 데이터를 읽고 쓰는 방법을 살펴봤다. 이번에는 여러 바이트가 메모리에 연속해서 놓일 때 그 바이트들을 어떻게 해석하는지 확인한다.

메모리는 문자열이나 정수 같은 의미를 직접 저장하지 않는다. 메모리에 저장되는 것은 바이트이고, 그 바이트를 어떤 크기와 방식으로 읽느냐에 따라 배열, 문자열 또는 하나의 숫자가 된다.

## 비교할 세 가지 데이터

다음 예제에는 겉으로 보기에 비슷하지만 의미가 다른 세 데이터가 있다.

```nasm
%include "io64.inc"

section .text
global CMAIN

CMAIN:
    PRINT_STRING message

    xor rax, rax
    ret

section .data
    ; 각각 독립된 1바이트 값 네 개
    bytes db 0x12, 0x34, 0x56, 0x78

    ; 하나의 4바이트 값
    number dd 0x12345678

    ; NULL 종료 ASCII 문자열
    message db 'Hello World', 0
```

x86-64 환경의 Memory View에서 각 레이블의 시작 주소를 확인하면 다음과 같은 바이트를 볼 수 있다.

```text
bytes   : 12 34 56 78
number  : 78 56 34 12
message : 48 65 6C 6C 6F 20 57 6F 72 6C 64 00
```

`bytes`와 `number`에는 코드상 같은 숫자가 등장하지만 메모리에 배치된 순서는 다르다. 이 차이를 이해하려면 먼저 1바이트 값의 연속과 하나의 여러 바이트 값을 구분해야 한다.

## 여러 값을 연속해서 배치하기

`db` 뒤에 값을 쉼표로 나열하면 각 값을 1바이트씩 연속된 주소에 배치한다.

```nasm
bytes db 0x12, 0x34, 0x56, 0x78
```

주소별로 보면 다음과 같다.

| 주소 | 저장된 값 |
| :--- | :--- |
| `bytes + 0` | `0x12` |
| `bytes + 1` | `0x34` |
| `bytes + 2` | `0x56` |
| `bytes + 3` | `0x78` |

여기서는 `0x12`, `0x34`, `0x56`, `0x78`이 각각 독립된 1바이트 값이다. 여러 값을 하나의 큰 정수로 선언한 것이 아니므로 작성한 순서대로 메모리에 놓인다.

이처럼 같은 크기의 데이터가 연속된 주소에 배치되면 배열처럼 접근할 수 있다.

```nasm
mov al, [bytes]        ; 0x12
mov bl, [bytes + 1]    ; 0x34
mov cl, [bytes + 2]    ; 0x56
mov dl, [bytes + 3]    ; 0x78
```

레이블은 첫 번째 바이트의 주소를 나타내고, 필요한 위치만큼 오프셋을 더해 다음 요소에 접근한다. 반복문으로 배열 전체를 순회하는 방법은 이후 배열과 주소 연산을 다루는 글에서 살펴본다.

## 문자열도 바이트의 연속이다

다음 선언은 문자열을 구성하는 문자들을 연속된 바이트로 배치한다.

```nasm
message db 'Hello World', 0
```

ASCII 인코딩에서 각 영문자는 정해진 숫자와 대응한다.

| 문자 | ASCII 값 |
| :---: | :---: |
| `H` | `0x48` |
| `e` | `0x65` |
| `l` | `0x6C` |
| `o` | `0x6F` |
| 공백 | `0x20` |
| `W` | `0x57` |
| `r` | `0x72` |
| `d` | `0x64` |

따라서 `message`의 메모리는 다음처럼 보인다.

```text
문자 :  H  e  l  l  o     W  o  r  l  d  끝
바이트: 48 65 6C 6C 6F 20 57 6F 72 6C 64 00
```

CPU와 메모리 입장에서는 이것도 숫자로 이루어진 바이트의 연속일 뿐이다. `PRINT_STRING`이 각 바이트를 문자 코드로 해석해 출력하기 때문에 화면에는 `Hello World`가 나타난다.

## 마지막의 `0`은 왜 필요한가

`PRINT_STRING`은 NULL 종료 문자열을 기대한다. 문자열을 출력할 때 시작 주소부터 한 바이트씩 읽다가 값이 `0`인 바이트를 만나면 문자열이 끝났다고 판단한다.

```nasm
message db 'Hello World', 0
```

마지막의 `0`은 출력할 문자가 아니라 문자열의 끝을 알리는 표시다. 이를 NULL 문자 또는 NULL terminator라고 부른다.

NULL 종료는 모든 문자열 표현에 반드시 적용되는 규칙은 아니다. 문자열 길이를 별도로 저장하거나, 데이터와 함께 길이를 전달하는 방식도 존재한다. 이번 예제에서는 `PRINT_STRING`이 NULL 종료 방식을 사용하기 때문에 마지막에 `0`을 추가한다.

종료 문자를 빠뜨리면 `PRINT_STRING`은 문자열 뒤의 메모리까지 계속 읽는다. 우연히 0을 만나 출력이 끝날 수도 있지만, 의도하지 않은 데이터가 출력되거나 유효하지 않은 메모리에 접근할 수 있다.

## 1바이트 값에는 엔디안이 없다

엔디안(Endianness)은 **하나의 여러 바이트 값**을 메모리에 어떤 바이트 순서로 배치할지 정하는 규칙이다.

1바이트 값은 더 작은 바이트로 나눌 수 없으므로 내부 순서를 결정할 필요가 없다. 따라서 다음처럼 각각 `db`로 선언한 값에는 엔디안으로 뒤집힐 내부 바이트가 없다.

```nasm
bytes db 0x12, 0x34, 0x56, 0x78
```

문자열 역시 각 문자의 바이트가 선언된 순서대로 놓인다. 리틀 엔디안 CPU라고 해서 `Hello`가 `olleH`로 저장되지는 않는다.

UTF-8의 한글처럼 문자 하나가 여러 바이트로 인코딩되는 경우에도 인코딩이 정한 바이트 순서를 그대로 저장한다. 이것은 정수의 바이트 순서를 정하는 엔디안과 구분해야 한다.

## 하나의 여러 바이트 값과 엔디안

다음 선언에서 `dd`는 `0x12345678`을 하나의 4바이트 값으로 배치한다.

```nasm
number dd 0x12345678
```

이 값을 네 개의 바이트로 나누면 다음과 같다.

```text
값          : 0x12345678
최상위 바이트: 0x12
              0x34
              0x56
최하위 바이트: 0x78
```

이 네 바이트를 낮은 주소부터 어떤 순서로 배치할지에 따라 리틀 엔디안과 빅 엔디안이 구분된다.

- **리틀 엔디안**: 최하위 바이트를 가장 낮은 주소에 배치
- **빅 엔디안**: 최상위 바이트를 가장 낮은 주소에 배치

| 주소 | 리틀 엔디안 | 빅 엔디안 |
| :--- | :---: | :---: |
| `number + 0` | `0x78` | `0x12` |
| `number + 1` | `0x56` | `0x34` |
| `number + 2` | `0x34` | `0x56` |
| `number + 3` | `0x12` | `0x78` |

x86과 x86-64 아키텍처는 리틀 엔디안을 사용한다. 따라서 현재 실습 환경의 Memory View에서는 `number`가 다음 순서로 보인다.

```text
낮은 주소                                높은 주소
   78             56             34             12
최하위 바이트                               최상위 바이트
```

흔히 “숫자가 거꾸로 저장된다”고 표현하지만, 정확히는 숫자를 구성하는 바이트 중 최하위 바이트가 가장 낮은 주소에 배치되는 것이다.

## `bytes`와 `number`는 무엇이 다른가

두 선언을 다시 비교해 본다.

```nasm
bytes  db 0x12, 0x34, 0x56, 0x78
number dd 0x12345678
```

| 레이블 | 선언의 의미 | x86-64 메모리 배치 |
| :--- | :--- | :--- |
| `bytes` | 독립된 1바이트 값 네 개 | `12 34 56 78` |
| `number` | 하나의 4바이트 값 | `78 56 34 12` |

`bytes`는 네 값을 순서대로 나열했다. 반면 `number`는 하나의 32비트 값을 선언했고, x86-64의 리틀 엔디안 규칙에 따라 그 값을 구성하는 바이트가 배치됐다.

메모리에 기록된 결과만 보면 둘 다 네 바이트지만, 소스에서 어떤 단위의 값으로 정의했으며 코드가 어떤 크기로 읽는지에 따라 의미가 달라진다.

## 여러 바이트 값을 작은 크기로 읽기

리틀 엔디안에서는 여러 바이트 값의 시작 주소에 최하위 바이트가 놓인다. 따라서 `number`의 같은 시작 주소에서 서로 다른 크기로 읽으면 다음과 같은 결과를 얻는다.

```nasm
mov al, [number]     ; 0x78
mov ax, [number]     ; 0x5678
mov eax, [number]    ; 0x12345678
```

```text
메모리: 78 56 34 12
        └ AL ┘
        └── AX ──┘
        └────── EAX ──────┘
```

이것을 리틀 엔디안의 특징으로 볼 수 있지만, 작은 크기로 읽는 동작이 자동으로 안전한 형변환을 해주는 것은 아니다. 더 큰 값의 상위 바이트는 읽지 않기 때문에 결과에서 잘려 나간다.

또한 메모리를 여러 크기로 해석할 때는 이전 글에서 다룬 접근 범위와 정렬, 데이터 경계를 함께 고려해야 한다.

## 네트워크 바이트 순서

서로 다른 시스템이 여러 바이트 정수를 주고받으려면 전송할 바이트 순서를 약속해야 한다. 전통적인 네트워크 바이트 순서(Network Byte Order)는 빅 엔디안이다.

중요한 점은 상대 서버의 CPU가 빅 엔디안이라고 가정하는 것이 아니다. 송신자와 수신자는 각자의 CPU 엔디안과 관계없이 프로토콜에서 정한 네트워크 바이트 순서에 맞춰 데이터를 변환한다.

C 계열의 소켓 API에서는 다음과 같은 변환 함수를 사용한다.

| 함수 | 변환 방향 | 대상 크기 |
| :--- | :--- | :--- |
| `htons` | Host → Network | 16비트 |
| `htonl` | Host → Network | 32비트 |
| `ntohs` | Network → Host | 16비트 |
| `ntohl` | Network → Host | 32비트 |

리틀 엔디안 호스트에서는 이 과정에서 바이트 순서가 바뀐다. 호스트의 바이트 순서가 이미 네트워크 순서와 같다면 변환 결과가 동일할 수도 있다. 코드는 호스트 환경을 추측해서 직접 바이트를 뒤집기보다 이러한 변환 함수를 사용해 프로토콜의 규칙을 표현하는 편이 안전하다.

## 디버거에서 확인할 것

예제를 실행할 때 각 레이블의 주소를 Memory View에서 찾아 다음 내용을 확인한다.

1. `bytes`의 네 값이 작성한 순서인 `12 34 56 78`로 보이는가?
2. `number`는 `78 56 34 12` 순서로 보이는가?
3. `message`의 각 문자가 ASCII 바이트와 대응하는가?
4. `message`의 마지막에 `00`이 있는가?
5. `number`를 AL, AX, EAX 크기로 읽었을 때 각각 `0x78`, `0x5678`, `0x12345678`이 되는가?

배열이나 문자열이 뒤집히지 않는데 `number`의 바이트만 반대 순서로 보이는 이유를 설명할 수 있다면 이번 실습의 목적을 이해한 것이다.

## 다음 학습: 저장한 값으로 연산하기

이번 글에서 확인한 핵심은 다음과 같다.

- 메모리는 데이터의 의미가 아니라 바이트를 저장한다.
- 여러 `db` 값과 문자열은 작성한 순서대로 연속 배치된다.
- `PRINT_STRING`은 값이 0인 바이트를 문자열의 끝으로 해석한다.
- 1바이트 값에는 내부 바이트 순서가 없으므로 엔디안의 영향을 받지 않는다.
- 하나의 여러 바이트 값은 엔디안에 따라 메모리 배치 순서가 달라진다.
- x86-64는 최하위 바이트를 낮은 주소에 두는 리틀 엔디안을 사용한다.
- 네트워크 데이터는 CPU가 아니라 프로토콜에서 정한 바이트 순서를 따라야 한다.

다음 글에서는 지금까지 배운 레지스터와 메모리를 사용해 덧셈, 뺄셈, 곱셈, 나눗셈을 수행한다. 특히 곱셈과 나눗셈이 여러 레지스터를 어떻게 사용하는지 살펴본다.
