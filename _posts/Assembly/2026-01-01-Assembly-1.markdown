어셈블리 공부의 첫 단계로 `Hello World`를 출력해 본다.

이번 글의 목적은 출력 자체보다 처음 보는 어셈블리 파일의 구성을 읽는 것이다. 짧은 코드 안에도 CPU가 실행하는 **명령어**, 어셈블러에 정보를 주는 **지시어**, 코드와 데이터의 위치를 나타내는 **레이블**, 여러 동작을 대신 작성해 주는 **매크로**가 함께 들어 있다.

> 이 예제는 NASM 문법과 `io64.inc`를 제공하는 학습 환경을 기준으로 한다. 환경에 따라 프로그램의 시작점과 입출력 방식은 달라질 수 있다.

## 첫 어셈블리 프로그램

```nasm
%include "io64.inc"

section .text
global CMAIN

CMAIN:
    PRINT_STRING msg

    xor rax, rax
    ret

section .data
    msg db 'Hello World', 0
```

프로그램의 흐름만 따라가면 단순하다.

1. `CMAIN`에서 실행을 시작한다.
2. `PRINT_STRING`으로 `msg`에 저장된 문자열을 출력한다.
3. `RAX`를 0으로 만든다.
4. `ret`으로 호출한 환경에 제어를 돌려준다.

하지만 각 줄이 모두 같은 종류의 문법은 아니다. 코드를 제대로 읽으려면 먼저 각 요소의 역할을 구분해야 한다.

## 코드를 위에서부터 읽어보기

### `%include "io64.inc"`

`%include`는 다른 파일의 내용을 현재 소스에 포함하는 NASM 전처리 지시어다. 이 예제에서는 `io64.inc`에 정의된 `PRINT_STRING`과 같은 입출력 매크로를 사용하기 위해 필요하다.

따라서 `PRINT_STRING`은 x86-64 CPU가 직접 실행하는 명령어가 아니다. 어셈블 과정에서 `io64.inc`에 정의된 코드로 확장되는 학습용 매크로다.

### `section .text`

`section`은 이후의 내용을 어느 섹션에 배치할지 어셈블러에 알려주는 지시어다. `.text`에는 CPU가 실행할 코드가 들어간다.

이 줄 자체가 실행되는 것은 아니다. 뒤에 나오는 `xor`, `ret` 등의 명령어를 실행 코드가 들어갈 섹션에 배치하도록 지정한다.

### `global CMAIN`

`global`은 `CMAIN` 심볼을 다른 오브젝트 파일이나 실행 환경에서 찾을 수 있도록 외부에 공개한다. 현재 학습 환경은 이 심볼을 찾아 어셈블리 코드의 실행을 시작한다.

운영체제가 모든 어셈블리 프로그램에서 항상 `CMAIN`을 직접 호출하는 것은 아니다. `CMAIN`이라는 이름과 진입 방식은 지금 사용하는 템플릿과 실행 환경에서 정한 규칙이다.

### `CMAIN:`

콜론(`:`)이 붙은 `CMAIN`은 레이블이다. 레이블은 코드나 데이터가 놓인 위치에 사람이 읽을 수 있는 이름을 붙인다.

레이블 자체도 CPU가 실행하는 명령어는 아니다. 점프하거나 함수를 호출할 위치, 또는 데이터를 참조할 위치를 표현할 때 사용한다.

### `PRINT_STRING msg`

`msg` 위치에 저장된 문자열을 출력한다. 앞서 살펴본 것처럼 `PRINT_STRING`은 실제 CPU 명령어 하나가 아니라 `io64.inc`에서 제공하는 매크로다.

콘솔 출력에는 운영체제 또는 런타임의 입출력 기능이 필요하다. 이 예제에서는 매크로가 그 과정을 감춰 주기 때문에 첫 학습부터 복잡한 호출 절차를 모두 구현하지 않아도 된다.

### `xor rax, rax`

`xor`는 두 값을 비트 단위로 배타적 논리합하는 CPU 명령어다. 같은 값의 각 비트를 XOR하면 모두 0이 되므로, `xor rax, rax`를 실행하면 `RAX`가 0이 된다.

이 예제에서는 실행을 마치기 전에 반환값으로 사용할 레지스터를 0으로 만드는 관용적인 표현으로 사용했다. `RAX`를 포함한 레지스터의 구조는 다음 글에서 자세히 살펴본다.

### `ret`

`ret`은 현재 코드를 호출한 위치로 실행 흐름을 되돌리는 CPU 명령어다. 구체적으로 어떤 주소로 돌아가는지 이해하려면 `call`, 반환 주소, 스택의 관계를 알아야 한다. 이 과정은 함수와 스택을 다루는 후반 글에서 확인한다.

### `section .data`

`.data`에는 프로그램 시작 전부터 값이 정해져 있는 데이터를 배치한다. 이 예제에서는 출력할 문자열이 들어 있다.

```nasm
msg db 'Hello World', 0
```

`msg`는 문자열이 시작되는 위치의 레이블이고, `db`는 데이터를 바이트 단위로 정의하는 NASM 지시어다. 각 문자는 문자 인코딩에 대응하는 바이트 값으로 저장되며 마지막의 `0`은 문자열의 끝을 나타낸다.

데이터를 정의하는 방법과 `.data`, `.bss`의 차이는 3편에서, 문자열이 메모리에 저장되는 방식은 4편에서 더 자세히 다룬다.

## 한 파일에 섞여 있는 서로 다른 요소

예제에 등장한 문법을 역할에 따라 나누면 다음과 같다.

| 코드 | 종류 | 역할 |
| :--- | :--- | :--- |
| `%include` | 전처리 지시어 | 다른 파일의 정의를 현재 소스에 포함 |
| `section` | 어셈블러 지시어 | 코드와 데이터를 배치할 섹션 지정 |
| `global` | 어셈블러 지시어 | 심볼을 외부에 공개 |
| `CMAIN:`, `msg` | 레이블 | 코드 또는 데이터의 위치에 이름 부여 |
| `PRINT_STRING` | 매크로 | 문자열 출력에 필요한 코드로 확장 |
| `xor`, `ret` | CPU 명령어 | 프로세서가 실제로 실행 |
| `db` | 데이터 정의 지시어 | 바이트 단위의 데이터를 배치 |

어셈블리 소스에 적힌 모든 단어가 기계어 명령어로 일대일 변환되는 것은 아니다. 일부는 어셈블러가 파일을 구성하기 위한 정보이고, 일부는 여러 코드로 확장되는 편의 기능이다.

## 소스 코드가 실행되기까지

작성한 `.asm` 파일은 그대로 CPU에 전달되지 않는다. 실행 가능한 프로그램이 되기까지 대략 다음 과정을 거친다.

```text
.asm 소스 파일
    ↓ 어셈블러
오브젝트 파일
    ↓ 링커
실행 파일
    ↓ 운영체제의 로더
메모리에 배치된 프로세스
```

- **어셈블(Assemble)**: 어셈블리 명령어를 기계어로 변환하고 코드와 데이터, 심볼 정보를 오브젝트 파일에 기록한다.
- **링크(Link)**: 오브젝트 파일과 필요한 라이브러리를 연결해 실행 파일을 만든다.
- **로드(Load)**: 운영체제가 실행 파일의 코드와 데이터를 프로세스의 가상 메모리에 배치하고 실행을 준비한다.

PE 헤더나 섹션 정렬처럼 실행 파일 내부를 구성하는 세부 규칙도 존재하지만, 지금 단계에서는 소스가 **어셈블 → 링크 → 로드**를 거쳐 실행된다는 흐름만 먼저 기억한다.

## 이번 글에서 확인한 것

첫 예제는 짧지만 이후 어셈블리 코드를 읽기 위한 기본 구조가 모두 들어 있다.

- `.text`에는 실행할 코드를, `.data`에는 미리 값을 가진 데이터를 배치한다.
- 레이블은 코드나 데이터의 위치에 이름을 붙인다.
- `PRINT_STRING`은 CPU 명령어가 아니라 학습 환경에서 제공하는 매크로다.
- `xor`와 `ret`은 CPU가 실제로 실행하는 명령어다.
- 어셈블리 소스는 어셈블과 링크를 거쳐 실행 파일이 된다.

다음 글에서는 CPU가 연산할 값을 임시로 보관하는 **레지스터**와 컴퓨터가 숫자를 표현하는 방식을 살펴본다.
