이전 글에서는 Flags를 확인해 조건에 따라 뒤쪽 레이블로 이동했다. 조건 점프의 목적지를 이전 주소에 있는 레이블로 바꾸면 같은 코드 블록을 여러 번 실행할 수 있다.

C++의 `while`, `do-while`, `for`는 초기화, 조건, 본문, 증감을 하나의 문법으로 표현한다. 어셈블리에서는 각 단계를 직접 배치하고 비교와 점프로 연결한다.

이번 글에서는 **조건을 검사하는 위치에 따라 반복 횟수가 어떻게 달라지는지**, 그리고 x86의 `LOOP` 명령어가 일반적인 조건 점프 방식과 무엇이 다른지 확인한다.

## 반복문을 구성하는 네 요소

일반적인 카운터 기반 반복문은 다음 네 부분으로 나눌 수 있다.

1. **초기화**: 카운터와 누적값의 시작 상태 설정
2. **조건 검사**: 반복을 계속할지 또는 종료할지 판단
3. **본문**: 반복할 작업 수행
4. **증감**: 다음 반복을 위해 카운터 변경

C++의 `for` 문을 예로 들면 각 요소가 한 줄에 모여 있다.

```cpp
int sum = 0;

for (int i = 1; i <= 10; ++i)
{
    sum += i;
}
```

어셈블리에서는 같은 흐름을 레이블과 점프로 풀어 쓴다.

```nasm
xor eax, eax       ; sum = 0
mov ecx, 1         ; i = 1

FOR_CHECK:
    cmp ecx, 10
    jg FOR_END     ; i > 10이면 종료

    add eax, ecx   ; sum += i
    inc ecx        ; ++i
    jmp FOR_CHECK

FOR_END:
```

CPU에는 `for`라는 문법이 보이지 않는다. 초기값을 만든 뒤 조건이 거짓이 될 때까지 이전 레이블로 이동하는 명령만 존재한다.

## 조건을 먼저 검사하는 `while` 형태

`while`은 본문에 들어가기 전에 조건을 확인한다.

```cpp
while (count > 0)
{
    ++executed;
    --count;
}
```

이를 어셈블리로 표현하면 다음과 같다.

```nasm
mov ecx, 3         ; count = 3
xor eax, eax       ; executed = 0

WHILE_CHECK:
    cmp ecx, 0
    je WHILE_END

    inc eax        ; ++executed
    dec ecx        ; --count
    jmp WHILE_CHECK

WHILE_END:
```

조건이 거짓이면 본문을 건너뛰고 종료 레이블로 이동한다. ECX를 처음부터 0으로 설정하면 `JE`가 바로 성립하므로 본문은 한 번도 실행되지 않는다.

```text
초기 ECX = 3 → 본문 3회 실행 → EAX = 3
초기 ECX = 0 → 본문 0회 실행 → EAX = 0
```

0회 실행 가능 여부는 조건 검사가 본문보다 앞에 있기 때문에 결정된다.

## 본문을 먼저 실행하는 `do-while` 형태

`do-while`은 본문을 먼저 실행한 뒤 반복 여부를 판단한다.

```cpp
do
{
    ++executed;
    --count;
}
while (count != 0);
```

```nasm
mov ecx, 3
xor eax, eax

DO_BODY:
    inc eax
    dec ecx
    cmp ecx, 0
    jne DO_BODY
```

조건 검사가 본문 뒤에 있기 때문에 정상적인 양수 카운터에서는 본문을 최소 한 번 실행한다.

하지만 초기 ECX가 0이라면 문제가 생긴다.

```text
초기 ECX = 0
본문 실행
DEC ECX → 0xFFFFFFFF
0이 아니므로 다시 반복
```

32비트 ECX는 0에서 1을 빼면 `0xFFFFFFFF`로 언더플로한다. 이 코드는 양수 카운터가 들어온다는 전제가 없다면 의도하지 않은 매우 긴 반복으로 이어질 수 있다.

본문을 먼저 실행해야 하는 요구사항이 아니라면, 반복 진입 전에 카운터가 유효한지 검사하는 편이 안전하다.

## `for` 형태로 1부터 100까지 더하기

1부터 100까지의 합을 구하며 초기화, 조건, 본문, 증감을 분리해 본다.

```nasm
xor eax, eax       ; EAX: 누적 합계
mov ecx, 1         ; ECX: 현재 더할 값
mov edx, 100       ; EDX: 마지막 값

SUM_CHECK:
    cmp ecx, edx
    jg SUM_END

    add eax, ecx
    inc ecx
    jmp SUM_CHECK

SUM_END:
```

레지스터의 역할은 다음과 같다.

| 레지스터 | 역할 | 시작값 | 종료 시 값 |
| :--- | :--- | ---: | ---: |
| EAX | 누적 합계 | 0 | 5050 |
| ECX | 현재 더할 값 | 1 | 101 |
| EDX | 반복 종료값 | 100 | 100 |

합계는 다음 수식으로도 검증할 수 있다.

$$
\sum_{k=1}^{N} k = \frac{N(N+1)}{2}
$$

$$
\frac{100 \times 101}{2} = 5050
$$

디버거에서 `SUM_END`에 도달했을 때 EAX가 `5050`인지 확인한다.

## 종료 조건을 `==`에만 의존하지 않는 이유

현재 값이 정확히 목표값과 같을 때만 종료하도록 만들 수도 있다.

```nasm
cmp ecx, 100
jne SUM_BODY
```

하지만 카운터가 어떤 이유로 목표값을 건너뛰면 더 이상 종료 조건을 만족하지 못한다.

```text
정상 흐름: 98 → 99 → 100 → 종료
잘못된 흐름: 98 → 101 → 102 → ...
```

범위를 순회하는 반복문에서는 경계를 넘었는지 검사하면 의도가 더 분명하다.

```nasm
cmp ecx, edx
jg SUM_END        ; signed 값에서 ECX > EDX이면 종료
```

카운터를 부호 없는 값으로 다룬다면 `JG`가 아니라 `JA` 계열을 사용해야 한다. 종료 조건에서도 이전 글에서 배운 signed와 unsigned 구분이 그대로 적용된다.

물론 실제 요구사항이 “특정 값과 같아질 때까지 반복”이라면 `JE/JNE`가 적절할 수 있다. 중요한 것은 카운터가 목표를 건너뛸 가능성과 반복이 끝나는 조건을 함께 설계하는 것이다.

## `LOOP` 명령어

x86에는 카운터 감소와 조건 점프를 한 명령으로 표현하는 `LOOP`가 있다.

```nasm
loop TARGET
```

현재 x86-64 학습 환경의 기본 주소 크기에서는 다음 순서로 동작한다.

1. RCX를 1 감소시킨다.
2. 감소한 RCX가 0이 아니면 TARGET으로 점프한다.
3. RCX가 0이면 바로 다음 명령어를 실행한다.

ECX에 값을 쓰면 RCX의 상위 32비트가 0으로 초기화되므로 다음 코드는 RCX 전체를 100으로 설정한다.

```nasm
mov ecx, 100
```

이를 이용해 100부터 1까지 역순으로 더할 수 있다.

```nasm
xor eax, eax
mov ecx, 100

jrcxz LOOP_END

LOOP_BODY:
    add eax, ecx
    loop LOOP_BODY

LOOP_END:
```

첫 반복에서 100을 더한 뒤 `LOOP`가 RCX를 99로 감소시키고 다시 `LOOP_BODY`로 이동한다. 마지막으로 1을 더한 뒤 RCX가 0이 되면 반복을 종료한다.

정수 덧셈에서는 더하는 순서를 바꿔도 결과가 같으므로 EAX에는 `5050`이 남는다.

## RCX가 0일 때 `LOOP`를 실행하면

`LOOP`는 현재 카운터가 0인지 먼저 확인하지 않는다. 카운터를 먼저 감소시킨 뒤 결과가 0인지 판단한다.

```nasm
mov ecx, 0
loop TARGET
```

현재 x86-64 기본 동작 기준으로 RCX는 다음과 같이 변한다.

```text
0x0000000000000000
        ↓ RCX - 1
0xFFFFFFFFFFFFFFFF
```

감소 결과가 0이 아니므로 TARGET으로 점프하고, 이후 매우 많은 횟수를 반복할 수 있다.

반복 횟수가 0일 가능성이 있다면 진입 전에 검사한다.

```nasm
mov ecx, count
jrcxz LOOP_END

LOOP_BODY:
    ; 반복 본문
    loop LOOP_BODY

LOOP_END:
```

`JRCXZ`는 RCX가 0이면 점프하며 Flags를 확인하지 않는다.

## `LOOP`는 Flags를 변경하지 않는다

`LOOP`를 다음 세 명령의 단순한 축약이라고 생각하기 쉽다.

```nasm
dec rcx
cmp rcx, 0
jne TARGET
```

카운터를 감소시키고 0이 아닐 때 점프한다는 흐름은 비슷하지만 Flags에 대한 부수 효과는 다르다.

- `DEC`와 `CMP`는 Flags를 변경한다.
- `LOOP`는 Flags를 변경하지 않는다.

따라서 루프 본문 마지막 연산이 만든 Flags는 `LOOP` 실행 후에도 유지될 수 있다. 반대로 일반 조건 점프 방식에서는 카운터 검사 과정이 기존 Flags를 덮어쓴다.

이 차이가 필요하다면 유용할 수 있지만, Flags가 오래 유지된다는 사실에 암묵적으로 의존하면 코드 흐름을 이해하기 어려워질 수도 있다.

## `LOOP`와 일반 조건 점프 비교

두 방식은 같은 반복을 표현할 수 있지만 특징이 다르다.

| 구분 | 일반 조건 점프 | `LOOP` |
| :--- | :--- | :--- |
| 카운터 | 원하는 범용 레지스터 선택 가능 | 현재 환경에서 RCX 사용 |
| 종료 조건 | 다양한 비교 조건 구성 가능 | 감소 후 0인지 확인 |
| Flags | 비교·감소 명령이 변경 | 변경하지 않음 |
| 표현 | 여러 명령 필요 | 한 명령으로 간결하게 표현 |
| 현대 x86 성능 | 컴파일러가 일반적으로 사용하는 형태 | 더 빠르다고 가정할 수 없음 |

`LOOP`는 반복 개념을 짧게 표현하지만 현대 x86 CPU에서 `DEC/JNZ`나 `SUB/JNZ`보다 성능상 유리하다고 볼 수 없다. 일반적인 컴파일러도 대부분 비교와 조건 점프 형태를 사용한다.

따라서 `LOOP`는 x86이 제공하는 전용 반복 명령으로 동작을 이해하되, 무조건 사용해야 하는 최적화 명령으로 받아들이지 않는 것이 좋다.

## `INC/DEC`와 `ADD/SUB`의 차이

`INC`와 `DEC`는 값을 1씩 변경한다.

```nasm
inc ecx
dec ecx
```

값만 보면 다음 연산과 같은 결과를 만든다.

```nasm
add ecx, 1
sub ecx, 1
```

하지만 Flags에 미치는 영향은 완전히 같지 않다.

- `INC`, `DEC`: 대부분의 산술 Flags를 변경하지만 CF는 유지
- `ADD`, `SUB`: CF를 포함한 산술 Flags를 갱신

따라서 이후에 CF를 사용해야 하는 코드에서는 두 방식을 임의로 교체하면 안 된다. “명령어가 짧고 빠르다”는 설명만으로 `INC/DEC`를 선택하기보다, 어떤 Flags를 보존하거나 갱신해야 하는지 확인해야 한다.

## 루프 안에서 함수나 매크로를 호출할 때

반복 카운터를 RCX에 저장한 상태로 함수나 출력 매크로를 호출하려면 해당 코드가 RCX를 보존하는지 확인해야 한다.

```nasm
mov ecx, 10

LOOP_BODY:
    ; 내부 호출이 RCX를 변경할 수 있음
    ; call SOME_FUNCTION

    dec ecx
    jne LOOP_BODY
```

호출 규약에 따라 RCX는 호출자가 보존해야 하는 레지스터일 수 있다. 내부 호출이 RCX를 변경하면 반복 횟수도 달라진다.

이번 글에서는 반복 흐름 자체에 집중하기 위해 루프 내부의 출력과 함수 호출을 제외했다. 함수 호출과 레지스터 보존 규칙은 이후 함수와 스택을 다루는 글에서 다시 살펴본다.

## 누적 결과의 크기도 확인해야 한다

반복 횟수가 정상이어도 누적 결과가 목적지 레지스터의 범위를 넘을 수 있다.

1부터 N까지의 합은 다음과 같이 증가한다.

$$
\frac{N(N+1)}{2}
$$

N이 커지면 EAX의 32비트 범위에 결과가 들어가지 않을 수 있다. 값을 signed로 해석한다면 OF를, unsigned로 해석한다면 CF를 확인하거나 더 넓은 RAX를 누적 레지스터로 사용하는 방법을 고려해야 한다.

반복 횟수와 누적 결과의 표현 범위는 서로 다른 문제이므로 각각 확인해야 한다.

## 전체 실습 코드

```nasm
%include "io64.inc"

section .text
global CMAIN

CMAIN:
    ; while 형태: 본문 3회 실행
    mov ecx, 3
    xor eax, eax

WHILE_CHECK:
    cmp ecx, 0
    je WHILE_END

    inc eax
    dec ecx
    jmp WHILE_CHECK

WHILE_END:
    ; for 형태: 1부터 100까지의 합
    xor eax, eax
    mov ecx, 1
    mov edx, 100

SUM_CHECK:
    cmp ecx, edx
    jg SUM_END

    add eax, ecx
    inc ecx
    jmp SUM_CHECK

SUM_END:
    ; 여기서 EAX = 5050 확인

    ; LOOP 형태: 100부터 1까지의 합
    xor eax, eax
    mov ecx, 100

    jrcxz LOOP_END

LOOP_BODY:
    add eax, ecx
    loop LOOP_BODY

LOOP_END:
    ; 여기서도 EAX = 5050 확인
    xor rax, rax
    ret
```

마지막 `xor rax, rax`는 합계 결과와 Flags를 변경한다. 디버거에서는 `SUM_END`와 `LOOP_END`에 중단점을 두고 EAX를 확인한 다음 실행을 계속한다.

## 디버거에서 확인할 것

1. while 형태에서 초기 ECX가 3이면 본문이 정확히 세 번 실행되는가?
2. while 형태의 초기 ECX를 0으로 바꾸면 본문을 건너뛰는가?
3. do-while 형태에서 초기 ECX가 0이면 언더플로가 발생하는가?
4. `SUM_END`에서 EAX는 5050, ECX는 101인가?
5. `LOOP`가 RCX를 감소시키지만 Flags는 변경하지 않는가?
6. `LOOP_END`에서도 EAX가 5050인가?
7. RCX가 0인 상태에서 `LOOP`를 실행하면 `0xFFFFFFFFFFFFFFFF`가 되는가?
8. `JRCXZ`가 RCX의 0 여부를 먼저 검사해 본문 진입을 막는가?
9. `INC/DEC`와 `ADD/SUB`가 CF에 서로 다르게 영향을 주는가?

## 다음 학습: 반복문으로 배열 순회하기

이번 글에서 확인한 핵심은 다음과 같다.

- 반복문은 조건 점프로 이전 레이블에 이동해 만든다.
- 초기화, 조건 검사, 본문, 증감이 반복문의 기본 요소다.
- 조건을 먼저 확인하는 while 형태는 본문을 0회 실행할 수 있다.
- 본문을 먼저 실행하는 do-while 형태는 최소 한 번 실행된다.
- 범위 반복에서는 목표값을 건너뛸 가능성까지 고려해 종료 조건을 설계한다.
- 현재 x86-64 환경에서 `LOOP`는 RCX를 감소시킨 뒤 0이 아니면 점프한다.
- RCX가 0인 상태에서 `LOOP`를 실행하면 언더플로로 매우 긴 반복이 생길 수 있다.
- `LOOP`는 Flags를 변경하지 않으며 일반 조건 점프보다 항상 빠른 명령은 아니다.
- `INC/DEC`와 `ADD/SUB`는 CF에 미치는 영향이 다르다.
- 함수나 매크로를 호출하는 루프에서는 카운터 레지스터 보존 여부를 확인해야 한다.

다음 글에서는 반복 카운터를 배열 인덱스로 사용하고, 시작 주소에 요소 크기만큼 오프셋을 더해 연속된 메모리를 순회한다.
