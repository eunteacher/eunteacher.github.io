지금까지 레지스터에 값을 넣고, 메모리 주소를 통해 원하는 크기의 데이터를 읽고 쓰는 방법을 살펴봤다. 이제 그 값을 사용해 덧셈, 뺄셈, 곱셈, 나눗셈을 수행한다.

사칙연산이라는 결과 자체는 익숙하지만 어셈블리에서는 명령어마다 입력과 출력 규칙이 다르다. `ADD`와 `SUB`는 목적지와 원본을 직접 지정하지만, `MUL`과 `DIV`는 명령어에 적지 않은 레지스터까지 암묵적으로 사용한다.

이번 글에서는 계산 결과만 확인하는 것이 아니라 **어떤 값을 입력으로 읽고, 몇 비트로 계산하며, 결과가 어느 레지스터에 남는지**를 추적한다.

## `ADD`와 `SUB`의 기본 형태

덧셈과 뺄셈은 두 개의 피연산자를 사용한다.

```nasm
add destination, source    ; destination = destination + source
sub destination, source    ; destination = destination - source
```

첫 번째 피연산자는 입력인 동시에 결과가 저장되는 목적지다. 두 번째 피연산자의 값은 연산 후에도 유지된다.

```nasm
mov al, 10
add al, 5      ; AL = 15

mov bl, 10
sub bl, 3      ; BL = 7
```

`add al, 5`는 AL의 기존 값 `10`과 상수 `5`를 더한 뒤 결과 `15`를 다시 AL에 저장한다. `sub bl, 3`도 같은 방식으로 BL을 갱신한다.

## 사용할 수 있는 피연산자 조합

일반적인 `ADD`와 `SUB`에서는 다음 조합을 사용할 수 있다.

| 목적지 | 원본 | 예제 |
| :--- | :--- | :--- |
| 레지스터 | 상수 | `add al, 5` |
| 레지스터 | 레지스터 | `add al, bl` |
| 레지스터 | 메모리 | `add al, [number]` |
| 메모리 | 상수 | `add byte [number], 5` |
| 메모리 | 레지스터 | `add [number], al` |

두 피연산자의 크기는 서로 맞아야 한다.

```nasm
add al, bl      ; 8비트 + 8비트
add ax, bx      ; 16비트 + 16비트
add eax, ebx    ; 32비트 + 32비트
add rax, rbx    ; 64비트 + 64비트
```

다음처럼 크기가 다른 레지스터를 바로 더할 수는 없다.

```nasm
add al, bx      ; 잘못된 예: 8비트와 16비트
```

필요하다면 먼저 작은 값을 큰 크기로 확장하거나, 큰 값에서 필요한 범위만 선택해야 한다.

## 주소를 더하는 것과 메모리 값을 더하는 것

다음 선언에서 `number`는 데이터가 배치된 위치를 나타내는 레이블이다.

```nasm
section .bss
    number resb 1
```

AL에 `number`의 주소가 아니라 그 위치에 저장된 값을 더하려면 대괄호를 사용한다.

```nasm
mov byte [number], 20

mov al, 10
add al, [number]       ; AL = 10 + 20
```

다음 코드는 같은 의미가 아니다.

```nasm
add al, number         ; number의 메모리 값을 읽는 코드가 아님
```

대괄호가 없는 `number`는 레이블이 나타내는 주소와 관련된 즉시값으로 해석될 수 있다. AL은 8비트이므로 일반적인 메모리 주소 전체를 피연산자로 사용할 수도 없고, 무엇보다 메모리에 저장된 값을 더하려는 의도와 맞지 않는다.

주소 자체를 계산하려는 경우에는 주소 크기에 맞는 레지스터를 사용한다.

```nasm
lea rax, [rel number]
add rax, 1             ; 다음 바이트의 주소 계산
```

## 메모리 연산과 접근 크기

상수를 메모리에 직접 더하거나 뺄 때는 접근 크기를 명시해야 한다.

```nasm
add byte [number], 5
sub byte [number], 2
```

상수 `5`만으로는 메모리에서 몇 바이트를 읽고 다시 써야 하는지 결정할 수 없다. `byte`는 이번 명령이 `number` 주소에서 1바이트를 읽어 계산한 뒤 1바이트 결과를 다시 저장하도록 지정한다.

원본이 레지스터라면 레지스터 크기를 통해 접근 크기를 알 수 있다.

```nasm
mov al, 3
add [number], al       ; AL에 맞춰 1바이트 연산
```

반면 일반적인 정수 `ADD`와 `SUB`는 두 개의 명시적인 메모리 피연산자를 지원하지 않는다.

```nasm
add [destination], [source]    ; 잘못된 예
```

두 메모리 값을 더하려면 하나를 레지스터로 가져와야 한다.

```nasm
mov al, [source]
add [destination], al
```

CPU는 `source`의 값을 레지스터로 읽은 뒤 `destination`의 값과 연산한다. 이 과정에서도 세 피연산자의 데이터 크기가 모두 맞아야 한다.

## 산술 결과는 Flags에도 남는다

`ADD`와 `SUB`는 목적지 값을 변경하는 동시에 RFLAGS의 상태 플래그도 갱신한다. 이후 조건 분기 명령어는 이 플래그를 보고 실행 흐름을 결정할 수 있다.

| 플래그 | 의미 |
| :--- | :--- |
| `ZF` | 결과가 0이면 설정 |
| `CF` | 부호 없는 연산에서 자리올림 또는 빌림이 발생하면 설정 |
| `OF` | 부호 있는 연산 결과가 표현 범위를 벗어나면 설정 |
| `SF` | 결과의 최상위 비트가 1이면 설정 |

8비트 레지스터는 `0`부터 `255`까지의 부호 없는 값을 표현할 수 있다.

```nasm
mov al, 255
add al, 1      ; AL = 0, CF = 1, ZF = 1
```

`255 + 1`은 8비트를 넘어가므로 AL에는 하위 8비트인 0만 남고, 자리올림을 나타내는 CF가 설정된다. 결과가 0이므로 ZF도 설정된다.

같은 8비트를 부호 있는 값으로 해석하면 범위는 `-128`부터 `127`이다.

```nasm
mov al, 127
add al, 1      ; AL = 0x80, OF = 1
```

`127 + 1`은 부호 있는 8비트 범위를 벗어나므로 OF가 설정된다. AL에 저장된 비트 `0x80`은 부호 있는 8비트로 해석하면 `-128`이다.

CPU가 별도의 자료형을 기억하는 것은 아니다. 같은 결과를 부호 없는 값으로 판단할 때는 CF를, 부호 있는 값으로 판단할 때는 OF를 확인한다. 플래그를 이용한 실제 조건 분기는 이후 글에서 자세히 다룬다.

## `MUL`은 입력 하나를 생략한다

`mul`은 부호 없는 정수 곱셈 명령어다. 코드에는 피연산자를 하나만 작성하지만 실제 곱셈에는 두 값이 필요하다.

```nasm
mul source
```

나머지 입력 하나와 결과가 저장될 위치는 피연산자 크기에 따라 자동으로 정해진다.

| 명령어 | 암묵적 입력 | 명시적 입력 | 결과 |
| :--- | :--- | :--- | :--- |
| `mul bl` | AL | BL | AX |
| `mul bx` | AX | BX | DX:AX |
| `mul ebx` | EAX | EBX | EDX:EAX |
| `mul rbx` | RAX | RBX | RDX:RAX |

8비트 값 두 개를 곱하면 결과에 최대 16비트가 필요하다. 같은 원리로 64비트 값 두 개의 전체 결과에는 최대 128비트가 필요하다.

CPU는 큰 결과를 한 레지스터에 모두 담을 수 없을 때 상위 절반과 하위 절반으로 나눈다.

```text
DX:AX
│  └─ 결과의 하위 16비트
└──── 결과의 상위 16비트
```

다음은 `5 × 8`을 계산하는 8비트 곱셈이다.

```nasm
mov al, 5
mov bl, 8
mul bl          ; AX = AL × BL = 40
```

입력은 AL과 BL이지만 결과는 AX 전체에 저장된다. 곱셈 전 AX 전체를 무조건 0으로 초기화할 필요는 없다. `mul bl`은 AL만 입력으로 사용하고 AX 전체를 결과로 덮어쓴다.

`mul`의 명시적 피연산자는 레지스터뿐 아니라 크기를 알 수 있는 메모리일 수도 있다.

```nasm
mul byte [number]    ; AX = AL × number의 1바이트 값
```

## `DIV`는 두 배 크기의 값을 나눈다

`div`는 부호 없는 정수 나눗셈 명령어다. 명령어에 적은 피연산자는 제수이고, 피제수와 결과 레지스터는 크기에 따라 암묵적으로 정해진다.

| 명령어 | 피제수 | 제수 | 몫 | 나머지 |
| :--- | :--- | :--- | :--- | :--- |
| `div bl` | AX | BL | AL | AH |
| `div bx` | DX:AX | BX | AX | DX |
| `div ebx` | EDX:EAX | EBX | EAX | EDX |
| `div rbx` | RDX:RAX | RBX | RAX | RDX |

곱셈이 두 배 크기의 결과를 만드는 것과 반대로, 나눗셈은 두 배 크기의 피제수를 입력으로 사용한다.

다음 코드는 `100 ÷ 3`을 계산한다.

```nasm
mov ax, 100
mov bl, 3
div bl          ; AL = 33, AH = 1
```

`div bl`은 AX 전체를 BL로 나눈다. 몫은 AL에, 나머지는 AH에 저장된다.

```text
100 ÷ 3 = 33 ... 1
             │      └─ AH: 나머지
             └──────── AL: 몫
```

## 나눗셈 전에 상위 절반을 준비하는 이유

16비트 이상의 제수를 사용할 때는 피제수가 두 레지스터에 걸쳐 있다. 작은 양수를 나누려면 상위 절반을 0으로 만들어야 한다.

```nasm
; 16비트: DX:AX ÷ BX
mov ax, 100
xor dx, dx
mov bx, 3
div bx

; 32비트: EDX:EAX ÷ EBX
mov eax, 100
xor edx, edx
mov ebx, 3
div ebx

; 64비트: RDX:RAX ÷ RBX
mov rax, 100
xor rdx, rdx
mov rbx, 3
div rbx
```

예를 들어 `div ebx`는 EAX만 보는 것이 아니라 `EDX:EAX`를 하나의 64비트 피제수로 해석한다. EDX에 이전 연산의 값이 남아 있다면 의도한 `100`보다 훨씬 큰 수를 나누게 된다.

상위 절반을 준비하는 이유는 막연히 쓰레기 값을 지우기 위해서가 아니라, 그 레지스터까지 실제 입력에 포함되기 때문이다.

## 나눗셈에서 발생할 수 있는 예외

`DIV`는 다음 상황에서 나눗셈 오류 예외를 발생시킨다.

1. 제수가 0인 경우
2. 계산된 몫이 정해진 몫 레지스터에 들어가지 않는 경우

`div bl`의 몫은 8비트 AL에 저장되므로 부호 없는 몫이 `255`를 초과하면 담을 수 없다. 이 경우 값의 일부만 남기는 것이 아니라 명령어 실행 중 예외가 발생한다.

```nasm
mov ax, 1000
mov bl, 2
div bl          ; 몫 500은 AL에 들어가지 않으므로 나눗셈 오류
```

제수가 사용자 입력이나 외부 데이터라면 0인지 먼저 확인해야 하며, 피제수와 제수의 범위를 고려해 몫이 목적지 크기를 넘지 않는지도 판단해야 한다.

## 부호 있는 곱셈과 나눗셈

`mul`과 `div`는 값을 부호 없는 정수로 해석한다. 음수가 포함된 연산에는 각각 `imul`과 `idiv`를 사용한다.

- `mul`: 부호 없는 곱셈
- `imul`: 부호 있는 곱셈
- `div`: 부호 없는 나눗셈
- `idiv`: 부호 있는 나눗셈

부호 있는 나눗셈에서는 상위 절반을 무조건 0으로 만드는 것이 아니라 피제수의 부호를 확장해야 한다.

| 피제수 크기 | 부호 확장 명령 | 확장 결과 |
| :--- | :--- | :--- |
| AX | `cwd` | DX:AX |
| EAX | `cdq` | EDX:EAX |
| RAX | `cqo` | RDX:RAX |

예를 들어 32비트 부호 있는 나눗셈은 다음과 같이 준비할 수 있다.

```nasm
mov eax, -100
cdq             ; EAX의 부호를 EDX까지 확장
mov ebx, 3
idiv ebx        ; EAX = -33, EDX = -1
```

`IMUL`은 `MUL`보다 다양한 피연산자 형식을 제공하지만, 이번 글에서는 부호 유무에 따라 명령어가 구분된다는 점까지만 확인한다.

## 전체 실습 코드

각 연산이 이전 결과에 의존하지 않도록 입력값을 매번 다시 설정한다.

```nasm
%include "io64.inc"

section .text
global CMAIN

CMAIN:
    ; ADD
    mov al, 10
    add al, 5               ; AL = 15

    ; SUB
    mov bl, 10
    sub bl, 3               ; BL = 7

    ; 메모리 + 상수
    mov byte [number], 20
    add byte [number], 5    ; number = 25

    ; MUL: 부호 없는 8비트 곱셈
    mov al, 5
    mov bl, 8
    mul bl                  ; AX = 40

    ; DIV: 부호 없는 8비트 나눗셈
    mov ax, 100
    mov bl, 3
    div bl                  ; AL = 33, AH = 1

    ; div 직후 AL과 AH를 확인한 다음 진행
    xor rax, rax
    ret

section .bss
    number resb 1
```

마지막의 `xor rax, rax`는 실행 환경에 반환할 값을 0으로 만들기 때문에 직전의 나눗셈 결과를 지운다. 디버거에서는 `div bl`을 실행한 직후 AL과 AH를 확인해야 한다.

## 디버거에서 확인할 것

1. `ADD`와 `SUB` 실행 후 목적지 레지스터만 결과로 갱신되는가?
2. `add byte [number], 5` 실행 후 메모리의 값이 `25`가 되는가?
3. `255 + 1`에서 AL, CF, ZF가 어떻게 변하는가?
4. `127 + 1`에서 AL과 OF가 어떻게 변하는가?
5. `mul bl` 실행 후 결과가 AL이 아니라 AX 전체에 저장되는가?
6. `div bl` 실행 후 몫과 나머지가 AL과 AH에 동시에 남는가?
7. `xor rax, rax`를 실행하면 나눗셈 결과가 사라지는가?

## 다음 학습: 비트 단위로 값 다루기

이번 글에서 확인한 핵심은 다음과 같다.

- `ADD`와 `SUB`는 첫 번째 피연산자에 결과를 다시 저장한다.
- 일반적인 정수 산술 명령에서는 메모리 두 곳을 직접 피연산자로 사용할 수 없다.
- 메모리를 직접 연산할 때는 접근 크기를 정확히 지정해야 한다.
- 산술 결과는 목적지뿐 아니라 상태 플래그에도 반영된다.
- `MUL`은 암묵적인 입력 레지스터를 사용하고 두 배 크기의 결과를 만든다.
- `DIV`는 두 배 크기의 피제수를 사용하며 몫과 나머지를 따로 저장한다.
- 나눗셈 전에는 피제수의 상위 절반을 연산의 부호에 맞게 준비해야 한다.
- `MUL`, `DIV`는 부호 없는 연산이고 `IMUL`, `IDIV`는 부호 있는 연산이다.

다음 글에서는 숫자를 하나의 값으로 계산하는 대신 각 비트를 직접 이동하거나 조합하는 시프트와 논리 연산을 살펴본다.
