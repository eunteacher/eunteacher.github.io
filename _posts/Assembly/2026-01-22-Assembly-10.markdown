이전 글까지는 모든 작업을 `CMAIN` 안에 작성했다. 같은 코드가 여러 곳에서 필요해지면 매번 복사하기보다 이름이 붙은 별도의 코드 블록으로 분리해 호출할 수 있다.

함수를 호출하려면 실행 위치를 함수로 옮기는 것만으로는 부족하다. 함수가 끝난 뒤 원래 코드의 어디로 돌아가야 하는지도 기억해야 한다. x86의 `CALL`과 `RET`은 이 반환 위치를 스택으로 관리한다.

이번 글에서는 **`CALL`이 반환 주소를 어떻게 저장하는지**, 그리고 호출자와 함수가 인자·반환값·레지스터 사용 방식을 왜 약속해야 하는지 살펴본다.

> 이 글의 호출 규약 예제는 현재 학습 환경과 같은 Windows x64를 기준으로 한다. 다른 운영체제와 ABI에서는 인자 전달 레지스터 등의 규칙이 달라질 수 있다.

## 함수는 이름이 붙은 코드 진입점이다

어셈블리의 함수는 특별한 `function` 선언으로 만들어지는 것이 아니다. 레이블로 코드의 시작 위치에 이름을 붙이고, `CALL`로 진입한 뒤 `RET`으로 호출자에게 돌아간다.

```nasm
GET_FORTY_TWO:
    mov eax, 42
    ret
```

다음과 같이 호출할 수 있다.

```nasm
call GET_FORTY_TWO
; 함수가 반환하면 EAX = 42
```

함수(Function), 프로시저(Procedure), 서브루틴(Subroutine)은 문맥에 따라 조금씩 다르게 구분되기도 하지만, 이 글에서는 `CALL`과 `RET`으로 실행되는 코드 블록을 편의상 함수라고 부른다.

## `JMP`와 `CALL`의 차이

`JMP`와 `CALL`은 모두 실행 위치를 다른 주소로 변경한다. 차이는 돌아올 위치를 자동으로 기록하는지 여부다.

### `JMP`

```nasm
jmp TARGET
```

`JMP`는 RIP를 대상 주소로 변경하지만 복귀 주소를 자동으로 저장하지 않는다. 대상 코드가 끝난 뒤 원래 위치로 돌아오려면 프로그래머가 별도의 방법으로 주소를 관리해야 한다.

### `CALL`

```nasm
call TARGET
```

`CALL`은 실행 위치를 변경하기 전에 호출 다음 명령어의 주소를 스택에 저장한다. 대상 함수의 `RET`은 이 주소를 사용해 호출 지점 다음으로 돌아온다.

| 명령어 | 실행 위치 변경 | 복귀 주소 자동 저장 |
| :--- | :---: | :---: |
| `JMP` | O | X |
| `CALL` | O | O |

`JMP`로는 절대 복귀할 수 없다는 뜻이 아니다. 차이는 함수 호출에 필요한 복귀 정보를 명령어가 자동으로 관리하는가에 있다.

## `CALL`이 반환 주소를 저장하는 과정

다음 코드를 살펴본다.

```nasm
call GET_FORTY_TWO
mov ebx, eax
```

`CALL`이 저장하는 반환 주소는 `CALL` 명령어 자체의 주소가 아니라 바로 다음에 실행할 `mov ebx, eax`의 주소다.

64비트 모드에서 `CALL`의 핵심 동작은 다음과 같이 이해할 수 있다.

```text
1. RSP를 8만큼 감소
2. [RSP]에 CALL 다음 명령어의 주소 저장
3. RIP를 함수 시작 주소로 변경
```

이를 “반환 주소를 스택에 push한다”고 표현할 수 있다. 다만 실제로 별도의 `PUSH` 명령을 실행하는 것이 아니라 `CALL` 명령 자체가 같은 효과를 만든다.

```text
CMAIN
  CALL GET_FORTY_TWO
      │
      ├─ [RSP]에 복귀 주소 저장
      └─ GET_FORTY_TWO로 이동
             │
             └─ RET
                  │
                  └─ CMAIN의 CALL 다음 명령으로 복귀
```

## `RET`이 호출 다음 명령으로 돌아가는 과정

함수 마지막의 `RET`은 현재 스택 맨 위에 있는 값을 반환 주소로 사용한다.

```nasm
GET_FORTY_TWO:
    mov eax, 42
    ret
```

핵심 동작은 다음과 같다.

```text
1. [RSP]의 8바이트 값을 RIP에 반영
2. RSP를 8만큼 증가
3. 해당 반환 주소부터 실행 재개
```

효과를 설명할 때 반환 주소를 pop한다고 표현할 수 있지만 일반적인 `POP RIP` 명령을 작성하는 것은 아니다. `RET` 자체가 스택의 반환 주소를 읽고 실행 흐름을 바꾼다.

호출 전후의 RSP를 단순화하면 다음과 같다.

```text
CALL 직전           : RSP = X
함수 진입 직후      : RSP = X - 8
RET 실행 직전       : [RSP] = 반환 주소
호출자에게 복귀 후  : RSP = X
```

함수가 스택을 올바르게 사용했다면 `RET` 후 RSP는 호출 전 위치로 돌아온다.

## 인자와 반환값에는 약속이 필요하다

CPU의 `CALL`은 반환 주소를 저장하고 함수로 이동할 뿐, 첫 번째 인자를 어느 레지스터에 넣어야 하는지 정하지 않는다.

다음과 같은 코드를 프로젝트 내부의 임시 약속으로 만들 수는 있다.

```text
입력: EAX, EBX
출력: ECX
```

하지만 다른 코드나 컴파일러가 이 함수를 호출하려면 같은 규칙을 알아야 한다. 인자 전달, 반환값, 레지스터 보존, 스택 배치 등을 정한 공통 약속을 호출 규약(Calling Convention) 또는 더 넓게 ABI의 일부라고 한다.

즉, 다음 두 종류의 규칙을 구분해야 한다.

- **CPU 명령어의 규칙**: `CALL`이 반환 주소를 저장하고 `RET`이 그 주소로 복귀
- **호출 규약의 규칙**: 인자와 반환값의 위치, 보존할 레지스터, 스택 정렬 등

## Windows x64의 인자와 반환 레지스터

Windows x64 호출 규약에서 일반적인 정수와 포인터 인자는 앞에서부터 다음 레지스터로 전달된다.

| 순서 | 인자 레지스터 |
| :---: | :---: |
| 첫 번째 | RCX |
| 두 번째 | RDX |
| 세 번째 | R8 |
| 네 번째 | R9 |

정수 또는 포인터 반환값은 일반적으로 RAX를 사용한다. 인자의 실제 크기가 32비트라면 RCX 전체 대신 ECX처럼 대응하는 부분 레지스터를 사용할 수 있다.

```nasm
mov ecx, 10        ; 첫 번째 32비트 정수 인자
mov edx, 5         ; 두 번째 32비트 정수 인자
call MAX
; EAX에 반환값
```

이것은 CPU 자체가 강제하는 법칙이 아니라 Windows x64 ABI의 약속이다. System V AMD64 ABI를 사용하는 Linux 계열 환경에서는 정수 인자 레지스터의 순서가 다르다.

## Windows x64의 레지스터 약속을 적용한 `MAX`

두 개의 signed 32비트 정수를 받아 더 큰 값을 반환하는 함수를 작성한다. 우선 이번 편에서는 Windows x64의 인자·반환 레지스터 약속에만 집중한다.

```nasm
; Input : ECX = first, EDX = second
; Return: EAX = max(first, second)
MAX:
    mov eax, edx

    cmp ecx, edx
    jle MAX_END

    mov eax, ecx

MAX_END:
    ret
```

함수는 먼저 두 번째 값을 반환 후보로 EAX에 넣는다. 첫 번째 값이 더 클 때만 EAX를 ECX로 교체한다.

```nasm
mov ecx, 10
mov edx, 5
call MAX
; EAX = 10
```

`JG/JL` 계열은 signed 비교이므로 이 함수는 입력을 부호 있는 정수로 해석한다. 부호 없는 최대값 함수라면 `JBE` 또는 `JA` 계열을 사용해야 한다.

이 `MAX`는 다른 함수를 호출하지 않고 별도의 지역 메모리도 사용하지 않는 leaf function이다. 레지스터만으로 작업을 마칠 수 있으므로 자체 스택 프레임을 만들지 않아도 된다.

다만 Windows x64 ABI를 완전하게 준수하는 호출자는 피호출자의 실제 사용 여부와 관계없이 shadow space와 호출 시점의 스택 정렬 규칙을 지켜야 한다. 아래의 간단한 호출 조각은 레지스터로 인자와 반환값을 전달하는 관계를 먼저 보여주기 위한 것이다.

## 호출자와 피호출자

함수를 호출한 코드를 호출자(Caller), 호출된 함수를 피호출자(Callee)라고 한다.

```text
CMAIN ── CALL MAX ──▶ MAX
Caller               Callee
```

호출 규약은 두 코드가 각각 어떤 책임을 갖는지 정한다.

- 호출자: 인자를 약속한 위치에 배치하고 호출 후 필요할 값을 적절히 보존
- 피호출자: 반환값을 약속한 위치에 배치하고 보존 대상 레지스터를 사용했다면 원래 값으로 복원

함수가 모든 레지스터를 무조건 저장하고 복원하는 것은 아니다. 일부 레지스터는 호출된 함수가 자유롭게 사용할 수 있고, 일부는 호출 전 값을 유지해야 한다. 이 역할 분담은 불필요한 저장과 복원을 줄인다.

## Caller-saved와 Callee-saved 레지스터

Windows x64에서 범용 레지스터의 대표적인 보존 규칙은 다음과 같다.

### Volatile 또는 caller-saved

```text
RAX, RCX, RDX, R8, R9, R10, R11
```

호출된 함수가 자유롭게 변경할 수 있다. 호출자가 함수 호출 뒤에도 기존 값이 필요하다면 호출 전에 별도로 보존해야 한다.

```nasm
mov ecx, 10
call SOME_FUNCTION

; 호출 뒤에도 ECX가 10이라고 가정하면 안 됨
```

첫 네 개의 인자 레지스터도 이 그룹에 포함된다. 함수는 인자를 사용한 뒤 해당 레지스터를 다른 용도로 재사용할 수 있다.

### Nonvolatile 또는 callee-saved

```text
RBX, RBP, RSI, RDI, RSP, R12, R13, R14, R15
```

피호출자가 이 레지스터를 변경한다면 반환 전에 호출 당시의 값으로 복원해야 한다.

```nasm
; 개념적 예시
SOME_FUNCTION:
    push rbx

    ; RBX 사용

    pop rbx
    ret
```

실제 함수에서는 스택 정렬과 unwind 규칙까지 함께 고려해야 한다. 여기서는 “누가 원래 값을 보존할 책임이 있는가”에 집중한다.

## 부분 레지스터만 바꿔도 전체 보존 규칙이 적용된다

RBX가 nonvolatile이라고 해서 BL이나 EBX는 자유롭게 바꿔도 되는 것이 아니다.

```nasm
mov ebx, 5
```

2편에서 확인했듯 EBX에 값을 쓰면 RBX의 하위 32비트가 바뀌고 상위 32비트는 0이 된다. 따라서 RBX 전체의 호출 전 값이 달라진다.

피호출자가 EBX나 BL을 포함해 RBX의 일부라도 수정했다면 호출 규약이 요구하는 RBX의 전체 값을 반환 전에 복원해야 한다.

이 때문에 함수의 임시값에는 자유롭게 변경할 수 있는 volatile 레지스터를 우선 사용하고, nonvolatile 레지스터가 필요할 때만 명시적으로 보존하는 방식이 자연스럽다.

## 중첩 호출과 반환 주소의 순서

함수 안에서 다른 함수를 호출할 수도 있다.

```nasm
OUTER:
    call INNER
    ret

INNER:
    mov eax, 42
    ret
```

호출 순서를 따라가면 반환 주소가 두 개 필요하다.

```text
1. CMAIN이 OUTER 호출
   스택: [CMAIN으로 돌아갈 주소]

2. OUTER가 INNER 호출
   스택: [OUTER로 돌아갈 주소]
         [CMAIN으로 돌아갈 주소]

3. INNER의 RET
   가장 최근 주소를 사용해 OUTER로 복귀

4. OUTER의 RET
   다음 주소를 사용해 CMAIN으로 복귀
```

마지막에 호출한 함수가 가장 먼저 반환하는 LIFO 순서다. 호출 깊이가 늘어날 때마다 반환 주소를 자동으로 중첩 관리하는 구조가 스택과 잘 맞는다.

“반환 주소를 레지스터로 관리할 수 없다”기보다, 여러 단계의 호출에서 계속 생기는 복귀 정보를 자동으로 쌓고 역순으로 꺼내기 위해 `CALL/RET`이 스택을 사용하는 것이다.

## 모든 함수에 스택 프레임이 필요한 것은 아니다

기존 코드에는 함수 시작 시 다음과 같은 줄이 자주 들어 있었다.

```nasm
mov rbp, rsp
```

이 한 줄만으로는 올바른 스택 프레임을 만든다고 보기 어렵다. 기존 RBP를 보존하지 않은 채 덮어쓸 수 있기 때문이다.

전통적인 프레임 포인터 기반 함수는 다음과 같은 형태를 사용할 수 있다.

```nasm
push rbp
mov rbp, rsp

; 함수 본문

mov rsp, rbp
pop rbp
ret
```

하지만 모든 함수가 이를 반드시 수행하는 것은 아니다. 앞서 작성한 `MAX`처럼 다음 조건을 만족하는 단순한 leaf function은 별도의 프레임 없이도 동작할 수 있다.

- 다른 함수를 호출하지 않음
- 별도의 스택 지역 공간이 필요하지 않음
- nonvolatile 레지스터를 변경하지 않음

현대 컴파일러도 필요에 따라 프레임 포인터를 생략할 수 있다. 스택 프레임은 함수라는 이유만으로 무조건 만드는 형식이 아니라, 지역 공간과 레지스터 보존, 디버깅·unwind 요구사항 등에 따라 구성한다.

## 추가 인자와 Shadow Space

Windows x64 호출 규약에는 인자 레지스터 외에도 스택과 관련된 규칙이 있다.

- 네 개를 초과하는 일반적인 정수·포인터 인자는 스택을 통해 전달
- 호출자는 피호출자가 인자 레지스터를 저장할 수 있도록 32바이트의 shadow space 준비
- 함수 호출 경계에서 정해진 스택 정렬 규칙 준수

따라서 외부 함수나 C++ 함수를 직접 호출할 때 단순히 RCX와 RDX에 값만 넣고 `CALL`하면 항상 충분한 것은 아니다.

이번 `MAX` 자체는 단순한 leaf function이라 별도 지역 스택 공간을 사용하지 않는다. 그러나 이를 호출하는 쪽의 shadow space 의무까지 사라지는 것은 아니다. 아래 전체 코드는 `io64.inc` 학습 템플릿 안에서 `CALL/RET`과 레지스터 전달을 관찰하기 위한 축약 예제이며, 외부 함수와 호환되는 완전한 Windows x64 호출 코드는 아니다. shadow space, 스택 정렬, 지역 변수 배치는 다음 글에서 스택 프레임과 함께 살펴본다.

## 전체 실습 코드

```nasm
%include "io64.inc"

section .text
global CMAIN

CMAIN:
    ; 인자 없는 함수와 반환값
    call GET_FORTY_TWO
    mov r10d, eax             ; R10D = 42

    ; Windows x64의 인자·반환 레지스터 배치를 적용한 MAX 호출
    mov ecx, 10
    mov edx, 5
    call MAX
    mov r11d, eax             ; R11D = 10

    ; 중첩 호출에서 반환 주소가 쌓이는 과정 확인
    call OUTER
    ; EAX = 42

    xor rax, rax
    ret

GET_FORTY_TWO:
    mov eax, 42
    ret

; Input : ECX = first, EDX = second
; Return: EAX = max(first, second)
MAX:
    mov eax, edx

    cmp ecx, edx
    jle MAX_END

    mov eax, ecx

MAX_END:
    ret

OUTER:
    call INNER
    ret

INNER:
    mov eax, 42
    ret
```

R10과 R11은 volatile 레지스터이므로 이 학습 코드 안에서 임시 결과를 관찰하는 데 사용했다. 이후 다른 함수를 호출하면 해당 값이 그대로 유지된다고 가정해서는 안 된다.

최종 `xor rax, rax`는 EAX에 남아 있던 함수 결과를 지운다. 디버거에서는 각 `CALL` 다음 줄과 각 함수 진입 시점에 중단점을 두고 확인한다.

## 디버거에서 확인할 것

1. `CALL` 직전과 함수 진입 직후의 RSP가 8바이트 차이 나는가?
2. 함수 진입 직후 `[RSP]`가 `CALL` 다음 명령어의 주소인가?
3. `RET` 후 RSP가 호출 전 값으로 돌아오는가?
4. `GET_FORTY_TWO` 반환 후 EAX가 42인가?
5. `MAX(10, 5)` 호출 후 EAX가 10인가?
6. `MAX`가 RSP나 nonvolatile 레지스터를 변경하지 않는가?
7. `OUTER → INNER` 호출에서 반환 주소가 두 단계로 쌓이는가?
8. INNER의 `RET`은 OUTER로, OUTER의 `RET`은 CMAIN으로 복귀하는가?
9. 함수가 EBX를 수정했을 때 RBX 전체의 값도 달라지는가?

## 다음 학습: 스택 프레임과 지역 데이터

이번 글에서 확인한 핵심은 다음과 같다.

- 함수는 `CALL`할 수 있는 이름이 붙은 코드 진입점이다.
- `JMP`는 복귀 주소를 자동으로 저장하지 않는다.
- `CALL`은 다음 명령어의 주소를 스택에 저장하고 함수로 이동한다.
- `RET`은 스택의 반환 주소를 이용해 호출 다음 위치로 돌아온다.
- 중첩 호출의 반환 주소는 LIFO 순서로 관리된다.
- 인자와 반환값에 사용할 위치는 CPU가 아니라 호출 규약이 정한다.
- Windows x64에서는 일반적인 첫 네 정수 인자가 RCX, RDX, R8, R9에 전달되고 반환값은 RAX에 놓인다.
- volatile 레지스터는 호출자가, nonvolatile 레지스터는 이를 변경한 피호출자가 보존할 책임이 있다.
- 부분 레지스터를 수정해도 해당 전체 레지스터의 보존 규칙을 지켜야 한다.
- 모든 함수가 별도의 스택 프레임을 반드시 만드는 것은 아니다.

다음 글에서는 RSP와 RBP를 이용해 함수가 사용할 스택 영역을 만들고, 지역 데이터와 보존한 레지스터를 배치하는 방법을 살펴본다.
