`Knight`와 `Mage`를 모두 `Player`의 한 종류로 설계했다면 호출하는 쪽에서 직업마다 별도의 함수를 만들지 않고 공통 인터페이스로 다룰 수 있어야 한다. 하지만 기반 클래스의 일반 멤버 함수를 호출하면 객체의 실제 타입이 아니라 표현식에 보이는 타입을 기준으로 함수가 결정된다.

가상 함수(Virtual function)는 기반 클래스의 포인터나 참조를 통해 호출하더라도 실제 객체에 맞는 파생 클래스의 동작을 선택한다. 이번 글에서는 일반 함수의 이름 숨김과 가상 함수 재정의를 구분하고, `override`, 순수 가상 함수, 추상 클래스와 `final`이 각각 어떤 설계 의도를 표현하는지 살펴본다.

## 일반 멤버 함수는 정적 타입을 기준으로 선택된다

기반 클래스와 파생 클래스에 같은 이름의 일반 함수가 있다.

```cpp
class Player
{
public:
    void Move() const
    {
        std::cout << "Player::Move()\n";
    }
};

class Knight : public Player
{
public:
    void Move() const
    {
        std::cout << "Knight::Move()\n";
    }
};
```

`Knight` 표현식으로 호출하면 파생 클래스 함수가 선택된다.

```cpp
Knight knight;
knight.Move(); // Knight::Move()
```

같은 객체를 `Player&`로 바라보면 결과가 달라진다.

```cpp
Player& player = knight;
player.Move(); // Player::Move()
```

`Move`가 가상 함수가 아니므로 호출할 함수는 표현식의 정적 타입을 기준으로 컴파일 시점에 결정된다. `Knight::Move`는 이 상황에서 런타임 다형적 재정의라기보다 기반 클래스의 같은 이름을 숨긴다.

## virtual은 실제 객체의 타입에 맞는 함수를 선택한다

기반 클래스 함수에 `virtual`을 붙인다.

```cpp
class Player
{
public:
    virtual void Move() const
    {
        std::cout << "Player::Move()\n";
    }
};
```

파생 클래스에서 같은 계약을 재정의한다.

```cpp
class Knight : public Player
{
public:
    void Move() const override
    {
        std::cout << "Knight::Move()\n";
    }
};
```

이제 기반 참조로 호출해도 실제 객체가 `Knight`이므로 `Knight::Move`가 실행된다.

```cpp
Knight knight;
Player& player = knight;
player.Move(); // Knight::Move()
```

```text
호출 표현식의 정적 타입: Player&
실제 객체의 동적 타입:   Knight
선택되는 최종 재정의:    Knight::Move
```

이처럼 실행 중 실제 객체에 따라 호출 대상을 선택하는 것을 동적 바인딩(Dynamic binding)이라고 한다.

## 다형적 호출에는 기반 클래스의 포인터나 참조를 사용한다

공통 행동을 실행하는 함수는 구체적인 직업 타입 대신 기반 타입의 참조를 받을 수 있다.

```cpp
void ExecuteTurn(Player& player)
{
    player.Move();
    player.Attack();
}
```

같은 함수에 서로 다른 파생 객체를 전달한다.

```cpp
Knight knight;
Mage mage;

ExecuteTurn(knight);
ExecuteTurn(mage);
```

호출 코드는 `Player` 인터페이스만 알지만 각 객체에 맞는 이동과 공격이 실행된다. 새로운 직업이 추가돼도 `ExecuteTurn`에 직업별 조건문을 추가할 필요가 없다.

기반 타입을 값으로 받으면 객체 슬라이싱(Object slicing)이 발생할 수 있다.

```cpp
void ExecuteTurn(Player player); // 파생 클래스 부분이 잘릴 수 있음
```

다형적 객체를 전달할 때는 수명과 null 허용 여부를 고려해 기반 클래스의 참조나 포인터를 사용한다.

## override는 재정의 의도를 컴파일러에 전달한다

가상 함수를 재정의하려 했지만 함수의 한정자가 달라질 수 있다.

```cpp
class Player
{
public:
    virtual void Move() const;
};

class Knight : public Player
{
public:
    void Move(); // const가 없어 다른 함수
};
```

`override`가 없으면 새로운 함수가 선언된 것으로 처리될 수 있다. `override`를 붙이면 기반 클래스의 가상 함수를 실제로 재정의하지 못할 때 컴파일 오류가 발생한다.

```cpp
class Knight : public Player
{
public:
    void Move() const override;
};
```

반환 타입과 매개변수, `const`, 참조 한정자처럼 재정의 규칙에 영향을 주는 차이를 컴파일러가 확인한다. 파생 클래스에서는 `virtual`을 다시 적지 않아도 가상 함수지만, 재정의 의도를 명확히 검증하기 위해 `override`를 사용하는 편이 안전하다.

## 순수 가상 함수는 파생 클래스가 제공할 계약을 선언한다

모든 플레이어가 공격할 수 있어야 하지만 `Player` 자체에는 구체적인 공격 방법이 없다고 가정한다.

```cpp
class Player
{
public:
    virtual void Attack() const = 0;
};
```

`= 0`을 붙인 함수는 순수 가상 함수(Pure virtual function)다. 순수 가상 함수가 하나라도 있는 클래스는 추상 클래스(Abstract class)가 되며 직접 객체를 만들 수 없다.

```cpp
// Player player; // 추상 클래스이므로 객체 생성 불가
```

구체적인 파생 클래스는 필요한 순수 가상 함수를 최종적으로 재정의해야 객체를 만들 수 있다.

```cpp
class Knight : public Player
{
public:
    void Attack() const override
    {
        std::cout << "Knight attacks with a sword\n";
    }
};
```

추상 클래스는 객체를 만들기 위한 완성된 타입이라기보다 파생 타입들이 지켜야 할 공통 인터페이스와 구현을 제공하는 기반으로 사용할 수 있다.

## 가상 함수가 하나라도 있다면 소멸자도 함께 검토한다

다형적으로 사용하는 기반 클래스는 기반 포인터를 통해 파생 객체를 제거할 가능성이 있다.

```cpp
Player* player = new Knight;
delete player;
```

이때 기반 클래스 소멸자가 가상이 아니면 동작이 정의되지 않는다. 기반 소멸자를 가상으로 선언하면 파생 소멸자부터 기반 소멸자까지 올바른 순서로 호출된다.

```cpp
class Player
{
public:
    virtual ~Player() = default;
    virtual void Attack() const = 0;
};
```

소유권을 직접 다루는 `new`와 `delete`는 이후 동적 할당 편에서 자세히 다룬다. 여기서는 기반 클래스를 통해 제거될 수 있는 다형적 타입이라면 가상 소멸자가 인터페이스 계약의 일부라는 점이 중요하다.

반대로 기반 클래스를 통한 제거를 금지하려는 설계라면 소멸자 접근 수준을 제한하는 다른 방식도 있다. 단순히 “상속했으니 항상 가상 소멸자”라고 외우기보다 객체가 어떤 방식으로 사용되고 제거되는지 확인한다.

## final은 더 이상의 재정의나 상속을 막는다

특정 가상 함수의 동작을 더 이상 바꾸지 못하게 하려면 `final`을 붙인다.

```cpp
class Knight : public Player
{
public:
    void Attack() const final;
};
```

`Knight`를 상속한 클래스가 `Attack`을 다시 재정의하면 컴파일 오류가 발생한다.

클래스 자체의 상속을 막을 수도 있다.

```cpp
class FinalBoss final : public Player
{
public:
    void Move() const override;
    void Attack() const override;
};
```

`final`은 성능을 위한 장식이 아니라 확장 지점을 닫겠다는 설계 의도를 표현한다. 이후 파생 타입이 생길 가능성을 막아도 되는지 판단한 뒤 사용한다.

## 가상 함수 테이블은 흔한 구현 방식이지만 표준의 계약은 아니다

컴파일러는 일반적으로 가상 함수 테이블과 이를 가리키는 숨은 포인터를 이용해 동적 호출을 구현한다. 각 객체의 동적 타입에 맞는 함수 주소를 찾아 호출하는 방식이다.

하지만 C++ 표준이 `vtable` 또는 `vptr`이라는 이름의 구조와 정확한 메모리 크기를 요구하지는 않는다. 따라서 다음 내용은 특정 ABI와 컴파일러 구현에 따라 달라질 수 있다.

```text
숨은 포인터의 위치와 크기
가상 함수 테이블의 실제 배치
다중 상속에서 사용하는 테이블의 수
가상 호출을 최적화하는 방식
```

언어 차원에서 의존할 수 있는 것은 기반 포인터나 참조를 통한 가상 함수 호출이 실제 객체의 최종 재정의를 선택한다는 동작이다. 객체 크기와 내부 배치가 필요하면 사용하는 컴파일러와 빌드 설정에서 따로 확인해야 한다.

## 전체 구현

하나의 `ExecuteTurn`이 서로 다른 플레이어의 행동을 실행하는 예제다.

```cpp
#include <cassert>
#include <iostream>

class Player
{
public:
    explicit Player(int hp) : hp_(hp)
    {
    }

    virtual ~Player() = default;

    virtual void Move() const
    {
        std::cout << "Player moves\n";
    }

    virtual void Attack() const = 0;

    int Hp() const
    {
        return hp_;
    }

private:
    int hp_;
};

class Knight final : public Player
{
public:
    Knight() : Player(150), stamina_(100)
    {
    }

    void Move() const override
    {
        std::cout << "Knight advances with armor\n";
    }

    void Attack() const override
    {
        std::cout << "Knight attacks with a sword\n";
    }

    int Stamina() const
    {
        return stamina_;
    }

private:
    int stamina_;
};

class Mage final : public Player
{
public:
    Mage() : Player(80), mp_(120)
    {
    }

    void Move() const override
    {
        std::cout << "Mage teleports\n";
    }

    void Attack() const override
    {
        std::cout << "Mage casts a spell\n";
    }

    int Mp() const
    {
        return mp_;
    }

private:
    int mp_;
};

void ExecuteTurn(const Player& player)
{
    player.Move();
    player.Attack();
}

void VerifyPlayers()
{
    Knight knight;
    Mage mage;

    assert(knight.Hp() == 150);
    assert(knight.Stamina() == 100);
    assert(mage.Hp() == 80);
    assert(mage.Mp() == 120);

    ExecuteTurn(knight);
    ExecuteTurn(mage);
}

int main()
{
    VerifyPlayers();
}
```

`ExecuteTurn`의 매개변수는 항상 `const Player&`지만 첫 번째 호출에서는 `Knight`의 함수가, 두 번째 호출에서는 `Mage`의 함수가 선택된다.

실행 흐름은 다음과 같다.

```text
Knight advances with armor
Knight attacks with a sword
Mage teleports
Mage casts a spell
```

`Player`는 순수 가상 함수가 있어 직접 생성할 수 없고, `Knight`와 `Mage`는 필요한 계약을 모두 재정의했으므로 생성할 수 있다. 두 클래스에 붙인 `final`은 이 예제에서 더 세분화된 직업 클래스를 만들지 않겠다는 선택이다.

## 다형적 계층을 검토할 때 확인할 기준

1. 호출자가 구체적인 파생 타입을 몰라도 되는 공통 동작이 있는가?
2. 다형적으로 호출할 함수가 기반 클래스에서 `virtual`로 선언됐는가?
3. 파생 클래스의 재정의 함수에 `override`를 붙였는가?
4. 기반 클래스에 의미 있는 기본 동작이 없는 함수는 순수 가상 함수가 자연스러운가?
5. 다형적 객체를 값으로 전달해 객체 슬라이싱을 만들고 있지 않은가?
6. 기반 클래스를 통해 객체를 제거할 수 있다면 소멸자가 가상인가?
7. 확장을 실제로 막아도 되는 경우에만 `final`을 사용했는가?
8. 가상 함수 테이블의 세부 구현을 C++ 표준의 보장처럼 설명하지 않았는가?

다형성의 핵심은 함수 이름을 똑같이 만드는 데 있지 않다. 호출자는 안정된 기반 인터페이스에 의존하고, 실제 행동은 각 파생 객체가 책임지게 만드는 데 있다.
