코드를 읽는 것만으로는 실행 중 어떤 경로가 선택됐고 값이 언제 잘못됐는지 확정하기 어렵다. 출력문을 여러 곳에 추가할 수도 있지만 문제가 발생한 순간의 지역 변수, 호출한 함수와 객체 상태를 한꺼번에 확인하기에는 한계가 있다.

디버거(Debugger)는 실행 중인 프로그램을 원하는 위치에서 멈추고 한 문장씩 진행하면서 상태 변화를 관찰하게 해 준다. 이번 글에서는 Visual Studio의 중단점, 단계별 실행, 조사식과 호출 스택을 이용해 Text RPG의 피해량 오류를 좁히는 과정을 살펴본다.

## 디버깅은 추측을 실행 상태로 확인하는 과정이다

버그를 발견했을 때 바로 코드를 고치기보다 먼저 재현 조건과 기대 결과를 정한다.

```text
재현 조건: 공격력 10인 기사가 방어력 2인 슬라임을 공격
기대 피해: 10 - 2 = 8
실제 피해: 6
```

이제 확인할 질문을 만든다.

1. `Attack`에 들어온 공격자와 대상은 올바른가?
2. 공격력과 방어력은 예상한 값인가?
3. 피해 계산 직후 값은 얼마인가?
4. 체력을 감소시키는 과정에서 값이 다시 바뀌는가?

디버거는 이 질문에 실행 상태로 답한다. “아마 생성자가 잘못됐을 것” 같은 추측과 실제로 확인한 사실을 구분한다.

## 디버깅 시작과 일반 실행을 구분한다

Visual Studio에서 흔히 사용하는 실행 방식은 다음과 같다.

```text
F5       디버깅 시작 또는 계속
Ctrl+F5  디버깅하지 않고 시작
Shift+F5 디버깅 중지
```

중단점과 단계별 실행을 사용하려면 `F5`로 디버거를 연결해 실행한다. `Ctrl+F5`는 프로그램의 일반 동작과 콘솔 출력을 빠르게 확인할 때 사용할 수 있지만 중단점에서 멈추지 않는다.

먼저 프로젝트가 디버깅할 실행 파일을 올바르게 시작하는지 확인한다. 솔루션에 프로젝트가 여러 개라면 시작 프로젝트와 명령줄 인자, 작업 디렉터리도 재현 조건에 영향을 줄 수 있다.

## Debug 구성은 관찰하기 쉬운 빌드를 만든다

Visual Studio의 Debug 구성은 일반적으로 디버그 정보 생성과 낮은 최적화 수준을 사용해 소스 코드와 실행 흐름을 대응시키기 쉽게 만든다.

Release 구성에서는 컴파일러가 함수를 인라인화하거나 문장 순서를 바꾸고 사용하지 않는 변수를 제거할 수 있다. 그래서 다음과 같은 현상이 나타날 수 있다.

- 중단점 위치가 이동하거나 활성화되지 않는다.
- 한 단계 실행이 소스 줄 순서와 다르게 보인다.
- 최적화로 제거된 변수를 조사할 수 없다.
- 함수가 호출 스택에 독립된 프레임으로 나타나지 않는다.

학습과 일반적인 논리 오류 추적은 Debug 구성에서 시작한다. 다만 Release에서만 발생하는 버그라면 해당 구성을 그대로 재현해야 한다. Debug 빌드에서 정상이라는 결과가 Release 빌드의 정확성을 보장하지 않는다.

## 중단점은 확인하고 싶은 문장 앞에서 실행을 멈춘다

코드 편집기 왼쪽 여백을 클릭하거나 커서를 둔 줄에서 `F9`를 누르면 중단점을 설정하거나 해제할 수 있다.

```cpp
int CalculateDamage(int attack, int defense)
{
    int damage = attack - defense * 2; // 이 줄에 중단점
    return std::max(0, damage);
}
```

중단점은 해당 줄을 실행하기 전에 프로그램을 멈춘다. 따라서 멈춘 직후 `damage`가 아직 초기화되지 않았거나 이전 값처럼 보일 수 있다. 해당 문장을 한 단계 실행한 뒤 결과를 확인해야 한다.

중단점이 속이 빈 원으로 표시되거나 적중하지 않는다면 다음 항목을 확인한다.

- 현재 실행 중인 바이너리와 열어 둔 소스가 같은 빌드에서 나왔는가?
- 빌드가 성공했고 최신 코드가 반영됐는가?
- 실행 경로에서 해당 함수가 실제로 호출되는가?
- 디버그 기호가 로드됐는가?
- 최적화 때문에 문장이 제거되거나 다른 위치로 합쳐지지 않았는가?

중단점이 안 걸린다는 사실만으로 코드가 실행되지 않았다고 단정하지 않는다.

## 단계별 실행은 함수 안으로 들어갈지 결정한다

프로그램이 멈춘 상태에서 다음 명령을 사용한다.

```text
F10       한 단계씩 코드 실행(Step Over)
F11       함수 안으로 이동(Step Into)
Shift+F11 현재 함수에서 나가기(Step Out)
F5        다음 중단점까지 계속
```

`F10`은 현재 줄을 실행하되 호출한 함수 내부를 한 줄씩 따라가지 않는다.

```cpp
int damage = CalculateDamage(attacker.Attack(), target.Defense());
```

이 줄에서 `F10`을 누르면 `CalculateDamage` 전체를 실행하고 다음 줄로 이동한다. 반환된 `damage`만 확인할 때 적합하다.

계산 과정 안에서 값이 잘못됐다고 판단하면 같은 줄에서 `F11`을 사용해 `CalculateDamage` 내부로 들어간다. 라이브러리 함수나 이미 확인한 함수에 들어갔다면 `Shift+F11`로 현재 함수 실행을 끝내고 호출한 위치로 돌아올 수 있다.

## 자동·로컬·조사식 창은 서로 다른 범위의 값을 보여준다

프로그램이 중단되면 변수 창에서 현재 상태를 확인할 수 있다.

```text
자동(Autos)   현재 줄과 주변에서 사용된 변수
지역(Locals)  현재 함수 프레임의 지역 변수와 매개변수
조사식(Watch) 직접 등록한 표현식
```

피해 계산 함수에서 지역 창을 보면 다음 값을 확인할 수 있다.

```text
attack  = 10
defense = 2
damage  = 6
```

입력값은 올바른데 `damage`만 틀렸으므로 생성자나 객체 선택보다 계산식에 원인이 있다는 근거가 생긴다.

조사식에는 단순 변수뿐 아니라 부작용이 없는 표현식을 등록할 수 있다.

```text
attacker.Attack()
target.Defense()
attack - defense
target.Hp()
```

함수 호출을 포함한 조사식은 평가 과정에서 프로그램 상태를 바꾸거나 예외를 일으킬 수 있다. Getter처럼 읽기만 한다는 것이 확실한 표현식을 사용하고 복잡한 로직은 지역 변수로 나눠 관찰한다.

## 호출 스택은 현재 위치까지 도달한 경로를 보여준다

현재 줄의 값만으로는 왜 그 함수가 호출됐는지 알 수 없을 수 있다. 호출 스택(Call Stack)은 현재 함수에 도달하기까지 쌓인 함수 프레임을 보여준다.

```text
main
└─ RunBattle
   └─ ExecuteTurn
      └─ Attack
         └─ CalculateDamage  ← 현재 중단 위치
```

호출 스택의 이전 프레임을 선택하면 해당 함수의 소스 위치와 그 프레임의 지역 변수를 확인할 수 있다. 같은 `CalculateDamage`가 여러 시스템에서 호출될 때 어떤 경로가 문제를 만들었는지 구분하는 데 유용하다.

원본 예제의 흐름은 다음처럼 단순하다.

```cpp
void Test1()
{
    int value = 0;
}

void Test2()
{
    Test1();
}
```

`Test2`를 통해 `Test1`에 들어가면 호출 스택에는 `main → Test2 → Test1`이 나타난다. `main`에서 `Test1`을 직접 호출하면 `Test2` 프레임은 존재하지 않는다. 함수 이름이 같아도 도달 경로가 다를 수 있다.

## 조건부 중단점은 필요한 상황에서만 멈춘다

반복문 안의 중단점이 매번 적중하면 문제 상황까지 계속 `F5`를 눌러야 한다.

```cpp
for (int turn = 1; turn <= 100; ++turn)
{
    ExecuteTurn(turn, player, monster);
}
```

중단점의 조건을 `turn == 37`처럼 설정하면 37번째 턴에서만 멈출 수 있다. 값이 특정 범위에 들어왔을 때도 조건을 사용할 수 있다.

```text
monster.Hp() <= 0
damage < 0
player == nullptr
```

적중 횟수 조건을 사용하면 몇 번째 호출에서 멈출지도 지정할 수 있다. 조건식은 중단점이 평가되는 위치에서 사용할 수 있는 이름과 상태를 기준으로 작성한다.

조건식 자체가 복잡하거나 상태를 변경하면 디버깅 결과에 영향을 줄 수 있다. 빠르게 평가할 수 있는 읽기 전용 조건을 사용한다.

## 작업 중단점은 멈추지 않고 정보를 기록할 수 있다

중단점의 작업(Action)을 설정하면 프로그램을 멈추는 대신 메시지를 출력하는 추적 지점으로 사용할 수 있다. 흔히 Tracepoint라고 부른다.

```text
Turn: {turn}, Player HP: {playerHp}, Monster HP: {monsterHp}
```

반복 실행 중 값의 흐름을 수집하면서 매번 수동으로 계속 실행하지 않아도 된다. 일반 출력문을 소스에 추가하지 않고 특정 디버깅 세션에서만 관찰할 수 있다는 장점이 있다.

다만 메시지 평가와 출력도 실행 시간에 영향을 준다. 타이밍에 민감한 멀티스레드 문제에서는 중단점과 로그가 증상을 바꿀 수 있다는 점을 고려한다.

## 데이터 중단점은 값이 바뀐 위치를 찾는 데 사용한다

어떤 값이 잘못됐다는 사실은 알지만 변경한 코드를 찾기 어려울 수 있다. 지원되는 환경에서 데이터 중단점(Data breakpoint)을 사용하면 지정한 메모리 위치의 값이 바뀔 때 실행을 멈출 수 있다.

예를 들어 `player.hp_`가 예상하지 못한 시점에 0이 된다면 해당 저장 위치의 변경을 감시한다. 멈춘 뒤 호출 스택을 확인하면 값을 기록한 경로를 찾을 수 있다.

데이터 중단점은 다음 조건에 주의한다.

- 감시 대상 객체가 살아 있는 동안만 주소가 유효하다.
- 컨테이너 재할당이나 객체 이동으로 주소가 바뀔 수 있다.
- 지원 범위와 설정 방식은 디버거 종류와 대상 플랫폼에 따라 다를 수 있다.
- 여러 스레드의 동시 접근 문제는 실행을 멈춘 순간만으로 완전히 설명되지 않을 수 있다.

객체 수명과 주소가 안정적인지 먼저 확인한다.

## 디버거에서 값을 바꿀 때는 관찰과 실험을 구분한다

조사식이나 직접 실행 창에서 변수 값을 바꿔 다른 분기를 시험할 수 있다.

```text
damage = 8
monsterHp = 1
```

이는 “이 값이었다면 이후 코드가 어떻게 동작하는가?”를 빠르게 실험하는 방법이다. 하지만 값을 수동으로 바꾼 뒤 정상 동작했다고 해서 원래 버그가 해결된 것은 아니다.

디버깅 결과를 기록할 때는 구분한다.

```text
관찰 사실: defense가 2인데 damage가 6으로 계산됐다.
원인: 계산식이 defense를 두 번 곱했다.
실험: damage를 8로 바꾸자 이후 체력은 예상대로 감소했다.
수정: attack - defense로 계산식을 변경했다.
검증: 동일 입력에서 자동 검증과 실행 결과가 모두 8을 확인했다.
```

## 피해량 오류를 단계적으로 추적한다

문제가 있는 코드는 방어력을 두 번 적용한다.

```cpp
int CalculateDamage(int attack, int defense)
{
    int damage = attack - defense * 2;
    return std::max(0, damage);
}
```

디버깅 순서는 다음과 같다.

1. `CalculateDamage`의 첫 줄에 중단점을 설정한다.
2. 공격력 10, 방어력 2인 시나리오를 `F5`로 실행한다.
3. 지역 창에서 `attack == 10`, `defense == 2`를 확인한다.
4. `F10`으로 계산 줄을 실행한다.
5. `damage == 6`을 확인한다.
6. 호출 스택에서 `RunBattleTurn → Attack → CalculateDamage` 경로를 확인한다.
7. 계산식을 `attack - defense`로 수정한다.
8. 같은 입력을 다시 실행해 `damage == 8`인지 확인한다.

수정 코드는 다음과 같다.

```cpp
int CalculateDamage(int attack, int defense)
{
    return std::max(0, attack - defense);
}
```

입력값이 예상과 같다는 사실을 확인했기 때문에 생성자나 호출 대상까지 불필요하게 수정하지 않는다. 잘못된 값이 처음 만들어지는 지점을 좁혀 최소 범위만 변경한다.

## 수정 후에는 디버거 밖에서도 검증한다

디버거에서 한 번 올바른 값이 보였다고 작업을 끝내지 않는다. 경계값과 반복 실행을 자동 검증으로 남긴다.

```cpp
#include <algorithm>
#include <cassert>
#include <iostream>

int CalculateDamage(int attack, int defense)
{
    return std::max(0, attack - defense);
}

void VerifyDamage()
{
    assert(CalculateDamage(10, 2) == 8);
    assert(CalculateDamage(5, 5) == 0);
    assert(CalculateDamage(3, 10) == 0);
    assert(CalculateDamage(0, 0) == 0);

    std::cout << "Damage: " << CalculateDamage(10, 2) << '\n';
}

int main()
{
    VerifyDamage();
}
```

실행 결과는 다음과 같다.

```text
Damage: 8
```

`assert`는 일반적으로 `NDEBUG`가 정의된 빌드에서 제거될 수 있으므로 프로그램의 필수 입력 검증이나 오류 처리를 대신하지 않는다. 학습 예제의 조건 확인이나 별도 테스트 코드를 통해 수정 결과를 반복 검증한다.

## 디버깅 순서를 정해 두면 수정 범위가 줄어든다

오류마다 사용하는 창은 달라도 기본 흐름은 유지할 수 있다.

```text
1. 증상과 기대 결과를 구체적인 값으로 기록
2. 동일한 입력으로 재현
3. 잘못된 값이 관찰되는 가까운 위치에 중단점 설정
4. 호출 스택으로 실행 경로 확인
5. 단계별 실행으로 값이 처음 달라지는 문장 탐색
6. 원인에 해당하는 최소 코드 수정
7. 같은 재현 절차로 수정 결과 확인
8. 경계값을 자동 검증으로 추가
```

중단점을 무작정 많이 추가하면 멈추는 위치만 늘어나고 확인할 질문은 불분명해진다. 각 중단점마다 어떤 변수와 가정을 확인할지 정한다.

## 디버깅할 때 확인할 기준

1. 증상을 재현하는 입력과 기대 결과가 구체적인가?
2. 현재 실행 파일이 최신 소스로 빌드됐는가?
3. 중단점은 문장 실행 전 상태에서 멈춘다는 점을 고려했는가?
4. `F10`, `F11`, `Shift+F11`을 목적에 맞게 구분하는가?
5. 지역 변수의 값과 호출 스택의 경로를 함께 확인했는가?
6. 반복 호출에는 조건부 중단점이나 적중 횟수를 사용했는가?
7. 조사식 평가나 수동 값 변경이 프로그램 상태에 영향을 주지 않았는가?
8. 최적화된 빌드에서 소스 줄과 실행 흐름이 달라질 수 있음을 고려했는가?
9. 디버거에서 관찰한 사실과 아직 확인하지 않은 추측을 구분했는가?
10. 수정 후 같은 재현 조건과 경계값을 자동으로 검증했는가?

디버거의 목적은 코드를 천천히 실행하는 데 있지 않다. 값이 예상과 처음 달라지는 지점과 그곳에 도달한 호출 경로를 찾아 원인이 아닌 코드를 함부로 수정하지 않도록 만드는 데 있다.
