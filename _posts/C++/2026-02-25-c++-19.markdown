앞에서는 이름을 사용하려면 해당 코드 위치에서 유효한 선언을 찾을 수 있어야 한다는 점을 살펴봤다. 함수 호출도 마찬가지다. 호출 위치에서 함수의 이름과 사용 방법을 알 수 없다면 컴파일러는 인자의 개수와 타입, 반환 결과를 검사할 수 없다.

그렇다고 호출보다 앞에 모든 함수 몸체를 몰아넣을 필요는 없다. **선언(Declaration)**으로 사용 방법을 먼저 알리고, **정의(Definition)**로 실제 동작을 제공하면 된다. 중요한 것은 선언과 정의를 외우는 데서 끝나지 않고, 문제가 컴파일·링크·실행 중 어느 단계에서 발생했는지 구분하는 것이다.

## 선언이 없을 때는 호출 자체를 해석할 수 없다

다음 코드는 `main`보다 아래에 `Add`를 정의한다.

```cpp
int main()
{
    int result = Add(10, 20);
}

int Add(int left, int right)
{
    return left + right;
}
```

사람은 파일 전체를 보고 아래에 `Add`가 있다는 사실을 쉽게 찾는다. 하지만 `main`의 호출을 해석하는 시점에는 사용할 수 있는 `Add` 선언이 아직 보이지 않는다.

컴파일러가 호출을 검사하려면 최소한 다음 정보가 필요하다.

- 함수의 이름은 무엇인가?
- 몇 개의 인자를 받는가?
- 각 매개변수의 타입은 무엇인가?
- 반환 타입은 무엇인가?

호출보다 앞에 함수 선언을 제공하면 이 정보를 알릴 수 있다.

```cpp
int Add(int left, int right);

int main()
{
    int result = Add(10, 20);
}

int Add(int left, int right)
{
    return left + right;
}
```

함수 몸체 없이 반환 타입, 이름, 매개변수 목록과 세미콜론을 적은 첫 줄이 함수 선언이다. 정의보다 앞에서 함수의 존재와 호출 방법을 알린다는 의미에서 **전방 선언(Forward declaration)**이라고 부른다.

## 정의를 먼저 배치하면 별도의 전방 선언이 필요하지 않다

함수 정의도 그 함수에 대한 선언 역할을 한다.

```cpp
int Add(int left, int right)
{
    return left + right;
}

int main()
{
    int result = Add(10, 20);
}
```

`main`을 처리하기 전에 이미 `Add`의 정의를 볼 수 있으므로 별도의 선언이 없어도 된다.

작은 단일 파일 예제에서는 호출되는 함수를 위에 정의하는 방식도 충분하다. 그러나 함수 수가 많아지고 여러 소스 파일에서 같은 함수를 사용하면 정의 순서만으로 의존 관계를 관리하기 어렵다. 이때 헤더의 선언과 소스 파일의 정의를 분리한다.

## 선언과 정의는 맡은 역할이 다르다

함수 선언은 호출자가 함수를 올바르게 사용하는 데 필요한 인터페이스를 제공한다.

```cpp
int CalculateDamage(int attack, int defence);
```

함수 정의는 실제 동작을 제공한다.

```cpp
int CalculateDamage(int attack, int defence)
{
    return attack > defence ? attack - defence : 0;
}
```

둘의 역할을 빌드 단계와 연결하면 다음과 같다.

| 구분 | 제공하는 정보 | 주로 필요한 단계 |
| :--- | :--- | :--- |
| 선언 | 이름, 매개변수 타입, 반환 타입 등 호출 방법 | 각 번역 단위의 컴파일 |
| 정의 | 함수 몸체와 실제 동작 | 최종 프로그램을 만드는 링크 |

정의도 선언의 한 종류다. 따라서 “선언 아니면 정의”처럼 완전히 배타적인 두 문법은 아니다. 몸체가 있는 함수 정의는 그 함수가 존재한다는 사실도 함께 알린다.

반대로 몸체가 없는 함수 선언만으로는 실행할 코드를 제공하지 않는다. 호출이 실제로 사용된다면 최종 링크 대상 어딘가에 대응하는 정의가 있어야 한다.

## 빌드 과정을 나누면 오류가 발생하는 위치가 보인다

여러 소스 파일로 이루어진 일반적인 C++ 프로그램은 개념적으로 다음 흐름을 거친다.

```text
헤더 포함과 전처리
        │
        ▼
각 소스 파일을 독립적인 번역 단위로 컴파일
        │
        ▼
오브젝트 파일 생성
        │
        ▼
오브젝트 파일과 라이브러리를 링크
        │
        ▼
실행 파일 생성
        │
        ▼
프로그램 실행
```

실제 빌드 도구는 병렬 컴파일, 증분 빌드, 링크 시간 최적화처럼 더 복잡한 과정을 사용할 수 있다. 그래도 오류를 진단할 때는 **컴파일 전에 실패했는가, 번역 단위 컴파일에서 실패했는가, 링크에서 실패했는가, 실행 중 잘못됐는가**를 먼저 구분하는 방식이 유효하다.

## 헤더는 선언을 여러 번역 단위에 공유한다

계산 함수의 선언을 헤더에 둔다.

```cpp
// GameMath.h
#pragma once

int CalculateDamage(int attack, int defence);
int CalculateRemainingHp(int hp, int damage);
```

정의는 소스 파일에 둔다.

```cpp
// GameMath.cpp
#include "GameMath.h"

#include <algorithm>

int CalculateDamage(int attack, int defence)
{
    return std::max(0, attack - defence);
}

int CalculateRemainingHp(int hp, int damage)
{
    return std::max(0, hp - damage);
}
```

호출하는 소스 파일은 헤더를 포함한다.

```cpp
// Main.cpp
#include "GameMath.h"

#include <iostream>

int main()
{
    int damage = CalculateDamage(25, 10);
    int remainingHp = CalculateRemainingHp(50, damage);
    std::cout << "Remaining HP: " << remainingHp << '\n';
}
```

`Main.cpp`를 컴파일할 때 컴파일러는 `GameMath.h`의 선언을 보고 두 호출이 올바른지 검사한다. `GameMath.cpp`는 함수 몸체가 들어 있는 별도의 오브젝트 파일을 만든다. 링크 단계에서 호출과 정의가 연결된다.

```text
Main.cpp + GameMath.h
        │ 컴파일
        ▼
    Main.obj ───────┐
                    ├─ 링크 ── 실행 파일
GameMath.cpp        │
        │ 컴파일    │
        ▼           │
  GameMath.obj ─────┘
```

오브젝트 파일의 확장자는 도구와 플랫폼에 따라 `.obj` 또는 `.o` 등을 사용한다.

## `#include`는 완성된 라이브러리를 자동으로 연결하지 않는다

헤더를 포함하면 전처리 과정에서 해당 헤더의 내용이 번역 단위에 들어온다. 호출에 필요한 선언을 볼 수 있게 되는 것이지, 함수 정의가 들어 있는 오브젝트 파일이나 라이브러리까지 자동으로 링크된다는 뜻은 아니다.

```cpp
#include "GameMath.h"
```

이 한 줄만으로 `GameMath.cpp`가 빌드 대상에 자동 추가되는 것은 아니다. 프로젝트 설정에서 해당 소스 파일을 컴파일하고, 생성된 오브젝트 파일이나 라이브러리가 링크 대상에 포함되어야 한다.

외부 라이브러리를 사용할 때도 같은 구분이 중요하다.

- 헤더 경로가 없거나 선언을 찾지 못한다면 컴파일 단계 문제일 수 있다.
- 헤더는 찾았지만 구현 라이브러리가 빠졌다면 링크 단계 문제일 수 있다.
- 헤더와 라이브러리의 버전 또는 빌드 설정이 맞지 않아도 링크 문제가 생길 수 있다.

## 헤더는 독립적으로 포함될 수 있게 작성한다

헤더는 여러 소스 파일에 포함될 수 있으므로 중복 포함을 막아야 한다.

```cpp
// GameMath.h
#pragma once

int CalculateDamage(int attack, int defence);
```

`#pragma once` 대신 전통적인 include guard를 사용할 수도 있다.

`#pragma once`는 주요 컴파일러에서 널리 지원하지만 C++ 표준이 규정한 지시문은 아니다. 이식성이 가장 중요한 환경에서는 표준 전처리 지시문으로 구성한 include guard를 선택할 수 있다.

```cpp
#ifndef GAME_MATH_H
#define GAME_MATH_H

int CalculateDamage(int attack, int defence);

#endif
```

또한 헤더가 사용하는 타입은 헤더 자체가 선언하거나 필요한 헤더를 포함해야 한다. 특정 소스 파일에서 우연히 먼저 포함한 다른 헤더에 의존하면 포함 순서에 따라 컴파일 성공 여부가 달라질 수 있다.

```cpp
// BattleResult.h
#pragma once

#include <string>

std::string MakeBattleResult(int damage);
```

`std::string`을 공개 인터페이스에서 사용하므로 이 헤더가 필요한 표준 헤더를 직접 포함한다.

## 구현 파일도 자신의 헤더를 먼저 포함한다

정의를 작성하는 소스 파일에서 대응하는 헤더를 먼저 포함하면 선언과 정의가 함께 검사된다.

```cpp
// GameMath.cpp
#include "GameMath.h"

int CalculateDamage(int attack, int defence)
{
    return attack > defence ? attack - defence : 0;
}
```

만약 헤더는 `int` 두 개를 받는다고 선언했는데 소스 파일에서 실수로 매개변수 타입을 바꾸면 다른 오버로드를 정의한 셈이 될 수 있다.

```cpp
// GameMath.h
int CalculateDamage(int attack, int defence);
```

```cpp
// 잘못 작성한 GameMath.cpp
#include "GameMath.h"

int CalculateDamage(double attack, double defence)
{
    return attack > defence ? static_cast<int>(attack - defence) : 0;
}
```

이 소스 파일 자체는 두 선언을 서로 다른 오버로드로 받아들여 컴파일될 수 있다. 하지만 헤더에 선언된 `CalculateDamage(int, int)`의 정의는 여전히 없다. `Main.cpp`가 정수 버전을 호출하면 링크 단계에서 해당 정의를 찾지 못한다.

자신의 헤더를 포함하는 습관이 모든 불일치를 자동으로 잡아 주지는 않지만, 반환 타입만 충돌하거나 필요한 타입·선언이 빠진 문제를 구현 파일 자체에서 발견하는 데 도움이 된다. 최종적으로는 선언된 각 인터페이스에 대응하는 정의가 실제 링크 대상에 있는지 확인해야 한다.

## 같은 함수를 여러 번 선언할 수 있다

서로 호환되는 함수 선언은 여러 위치에서 나타날 수 있다.

```cpp
int Add(int left, int right);
int Add(int first, int second);
```

매개변수 이름은 함수 타입을 구분하는 요소가 아니므로 두 줄은 같은 함수를 선언한다. 선언에서 매개변수 이름을 생략할 수도 있다.

```cpp
int Add(int, int);
```

하지만 독자가 각 인자의 역할을 알 수 있도록 공개 헤더에는 의미 있는 이름을 적는 편이 좋다.

선언이 여러 번 가능하다고 해서 서로 다른 반환 타입이나 호환되지 않는 선언을 마음대로 섞을 수 있는 것은 아니다.

```cpp
int GetScore();
// double GetScore();
```

매개변수 목록이 같은 함수는 반환 타입만으로 오버로드할 수 없다. 두 번째 줄까지 활성화하면 기존 선언과 충돌한다.

## 일반 함수 정의는 프로그램에 하나가 필요하다

일반적인 비인라인 함수를 헤더에 직접 정의하고 여러 소스 파일에서 포함하면 같은 정의가 여러 번 생길 수 있다.

```cpp
// GameMath.h
#pragma once

int Add(int left, int right)
{
    return left + right;
}
```

`Main.cpp`와 `Battle.cpp`가 이 헤더를 모두 포함하면 각 번역 단위에 `Add` 정의가 생긴다. 최종 링크에서 다중 정의 오류가 발생할 수 있다.

일반 함수는 헤더에 선언만 두고 하나의 소스 파일에 정의한다.

```cpp
// GameMath.h
#pragma once

int Add(int left, int right);
```

```cpp
// GameMath.cpp
#include "GameMath.h"

int Add(int left, int right)
{
    return left + right;
}
```

프로그램에서 하나의 정의만 허용되는 대상과 여러 번역 단위에 동일한 정의가 허용되는 대상에 관한 규칙을 ODR(One Definition Rule)이라고 한다.

## 헤더에 정의해야 하는 경우도 있다

“헤더에는 선언, 소스에는 정의”는 유용한 기본 구조지만 모든 코드에 적용되는 절대 규칙은 아니다.

`inline` 함수는 ODR 조건을 만족하는 동일한 정의를 여러 번역 단위에 둘 수 있다.

```cpp
// GameMath.h
#pragma once

inline int Add(int left, int right)
{
    return left + right;
}
```

클래스 정의 안에서 몸체를 작성한 멤버 함수도 일반적으로 암시적 `inline` 규칙이 적용된다.

```cpp
class Player
{
public:
    int GetHp() const
    {
        return Hp;
    }

private:
    int Hp = 100;
};
```

템플릿은 사용하는 번역 단위에서 정의를 볼 수 있어야 하는 경우가 많아 보통 헤더에 정의한다. C++17부터는 `inline` 변수도 여러 번역 단위에서 공유할 정의를 헤더에 둘 수 있다.

이 예외들은 이후 해당 문법을 배울 때 구체적으로 다루고, 지금은 헤더에 몸체가 있다는 사실만으로 무조건 잘못된 코드는 아니라는 점을 기억한다.

## 선언을 찾지 못하면 주로 컴파일 오류가 발생한다

호출 위치에서 사용할 수 있는 선언이 없다면 해당 번역 단위를 컴파일할 수 없다.

```cpp
int main()
{
    int result = Multiply(3, 4);
}
```

컴파일러에 따라 “식별자를 찾을 수 없다”, “이 스코프에 선언되지 않았다”와 같은 메시지를 표시한다.

선언은 찾았지만 호출 형태가 맞지 않아도 컴파일 단계에서 실패한다.

```cpp
int Multiply(int left, int right);

int main()
{
    // int result = Multiply(3);
}
```

컴파일러가 보고 있는 한 번역 단위 안에서 이름 검색, 타입 검사, 오버로드 선택을 수행할 수 없기 때문이다.

이때 먼저 확인할 내용은 다음과 같다.

1. 필요한 헤더를 포함했는가?
2. 함수가 올바른 네임스페이스에 있는가?
3. 호출 위치보다 앞에서 선언을 볼 수 있는가?
4. 인자의 개수와 타입이 선언에 맞는가?
5. 조건부 컴파일 때문에 선언이 제외되지 않았는가?

## 선언은 보이지만 정의를 찾지 못하면 링크 오류가 발생한다

다음 코드는 컴파일러가 호출을 검사하는 데 필요한 선언을 가지고 있다.

```cpp
int Multiply(int left, int right);

int main()
{
    int result = Multiply(3, 4);
}
```

그러나 링크 대상 어디에도 `Multiply(int, int)` 정의가 없다면 실행 파일을 완성할 수 없다. 도구에 따라 `unresolved external symbol`, `undefined reference`와 같은 메시지를 표시한다.

링크 오류에서는 다음 내용을 확인한다.

1. 선언과 정확히 대응하는 정의를 작성했는가?
2. 정의가 들어 있는 `.cpp` 파일이 빌드 대상에 포함됐는가?
3. 필요한 정적·동적 라이브러리가 링크 대상에 포함됐는가?
4. 네임스페이스, 클래스 범위, `const` 한정, 매개변수 타입이 일치하는가?
5. 선언을 제공한 헤더와 링크한 라이브러리의 버전이 맞는가?
6. 빌드 대상과 라이브러리의 플랫폼·구성 설정이 호환되는가?

함수 이름이 눈으로 같아 보여도 네임스페이스나 매개변수 타입 등이 다르면 링커 관점에서는 다른 대상을 찾는 것일 수 있다.

## 정의가 여러 개여도 링크 오류가 발생할 수 있다

정의 누락과 반대로 같은 비인라인 함수 정의가 여러 오브젝트 파일에 들어가도 문제가 된다.

```cpp
// First.cpp
int GetMaxHp()
{
    return 100;
}
```

```cpp
// Second.cpp
int GetMaxHp()
{
    return 200;
}
```

두 파일을 같은 프로그램에 링크하면 링커는 어느 정의를 사용해야 할지 임의로 선택하는 것이 아니라 다중 정의 오류를 보고할 수 있다.

오류 메시지는 도구마다 `multiple definition`, `already defined`, `duplicate symbol`처럼 다르게 표현된다. 공통 원인은 하나여야 할 외부 정의가 여러 링크 입력에 들어왔다는 점이다.

## 컴파일 성공은 프로그램 동작의 정확성을 보장하지 않는다

선언과 정의가 모두 존재해 빌드에 성공해도 호출 순서나 전달한 값이 의도와 다를 수 있다.

```cpp
#include <iostream>

int CalculateDamage(int attack, int defence)
{
    return attack - defence;
}

void RunBattle()
{
    int damage = CalculateDamage(10, 20);
    std::cout << "Damage: " << damage << '\n';
}

int main()
{
    RunBattle();
}
```

이 코드는 선언과 정의 문제 없이 빌드될 수 있지만 피해량이 음수가 되는 것이 게임 규칙에 맞는지는 별도의 논리 문제다.

빌드 단계는 함수 사용이 C++ 타입 규칙과 링크 조건을 만족하는지 확인한다. 함수에 전달한 값이 도메인 규칙에 맞는지, 실행 경로가 의도한 순서인지는 테스트와 디버깅으로 확인해야 한다.

## 호출 스택은 실행된 뒤의 흐름을 추적한다

호출 스택(Call stack)은 프로그램이 실행 중일 때 현재 위치까지 이어진 활성 함수 호출을 보여준다.

다음 코드는 앞에서 작성한 `CalculateDamage` 선언과 정의를 함께 사용한다고 가정한 호출부 예제다.

```cpp
void ResolveDamage()
{
    int damage = CalculateDamage(25, 10);
}

void RunBattle()
{
    ResolveDamage();
}

int main()
{
    RunBattle();
}
```

`CalculateDamage` 내부에서 실행을 멈추면 논리적인 호출 관계는 다음과 같다.

```text
CalculateDamage
ResolveDamage
RunBattle
main
```

호출 스택으로는 “어떤 실행 경로를 거쳐 이 함수까지 왔는가?”를 확인할 수 있다. 반면 선언 누락이나 정의 누락으로 실행 파일조차 만들어지지 않았다면 런타임 호출 스택을 볼 수 없다.

| 문제 | 확인할 정보 |
| :--- | :--- |
| 이름이나 호출 형태를 해석하지 못함 | 컴파일러 진단과 해당 번역 단위의 선언 |
| 호출에 대응하는 구현을 연결하지 못함 | 링커 진단과 오브젝트·라이브러리 구성 |
| 예상하지 않은 함수 경로로 실행됨 | 디버거의 호출 스택 |
| 값이 잘못 계산됨 | 매개변수, 지역 변수, 조건문과 테스트 결과 |

호출 스택은 빌드 오류를 고치는 도구가 아니라 빌드된 프로그램의 실행 흐름을 추적하는 도구다.

## 세 함수의 선언과 실행 흐름을 함께 구성한다

헤더에는 세 함수의 인터페이스를 선언한다.

```cpp
// Battle.h
#pragma once

int AddCriticalBonus(int damage);
int CalculateDamage(int attack, int defence, bool critical);
void RunAttack(int attack, int defence);
```

소스 파일에는 정의를 둔다.

```cpp
// Battle.cpp
#include "Battle.h"

#include <algorithm>
#include <iostream>

int AddCriticalBonus(int damage)
{
    return damage + 5;
}

int CalculateDamage(int attack, int defence, bool critical)
{
    int damage = std::max(0, attack - defence);

    if (critical)
    {
        damage = AddCriticalBonus(damage);
    }

    return damage;
}

void RunAttack(int attack, int defence)
{
    int damage = CalculateDamage(attack, defence, true);
    std::cout << "Damage: " << damage << '\n';
}
```

호출자는 헤더의 선언만 보고 함수를 사용한다.

```cpp
// Main.cpp
#include "Battle.h"

int main()
{
    RunAttack(25, 10);
}
```

이 구조를 빌드와 실행의 두 관점으로 나눌 수 있다.

```text
빌드 시점
Main.cpp   ── Battle.h 선언으로 호출 검사 ──┐
Battle.cpp ── Battle.h 선언과 함수 정의 ───┤
                                            └─ 링크

실행 시점
main → RunAttack → CalculateDamage → AddCriticalBonus
```

컴파일 시점에는 각 호출 위치에서 선언을 이용해 타입을 검사한다. 링크 시점에는 `Battle.cpp`에서 만든 정의를 호출과 연결한다. 실행 시점에는 실제 인자와 지역 객체를 가진 함수 호출들이 순서대로 활성화된다.

`AddCriticalBonus`에 중단점을 걸면 디버거 호출 스택에서 `main → RunAttack → CalculateDamage → AddCriticalBonus`로 이어진 경로를 확인할 수 있다. 최적화 빌드에서는 일부 함수가 인라인되어 일반 프레임과 다르게 보일 수 있다는 점은 앞 편에서 확인했다.

## 오류 메시지보다 먼저 실패 단계를 분류한다

도구마다 오류 코드와 문장은 다르지만 진단 순서는 크게 달라지지 않는다.

```text
1. 전처리 단계인가?
   └─ 헤더 경로, 조건부 컴파일, 매크로 확인

2. 컴파일 단계인가?
   └─ 선언, 스코프, 타입, 호출 형태 확인

3. 링크 단계인가?
   └─ 정의, 소스 파일, 라이브러리, 중복 심볼 확인

4. 실행 단계인가?
   └─ 호출 스택, 인자, 지역 상태, 조건 흐름 확인
```

예를 들어 “함수를 찾을 수 없다”는 표현만 보고 무조건 전방 선언을 추가하면 안 된다. 컴파일러가 이름을 찾지 못한 것인지, 링커가 정의 심볼을 찾지 못한 것인지에 따라 수정할 위치가 완전히 다르다.

- 컴파일러가 선언을 모른다면 필요한 헤더와 스코프를 확인한다.
- 링커가 정의를 못 찾는다면 구현 파일과 라이브러리 구성을 확인한다.
- 프로그램이 잘못된 경로로 함수를 호출한다면 실행 중 호출 스택을 확인한다.

선언을 임시로 복사해 붙이거나 빈 정의를 만드는 방식은 당장의 메시지만 바꾸고 인터페이스 불일치를 숨길 수 있다. 실제로 공유해야 하는 헤더와 하나의 올바른 정의를 기준으로 문제를 해결한다.

## 다음 학습: 같은 이름의 여러 함수 중 하나를 고르는 방법

함수 선언은 호출 위치에서 사용할 수 있어야 하고, 실제 사용된 함수에는 링크 가능한 정의가 필요하다. 헤더는 선언을 번역 단위에 공유하지만 구현 파일이나 라이브러리를 자동으로 링크하지 않는다. 빌드가 끝난 뒤의 실행 경로는 컴파일러나 링커 오류가 아니라 디버거의 호출 스택으로 추적한다.

다음 글에서는 같은 이름을 가진 여러 함수가 선언되어 있을 때 컴파일러가 인자의 개수와 타입을 기준으로 후보를 선택하는 오버로딩, 생략한 인자를 호출 위치에서 채우는 기본 인자, 자기 자신을 다시 호출하는 재귀 함수를 구분해 살펴본다.
