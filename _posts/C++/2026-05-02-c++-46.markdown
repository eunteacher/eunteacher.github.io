정수 멤버만 가진 클래스는 컴파일러가 만들어 주는 복사 생성자와 복사 대입 연산자로도 자연스럽게 복사된다. 하지만 클래스가 `new`로 만든 객체를 원시 포인터로 소유하면 포인터 값만 복사돼 두 객체가 하나의 자원을 소유한다고 착각하는 상태가 될 수 있다.

이 문제를 이해하려면 “포인터를 복사했다”와 “포인터가 가리키는 객체를 복제했다”를 구분해야 한다. 이번 글에서는 얕은 복사가 이중 해제를 만드는 과정과 깊은 복사, 복사 생성자·복사 대입·소멸자를 함께 설계하는 Rule of Three를 살펴본다.

## 컴파일러의 기본 복사는 각 기반과 멤버를 복사한다

복사 동작을 직접 선언하지 않으면 조건을 만족할 때 컴파일러가 복사 생성자와 복사 대입 연산자를 암시적으로 선언할 수 있다.

```cpp
class Player
{
public:
    int level_ = 1;
};
```

```cpp
Player original;
Player copied = original;
```

암시적 복사 생성자는 각 직접 기반 클래스와 비정적 데이터 멤버를 해당 복사 방식으로 초기화한다. 클래스 타입 멤버에는 그 타입의 복사 생성자가 사용되고 정수나 포인터 같은 멤버는 값이 복사된다.

이를 모든 객체의 메모리를 무조건 통째로 복사하는 비트 복사라고 설명하면 정확하지 않다. 멤버 타입에 따라 사용자 정의 복사 생성자가 호출될 수도 있다.

복사 대입도 각 기반 클래스와 멤버에 복사 대입을 수행한다. 단순한 값 멤버만 있고 각 멤버의 복사 의미가 클래스가 원하는 의미와 같다면 기본 복사가 적합하다.

## 원시 포인터의 기본 복사는 주소 값을 복사한다

`Knight`가 동적으로 생성한 `Pet`을 소유한다고 가정한다.

```cpp
class Knight
{
public:
    Knight() : pet_(new Pet)
    {
    }

    ~Knight()
    {
        delete pet_;
    }

private:
    Pet* pet_;
};
```

컴파일러가 제공하는 복사 생성자는 `pet_` 포인터의 주소 값을 복사한다.

```cpp
Knight first;
Knight second = first;
```

```text
first.pet_  ─┐
             ├─ 같은 Pet 객체
second.pet_ ─┘
```

두 `Knight`가 모두 자신이 `Pet`을 단독 소유한다고 생각하고 소멸자에서 `delete pet_`를 실행한다. 첫 번째 해제 후 두 번째 해제는 같은 객체를 다시 제거하므로 정의되지 않은 동작이다.

이처럼 포인터가 가리키는 대상까지 복제하지 않고 포인터 값만 복사하는 것을 얕은 복사(Shallow copy)라고 부른다.

## 얕은 복사가 항상 잘못된 것은 아니다

포인터가 객체를 소유하지 않고 잠시 관찰하기만 한다면 같은 주소를 복사하는 것이 의도일 수 있다.

```cpp
class TargetTracker
{
private:
    Monster* target_ = nullptr; // 비소유 관찰 포인터
};
```

복사된 추적기가 같은 몬스터를 바라보는 것이 올바른 요구사항일 수 있다. 공유 소유권을 표현하는 타입도 복사 후 같은 객체를 가리키도록 설계된다.

문제는 복사 방식과 소유권 의미가 일치하지 않을 때 발생한다.

```text
비소유 포인터      주소 공유가 자연스러울 수 있음
공유 소유 자원     의도적인 공유와 수명 관리가 필요
독점 소유 자원     복사 금지 또는 독립 자원 복제가 필요
```

원시 포인터만 봐서는 어느 의미인지 알기 어렵다. 소유권을 이름, 인터페이스와 자원 관리 타입으로 분명히 표현해야 한다.

## 깊은 복사는 가리키는 대상까지 새로 만든다

각 `Knight`가 독립적인 `Pet`을 가져야 한다면 복사할 때 새로운 `Pet` 객체를 만든다.

```cpp
Knight::Knight(const Knight& other) : Player(other), hp_(other.hp_), pet_(new Pet(*other.pet_))
{
}
```

```text
first.pet_  → 첫 번째 Pet 객체
second.pet_ → 복제된 두 번째 Pet 객체
```

포인터 주소는 다르지만 두 `Pet`의 초기 상태는 같다. 이후 한 기사의 펫 상태를 바꿔도 다른 기사의 펫에는 영향을 주지 않는다. 이를 깊은 복사(Deep copy)라고 한다.

초기화 목록의 `Player(other)`도 중요하다. 직접 작성한 파생 클래스 복사 생성자에서 기반 생성자를 지정하지 않으면 기반 클래스는 복사 생성되는 대신 기본 생성될 수 있다. 원본 예제는 이 호출이 빠져 있어 기사의 레벨이 복사되지 않는다.

## 복사 생성자와 복사 대입은 출발 상태가 다르다

복사 생성자는 아직 존재하지 않는 새 객체를 만든다.

```cpp
Knight copied = original;
Knight another(original);
```

대상 객체가 가진 기존 자원이 없으므로 원본 상태를 이용해 멤버를 직접 초기화한다.

복사 대입은 이미 수명이 시작된 객체를 변경한다.

```cpp
Knight destination;
destination = original;
```

`destination`은 이미 자신의 `Pet`을 소유하고 있다. 새 자원을 복사한 뒤 기존 자원을 정리하고 소유권을 교체해야 한다.

```text
복사 생성  빈 객체 수명을 원본의 복사본으로 시작
복사 대입  기존 객체가 가진 자원을 정리하고 원본 상태로 교체
```

## 복사 대입에서 새 포인터만 대입하면 메모리가 누수된다

원본 코드는 복사 대입에서 다음 작업만 수행한다.

```cpp
pet_ = new Pet(*other.pet_);
```

`pet_`에는 대입 전에 대상 객체가 소유하던 `Pet` 주소가 들어 있다. 새 주소로 덮어쓰면 기존 주소를 잃어버려 그 객체를 해제할 수 없다.

```text
대입 전 pet_ → 기존 Pet
새 Pet 할당
pet_에 새 주소 대입
기존 Pet 주소를 잃음 → 메모리 누수
```

기존 자원을 반드시 정리해야 하지만 먼저 삭제한 뒤 복사하는 코드도 문제가 있다.

```cpp
delete pet_;
pet_ = new Pet(*other.pet_);
```

새 할당이나 `Pet` 복사 생성자가 실패해 예외를 던지면 `pet_`에는 이미 해제된 주소가 남는다. 객체가 유효한 상태를 잃고 나중에 다시 해제될 가능성도 생긴다.

## 먼저 복제에 성공한 뒤 기존 자원과 교체한다

현재 클래스에서는 새로운 펫 복제를 먼저 완료할 수 있다.

```cpp
Knight& Knight::operator=(const Knight& other)
{
    if (this == &other)
    {
        return *this;
    }

    Pet* copiedPet = new Pet(*other.pet_);

    Player::operator=(other);
    hp_ = other.hp_;
    delete pet_;
    pet_ = copiedPet;
    return *this;
}
```

`new Pet`이 실패하면 기존 `pet_`는 아직 건드리지 않았으므로 대상 객체의 원래 상태가 유지된다. 복제에 성공한 뒤 기반 상태와 값을 복사하고 기존 펫을 제거해 새 펫으로 교체한다.

이 예제의 `Player` 대입과 정수 대입은 예외를 던지지 않는다. 일반 클래스에서는 복제 후 이어지는 다른 대입도 예외를 던질 수 있는지 확인해야 한다. 복사 후 교환(Copy-and-swap) 같은 방식으로 더 넓은 예외 안전성을 구성할 수도 있다.

## 자기 대입을 먼저 확인한다

객체에 자기 자신을 대입할 수도 있다.

```cpp
knight = knight;
```

위 구현은 `this`와 원본 주소를 비교해 아무 작업 없이 반환한다.

```cpp
if (this == &other)
{
    return *this;
}
```

자기 대입 검사가 없더라도 올바르게 동작하도록 구현할 수 있지만, 기존 자원을 먼저 제거하는 단순 구현에서는 원본 데이터까지 함께 사라질 수 있다. 어떤 방식을 사용하든 자기 대입 후 객체가 유효해야 한다.

## 소멸자·복사 생성자·복사 대입은 한 세트로 검토한다

클래스가 직접 소유한 자원을 소멸자에서 정리한다면 기본 복사로 같은 자원을 공유해도 되는지 확인해야 한다.

```text
소멸자             소유 자원을 어떻게 정리하는가?
복사 생성자        새 객체가 독립 자원을 어떻게 얻는가?
복사 대입 연산자   기존 자원을 어떻게 교체하는가?
```

셋 중 하나를 직접 작성해야 하는 자원 소유 클래스라면 나머지 둘도 함께 필요할 가능성이 높다는 지침을 Rule of Three라고 한다.

이 규칙이 모든 클래스에 세 함수를 직접 작성하라는 뜻은 아니다. 복사를 허용하지 않을 타입은 복사 연산을 `= delete`로 막을 수 있고, 자원을 값 멤버나 표준 자원 관리 타입에 맡기면 컴파일러의 기본 동작을 사용할 수 있다.

## 상속이 있다면 기반 클래스 복사도 명시한다

직접 작성한 복사 생성자는 기반 클래스와 멤버를 자동으로 복사해 주지 않는다. 초기화 목록에서 생략된 기반 클래스는 기본 생성될 수 있다.

```cpp
Knight::Knight(const Knight& other) : Player(other), hp_(other.hp_), pet_(new Pet(*other.pet_))
{
}
```

복사 대입에서도 기반 클래스의 대입 연산자를 호출한다.

```cpp
Player::operator=(other);
```

파생 클래스 객체를 복사한다는 것은 파생 클래스에 새로 추가한 멤버만 맞추는 작업이 아니다. 기반 클래스 부분까지 원본과 같은 의미의 상태가 되도록 해야 한다.

다만 다형적 기반 클래스의 복사를 허용하면 객체 슬라이싱과 복제 의미가 복잡해질 수 있다. 실제 다형적 계층에서는 복사를 금지하거나 가상 `Clone` 인터페이스를 제공하는 설계도 검토한다.

## 전체 구현

`Knight`가 펫을 독점 소유하면서 복사할 때마다 독립적인 `Pet`을 만드는 예제다.

```cpp
#include <algorithm>
#include <cassert>
#include <iostream>

class Player
{
public:
    explicit Player(int level = 1) : level_(std::max(1, level))
    {
    }

    int Level() const
    {
        return level_;
    }

protected:
    void SetLevel(int level)
    {
        level_ = std::max(1, level);
    }

private:
    int level_;
};

class Pet
{
public:
    explicit Pet(int affection = 0) : affection_(std::clamp(affection, 0, 100))
    {
        ++aliveCount_;
    }

    Pet(const Pet& other) : affection_(other.affection_)
    {
        ++aliveCount_;
    }

    Pet& operator=(const Pet&) = default;

    ~Pet()
    {
        --aliveCount_;
    }

    void AddAffection(int amount)
    {
        if (amount <= 0)
        {
            return;
        }

        affection_ = amount >= 100 - affection_ ? 100 : affection_ + amount;
    }

    int Affection() const
    {
        return affection_;
    }

    static int AliveCount()
    {
        return aliveCount_;
    }

private:
    int affection_;
    inline static int aliveCount_ = 0;
};

class Knight : public Player
{
public:
    Knight(int level = 1, int hp = 100, int petAffection = 0) : Player(level), hp_(std::max(0, hp)), pet_(new Pet(petAffection))
    {
    }

    Knight(const Knight& other) : Player(other), hp_(other.hp_), pet_(new Pet(*other.pet_))
    {
    }

    Knight& operator=(const Knight& other)
    {
        if (this == &other)
        {
            return *this;
        }

        Pet* copiedPet = new Pet(*other.pet_);

        Player::operator=(other);
        hp_ = other.hp_;
        delete pet_;
        pet_ = copiedPet;
        return *this;
    }

    ~Knight()
    {
        delete pet_;
    }

    void TrainPet(int amount)
    {
        pet_->AddAffection(amount);
    }

    int Hp() const
    {
        return hp_;
    }

    int PetAffection() const
    {
        return pet_->Affection();
    }

    const Pet* PetAddress() const
    {
        return pet_;
    }

private:
    int hp_;
    Pet* pet_;
};

void VerifyDeepCopy()
{
    assert(Pet::AliveCount() == 0);

    {
        Knight original{10, 200, 40};
        Knight copied = original;

        assert(copied.Level() == 10);
        assert(copied.Hp() == 200);
        assert(copied.PetAffection() == 40);
        assert(copied.PetAddress() != original.PetAddress());

        copied.TrainPet(20);
        assert(original.PetAffection() == 40);
        assert(copied.PetAffection() == 60);

        Knight assigned{1, 50, 5};
        assigned = original;

        assert(assigned.Level() == 10);
        assert(assigned.Hp() == 200);
        assert(assigned.PetAffection() == 40);
        assert(assigned.PetAddress() != original.PetAddress());
        assert(Pet::AliveCount() == 3);

        const Pet* beforeSelfAssignment = assigned.PetAddress();
        assigned = assigned;
        assert(assigned.PetAddress() == beforeSelfAssignment);
        assert(Pet::AliveCount() == 3);

        std::cout << "original pet affection: " << original.PetAffection() << '\n';
        std::cout << "copied pet affection: " << copied.PetAffection() << '\n';
        std::cout << "owned pets: " << Pet::AliveCount() << '\n';
    }

    assert(Pet::AliveCount() == 0);
}

int main()
{
    VerifyDeepCopy();
}
```

실행 결과는 다음과 같다.

```text
original pet affection: 40
copied pet affection: 60
owned pets: 3
```

복사 직후 두 펫의 애정도는 같지만 주소는 다르다. 복사본의 펫만 훈련한 뒤 원본은 40을 유지하고 복사본은 60이 되므로 상태가 독립적이라는 점을 확인할 수 있다.

복사 대입에서는 대상이 원래 소유하던 펫을 새 복제본으로 교체한다. 같은 객체를 자기 자신에게 대입했을 때는 주소와 상태가 그대로 유지된다. 블록을 벗어난 뒤 살아 있는 펫 수가 0인지 확인해 모든 소유 자원이 한 번씩 정리됐는지도 검증한다.

## 가능하면 Rule of Zero를 목표로 한다

원시 포인터로 직접 소유권을 관리하면 복사뿐 아니라 예외, 이동과 소멸까지 클래스가 책임져야 한다. 펫을 값 멤버로 포함할 수 있다면 가장 단순하다.

```cpp
class Knight
{
private:
    Pet pet_;
};
```

독점 동적 소유가 필요하면 `std::unique_ptr<Pet>`로 소유권을 표현할 수 있다. 기본 복사는 금지되므로 독립 복제가 필요할 때 복사 정책을 의도적으로 구현한다.

멤버 타입들이 자신의 자원을 올바르게 관리하게 만들고 바깥 클래스는 소멸자·복사·이동 연산을 직접 작성하지 않는 설계를 Rule of Zero라고 한다. 직접 관리할 자원이 줄어들수록 누수와 이중 해제 가능성도 줄어든다.

이동 연산까지 직접 관리하는 Rule of Five와 `std::unique_ptr`의 구체적인 복사·이동 방식은 이후 글에서 다룬다.

## 자원 소유 클래스의 복사를 검토할 때 확인할 기준

1. 포인터가 소유, 공유, 비소유 중 어떤 의미인지 명확한가?
2. 기본 복사가 주소만 공유해도 클래스의 의미가 유지되는가?
3. 독립 소유라면 복사 생성자가 새로운 자원을 만드는가?
4. 파생 클래스 복사 생성자에서 기반 클래스도 복사하는가?
5. 복사 대입에서 대상이 기존에 소유하던 자원을 정리하는가?
6. 새 자원 복제에 실패해도 기존 객체가 유효한 상태를 유지하는가?
7. 자기 대입 후에도 주소와 값이 올바른가?
8. 소멸자, 복사 생성자와 복사 대입을 함께 검토했는가?
9. 복사가 불필요한 타입이라면 `= delete`로 금지할 수 있는가?
10. 값 멤버나 표준 자원 관리 타입으로 Rule of Zero를 적용할 수 있는가?

깊은 복사는 포인터가 보이면 무조건 `new`를 한 번 더 호출하는 기법이 아니다. 복사된 두 객체가 자원을 독립적으로 소유해야 한다는 클래스의 의미를 구현하는 방식이다. 먼저 소유권 정책을 정한 뒤 그 정책에 맞는 복사와 소멸을 설계해야 한다.
