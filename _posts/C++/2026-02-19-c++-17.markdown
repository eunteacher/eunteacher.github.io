앞에서는 함수의 이름, 매개변수, 반환 타입이 호출자와 함수 사이의 계약을 만든다는 점을 살펴봤다. 하지만 함수가 연속해서 호출되면 각 함수의 매개변수와 지역 변수는 어떻게 서로 구분되고, 실행이 끝난 뒤에는 어떻게 정확한 호출 지점으로 돌아갈까?

이 질문에 답할 때 흔히 **스택 프레임(Stack frame)**을 사용한다. 다만 C++ 언어가 특정한 스택 구조를 직접 규정하는 것은 아니다. 먼저 C++ 코드에서 보장되는 호출 흐름을 이해하고, 그 흐름을 컴퓨터가 구현하는 대표적인 방법으로 스택 프레임을 살펴봐야 한다.

## 중첩된 함수 호출의 흐름부터 추적한다

세 함수가 차례로 호출되는 간단한 예제를 보자.

```cpp
#include <iostream>

int AddBonus(int damage)
{
    int result = damage + 3;
    return result;
}

int CalculateDamage(int attack, int defence)
{
    int baseDamage = attack - defence;
    int finalDamage = AddBonus(baseDamage);
    return finalDamage;
}

int main()
{
    int playerAttack = 20;
    int monsterDefence = 8;
    int damage = CalculateDamage(playerAttack, monsterDefence);
    std::cout << "Damage: " << damage << '\n';
}
```

호출 순서를 코드의 제어 흐름으로 펼치면 다음과 같다.

```text
main 시작
  └─ CalculateDamage(20, 8) 호출
       ├─ baseDamage = 12
       └─ AddBonus(12) 호출
            ├─ result = 15
            └─ 15 반환
       ├─ finalDamage = 15
       └─ 15 반환
  ├─ damage = 15
  └─ 결과 출력
```

`AddBonus`가 실행되는 동안 `CalculateDamage`는 끝난 것이 아니다. 자신의 실행을 잠시 멈추고 `AddBonus`의 결과를 기다린다. `AddBonus`가 반환되면 `CalculateDamage`는 호출문 다음 흐름을 이어가고, 다시 `main`으로 결과를 반환한다.

이처럼 아직 끝나지 않은 함수 호출을 **활성 호출(Active call)**이라고 생각할 수 있다.

| 시점 | 활성 호출 |
| :--- | :--- |
| `main` 실행 | `main` |
| `CalculateDamage` 실행 | `main` → `CalculateDamage` |
| `AddBonus` 실행 | `main` → `CalculateDamage` → `AddBonus` |
| `AddBonus` 반환 후 | `main` → `CalculateDamage` |
| `CalculateDamage` 반환 후 | `main` |

가장 나중에 호출된 함수가 가장 먼저 끝난다. 이 후입선출(Last In, First Out) 구조 때문에 함수 호출을 설명할 때 스택 모델이 자연스럽게 등장한다.

## C++가 보장하는 것과 구현이 선택하는 것을 구분한다

소스 코드 수준에서 중요하게 볼 내용은 다음과 같다.

- 호출된 함수의 매개변수가 인자로 초기화된다.
- 함수 몸체의 문장들이 실행된다.
- 자동 저장 기간을 가진 지역 객체는 각 호출마다 별도로 생성된다.
- `return`이 실행되면 호출자에게 제어가 돌아간다. `void` 함수는 몸체 끝에 도달해도 반환되지만, `main`을 제외한 값을 반환하는 함수에는 정상 경로마다 반환값이 필요하다.
- 반환값이 있다면 호출 표현식의 결과로 전달된다.

반면 다음 내용은 C++ 문법만으로 고정되지 않는다.

- 인자가 레지스터와 메모리 중 어디에 놓이는가?
- 스택이 낮은 주소와 높은 주소 중 어느 방향으로 자라는가?
- 프레임 포인터 전용 레지스터를 사용하는가?
- 지역 변수가 실제 스택 메모리를 차지하는가?
- 반환값이 어떤 레지스터나 메모리를 통해 전달되는가?
- 소스 코드의 함수 호출이 기계 코드에도 별도 호출로 남는가?

이런 세부 사항은 대상 CPU, 운영체제, ABI(Application Binary Interface), 호출 규약(Calling convention), 컴파일러와 최적화 설정에 따라 달라질 수 있다.

따라서 다음 두 문장은 구분해서 사용해야 한다.

> 함수가 호출될 때마다 그 호출만의 매개변수와 지역 객체가 존재한다.

이는 C++ 코드의 의미를 설명한다.

> 함수가 호출될 때마다 모든 매개변수와 지역 변수가 메모리 스택에 순서대로 저장된다.

이는 모든 C++ 프로그램에 보장되는 규칙이 아니다. 전형적인 구현을 지나치게 단순화한 설명이다.

## 호출 스택은 아직 끝나지 않은 호출의 순서를 보여준다

**호출 스택(Call stack)**은 현재 실행 중이거나 반환을 기다리는 호출의 중첩 관계를 설명하는 개념이다.

앞의 예제에서 `AddBonus`가 실행 중이라면 호출 관계는 다음과 같다.

```text
가장 최근 호출
┌─────────────────────────────┐
│ AddBonus                    │
├─────────────────────────────┤
│ CalculateDamage             │
├─────────────────────────────┤
│ main                        │
└─────────────────────────────┘
가장 먼저 시작한 호출
```

여기서 위쪽의 `AddBonus`가 먼저 반환되고, 그다음 `CalculateDamage`, 마지막으로 `main`이 끝난다.

호출 스택은 함수 이름의 목록만을 뜻하지 않는다. 디버거에서는 각 호출이 어느 코드 위치에서 다음 함수를 불렀는지 함께 보여주므로, 현재 위치까지 도달한 경로를 역으로 추적할 수 있다.

## 스택 프레임은 한 번의 호출을 지원하는 실행 문맥이다

**스택 프레임(Stack frame)** 또는 **호출 프레임(Call frame)**은 한 번의 함수 호출을 실행하고 원래 호출자로 돌아가기 위해 구현이 관리하는 정보 묶음이다.

일반적인 네이티브 환경에서는 다음과 같은 정보 일부가 스택 프레임과 관련될 수 있다.

| 정보 | 필요한 이유 |
| :--- | :--- |
| 반환 주소 | 함수가 끝난 뒤 호출자의 어느 위치로 돌아갈지 기록한다. |
| 보존해야 하는 레지스터 값 | 호출 전후에 유지하기로 약속한 레지스터 상태를 복원한다. |
| 스택에 전달된 인자 | 호출 규약상 레지스터에 담지 못했거나 스택 전달 대상으로 정한 인자를 보관한다. |
| 지역 객체와 임시 저장 공간 | 레지스터에 둘 수 없거나 주소가 필요한 데이터를 저장한다. |
| 정렬을 위한 여유 공간 | ABI가 요구하는 스택 정렬 조건을 만족한다. |
| 호출자가 받을 반환값을 위한 정보 | 큰 객체 반환처럼 별도 저장 공간이 필요한 호출을 지원한다. |

이 표는 가능한 구성 요소를 설명한 것이지, 모든 함수가 이 항목을 전부 갖는다는 뜻은 아니다. 빈 함수나 단순 계산 함수는 최적화 후 별도의 프레임이 사라질 수 있고, 사용하지 않는 지역 변수는 코드와 함께 제거될 수도 있다.

## 같은 함수도 호출할 때마다 독립된 상태를 가진다

같은 함수를 두 번 호출해도 각 호출의 매개변수와 지역 객체는 서로 다른 객체다.

```cpp
int AddOne(int value)
{
    int result = value + 1;
    return result;
}

int main()
{
    int first = AddOne(10);
    int second = AddOne(20);
}
```

첫 번째 호출의 `value`는 10으로, 두 번째 호출의 `value`는 20으로 초기화된다. 첫 호출이 끝난 뒤 두 번째 호출이 시작되므로 두 호출의 상태가 섞이지 않는다.

같은 함수가 끝나기 전에 다시 자신을 호출하는 재귀에서도 이 원칙은 유지된다.

```cpp
int SumTo(int number)
{
    if (number <= 1)
    {
        return number;
    }

    return number + SumTo(number - 1);
}
```

`SumTo(3)`의 활성 호출을 펼치면 다음과 같다.

```text
SumTo(3)
  └─ 3 + SumTo(2)
           └─ 2 + SumTo(1)
                    └─ 1 반환
           └─ 2 + 1 = 3 반환
  └─ 3 + 3 = 6 반환
```

동시에 활성화된 각 호출은 서로 다른 `number` 매개변수를 가진다. 일반적인 구현에서는 각 재귀 호출을 위한 프레임이 추가되므로 이전 호출의 계산을 보존한 채 다음 호출을 처리할 수 있다.

## 지역 변수 이름이 같아도 서로 다른 객체다

다른 함수에 같은 이름의 지역 변수를 선언할 수 있다.

```cpp
int Double(int value)
{
    int result = value * 2;
    return result;
}

int Triple(int value)
{
    int result = value * 3;
    return result;
}
```

`Double`의 `result`와 `Triple`의 `result`는 이름만 같을 뿐 서로 다른 선언으로 만들어진 별개의 객체다. 어느 이름을 코드에서 사용할 수 있는지는 스코프 규칙이 결정하고, 객체가 언제 생성되고 소멸하는지는 수명과 저장 기간 규칙이 결정한다.

스택 프레임은 이런 독립성을 구현하는 대표적인 방법이지만 독립성 자체의 근거를 “변수 이름이 스택의 다른 칸에 있기 때문”으로만 이해해서는 안 된다. 컴파일러가 두 값을 레지스터에 두거나 계산으로 대체해도 프로그램의 관찰 가능한 의미는 유지되어야 한다.

## 값 매개변수도 반드시 스택에 복사되는 것은 아니다

값 전달 함수에서는 매개변수가 인자의 값으로 초기화된 별도 객체라는 점을 앞에서 확인했다.

```cpp
void Increase(int value)
{
    ++value;
}

int main()
{
    int hp = 10;
    Increase(hp);
}
```

`Increase` 안의 `value`를 변경해도 `main`의 `hp`는 바뀌지 않는다. 이것이 소스 코드에서 관찰할 수 있는 핵심이다.

하지만 이를 “`hp`의 값이 항상 메모리 스택의 다른 칸으로 복사된다”라고 설명하면 구현을 단정하게 된다. 호출 규약은 작은 정수 인자를 레지스터로 전달할 수 있고, 최적화된 코드에서는 호출 자체와 `value`의 저장 공간이 사라질 수도 있다.

다음 두 층을 구분하면 혼동이 줄어든다.

| 관점 | 설명 |
| :--- | :--- |
| C++ 언어 | `value`는 `hp`와 별개의 매개변수 객체다. |
| 일반적인 구현 | 값이 레지스터 또는 스택 등을 통해 함수에 전달될 수 있다. |

## 호출자는 멈춘 위치를 기억해야 한다

함수 호출이 끝나면 호출자는 호출 표현식 다음 작업을 계속해야 한다.

```cpp
int damage = CalculateDamage(20, 8);
std::cout << damage << '\n';
```

`CalculateDamage`가 반환된 뒤에는 두 번째 줄의 출력을 이어가야 한다. 기계 코드 수준에서는 이를 위해 돌아갈 위치가 필요하며, 보통 호출 명령과 호출 규약이 반환 주소를 관리한다.

다만 반환 주소가 항상 지역 변수 옆의 스택 메모리에 놓인다고 단정할 수는 없다. 아키텍처에 따라 호출 명령이 스택을 사용할 수도 있고 링크 레지스터 같은 전용 레지스터를 사용할 수도 있다. 중첩 호출이 이어지면 필요한 상태를 다른 위치에 보존할 수도 있다.

중요한 것은 구현 위치가 아니라 다음 관계다.

```text
호출자: 함수 호출 전까지 실행
                 │
                 ▼
피호출자: 함수 몸체 실행
                 │
                 ▼
호출자: 호출 결과를 받고 다음 흐름 계속
```

호출하는 함수를 **호출자(Caller)**, 호출되는 함수를 **피호출자(Callee)**라고 부른다.

## 호출 규약은 함수 경계의 약속이다

서로 따로 컴파일된 코드가 함수를 호출하려면 인자와 반환값을 어디에 둘지, 어떤 레지스터를 누가 보존할지 같은 규칙에 동의해야 한다. 이 약속이 호출 규약이다.

호출 규약에는 일반적으로 다음과 같은 결정이 포함된다.

- 인자를 전달하는 레지스터의 종류와 순서
- 스택으로 전달하는 인자의 위치
- 반환값을 전달하는 방법
- 호출자가 보존할 레지스터와 피호출자가 보존할 레지스터
- 호출 전 스택 정렬 조건
- 함수 이름을 바이너리에 표현하는 방식과의 연계

C++ 소스만 공부할 때 모든 ABI 세부 규칙을 외울 필요는 없다. 하지만 다음 상황에서는 호출 규약이 실제 문제로 드러날 수 있다.

- 서로 다른 컴파일러나 빌드 설정으로 만든 라이브러리를 연결한다.
- C 함수 또는 운영체제 API와 상호 운용한다.
- 함수 포인터의 타입과 호출 규약이 맞지 않는다.
- 디버거나 어셈블리에서 인자 전달 과정을 확인한다.
- 플러그인과 동적 라이브러리의 바이너리 인터페이스를 유지한다.

호출 규약이 일치해야 호출자와 피호출자가 같은 데이터를 같은 방식으로 해석할 수 있다.

## 함수 진입과 종료 코드는 고정된 공식이 아니다

전형적인 함수 호출 설명에서는 피호출자가 시작할 때 스택 공간을 확보하고, 끝날 때 원래 상태로 되돌리는 과정을 보여준다. 이를 함수 프롤로그(Prologue)와 에필로그(Epilogue)라고 부르기도 한다.

개념적으로는 다음처럼 표현할 수 있다.

```text
함수 진입
  ├─ 필요한 호출 상태 보존
  ├─ 지역 데이터에 필요한 공간 준비
  └─ 함수 몸체 실행

함수 종료
  ├─ 반환값 준비
  ├─ 보존한 상태 복원
  └─ 호출자에게 반환
```

많은 환경에서 스택 포인터(Stack pointer)는 현재 스택 경계를 가리키고, 프레임을 위해 필요한 만큼 이동한다. 스택이 높은 주소에서 낮은 주소로 자라는 구현이라면 다음과 같은 개념식으로 나타낼 수 있다.

$$SP_{new} = SP_{old} - FrameSize$$

하지만 이 식은 특정 방향으로 성장하는 전형적인 구현을 설명할 뿐 C++ 표준의 공식이 아니다. 실제 프레임 크기에는 정렬과 임시 공간이 포함될 수 있고, 최적화 결과 프레임 크기가 0이거나 별도 프레임이 없을 수도 있다.

## 프레임 포인터는 항상 존재하지 않는다

스택 프레임 설명에서 프레임 포인터(Frame pointer)를 자주 볼 수 있다. 프레임 포인터는 함수 실행 중 프레임 내부의 데이터에 일정한 기준점으로 접근하도록 돕는 레지스터다.

그러나 컴파일러는 해당 레지스터를 일반 계산에 활용하기 위해 프레임 포인터를 생략할 수 있다. 디버그 정보와 unwind 정보가 있다면 전용 프레임 포인터 없이도 호출 스택을 복원할 수 있는 환경도 있다.

따라서 다음처럼 이해한다.

- 스택 포인터는 네이티브 호출 구현에서 핵심적으로 사용되는 경우가 많다.
- 프레임 포인터는 디버깅과 프레임 접근에 유용할 수 있다.
- 모든 함수가 독립된 프레임 포인터를 갖는다고 보장되지는 않는다.

## 최적화하면 소스 코드와 호출 프레임이 일대일로 대응하지 않을 수 있다

다음 함수는 별도의 호출로 작성되어 있다.

```cpp
int Square(int value)
{
    return value * value;
}

int GetArea()
{
    return Square(5);
}
```

최적화하지 않은 빌드에서는 `GetArea`가 `Square`를 호출하는 형태가 남을 수 있다. 반면 최적화된 빌드에서는 컴파일러가 다음과 같은 판단을 할 수 있다.

- `Square`의 몸체를 `GetArea` 안에 펼친다.
- `Square(5)`를 컴파일 시간에 계산해 25로 대체한다.
- 사용되지 않는 중간 객체와 저장 공간을 제거한다.
- 함수 전체가 필요하지 않다면 호출자와 함께 제거한다.

이 경우 소스에는 `Square` 호출이 있어도 실행 중 별도의 `Square` 프레임이 없을 수 있다. `inline` 키워드가 있어야만 이런 최적화가 가능한 것도 아니며, 키워드가 있다고 반드시 프레임이 사라지는 것도 아니다.

디버거에서 소스 한 줄씩 실행할 때 위치가 건너뛰거나 지역 변수가 “최적화되어 사용할 수 없음”으로 표시되는 이유도 이 차이와 관련될 수 있다.

## 디버거의 호출 스택으로 도달 경로를 확인한다

중첩 호출을 이해하는 가장 실용적인 방법은 디버거에서 함수 내부에 중단점을 걸고 호출 스택을 확인하는 것이다.

앞의 예제에서 `AddBonus`의 `return` 줄에 중단점을 둔다면 다음 내용을 확인할 수 있다.

1. 현재 실행 위치는 `AddBonus`다.
2. `CalculateDamage`가 `AddBonus`를 호출했다.
3. `main`이 `CalculateDamage`를 호출했다.
4. 각 프레임을 선택하면 그 호출 시점의 매개변수와 지역 변수를 확인할 수 있다.

디버거 제품마다 표시 방식은 다르지만 보통 다음과 같은 형태다.

```text
AddBonus(damage=12)
CalculateDamage(attack=20, defence=8)
main()
```

이는 앞의 코드를 기준으로 기대할 수 있는 논리적 호출 관계를 나타낸 예시이며, 실제 주소·모듈명·프레임 표시는 빌드 환경에 따라 달라진다.

호출 스택은 특히 다음 문제를 추적할 때 유용하다.

- 예상하지 않은 경로에서 함수가 호출됐다.
- 여러 호출자를 가진 함수에 잘못된 인자가 들어왔다.
- 예외나 충돌이 발생한 위치까지 어떤 함수들이 이어졌는지 알고 싶다.
- 재귀 호출이 끝나지 않고 계속 깊어진다.
- 콜백이 어느 시스템에서 시작됐는지 찾고 싶다.

현재 줄만 보면 “어디에서 호출됐는가?”를 알기 어렵지만 호출 스택을 보면 실행 경로 전체를 거슬러 올라갈 수 있다.

## 디버그 빌드와 최적화 빌드의 호출 스택은 다르게 보일 수 있다

디버그 빌드는 소스 코드와 실행 흐름을 비교적 쉽게 대응시키도록 최적화를 줄이는 경우가 많다. 그래서 지역 변수와 함수 프레임이 소스 구조에 가깝게 보일 수 있다.

최적화 빌드에서는 다음 현상이 나타날 수 있다.

- 인라인된 함수가 일반 프레임처럼 보이지 않는다.
- 지역 변수가 제거되거나 여러 위치로 이동한다.
- 코드 실행 순서가 소스의 작성 순서와 다르게 보인다.
- 일부 함수가 호출 스택에서 생략된 것처럼 보인다.
- 꼬리 호출 최적화로 현재 프레임을 재사용할 수 있다.

컴파일러와 디버거는 인라인 호출 정보를 별도로 보여주기도 하지만 언제나 원래 소스와 완벽히 같은 모습이 되는 것은 아니다. 디버깅할 때는 현재 보고 있는 바이너리의 최적화 설정과 디버그 심볼이 일치하는지 함께 확인한다.

## 재귀 호출에는 반드시 종료 조건이 필요하다

재귀 함수는 문제를 더 작은 같은 형태의 문제로 바꾼다.

```cpp
int Countdown(int number)
{
    if (number <= 0)
    {
        return 0;
    }

    return Countdown(number - 1);
}
```

`number <= 0`은 더 이상 재귀 호출을 만들지 않는 종료 조건(Base case)이다. 종료 조건이 없거나 도달할 수 없다면 활성 호출이 계속 늘어날 수 있다.

```cpp
void RepeatForever()
{
    RepeatForever();
}
```

일반적인 실행 환경에서는 사용 가능한 호출 스택 공간 같은 자원이 고갈되어 프로그램이 비정상적으로 종료될 수 있다. 흔히 이를 **스택 오버플로(Stack overflow)**라고 부른다. 다만 C++ 표준이 반드시 특정한 “스택 오버플로 예외”를 발생시키도록 정한 것은 아니다.

종료 조건이 있다는 사실만으로 항상 안전한 것도 아니다. 입력값에 따라 재귀 깊이가 지나치게 커질 수 있다면 반복문으로 바꾸거나 명시적인 자료구조를 사용하는 방식도 검토한다.

## 꼬리 호출이 항상 프레임을 재사용하는 것은 아니다

함수의 마지막 작업이 다른 함수 호출의 결과를 그대로 반환하는 형태를 꼬리 호출(Tail call)이라고 한다.

```cpp
int Countdown(int number)
{
    if (number <= 0)
    {
        return 0;
    }

    return Countdown(number - 1);
}
```

컴파일러는 조건이 맞으면 새 프레임을 계속 추가하지 않고 현재 프레임을 재사용하는 꼬리 호출 최적화를 적용할 수 있다. 그러나 일반적인 C++ 함수에서 이 최적화가 반드시 수행된다는 보장은 없다.

따라서 “꼬리 재귀로 작성했으니 호출 깊이와 관계없이 안전하다”라고 가정해서는 안 된다. 스택 사용량이 실제 요구사항이라면 대상 컴파일러와 빌드 설정에서 생성된 코드를 확인한다.

## 큰 객체 전달을 프레임 크기만으로 판단하지 않는다

큰 객체를 값으로 전달하면 복사 비용과 별도 매개변수 객체를 고려해야 한다.

```cpp
struct PlayerData
{
    int values[1024];
};

int GetFirstValue(PlayerData player)
{
    return player.values[0];
}
```

읽기만 한다면 `const` 참조로 받을 수 있다.

```cpp
int GetFirstValue(const PlayerData& player)
{
    return player.values[0];
}
```

하지만 “참조는 포인터 하나만 스택에 쌓이므로 언제나 더 빠르다”라고 단정할 수는 없다. 복사 생략, 인라인, 캐시 접근, 객체 크기와 타입 특성에 따라 비용이 달라진다. 작은 타입은 값 전달이 더 단순할 수 있고, 함수가 복사본을 필요로 한다면 값 매개변수가 의도를 잘 표현할 수도 있다.

인터페이스는 먼저 소유 관계와 수정 가능성을 기준으로 선택하고, 성능이 중요한 구간은 측정 결과로 판단한다. 참조 자체의 규칙은 이후 글에서 별도로 다룬다.

## 전체 예제로 호출의 진입과 반환 순서를 확인한다

다음 코드는 각 함수가 시작하고 끝나는 지점을 직접 출력해 중첩된 호출 순서를 보여준다.

```cpp
#include <algorithm>
#include <iostream>

int AddCriticalBonus(int damage)
{
    std::cout << "  Enter AddCriticalBonus\n";
    int result = damage + 5;
    std::cout << "  Leave AddCriticalBonus: " << result << '\n';
    return result;
}

int CalculateDamage(int attack, int defence, bool critical)
{
    std::cout << " Enter CalculateDamage\n";
    int damage = std::max(0, attack - defence);

    if (critical)
    {
        damage = AddCriticalBonus(damage);
    }

    std::cout << " Leave CalculateDamage: " << damage << '\n';
    return damage;
}

void RunAttack(int attack, int defence)
{
    std::cout << "Enter RunAttack\n";
    int damage = CalculateDamage(attack, defence, true);
    std::cout << "Damage: " << damage << '\n';
    std::cout << "Leave RunAttack\n";
}

int main()
{
    std::cout << "Enter main\n";
    RunAttack(25, 10);
    std::cout << "Leave main\n";
}
```

코드의 제어 흐름을 따라가면 출력 순서는 다음과 같다.

```text
Enter main
Enter RunAttack
 Enter CalculateDamage
  Enter AddCriticalBonus
  Leave AddCriticalBonus: 20
 Leave CalculateDamage: 20
Damage: 20
Leave RunAttack
Leave main
```

들어가는 순서는 `main → RunAttack → CalculateDamage → AddCriticalBonus`이고, 나오는 순서는 그 반대다. 들여쓰기는 실제 메모리 주소나 프레임 크기를 나타내지 않고 호출 깊이를 눈으로 구분하기 위한 표시다.

`AddCriticalBonus` 내부에 중단점을 두고 디버거의 호출 스택을 보면 다음 관계를 확인할 수 있다.

```text
AddCriticalBonus
CalculateDamage
RunAttack
main
```

이 예제를 디버그 빌드와 최적화 빌드에서 각각 살펴보면 함수 인라인 여부와 지역 변수 표시가 어떻게 달라지는지도 비교할 수 있다.

## 함수 호출을 이해할 때 확인할 기준

함수 호출과 스택 프레임을 설명할 때는 다음 질문을 순서대로 확인한다.

1. 지금 실행 중인 함수는 무엇인가?
2. 이 함수를 호출한 호출자는 무엇인가?
3. 아직 반환되지 않은 활성 호출은 어떤 순서로 중첩되어 있는가?
4. 각 호출에 속한 매개변수와 지역 객체는 무엇인가?
5. 어디까지가 C++ 언어의 규칙이고 어디부터가 ABI와 컴파일러의 구현인가?
6. 현재 빌드에서 인라인과 최적화가 적용됐는가?
7. 실제 실행 경로가 필요하다면 디버거의 호출 스택에서 무엇이 보이는가?

호출 스택은 실행 경로를 이해하는 모델이고, 스택 프레임은 그 호출을 구현하기 위한 실행 문맥이다. 두 개념을 같은 말처럼 사용하지 않으면 디버거와 어셈블리를 볼 때도 훨씬 정확하게 상황을 해석할 수 있다.

## 다음 학습: 이름의 범위와 객체의 수명

함수 호출마다 매개변수와 지역 객체는 독립적으로 존재하지만, 그 사실을 모든 값이 반드시 메모리 스택에 저장된다는 뜻으로 해석해서는 안 된다. 실제 프레임 구성은 호출 규약과 최적화에 따라 달라지고, 디버거의 호출 스택은 현재까지 이어진 활성 호출 관계를 보여준다.

다음 글에서는 함수와 블록 안에서 이름을 사용할 수 있는 범위, 객체가 살아 있는 기간, 값 매개변수가 원본과 분리되는 이유를 각각 스코프·수명·값 전달의 관점에서 구분한다.
