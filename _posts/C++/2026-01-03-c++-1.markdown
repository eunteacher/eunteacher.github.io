C++ 프로그램으로 `Hello World!`를 출력해 보고, 작성한 소스 코드가 어떤 과정을 거쳐 실행되는지 알아보자.

## 첫 C++ 프로그램

```cpp
#include <iostream>

int main()
{
    std::cout << "Hello World!\n";
    return 0;
}
```

실행 결과:

```text
Hello World!
```

코드의 역할을 간단히 나누면 다음과 같다.

| 코드 | 역할 |
|---|---|
| `#include <iostream>` | 표준 입출력에 필요한 선언을 가져온다. |
| `int main()` | 프로그램의 기본 실행 흐름이 시작되는 함수다. |
| `std::cout << "Hello World!\n";` | 표준 출력으로 `Hello World!`를 내보내고 줄을 바꾼다. |
| `return 0;` | 정상 종료 상태를 실행 환경에 전달한다. |

## `#include <iostream>`

`std::cout`을 사용하려면 컴파일러가 그것이 무엇인지 알아야 한다. 이를 위해 표준 입출력 헤더인 `<iostream>`을 포함한다.

```cpp
#include <iostream>
```

`#include`는 전처리 지시문이다. 소스 코드를 본격적으로 컴파일하기 전에, 지정한 헤더의 내용을 가져오는 역할을 한다.

헤더를 포함할 때는 다음 두 가지 표기를 볼 수 있다.

```cpp
#include <iostream>
#include "Player.h"
```

- `<iostream>`: 표준 라이브러리 헤더 등을 포함할 때 사용한다.
- `"Player.h"`: 직접 작성한 프로젝트 헤더 등을 포함할 때 사용한다.

두 표기는 헤더를 찾는 경로와 순서에 차이가 있다. 구체적인 검색 방식은 컴파일러와 프로젝트 설정에 따라 달라진다.

## 사용자 코드의 진입점 `main`

```cpp
int main()
{
    // 실행할 코드
}
```

일반적인 C++ 콘솔 프로그램에서는 `main` 함수부터 기본 실행 흐름을 따라가면 된다.

중괄호 `{ }` 안에 실행할 내용을 작성하며, 위 예제에서는 문자열을 출력한 다음 `return 0;`으로 함수를 끝낸다.

정확히는 운영체제가 프로그램을 불러오고 실행 환경을 준비하는 과정이 먼저 있다. 전역 객체의 초기화처럼 `main` 전에 실행되는 코드도 있지만, 처음에는 **“프로그램의 기본 실행 흐름은 `main`에서 시작한다”**고 이해하면 된다.

## `std::cout`으로 출력하기

```cpp
std::cout << "Hello World!\n";
```

`std::cout`은 표준 출력 스트림이다. 일반적인 콘솔 실행에서는 여기에 전달한 내용이 콘솔에 표시된다.

- `std::cout`: C++ 표준 라이브러리에서 제공하는 표준 출력 스트림
- `<<`: 오른쪽의 내용을 출력 스트림에 전달하는 연산자
- `"Hello World!\n"`: 출력할 문자열. 마지막의 `\n`은 줄바꿈을 나타낸다.

즉, **“`Hello World!`를 출력하고 다음 줄로 이동한다”**는 코드다.

## `return 0;`과 종료 상태

`main` 앞의 `int`는 정수를 반환한다는 뜻이다.

```cpp
return 0;
```

여기서 `0`은 화면에 출력되는 값이 아니라, 프로그램을 실행한 환경에 전달하는 종료 상태다. 정상적으로 실행을 마쳤다는 의미로 사용한다.

`main`은 특별히 마지막 중괄호까지 실행되면 `return 0;`을 생략해도 같은 의미로 처리된다.

```cpp
int main()
{
    std::cout << "Hello World!\n";
}
```

다만 처음에는 프로그램이 끝나는 지점을 명확하게 볼 수 있도록 직접 작성해 두어도 좋다.

## 소스 파일에서 실행 파일까지

작성한 `.cpp` 파일을 운영체제가 그대로 실행하는 것은 아니다. 소스 코드를 기계어로 바꾸고 필요한 코드를 연결해 실행 파일을 만들어야 한다.

프로그램을 만드는 과정을 **준비 → 번역 → 연결 → 실행**으로 생각하면 된다.

```text
소스 코드 작성
    ↓
필요한 헤더와 설정을 반영한다.          [전처리]
    ↓
C++ 코드를 기계어로 번역한다.          [컴파일·어셈블]
    ↓
다른 파일과 라이브러리 코드를 연결한다.  [링크]
    ↓
완성된 실행 파일을 실행한다.           [로드·실행]
```

예를 들어 `Hello World!`를 출력하는 프로그램이라면 다음과 같다.

1. `<iostream>`을 포함해 입출력에 필요한 선언을 준비한다.
2. `main`에 작성한 C++ 코드를 기계어로 번역한다.
3. 표준 라이브러리 등 실행에 필요한 코드와 연결한다.
4. 운영체제가 완성된 프로그램을 불러와 실행한다.

이처럼 소스 코드로 실행 파일 등의 결과물을 만드는 작업을 **빌드**라고 한다. **빌드와 실행은 별개의 작업**이다.

각 단계에서 어떤 일이 일어나는지 조금 더 살펴보자.

### 1. 전처리 — 컴파일할 내용을 준비한다

전처리 단계에서는 `#`으로 시작하는 지시문을 처리한다.

대표적인 작업은 다음과 같다.

- `#include`: 지정한 헤더의 내용을 포함한다.
- `#define`: 매크로를 정의하고, 코드에서 사용된 매크로를 치환한다.
- `#if`, `#ifdef`: 조건에 따라 컴파일할 내용을 선택한다.

예제에서는 다음 지시문이 처리된다.

```cpp
#include <iostream>
```

이 과정을 통해 컴파일러가 `std::cout` 등 입출력 관련 이름을 이해하는 데 필요한 선언을 볼 수 있게 된다.

단, **헤더를 포함하는 것과 라이브러리를 연결하는 것은 다른 작업**이다. 헤더에 정의가 들어 있는 경우도 있지만, `#include`만으로 모든 라이브러리의 구현이 소스 파일에 들어오는 것은 아니다.

### 2. 컴파일·어셈블 — 오브젝트 파일을 만든다

컴파일과 어셈블은 개념적으로 다음과 같이 나누어 이해하면 된다.

- **컴파일**: 전처리된 C++ 코드의 문법·타입 등을 검사하고, 어셈블리 코드로 변환한다.
- **어셈블**: 어셈블리 코드를 기계어로 변환해 **오브젝트 파일**을 만든다.

어셈블리 코드는 CPU가 수행할 명령을 사람이 읽을 수 있는 기호로 표현한 코드다. 즉, **컴파일은 어셈블리 코드로, 어셈블은 기계어로 바꾸는 단계**라고 기억하면 된다.

실제 도구에서는 이 과정이 통합되어 중간 어셈블리 파일이 따로 만들어지지 않을 수도 있다.

Visual Studio 환경에서는 보통 `.obj` 확장자를 사용한다.

```text
main.cpp
    ↓ 전처리·컴파일·어셈블
main.obj
```

오브젝트 파일에는 기계어 코드뿐 아니라, 이후 연결에 필요한 정보도 들어 있다. 아직 다른 파일에 있는 함수 등의 연결이 끝나지 않았을 수 있으므로, 일반적인 실행 파일처럼 바로 실행할 수는 없다.

여러 `.cpp` 파일이 있다면 각각 따로 컴파일된다.

```text
main.cpp   → main.obj
Player.cpp → Player.obj
```

이때 `.cpp` 파일 하나와 그 파일이 포함한 헤더 등을 전처리한 결과를 **번역 단위**라고 한다. 컴파일러는 이 번역 단위를 기준으로 코드를 처리한다.

### 3. 링크 — 나뉜 코드를 연결한다

링커는 오브젝트 파일과 필요한 라이브러리를 연결해 실행 파일을 만든다.

```text
main.obj ────┐
             │
Player.obj ──┼── 링크 → Game.exe
             │
라이브러리 ──┘
```

예를 들어 `main.cpp`에서 `Player.cpp`에 정의한 함수를 호출한다면, 컴파일 단계에서는 호출에 필요한 정보를 남겨 두고 링크 단계에서 실제 정의와 연결한다.

라이브러리 연결 방식에 따라 필요한 코드가 실행 파일에 포함되기도 하고, 실행할 때 별도의 동적 라이브러리를 사용하도록 연결되기도 한다.

중요한 점은 **각 소스 파일을 번역하는 작업과, 번역된 결과를 연결하는 작업이 나뉘어 있다**는 것이다.

### 4. 로드·실행 — 완성된 프로그램을 실행한다

실행 파일을 실행하면 운영체제가 프로그램의 코드와 데이터를 메모리에 배치하고, 실행에 필요한 환경을 준비한다.

이후 시작 코드와 런타임 초기화 등을 거쳐 `main`이 호출된다.

```text
Game.exe 실행
    ↓
운영체제가 프로그램을 메모리에 로드
    ↓
시작 코드 실행 및 초기화
    ↓
main 호출
    ↓
Hello World! 출력
    ↓
프로그램 종료
```

정리하면, **빌드는 실행할 프로그램을 만드는 과정이고, 실행은 만들어진 프로그램을 실제로 동작시키는 과정**이다.

## Visual Studio의 Solution과 Project

Visual Studio에서는 솔루션과 프로젝트를 구분한다.

- **프로젝트(Project)**: 소스 파일과 빌드 설정 등을 관리하는 단위다. 실행 파일이나 라이브러리 같은 결과물을 만든다.
- **솔루션(Solution)**: 하나 이상의 프로젝트를 묶어서 관리하는 단위다.

```text
솔루션
├── 게임 프로젝트
├── 도구 프로젝트
└── 테스트 프로젝트
```

처음에는 솔루션 하나에 콘솔 프로그램 프로젝트 하나를 만들어 사용하면 된다.

프로젝트가 여러 개라면 실행할 대상을 **시작 프로젝트**로 지정한다.

## 빌드·실행·디버깅의 차이

| 구분 | 의미 | Visual Studio 기본 단축키 |
|---|---|---|
| 빌드 | 소스 코드로 실행 파일 등의 결과물을 만든다. | `Ctrl + Shift + B` |
| 디버깅 없이 실행 | 디버거를 붙이지 않고 프로그램을 실행한다. | `Ctrl + F5` |
| 디버깅 시작 | 실행 중인 코드와 변수 등을 확인할 수 있도록 디버거를 붙여 실행한다. | `F5` |

단축키는 키보드 설정에 따라 달라질 수 있다.

실행 명령을 눌렀을 때 변경된 코드가 있다면 Visual Studio 설정에 따라 빌드가 먼저 진행될 수 있다. 그래서 한 번의 동작처럼 보이지만, 빌드와 실행은 구분되는 과정이다.

## `\n`과 `std::endl`의 차이

다음 두 코드는 모두 문자열 뒤에 줄바꿈을 넣는다.

```cpp
std::cout << "Hello World!\n";
std::cout << "Hello World!" << std::endl;
```

차이는 **출력 버퍼를 비우는 작업을 요청하는지**에 있다.

| 구분 | 동작 |
|---|---|
| `\n` | 줄바꿈 문자를 넣는다. |
| `std::endl` | 줄바꿈 문자를 넣고 출력 버퍼를 비운다. |

출력 버퍼는 출력할 내용을 잠시 모아 두는 공간이다. 버퍼를 비우는 **플러시(flush)**는 모아 둔 내용을 실제 출력 대상으로 전달하도록 요청하는 작업이다.

단순히 줄만 바꾸고 싶다면 `\n`을 사용하면 된다. `std::endl`을 반복해서 사용하면 매번 플러시를 요청하므로 출력이 많은 코드에서는 불필요한 비용이 생길 수 있다.

다만 `\n`을 사용했다고 출력이 반드시 버퍼에 남아 있는 것은 아니다. 버퍼가 비워지는 시점은 출력 환경과 스트림 설정 등의 영향도 받는다.

## 복습하며 정리한 내용

복습하면서 헷갈렸던 부분을 다시 정리했다. 단계별 이름을 외우는 것보다, 각 단계에서 무엇을 처리하고 어떤 결과가 나오는지 구분하는 게 중요했다.

### 1. C++ 코드에서 실행까지

작성한 C++ 코드가 실행되기까지의 과정은 크게 네 단계로 나눌 수 있다.

```text
전처리
  ↓
컴파일 + 어셈블
  ↓
링크
  ↓
로드 + 실행
```

- **전처리**: 헤더 포함, 매크로 치환, 조건부 컴파일을 처리한다.
- **컴파일 + 어셈블**: 전처리된 코드를 분석하고, 기계어 코드 등이 담긴 오브젝트 파일을 만든다.
- **링크**: 오브젝트 파일과 필요한 라이브러리를 연결해 실행 파일을 만든다.
- **로드 + 실행**: 운영체제가 프로그램을 메모리에 배치하고, 초기화 과정을 거쳐 실행한다.

여기서 **실행 파일을 만드는 과정까지가 빌드**이고, 만들어진 파일을 **로드해서 실행하는 것은 별개의 과정**이다.

### 2. Translation Unit과 Object File은 다르다

처음에는 번역 단위와 오브젝트 파일을 비슷하게 생각했는데, 서로 다른 단계의 결과다.

```text
.cpp + 포함된 헤더
        ↓ 전처리
Translation Unit
        ↓ 컴파일·어셈블
Object File (.obj)
```

**Translation Unit은 전처리를 거쳐 컴파일러가 처리하는 단위**이고, **Object File은 이를 컴파일·어셈블한 결과물**이다.

각 번역 단위를 독립적으로 컴파일하므로, `Player.cpp`만 수정했다면 해당 번역 단위를 다시 컴파일하고 링크할 수 있다. 전체 소스를 매번 다시 컴파일하지 않아도 되므로 빌드 시간을 줄일 수 있다.

다만 헤더를 수정하면 그 헤더를 포함하는 여러 번역 단위가 다시 컴파일될 수 있다.

그리고 `#include`는 파일을 연결한다는 느낌 때문에 헷갈릴 수 있지만, **링크가 아니라 전처리 단계**에 해당한다.

### 3. 선언과 정의는 서로 다른 역할을 한다

함수 선언은 컴파일러에 함수의 이름과 반환형, 매개변수 타입을 알려준다.

```cpp
void Attack();
```

호출하는 위치에서 이 선언을 알고 있다면, 함수의 몸통이 다른 `.cpp`에 있어도 호출 코드를 컴파일할 수 있다.

실제 동작을 작성한 부분은 정의다.

```cpp
void Attack()
{
}
```

각 소스 파일을 컴파일한 뒤, 호출한 함수의 실제 정의를 연결하는 작업은 링크 단계에서 이루어진다.

```text
Player.obj ─┐
Enemy.obj  ─┼─→ 링크 → Game.exe
Game.obj   ─┤
라이브러리 ─┘
```

선언을 보고 호출 코드를 컴파일하는 것과, 실제 정의를 찾아 연결하는 것은 다른 작업이다.

### 4. 컴파일 오류·링크 오류·런타임 문제

오류도 어느 단계에서 발생했는지 나눠서 생각하니 이해하기 쉬웠다.

#### 컴파일 오류

문법이나 타입 등이 맞지 않아 코드를 정상적으로 컴파일할 수 없는 경우다.

```cpp
int hp = "Hello";
```

정수 변수에 문자열을 넣으려 하므로 타입이 맞지 않는다.

함수 선언을 모르는 상태에서 호출하는 것도 컴파일 오류다.

```cpp
int main()
{
    Attack(); // 이 위치에서 Attack의 선언을 찾을 수 없다.
}
```

#### 링크 오류

선언이 있어 호출 코드는 컴파일했지만, 필요한 정의를 링크 단계에서 찾지 못하는 경우다.

```cpp
void Attack();

int main()
{
    Attack();
}
```

이 코드와 연결되는 다른 소스 파일이나 라이브러리에도 `Attack()`의 정의가 없다면 링크 오류가 발생한다.

#### 런타임 문제

컴파일과 링크를 통과해 실행 파일이 만들어졌더라도, 실행 중 문제가 생길 수 있다.

```cpp
int* ptr = nullptr;
*ptr = 10;
```

널 포인터를 역참조하는 코드는 **정의되지 않은 동작**을 일으킨다. 실행 중 충돌할 수 있지만, 반드시 일정한 방식으로 오류가 난다고 보장되는 것은 아니다.

함수 호출 예제를 기준으로 간단히 기억하면 다음과 같다.

> 선언을 찾을 수 없다 → 컴파일 오류  
> 호출한 함수의 정의를 찾을 수 없다 → 링크 오류  
> 실행 중 잘못된 동작을 한다 → 런타임 문제

물론 각 단계의 오류가 이 경우에만 해당하는 것은 아니다.

### 5. 선언·정의의 일치와 인자 변환은 별개다

다음 선언과 정의는 서로 짝이 맞지 않는다.

```cpp
void TakeDamage(int);

void TakeDamage(float)
{
}
```

`TakeDamage(int)`와 `TakeDamage(float)`는 매개변수 타입이 다른 별개의 함수다.

따라서 `int` 버전을 호출하면서 해당 정의를 제공하지 않으면 링크 오류가 발생할 수 있다. 이름이 같다고 `float` 버전의 정의로 연결되는 것은 아니다.

반면 다음은 다른 상황이다.

```cpp
void TakeDamage(float);

int main()
{
    TakeDamage(10);
}

void TakeDamage(float damage)
{
}
```

여기서는 선언과 정의가 모두 `float`로 일치한다. 호출할 때 전달한 정수 `10`이 `float`로 변환된다.

즉, **선언과 정의가 일치하는지**와 **호출할 때 인자가 변환될 수 있는지**는 구분해서 봐야 한다.

### 6. `main`과 실제 Entry Point는 구분한다

`main`이 프로그램의 시작점이라고만 생각했는데, 실행 파일의 실제 Entry Point와는 구분할 필요가 있었다.

일반적인 C++ 실행 환경의 흐름은 다음과 같다.

```text
실행 파일
    ↓
운영체제가 코드와 데이터를
프로세스의 가상 메모리에 배치
    ↓
실제 Entry Point에서 실행 시작
    ↓
런타임 초기화
    ↓
main 호출
```

운영체제가 `main`이라는 함수 이름을 찾아 직접 호출하는 것은 아니다. 실행 파일에 기록된 Entry Point에서 시작하고, 초기화 과정을 거쳐 `main`이 호출된다.

또한 전역 객체의 초기화처럼 `main` 전에 실행되는 사용자 코드도 있다. 따라서 `main`은 **일반적인 프로그램의 기본 실행 흐름을 작성하는 진입점**으로 이해해 두었다.

### 7. `std::endl`은 줄바꿈만 하는 것이 아니다

```cpp
std::cout << "Hello\n";
std::cout << "Hello" << std::endl;
```

둘 다 줄바꿈을 하지만, `std::endl`은 출력 버퍼를 비우는 **플러시(flush)**도 요청한다.

플러시는 버퍼에 모아 둔 출력을 출력 대상으로 내보내도록 하는 작업이다.

- `\n`: 줄바꿈 문자를 출력한다.
- `std::endl`: 줄바꿈 문자를 출력하고 플러시한다.

단순히 줄만 바꾸려면 `\n`을 사용하면 된다. 반복적인 출력에서 `std::endl`을 사용하면 매번 플러시를 요청하므로 불필요한 비용이 생길 수 있다.

다만 `\n`을 사용하더라도 출력 환경이나 스트림 설정에 따라 버퍼가 비워질 수 있다. 차이는 **줄바꿈과 함께 플러시를 명시적으로 요청하느냐**에 있다.
