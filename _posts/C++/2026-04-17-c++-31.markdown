C++ 21편에서는 Text RPG의 전역 상태를 구조체로 묶고, 피해 계산과 상태 변경을 각각의 함수로 분리했다. 이번 원본 코드는 여기서 한 단계 더 나아가 구조체 안에 생성자와 멤버 함수를 추가한다.

데이터와 함수가 같은 구조체 안에 있다는 사실만으로 설계가 자동으로 안전해지는 것은 아니다. 빈 기본 생성자가 초기화되지 않은 능력치를 만들고, 피해 계산 순서가 잘못되면 높은 방어력이 체력을 회복시키는 버그도 생긴다.

이번 글에서는 문법을 나열하기보다 `Stats` 객체가 스스로 지켜야 할 조건을 먼저 정하고, 생성자와 멤버 함수가 그 조건을 어떻게 유지하는지 살펴본다.

## 외부 함수에서 객체의 동작으로 이동한다

상태와 동작을 완전히 분리하면 다음과 같은 구조가 된다.

```cpp
struct Stats
{
    int hp;
    int attack;
    int defense;
};

int CalculateDamage(const Stats& target, int incomingAttack);
void ApplyDamage(Stats& target, int damage);
bool IsDead(const Stats& target);
```

이 방식은 각 함수의 입력과 변경 대상을 명확히 보여준다. 반면 호출자는 항상 올바른 순서로 함수를 조합해야 한다.

```cpp
int damage = CalculateDamage(monster.stats, player.stats.attack);
ApplyDamage(monster.stats, damage);
```

피해 계산과 체력 변경이 언제나 한 동작으로 실행돼야 한다면 `Stats`의 멤버 함수로 묶을 수 있다.

```cpp
int damage = monster.stats.TakeDamage(player.stats.attack);
```

호출 형태만 봐도 몬스터의 능력치가 공격을 받아 상태를 변경한다는 관계가 드러난다.

멤버 함수는 단순히 함수 위치를 구조체 안으로 옮기는 문법이 아니다. 특정 타입의 상태를 읽거나 변경하는 동작을 그 타입의 인터페이스로 만든다.

## 구조체도 생성자와 멤버 함수를 가질 수 있다

C++의 `struct`는 데이터만 담는 문법으로 제한되지 않는다.

```cpp
struct Stats
{
    int hp;
    int attack;
    int defense;

    Stats(int hp, int attack, int defense);
    int TakeDamage(int incomingAttack);
    bool IsDead() const;
};
```

이 구조체에는 세 종류의 멤버가 있다.

| 종류 | 예 | 역할 |
| :--- | :--- | :--- |
| 데이터 멤버 | `hp`, `attack`, `defense` | 객체가 보관하는 상태 |
| 생성자 | `Stats(...)` | 객체가 만들어질 때 초기 상태 설정 |
| 멤버 함수 | `TakeDamage`, `IsDead` | 해당 객체의 상태를 사용하거나 변경 |

`struct`의 멤버는 기본적으로 `public`이다. 따라서 원본 코드의 `public:` 접근 지정자는 동작을 바꾸지 않는다.

```cpp
struct Stats
{
public:
    int hp;
};
```

`class`는 멤버와 기반 클래스의 기본 접근이 `private`이고 `struct`는 `public`이라는 차이가 있지만, 둘 다 생성자와 멤버 함수를 가질 수 있다. 어떤 키워드를 사용했는지만으로 객체 지향 여부가 결정되는 것은 아니다.

## 생성자는 반환 타입을 적지 않는다

생성자는 타입과 같은 이름을 사용하며 반환 타입을 선언하지 않는다.

```cpp
struct Stats
{
    Stats(int hp, int attack, int defense)
    {
    }
};
```

다음 선언은 인자와 일치하는 생성자를 호출해 객체를 만든다.

```cpp
Stats knightStats(200, 40, 10);
Stats mageStats{180, 55, 8};
```

중괄호 초기화도 같은 생성자를 호출한다. 이번 예제에서는 값 목록의 경계를 보기 쉬워 중괄호를 사용한다.

생성자의 목적은 객체를 만든 다음 나중에 채우는 것이 아니라, 객체가 존재하기 시작하는 순간 필요한 상태를 갖게 하는 것이다.

## 멤버는 생성자 본문보다 멤버 초기화 목록에서 초기화한다

원본 생성자는 본문에서 각 멤버에 대입한다.

```cpp
Stats(int hp, int attack, int defense)
{
    this->hp = hp;
    this->attack = attack;
    this->defense = defense;
}
```

이 코드는 기본 타입 멤버에서 원하는 값을 만들 수 있다. 하지만 생성자 본문이 실행되기 전에 데이터 멤버의 초기화 단계가 이미 진행된다.

멤버 초기화 목록을 사용하면 각 멤버를 원하는 값으로 직접 초기화한다.

```cpp
Stats(int hp, int attack, int defense) : hp(hp), attack(attack), defense(defense)
{
}
```

콜론 뒤 표현식은 다음 관계를 나타낸다.

```text
멤버 hp       <- 매개변수 hp
멤버 attack   <- 매개변수 attack
멤버 defense  <- 매개변수 defense
```

`const` 멤버, 참조 멤버와 기본 생성할 수 없는 멤버 객체는 생성자 본문에서 나중에 대입하는 방식으로 설정할 수 없으므로 초기화 목록이 반드시 필요하다.

이번 `int` 멤버에서는 결과 차이가 눈에 띄지 않을 수 있지만 모든 멤버를 일관된 방식으로 초기화하는 습관을 만들 수 있다.

## 같은 이름은 `this` 또는 초기화 위치로 구분한다

생성자 매개변수와 데이터 멤버 이름이 같으면 함수 본문에서 매개변수가 우선 보인다.

```cpp
this->hp = hp;
```

왼쪽 `this->hp`는 현재 객체의 데이터 멤버이고 오른쪽 `hp`는 생성자 매개변수다.

비정적 멤버 함수에는 현재 함수를 호출한 객체를 가리키는 `this` 포인터가 있다.

```text
knightStats.TakeDamage(20)
        │
        └─ TakeDamage 안의 this는 knightStats를 가리킴
```

멤버 초기화 목록에서는 다음처럼 작성할 수 있다.

```cpp
Stats(int hp, int attack, int defense) : hp(hp), attack(attack), defense(defense)
{
}
```

각 `hp(hp)`의 첫 번째 이름은 초기화할 멤버가 오는 자리이고 괄호 안 이름은 매개변수 표현식이다.

모든 멤버 접근에 `this->`를 붙여야 하는 것은 아니다.

```cpp
bool IsDead() const
{
    return hp == 0;
}
```

이름 충돌을 구분해야 하거나 현재 객체의 포인터를 명시적으로 전달할 때 `this`가 필요하다. 단순 접근에서는 생략하는 편이 자연스럽다.

## 빈 기본 생성자는 정수 멤버를 안전하게 만들지 않는다

원본 코드에는 본문이 비어 있는 기본 생성자가 있다.

```cpp
Stats()
{
}
```

이 생성자가 호출돼도 `hp`, `attack`, `defense`에 값이 대입되지 않는다. 자동 저장 기간의 객체라면 기본 타입 멤버에 정해지지 않은 값이 남을 수 있다.

```cpp
Stats stats;
// stats.hp를 읽을 수 있는 유효한 게임 상태라고 가정하면 안 된다.
```

빈 생성자를 작성했다는 사실과 멤버가 0으로 초기화됐다는 사실은 다르다.

기본 상태가 실제로 의미 있다면 기본 멤버 초기값을 지정할 수 있다.

```cpp
struct Stats
{
    int hp = 0;
    int attack = 0;
    int defense = 0;
};
```

하지만 체력과 능력치를 반드시 전달해야만 유효한 캐릭터를 만들 수 있다면 기본 생성 자체를 제공하지 않는 편이 계약을 더 정확하게 표현한다.

```cpp
struct Stats
{
    Stats() = delete;
    Stats(int hp, int attack, int defense) : hp(hp), attack(attack), defense(defense) {}

    int hp;
    int attack;
    int defense;
};
```

사용자 선언 생성자가 하나라도 있으면 컴파일러가 인자 없는 기본 생성자를 자동으로 제공하지 않는다. 따라서 이번 최종 구현에서는 `Stats() = delete`를 따로 적지 않고 인자 세 개를 받는 생성자만 선언한다.

## 플레이어도 생성 즉시 유효한 상태를 갖게 한다

원본 코드는 먼저 빈 플레이어를 만든 뒤 선택 함수가 값을 대입한다.

```cpp
Player player;
CreatePlayer(player);
```

사용자가 올바른 직업을 선택하기 전까지 `player`의 타입과 능력치는 유효하게 초기화되지 않을 수 있다. 현재 흐름에서 그 값을 먼저 읽지 않도록 조심하더라도 객체 자체는 불완전한 상태로 존재한다.

선택 결과로 완성된 플레이어를 반환하면 생성과 유효 상태가 같은 시점에 이루어진다.

```cpp
Player player = MakePlayer(PlayerType::Knight);
```

플레이어 타입도 생성자를 통해 설정한다.

```cpp
struct Player
{
    Player(PlayerType type, Stats stats) : type(type), stats(stats) {}

    PlayerType type;
    Stats stats;
};
```

`Stats`에 기본 생성자가 없으므로 `Player` 생성자는 `stats`를 초기화 목록에서 직접 초기화해야 한다.

## 생성자는 입력값을 객체의 조건에 맞게 정리할 수 있다

게임 능력치에 음수 값을 허용하지 않는다고 정하면 생성자가 그 조건을 적용할 수 있다.

```cpp
#include <algorithm>

Stats(int hp, int attack, int defense) : hp(std::max(0, hp)), attack(std::max(0, attack)), defense(std::max(0, defense))
{
}
```

이 생성자를 통과한 직후에는 다음 조건을 기대한다.

```text
hp >= 0
attack >= 0
defense >= 0
```

음수 입력을 0으로 보정하는 정책이 항상 정답인 것은 아니다. 잘못된 입력을 예외나 오류 결과로 거절할 수도 있다. 중요한 점은 어떤 정책을 선택했는지 생성 경계에서 일관되게 적용하는 것이다.

이번 학습 예제는 작은 정수 능력치를 사용하고 음수를 0으로 보정한다. 실제 게임에서는 허용 가능한 최댓값과 정수 오버플로우 가능성도 별도 규칙으로 정해야 한다.

## 원본 피해 계산은 방어력이 높으면 체력을 회복시킨다

원본 `Attacked`는 체력을 먼저 변경한 다음 피해량이 음수인지 검사한다.

```cpp
int Attacked(int incomingAttack)
{
    hp = hp - (incomingAttack - defense);

    if (incomingAttack - defense < 0)
    {
        return 0;
    }

    return incomingAttack - defense;
}
```

공격력 5, 방어력 10, 현재 체력 100을 대입하면 계산은 다음과 같다.

```text
incomingAttack - defense = 5 - 10 = -5
hp = 100 - (-5)
hp = 105
```

함수는 이후에 0을 반환하지만 이미 체력은 5 증가했다. 반환값만 보정해서는 먼저 발생한 잘못된 상태 변경을 되돌릴 수 없다.

필요한 순서는 다음과 같다.

```text
1. 실제 피해량을 0 이상으로 계산한다.
2. 계산된 피해량만 체력에서 뺀다.
3. 체력이 0 아래로 내려가지 않게 제한한다.
4. 실제로 감소한 체력을 반환한다.
```

상태를 변경하기 전에 입력과 계산 결과를 먼저 유효한 범위로 정리해야 한다.

## 피해량 계산은 상태를 읽기만 하는 멤버 함수로 둔다

같은 공격력과 방어력으로 예상 피해량만 확인할 수 있도록 계산을 분리한다.

```cpp
int CalculateDamage(int incomingAttack) const
{
    return incomingAttack > defense ? incomingAttack - defense : 0;
}
```

함수 뒤의 `const`는 이 멤버 함수가 현재 객체의 비정적 데이터 멤버를 변경하지 않는다는 계약이다.

```cpp
const Stats armored{100, 20, 10};
int damage = armored.CalculateDamage(5);
```

`const Stats` 객체에서도 호출할 수 있으며 결과는 0이다. `const`를 생략한 멤버 함수는 기본적으로 객체 상태를 변경할 가능성이 있으므로 `const` 객체에서 호출할 수 없다.

같은 이름의 함수라도 다음 두 `const`는 위치와 의미가 다르다.

```cpp
int CalculateDamage(int incomingAttack) const;
```

- 매개변수 앞에는 `const`가 없다. `incomingAttack`은 값으로 복사된 정수다.
- 함수 뒤의 `const`는 현재 `Stats` 객체를 이 함수를 통해 변경하지 않겠다는 뜻이다.

## 피해 적용은 한 번의 멤버 함수 호출로 완성한다

실제 상태 변경 함수는 계산 결과를 사용한다.

```cpp
int TakeDamage(int incomingAttack)
{
    int damage = CalculateDamage(incomingAttack);
    int previousHp = hp;
    hp = std::max(0, hp - damage);
    return previousHp - hp;
}
```

반환값은 공식상 피해량이 아니라 실제로 감소한 체력이다.

```text
현재 hp = 10, 계산 피해량 = 30
변경 후 hp = 0
실제로 감소한 hp = 10
```

이 구분은 과도한 피해량을 화면에 표시하거나 흡혈처럼 실제 감소량에 의존하는 규칙을 추가할 때 중요할 수 있다.

`TakeDamage`는 다음 조건을 유지한다.

- 방어력이 공격력보다 높아도 체력이 증가하지 않는다.
- 체력은 0보다 작아지지 않는다.
- 반환 피해량은 음수가 아니다.
- 이미 체력이 0이라면 추가로 감소한 양은 0이다.

## 사망 판정은 객체를 변경하지 않는다

사망 여부는 체력을 읽어서 판단한다.

```cpp
bool IsDead() const
{
    return hp == 0;
}
```

생성자와 `TakeDamage`가 `hp >= 0` 조건을 항상 유지하므로 `hp == 0`으로 판정할 수 있다.

만약 구조체의 public 멤버를 외부 코드가 직접 음수로 바꿀 수 있다면 이 조건은 깨질 수 있다. 이번 단계에서는 구조체 문법을 유지하되 모든 체력 변경을 `TakeDamage`로 모으는 사용 규칙을 따른다.

더 강한 강제가 필요해지면 멤버를 `private`으로 옮기고 읽기·변경 인터페이스만 공개하는 클래스로 발전시킬 수 있다. 접근 제한은 문법을 복잡하게 만들기 위한 것이 아니라 유효 상태를 깨뜨리는 경로를 줄이는 수단이다.

## 팩토리 함수는 종류를 구체적인 능력치로 변환한다

생성자는 전달받은 능력치를 유효한 `Stats` 객체로 만든다. 직업마다 어떤 능력치를 사용할지는 별도의 팩토리 함수가 결정한다.

```cpp
Player MakePlayer(PlayerType type)
{
    switch (type)
    {
    case PlayerType::Knight:
        return Player{type, Stats{200, 40, 10}};
    case PlayerType::Mage:
        return Player{type, Stats{180, 55, 8}};
    case PlayerType::Archer:
        return Player{type, Stats{160, 45, 6}};
    }

    throw std::invalid_argument("Unknown player type");
}
```

역할은 다음처럼 나뉜다.

| 구성 요소 | 책임 |
| :--- | :--- |
| `Stats` 생성자 | 능력치를 유효한 범위로 초기화 |
| `Player` 생성자 | 플레이어 종류와 능력치를 하나의 객체로 결합 |
| `MakePlayer` | 직업별 초기 능력치 선택 |

원본에는 `CreatePlayer(Player&)`와 `CreatePlayer(PlayerType, ...)`처럼 같은 이름의 함수가 서로 다른 생성 흐름을 담당했다. 오버로딩 자체는 가능하지만 입력 처리와 객체 생성을 이름으로 구분하면 호출 흐름을 더 쉽게 읽을 수 있다.

## 플레이어와 몬스터의 공통 상태만 재사용한다

플레이어와 몬스터 모두 능력치를 가지지만 종류를 나타내는 열거형은 서로 다르다.

```cpp
enum class PlayerType
{
    Knight,
    Mage,
    Archer
};

enum class MonsterType
{
    Orc,
    Goblin,
    Skeleton
};
```

공통 능력치는 `Stats`로 재사용하고 개체별 종류는 각 구조체가 보관한다.

```cpp
struct Player
{
    Player(PlayerType type, Stats stats) : type(type), stats(stats) {}

    PlayerType type;
    Stats stats;
};

struct Monster
{
    Monster(MonsterType type, Stats stats) : type(type), stats(stats) {}

    MonsterType type;
    Stats stats;
};
```

아직 두 구조체의 모양이 비슷하더라도 무조건 하나의 상속 계층으로 만들 필요는 없다. 현재 요구사항에서 공통으로 재사용할 대상은 능력치와 피해 규칙이며, 이를 `Stats` 멤버 객체로 조합했다.

기능이 추가되어 플레이어만 경험치와 장비를 가지고 몬스터만 보상과 인공지능 상태를 갖게 되면 두 타입은 자연스럽게 다른 방향으로 확장될 수 있다.

## 전투 코드는 객체가 제공하는 동작을 조합한다

멤버 함수를 사용하면 한 번의 공격을 다음처럼 표현한다.

```cpp
int damage = monster.stats.TakeDamage(player.stats.attack);
```

이 호출에서 역할은 분명하다.

```text
공격력 제공: player.stats.attack
피해 규칙과 상태 변경: monster.stats.TakeDamage(...)
변경 대상: monster.stats.hp
결과: 실제 감소한 체력
```

전투 전체 흐름은 플레이어와 몬스터의 멤버 함수를 순서대로 조합한다.

```cpp
BattleResult Fight(Player& player, Monster monster)
```

플레이어는 전투 뒤 남은 체력을 유지해야 하므로 참조로 받고, 몬스터는 이번 전투에서만 사용하는 복사본으로 받는다.

멤버 함수를 만들었다고 해서 전투의 모든 책임을 `Stats`에 넣지는 않는다. 누가 먼저 공격하는지, 언제 전투를 끝내는지와 승패 결과는 개별 능력치보다 상위 규칙이므로 `Fight`가 담당한다.

## 피해가 전혀 없으면 반복문이 끝나지 않을 수 있다

플레이어와 몬스터의 공격력이 상대 방어력보다 모두 낮으면 어느 쪽 체력도 줄지 않는다.

```text
플레이어가 주는 피해 = 0
몬스터가 주는 피해   = 0
```

단순히 `while (!IsDead())`를 반복하면 사망 조건이 영원히 성립하지 않는다. 전투를 시작하기 전에 예상 피해량을 확인해 교착 상태를 별도 결과로 처리한다.

```cpp
int playerDamage = monster.stats.CalculateDamage(player.stats.attack);
int monsterDamage = player.stats.CalculateDamage(monster.stats.attack);

if (playerDamage == 0 && monsterDamage == 0)
{
    return BattleResult::Stalemate;
}
```

이 내용은 21편에서 외부 함수로 확인했던 규칙과 같다. 이번에는 `Stats`의 읽기 전용 멤버 함수가 같은 조건을 제공한다는 점만 연결한다.

## 고정된 상태로 생성자와 멤버 함수를 검증한다

사용자 입력과 난수를 제외하면 능력치 규칙을 독립적으로 확인할 수 있다.

```cpp
#include <cassert>

void VerifyStats()
{
    Stats armored{100, 20, 10};
    int blockedDamage = armored.TakeDamage(5);
    assert(blockedDamage == 0);
    assert(armored.hp == 100);

    Stats target{10, 0, 3};
    int appliedDamage = target.TakeDamage(100);
    assert(appliedDamage == 10);
    assert(target.hp == 0);
    assert(target.IsDead());

    Stats corrected{-10, -20, -30};
    assert(corrected.hp == 0);
    assert(corrected.attack == 0);
    assert(corrected.defense == 0);
}
```

첫 번째 검사는 원본 코드의 체력 회복 버그가 다시 발생하지 않는지 확인한다. 두 번째 검사는 체력이 0 아래로 내려가지 않고 실제 감소량을 반환하는지 확인한다. 세 번째 검사는 생성자의 음수 보정 정책을 확인한다.

`assert`는 `NDEBUG`가 정의된 빌드에서 제거될 수 있으므로 반드시 실행해야 하는 게임 입력 검증이나 오류 처리 수단으로 사용하지 않는다.

## 전체 예제로 구조체가 상태 조건을 유지하게 한다

이번 글의 핵심만 확인할 수 있도록 메뉴 입력과 난수 생성을 제외한 전투 예제를 구성한다.

```cpp
#include <algorithm>
#include <cassert>
#include <iostream>
#include <stdexcept>

enum class PlayerType
{
    Knight,
    Mage,
    Archer
};

enum class MonsterType
{
    Orc,
    Goblin,
    Skeleton
};

enum class BattleResult
{
    Victory,
    Defeat,
    Stalemate
};

struct Stats
{
    Stats(int hp, int attack, int defense) : hp(std::max(0, hp)), attack(std::max(0, attack)), defense(std::max(0, defense)) {}

    int CalculateDamage(int incomingAttack) const
    {
        return incomingAttack > defense ? incomingAttack - defense : 0;
    }

    int TakeDamage(int incomingAttack)
    {
        int damage = CalculateDamage(incomingAttack);
        int previousHp = hp;
        hp = std::max(0, hp - damage);
        return previousHp - hp;
    }

    bool IsDead() const
    {
        return hp == 0;
    }

    int hp;
    int attack;
    int defense;
};

struct Player
{
    Player(PlayerType type, Stats stats) : type(type), stats(stats) {}

    PlayerType type;
    Stats stats;
};

struct Monster
{
    Monster(MonsterType type, Stats stats) : type(type), stats(stats) {}

    MonsterType type;
    Stats stats;
};

Player MakePlayer(PlayerType type)
{
    switch (type)
    {
    case PlayerType::Knight:
        return Player{type, Stats{200, 40, 10}};
    case PlayerType::Mage:
        return Player{type, Stats{180, 55, 8}};
    case PlayerType::Archer:
        return Player{type, Stats{160, 45, 6}};
    }

    throw std::invalid_argument("Unknown player type");
}

Monster MakeMonster(MonsterType type)
{
    switch (type)
    {
    case MonsterType::Orc:
        return Monster{type, Stats{150, 25, 6}};
    case MonsterType::Goblin:
        return Monster{type, Stats{75, 10, 2}};
    case MonsterType::Skeleton:
        return Monster{type, Stats{100, 20, 4}};
    }

    throw std::invalid_argument("Unknown monster type");
}

BattleResult Fight(Player& player, Monster monster)
{
    int playerDamage = monster.stats.CalculateDamage(player.stats.attack);
    int monsterDamage = player.stats.CalculateDamage(monster.stats.attack);

    if (playerDamage == 0 && monsterDamage == 0)
    {
        return BattleResult::Stalemate;
    }

    while (true)
    {
        int appliedDamage = monster.stats.TakeDamage(player.stats.attack);
        std::cout << "Player dealt " << appliedDamage << " damage.\n";

        if (monster.stats.IsDead())
        {
            return BattleResult::Victory;
        }

        appliedDamage = player.stats.TakeDamage(monster.stats.attack);
        std::cout << "Monster dealt " << appliedDamage << " damage.\n";

        if (player.stats.IsDead())
        {
            return BattleResult::Defeat;
        }
    }
}

void VerifyStats()
{
    Stats armored{100, 20, 10};
    int blockedDamage = armored.TakeDamage(5);
    assert(blockedDamage == 0);
    assert(armored.hp == 100);

    Stats target{10, 0, 3};
    int appliedDamage = target.TakeDamage(100);
    assert(appliedDamage == 10);
    assert(target.hp == 0);
    assert(target.IsDead());

    Stats corrected{-10, -20, -30};
    assert(corrected.hp == 0);
    assert(corrected.attack == 0);
    assert(corrected.defense == 0);
}

int main()
{
    VerifyStats();

    Player player = MakePlayer(PlayerType::Knight);
    Monster monster = MakeMonster(MonsterType::Orc);
    BattleResult result = Fight(player, monster);

    if (result == BattleResult::Victory)
    {
        std::cout << "Victory\n";
    }
    else if (result == BattleResult::Defeat)
    {
        std::cout << "Defeat\n";
    }
    else
    {
        std::cout << "Stalemate\n";
    }
}
```

이 예제는 `Stats`의 생성자와 멤버 함수에 집중하기 위해 다음 요소를 의도적으로 제외했다.

- 사용자 메뉴 입력과 입력 실패 복구
- 난수를 사용한 몬스터 선택
- 여러 몬스터를 보관하는 배열
- 로비와 게임 화면의 상태 전환

이 기능들은 21편에서 이미 다뤘거나 이번 글의 핵심과 다른 변경 이유를 가진다. 긴 원본 코드를 모두 유지하는 것보다 구조체가 어떤 조건을 책임지는지 확인할 수 있는 범위만 남겼다.

## 생성자와 멤버 함수를 적용할 때 확인할 기준

1. 객체가 생성된 직후 모든 멤버가 유효한 값을 가지는가?
2. 빈 기본 생성자가 초기화되지 않은 기본 타입 멤버를 남기지 않는가?
3. 생성자 본문의 대입보다 멤버 초기화 목록이 적합하지 않은가?
4. `this`가 실제로 이름 충돌을 구분할 때만 사용되는가?
5. 객체를 읽기만 하는 멤버 함수에 `const`가 붙어 있는가?
6. 상태를 변경하기 전에 계산 결과를 유효한 범위로 정리하는가?
7. 반환한 피해량이 공식상 피해인지 실제 감소량인지 계약이 분명한가?
8. 체력과 능력치가 허용 범위를 벗어나는 경로가 남아 있지 않은가?
9. 생성자, 팩토리 함수와 입력 함수의 책임을 구분했는가?
10. 객체 하나의 규칙과 전투 전체의 진행 규칙을 한 타입에 몰아넣지 않았는가?

구조체 안에 함수를 넣는 목적은 관련 있어 보이는 코드를 한곳에 모으는 데서 끝나지 않는다. 객체가 생성될 때부터 유효한 상태를 갖고, 공개된 동작을 거친 뒤에도 그 조건을 유지하도록 만드는 것이 핵심이다.
