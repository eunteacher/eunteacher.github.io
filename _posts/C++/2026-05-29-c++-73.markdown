`std::unique_ptr`는 소유자가 한 명인 객체에 가장 명확한 선택이다. 하지만 하나의 동적 객체가 여러 독립적인 작업이나 객체에 의해 함께 소유되어야 하고, 마지막 소유자가 사라질 때까지 살아 있어야 하는 경우도 있다.

`std::shared_ptr<T>`는 같은 제어 블록을 공유하는 소유자의 수를 관리한다. 마지막 공유 소유자가 사라지면 관리 객체를 삭제한다. `std::weak_ptr<T>`는 같은 제어 블록을 관찰하지만 소유자 수를 늘리지 않으며, 객체가 아직 살아 있는지 확인한 뒤 임시 공유 소유권을 얻을 수 있다.

공유 포인터의 핵심은 자동 삭제보다 **누가 객체의 수명을 연장할 권한을 가져야 하는지** 구분하는 데 있다. 모든 포인터를 `shared_ptr`로 바꾸면 수명 문제는 사라지는 것이 아니라 소유 관계가 보이지 않게 되고 순환 참조라는 새로운 문제가 생길 수 있다.

## shared_ptr은 객체와 제어 블록을 함께 관리한다

`shared_ptr`의 동작을 이해하려면 관리 객체와 제어 블록(control block)을 구분해야 한다.

```text
shared_ptr A ─┐
              ├─→ 제어 블록 ─→ 관리 객체
shared_ptr B ─┘      │
                     ├─ 공유 소유 정보
                     ├─ weak 관찰 정보
                     └─ deleter 및 allocator 관련 상태
```

`shared_ptr` 복사본들은 같은 제어 블록을 공유한다. 제어 블록은 관리 객체의 삭제 시점과 자신이 유지될 시점을 판단하는 데 필요한 정보를 가진다.

구체적인 카운터 타입, 메모리 배치와 weak 관련 내부 숫자 계산은 표준 라이브러리 구현 세부 사항이다. 프로그램은 다음 공개 계약에 의존한다.

- 공유 소유자가 하나 이상이면 관리 객체가 살아 있다.
- 마지막 공유 소유자가 사라지면 관리 객체가 지정된 deleter로 삭제된다.
- `weak_ptr`가 남아 있으면 객체 삭제 후에도 관찰 상태를 판별할 제어 정보가 유지될 수 있다.
- 마지막 weak 관찰자까지 사라지면 제어 블록도 정리된다.

원본처럼 `_refCount`, `_weakCount`를 정수 두 개로 단순화한 모델은 개념 설명에는 도움이 되지만 표준 구현의 정확한 구조라고 볼 수 없다.

## make_shared로 공유 객체를 만든다

일반적인 생성은 `std::make_shared`를 사용한다.

```cpp
auto knight = std::make_shared<Knight>(100, 10);
```

객체 생성자 인자를 전달하며 예외가 발생해도 소유권이 중간에 유실되지 않는다. 일반적인 구현에서는 관리 객체와 제어 블록을 하나의 메모리 할당으로 구성할 수 있어 다음 직접 생성보다 할당 횟수와 지역성 측면에서 유리할 수 있다.

```cpp
std::shared_ptr<Knight> knight(new Knight(100, 10));
```

`make_shared`가 항상 모든 상황에 맞는 것은 아니다.

- 사용자 정의 deleter를 직접 지정해야 한다.
- 객체와 제어 블록의 할당 방식을 분리해야 한다.
- 큰 객체가 삭제된 뒤에도 `weak_ptr` 때문에 결합 할당 영역이 유지되는 것이 부담스럽다.
- 생성자 접근 제어 때문에 팩토리 구조를 별도로 설계해야 한다.

기본적인 공유 객체에는 `make_shared`를 우선하고, 다른 수명·할당 정책이 실제로 필요할 때 생성자를 직접 사용한다.

## 복사하면 같은 객체의 소유자가 늘어난다

`shared_ptr`는 복사할 수 있다.

```cpp
auto first = std::make_shared<Knight>();
auto second = first;

assert(first.get() == second.get());
```

객체를 깊게 복사한 것이 아니라 같은 객체와 제어 블록의 공유 소유권을 복사한 것이다. 한 포인터를 통해 객체를 수정하면 다른 포인터에서도 같은 변경을 본다.

```cpp
first->SetHp(50);
assert(second->GetHp() == 50);
```

`use_count()`로 현재 공유 소유자 수를 관찰할 수 있다.

```cpp
assert(first.use_count() == 2);
```

하지만 `use_count()`는 진단과 학습에는 유용해도 프로그램의 핵심 동기화나 소유권 분기 조건으로 사용하기 어렵다. 값을 읽은 직후 다른 스레드나 코드에서 소유자가 늘거나 줄 수 있고, 정확히 1이라는 사실이 관리 객체에 대한 다른 비소유 접근까지 없다는 뜻도 아니다.

## 이동은 소유자 수를 늘리지 않는다

`shared_ptr`도 이동할 수 있다.

```cpp
auto first = std::make_shared<Knight>();
auto second = std::move(first);

assert(first == nullptr);
assert(second.use_count() == 1);
```

기존 공유 소유권을 새 `shared_ptr` 객체로 옮기므로 소유자 수를 추가하지 않는다. 복사와 이동 중 어떤 의미가 필요한지 함수 인터페이스에서 구분한다.

## 함수 인자는 수명 의도를 드러내야 한다

함수가 호출 이후에도 객체의 수명을 연장해야 한다면 `shared_ptr`을 값으로 받아 복사하거나 이동해 저장할 수 있다.

```cpp
void Schedule(std::shared_ptr<Task> task)
{
    pendingTasks.push_back(std::move(task));
}
```

함수가 호출 동안 객체만 관찰한다면 `const T&` 또는 `T*`가 더 직접적이다.

```cpp
void PrintTask(const Task& task);
void SetOptionalTarget(Task* target);
```

공유 소유자의 복사를 피하면서 특정 API가 `shared_ptr` 자체를 관찰해야 한다면 `const std::shared_ptr<T>&`를 사용할 수 있지만, 단순 객체 접근에 습관적으로 요구하면 호출자가 반드시 공유 소유 방식을 사용하도록 결합된다.

```text
shared_ptr<T> 값      : 공유 소유권을 획득하거나 전달할 가능성
const shared_ptr<T>&  : shared_ptr 핸들 자체를 관찰
T&                    : null이 아닌 객체를 비소유 관찰
T*                    : null 가능 객체를 비소유 관찰
weak_ptr<T>           : 나중에 사용할 수 있지만 수명은 연장하지 않는 관찰
```

## 같은 원시 포인터로 shared_ptr을 두 번 만들면 안 된다

다음 코드는 매우 위험하다.

```cpp
Knight* raw = new Knight;

std::shared_ptr<Knight> first(raw);
std::shared_ptr<Knight> second(raw);
```

두 `shared_ptr`은 서로를 알지 못하는 독립적인 제어 블록을 만든다.

```text
first  ─→ 제어 블록 A ─→ raw
second ─→ 제어 블록 B ─→ raw
```

각 제어 블록은 자신이 마지막 소유자가 됐을 때 같은 `raw`를 삭제하므로 이중 해제가 발생한다.

하나의 `shared_ptr`을 먼저 만든 뒤 복사한다.

```cpp
auto first = std::make_shared<Knight>();
auto second = first;
```

원시 포인터에서 새로운 공유 소유권을 시작하는 지점은 정확히 한 번이어야 한다.

## 직접 만든 참조 카운팅 포인터는 예외 경로가 많다

원본의 학습용 `SharedPtr` 복사 대입은 새 포인터와 제어 블록을 덮어쓴 뒤 새 참조 횟수만 증가시킨다.

```cpp
_ptr = other._ptr;
_block = other._block;
++_block->_refCount;
```

대입 대상이 이전에 소유하던 객체의 참조 횟수를 먼저 감소시키지 않으므로 그 객체와 제어 블록이 누수될 수 있다. 자기 대입, 이동, 빈 포인터, 예외, 사용자 정의 deleter, weak 관찰과 스레드 안전성까지 처리하려면 구현이 훨씬 복잡해진다.

참조 횟수만 맞추면 표준 `shared_ptr`과 같아지는 것이 아니다. 직접 구현은 원리를 이해하는 실습으로 한정하고 실제 소유권에는 검증된 표준 타입을 사용한다.

## weak_ptr은 소유하지 않는 관찰자다

`weak_ptr`는 `shared_ptr`에서 만들 수 있지만 공유 소유자 수를 늘리지 않는다.

```cpp
auto owner = std::make_shared<Knight>();
std::weak_ptr<Knight> observer = owner;

assert(owner.use_count() == 1);
```

`weak_ptr`만으로 객체를 역참조할 수 없다. 관찰하는 동안 마지막 소유자가 사라질 수 있기 때문이다.

```cpp
// observer->Attack(); // 직접 접근 불가
```

객체가 살아 있다면 `lock()`으로 임시 `shared_ptr`을 얻는다.

```cpp
if (auto locked = observer.lock())
{
    locked->Attack();
}
```

성공한 `locked`는 자신의 수명이 끝날 때까지 객체가 삭제되지 않도록 공유 소유권을 유지한다. 이미 객체가 삭제됐다면 빈 `shared_ptr`을 반환한다.

## expired 검사보다 lock 결과를 바로 확인한다

`expired()`는 관찰 대상이 이미 삭제됐는지 알려 준다.

```cpp
bool gone = observer.expired();
```

하지만 다음처럼 검사와 획득을 분리하면 둘 사이에 다른 스레드나 코드에서 마지막 소유자가 사라질 수 있다.

```cpp
if (!observer.expired())
{
    auto locked = observer.lock();
    // locked가 반드시 비어 있지 않다고 별도 가정하면 안 됨
}
```

필요한 것은 “살아 있다는 사실 확인”이 아니라 “사용하는 동안 수명을 확보한 포인터”이므로 `lock()` 결과를 직접 검사한다.

```cpp
if (auto locked = observer.lock())
{
    locked->Attack();
}
```

`expired()`는 상태 표시나 진단에 사용할 수 있지만 안전한 접근에는 `lock()`이 핵심이다.

## shared_ptr끼리 순환하면 객체가 소멸하지 않는다

두 객체가 서로를 `shared_ptr`로 소유한다고 하자.

```cpp
class Knight
{
public:
    std::shared_ptr<Knight> target;
};

auto first = std::make_shared<Knight>();
auto second = std::make_shared<Knight>();

first->target = second;
second->target = first;
```

```text
외부 first  ─→ Knight A ─shared→ Knight B
외부 second ─→ Knight B ─shared→ Knight A
```

외부의 `first`와 `second`가 사라져도 A는 B가, B는 A가 서로를 소유한다. 두 객체의 공유 소유자 수가 0이 되지 않아 자동 삭제되지 않는다.

참조 카운팅은 도달할 수 없는 순환 그래프를 가비지 컬렉터처럼 발견하지 않는다. 공유 소유 관계에 방향을 정하고 한쪽을 비소유 관찰로 만들어야 한다.

## 부모는 자식을 소유하고 자식은 부모를 관찰한다

트리 구조에서는 부모가 자식을 `shared_ptr`로 소유하고 자식은 부모를 `weak_ptr`로 관찰할 수 있다.

```cpp
class Node
{
public:
    std::vector<std::shared_ptr<Node>> children;
    std::weak_ptr<Node> parent;
};
```

```text
Parent ──shared──→ Child
Parent ←──weak──── Child
```

부모가 사라지면 자식의 weak 관찰은 만료되며 부모 수명을 억지로 연장하지 않는다. 자식이 부모를 사용하려면 `lock()`으로 일시적인 공유 소유권을 얻는다.

```cpp
if (auto parent = child->parent.lock())
{
    parent->Update();
}
```

어느 방향을 weak로 만들지는 자료구조의 실제 소유 의미에 따라 결정한다. 순환을 발견한 뒤 임의로 한쪽을 weak로 바꾸는 것이 아니라 누가 누구의 생존을 책임지는지 먼저 정의한다.

## enable_shared_from_this는 기존 제어 블록을 재사용한다

객체가 멤버 함수 안에서 자신을 가리키는 `shared_ptr`을 얻어야 할 수 있다. 다음 방식은 사용하면 안 된다.

```cpp
std::shared_ptr<Node> GetSelf()
{
    return std::shared_ptr<Node>(this);
}
```

이미 외부 `shared_ptr`이 객체를 소유한다면 `this`로 새 `shared_ptr`을 만드는 순간 독립 제어 블록이 생겨 이중 해제 위험이 발생한다.

`std::enable_shared_from_this<T>`를 상속하고 `shared_from_this()`를 사용하면 기존 제어 블록을 공유하는 포인터를 얻을 수 있다.

```cpp
class Node : public std::enable_shared_from_this<Node>
{
public:
    void AddChild(const std::shared_ptr<Node>& child)
    {
        child->parent = shared_from_this();
        children.push_back(child);
    }

    std::vector<std::shared_ptr<Node>> children;
    std::weak_ptr<Node> parent;
};
```

객체가 먼저 `shared_ptr`의 소유 대상이어야 한다.

```cpp
auto node = std::make_shared<Node>();
```

스택 객체나 아직 공유 소유되지 않은 객체에서 `shared_from_this()`를 호출하면 `std::bad_weak_ptr`가 발생할 수 있다. C++17의 `weak_from_this()`는 비소유 관찰 포인터가 필요할 때 사용할 수 있다.

생성자 안에서도 아직 외부 공유 소유 설정이 완성되지 않았으므로 `shared_from_this()`를 호출하지 않는다. 팩토리로 생성한 뒤 별도 초기화 단계에서 연결한다.

## shared_ptr은 객체 접근을 자동으로 스레드 안전하게 만들지 않는다

같은 제어 블록을 공유하는 서로 다른 `shared_ptr` 객체의 복사와 소멸을 여러 스레드에서 수행할 수 있도록 참조 카운팅 관리가 설계돼 있다. 그러나 관리 대상 `T`의 멤버 접근까지 자동으로 동기화하지 않는다.

```cpp
auto shared = std::make_shared<Counter>();
```

여러 스레드가 `shared->value`를 동시에 수정한다면 `Counter` 자체에 mutex나 atomic 같은 동기화가 필요하다.

같은 하나의 `shared_ptr` 변수 객체를 여러 스레드가 동시에 비상수 변경하는 것도 별도 동기화 없이 안전하지 않다. 공유 포인터 변수의 원자적 교체가 필요하면 C++20의 `std::atomic<std::shared_ptr<T>>` 같은 도구를 검토한다.

```text
제어 블록의 소유자 수 관리 ≠ 관리 객체 T의 스레드 안전성
```

참조 카운팅의 원자 연산 자체도 비용이 있으므로 공유 소유가 필요하지 않은 곳에 `shared_ptr`을 기본 선택으로 쓰지 않는다.

## use_count는 객체 사용 가능 여부를 대신하지 않는다

`use_count() == 1`이면 현재 관찰한 순간 해당 제어 블록의 공유 소유자가 하나라는 뜻이다. 다음을 보장하지 않는다.

- 다른 스레드가 곧 소유권을 복사하지 않는다.
- 원시 포인터나 참조로 접근하는 코드가 없다.
- 관리 객체를 동기화 없이 수정해도 안전하다.
- 소유자가 하나뿐이어야 하는 도메인 불변식이 유지된다.

객체 접근 가능 여부는 보유한 `shared_ptr` 자체로 판단하고, weak 관찰에서는 `lock()` 결과로 판단한다. `use_count`에 맞춘 비즈니스 로직은 경쟁 상태와 결합되기 쉽다.

## 별칭 shared_ptr은 소유 객체와 가리키는 주소가 다를 수 있다

`shared_ptr`에는 다른 객체의 제어 블록을 공유하면서 그 객체의 멤버 주소를 가리키는 별칭 생성자가 있다.

```cpp
struct Player
{
    Inventory inventory;
};

auto player = std::make_shared<Player>();
std::shared_ptr<Inventory> inventory(player, &player->inventory);
```

`inventory.get()`은 `Inventory*`를 반환하지만 소유권은 `player`의 제어 블록과 연결돼 있다. `inventory`가 남아 있는 동안 전체 `Player` 객체가 살아 있다.

따라서 `shared_ptr`의 저장 포인터가 같다는 사실과 소유권이 같은 제어 블록이라는 사실은 엄밀히 다른 개념이다. 일반 코드에서는 별칭 생성자가 드물지만 `get()` 주소만 보고 소유 관계를 추측하면 안 되는 이유다.

## 사용자 정의 deleter는 제어 블록에 보관된다

`shared_ptr`도 사용자 정의 deleter를 사용할 수 있다.

```cpp
std::shared_ptr<Resource> resource(OpenResource(), ResourceDeleter{});
```

deleter 타입이 `shared_ptr<T>`의 템플릿 인자에 나타나는 `unique_ptr`과 달리, shared deleter는 제어 블록에 타입 소거되어 보관된다. 서로 다른 deleter를 가진 포인터도 같은 `std::shared_ptr<Resource>` 타입으로 다룰 수 있다.

deleter는 마지막 공유 소유자가 사라질 때 정확히 관리 객체를 정리해야 하며 예외를 밖으로 던지지 않아야 한다. `make_shared`에는 별도 사용자 정의 deleter를 전달할 수 없다.

## 전체 구현

부모가 자식을 공유 소유하고 자식이 부모를 weak로 관찰하는 구조에서 소유자 수와 만료 시점을 확인한다.

```cpp
#include <cassert>
#include <iostream>
#include <memory>
#include <string>
#include <utility>
#include <vector>

class Node : public std::enable_shared_from_this<Node>
{
public:
    explicit Node(std::string name) : name_(std::move(name)) { ++aliveCount; }
    ~Node() { --aliveCount; }

    void AddChild(const std::shared_ptr<Node>& child)
    {
        child->parent_ = shared_from_this();
        children_.push_back(child);
    }

    const std::string& name() const noexcept { return name_; }
    std::weak_ptr<Node> parent() const noexcept { return parent_; }
    std::size_t childCount() const noexcept { return children_.size(); }

    inline static int aliveCount = 0;

private:
    std::string name_;
    std::vector<std::shared_ptr<Node>> children_;
    std::weak_ptr<Node> parent_;
};

int main()
{
    auto root = std::make_shared<Node>("Root");
    auto child = std::make_shared<Node>("Child");

    root->AddChild(child);

    assert(root.use_count() == 1);
    assert(child.use_count() == 2);
    assert(root->childCount() == 1);
    assert(Node::aliveCount == 2);

    auto rootCopy = root;
    assert(root.use_count() == 2);

    std::cout << "Root owners after copy: " << root.use_count() << '\n';
    std::cout << "Child owners in tree: " << child.use_count() << '\n';

    rootCopy.reset();
    std::weak_ptr<Node> parentObserver = child->parent();

    if (auto parent = parentObserver.lock())
    {
        std::cout << "Parent from weak pointer: " << parent->name() << '\n';
    }

    root.reset();

    assert(parentObserver.expired());
    assert(parentObserver.lock() == nullptr);
    assert(Node::aliveCount == 1);

    std::cout << std::boolalpha;
    std::cout << "Parent expired after root reset: " << parentObserver.expired() << '\n';
    std::cout << "Nodes alive with child owner: " << Node::aliveCount << '\n';

    child.reset();

    assert(Node::aliveCount == 0);
    std::cout << "Nodes alive after all owners reset: " << Node::aliveCount << '\n';
}
```

실행 결과는 다음과 같다.

```text
Root owners after copy: 2
Child owners in tree: 2
Parent from weak pointer: Root
Parent expired after root reset: true
Nodes alive with child owner: 1
Nodes alive after all owners reset: 0
```

`root`와 `rootCopy`가 같은 제어 블록을 소유하므로 부모의 공유 소유자 수는 2다. 자식은 지역 변수 `child`와 부모의 `children_` 벡터가 함께 소유해 공유 소유자 수가 2다. 자식의 부모 포인터는 weak이므로 부모 소유자 수를 늘리지 않는다.

`rootCopy`를 비운 뒤 weak 포인터를 `lock()`하면 임시 공유 소유권을 얻어 부모 이름을 안전하게 읽는다. `root`까지 비우면 부모가 삭제되고 그 벡터가 가지고 있던 자식 소유권도 해제된다. 외부 `child`만 남아 자식 하나가 살아 있으며, 부모 weak 관찰은 만료된다. 마지막 `child`를 비우면 모든 노드가 삭제된다.

## shared_ptr와 weak_ptr을 사용할 때 확인할 기준

1. 단독 소유로 충분한데 `shared_ptr`을 기본 선택하지 않았는가?
2. 실제로 서로 독립적인 여러 소유자가 객체 수명을 연장해야 하는가?
3. 기본 공유 객체는 `make_shared`로 만들 수 있는가?
4. `shared_ptr` 복사가 객체 복제가 아니라 공유 소유권 복사임을 아는가?
5. 소유권을 늘릴 필요가 없는 함수는 객체 참조나 포인터를 받는가?
6. 같은 원시 포인터로 독립적인 제어 블록을 두 개 만들지 않는가?
7. 직접 만든 참조 카운팅 포인터보다 표준 구현을 사용하는가?
8. 관찰 관계에는 공유 소유권을 늘리지 않는 `weak_ptr`이 적합한가?
9. weak 객체 접근에서 `expired()`와 사용을 분리하지 않고 `lock()` 결과를 확인하는가?
10. 공유 소유 관계 그래프에 `shared_ptr` 순환이 없는가?
11. 부모·자식처럼 어느 방향이 수명을 책임지는지 먼저 정했는가?
12. 객체 내부에서 공유 자기 참조가 필요하면 `enable_shared_from_this`를 올바르게 사용하는가?
13. `shared_from_this()` 호출 전에 객체가 shared 소유 상태인지 확인했는가?
14. 참조 카운팅과 관리 객체의 스레드 안전성을 혼동하지 않는가?
15. `use_count()`를 동기화나 비즈니스 불변식 판단에 의존하지 않는가?

`shared_ptr`의 핵심은 여러 포인터가 같은 주소를 가리키는 데 있지 않다. 여러 소유자가 같은 제어 블록을 통해 하나의 수명을 공동으로 책임지는 데 있다. 소유하지 않는 관계까지 공유 포인터로 만들면 참조 횟수는 객체 그래프의 순환을 끊지 못한다. 수명을 책임지는 방향은 `shared_ptr`, 관찰만 하는 반대 방향은 `weak_ptr`로 표현해야 한다.

## C++ 기초 시리즈를 마치며

배열과 포인터에서 시작해 객체 수명, 템플릿, STL 컨테이너, 반복자, 이동 의미론과 스마트 포인터까지 이어졌다. 뒤쪽 주제들을 관통하는 기준은 문법 자체보다 다음 세 가지였다.

```text
누가 자원을 소유하는가?
객체와 참조는 언제까지 유효한가?
복사·이동·삭제 뒤 어떤 불변식이 유지되는가?
```

표준 컨테이너와 스마트 포인터는 이 질문에 대한 검증된 정책을 타입과 인터페이스로 제공한다. 직접 구현은 내부 원리를 이해하는 학습에 사용하고, 실제 코드에서는 소유권과 수명 의도가 가장 잘 드러나는 표준 도구를 선택한다.
