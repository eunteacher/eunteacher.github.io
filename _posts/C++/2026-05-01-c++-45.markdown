`Weapon`과 `Armor`를 `Item`의 한 종류로 설계하면 서로 다른 아이템을 `Item*` 또는 `Item&`로 다룰 수 있다. 이 과정에서는 객체 자체를 다른 타입으로 만드는 것이 아니라 같은 객체의 기반 클래스 부분을 가리키도록 포인터나 참조가 변환된다.

파생 타입에서 기반 타입으로 가는 변환은 상속 관계가 보장하지만 반대 방향은 실제 객체 타입을 추가로 확인해야 한다. 기반 포인터로 동적 객체를 제거한다면 소멸자 설계도 타입 변환만큼 중요하다.

## 포인터 변환은 객체 복사가 아니다

동적으로 생성한 `Weapon`을 가리키는 포인터가 있다.

```cpp
Weapon* weapon = new Weapon;
Item* item = weapon;
```

두 번째 줄에서 `Weapon` 객체가 복사되어 별도의 `Item` 객체가 만들어지는 것은 아니다. 두 포인터가 하나의 객체를 서로 다른 타입의 인터페이스로 바라본다.

```text
Weapon* ─┐
         ├─ 같은 Weapon 객체
Item*   ─┘  └─ 내부의 Item 기반 클래스 부분
```

공개 상속 관계에서 `Weapon*`를 `Item*`로 바꾸는 변환은 암시적으로 허용된다.

```cpp
class Weapon : public Item
{
};
```

다중 상속이나 가상 상속에서는 기반 클래스 부분의 위치에 맞춰 포인터 값이 조정될 수 있다. 따라서 변환 전후 포인터의 숫자 주소가 언제나 같다고 가정하지 않는다. C++ 변환 규칙이 올바른 기반 클래스 부분을 가리키게 한다는 점에 의존한다.

## 파생 타입에서 기반 타입으로 가는 업캐스팅

파생 클래스는 기반 클래스의 한 종류이므로 다음 변환은 자연스럽다.

```cpp
Weapon weapon;
Item* itemPointer = &weapon;
Item& itemReference = weapon;
```

이를 흔히 업캐스팅(Upcasting)이라고 부른다. 접근 가능한 모호하지 않은 공개 기반 클래스라면 명시적인 캐스트 없이 변환할 수 있다.

함수는 구체적인 아이템 타입 대신 기반 참조를 받을 수 있다.

```cpp
void UseItem(const Item& item)
{
    item.Use();
}
```

```cpp
Weapon weapon;
Armor armor;

UseItem(weapon);
UseItem(armor);
```

`Use`가 가상 함수라면 실제 객체에 맞는 최종 재정의가 실행된다. 호출하는 쪽에서는 아이템 종류를 검사하고 직접 캐스팅할 필요가 없다.

## 기반 타입에서 파생 타입으로 가는 다운캐스팅은 조건이 필요하다

모든 무기는 아이템이지만 모든 아이템이 무기는 아니다.

```cpp
Item* item = GetItem();
// Weapon* weapon = item; // 암시적 변환 불가
```

기반 포인터만 보고 실제 객체가 `Weapon`이라고 확정할 수 없으므로 반대 방향은 암시적으로 허용되지 않는다.

강제 캐스트를 작성하면 컴파일되는 경우가 있지만 실제 객체가 대상 파생 타입이라는 사실까지 만들어 주지는 않는다.

```cpp
Item* item = new Armor;
// Weapon* weapon = (Weapon*)item;
// weapon->Sharpen(); // 실제 객체는 Armor이므로 올바른 Weapon 사용이 아님
```

잘못 변환된 포인터로 파생 클래스 멤버에 접근하면 동작이 정의되지 않는다. 명시적으로 작성했다는 이유만으로 안전한 변환이 되는 것이 아니다.

## 동작이 필요하다면 다운캐스팅보다 가상 함수를 먼저 검토한다

원본 코드는 아이템 종류 값을 확인한 뒤 각각의 파생 타입으로 변환한다.

```cpp
if (item->Type() == ItemType::Weapon)
{
    Weapon* weapon = (Weapon*)item;
    weapon->PrintDamage();
}
```

타입 태그와 실제 객체 타입이 항상 일치하도록 직접 유지해야 한다. 새로운 아이템이 추가될 때 조건문도 계속 수정된다.

각 아이템이 수행할 동작을 가상 함수로 정의하면 타입 판단을 객체에 맡길 수 있다.

```cpp
class Item
{
public:
    virtual void Describe() const = 0;
};

class Weapon : public Item
{
public:
    void Describe() const override;
};

class Armor : public Item
{
public:
    void Describe() const override;
};
```

호출 코드는 기반 인터페이스만 사용한다.

```cpp
item->Describe();
```

파생 타입 고유의 데이터가 정말 필요한 상황이라면 런타임 검사가 가능한 `dynamic_cast`를 검토할 수 있다. 포인터 변환이 실패하면 null을 반환하며, 기반 클래스는 가상 함수를 하나 이상 가진 다형적 타입이어야 한다.

```cpp
if (Weapon* weapon = dynamic_cast<Weapon*>(item))
{
    weapon->Sharpen();
}
```

캐스트 종류별 조건과 비용은 이후 명명 캐스트 편에서 자세히 다룬다. 먼저 공통 동작을 가상 함수로 표현할 수 없는지 확인한다.

## 값 변환은 객체 슬라이싱을 만들 수 있다

포인터나 참조 업캐스팅은 원래 파생 객체를 유지한다. 반면 `Item`이 직접 생성 가능한 구체 기반 클래스라고 가정하면 파생 객체를 기반 클래스 값으로 복사할 때 기반 부분만 새 객체에 복사된다.

```cpp
Weapon weapon;
Item copiedItem = weapon;
```

이를 객체 슬라이싱(Object slicing)이라고 한다. `copiedItem`은 더 이상 `Weapon` 객체가 아니며 무기 고유 멤버도 포함하지 않는다.

값 매개변수도 복사를 만든다.

```cpp
void InspectItem(Item item);

InspectItem(itemObject);
InspectItem(*itemPointer);
```

원본 코드의 설명과 달리 두 호출 모두 값 매개변수 `item`을 만들기 위해 복사가 필요하다. 포인터를 역참조했다는 이유로 복사가 사라지는 것은 아니다.

다형성을 유지하고 복사를 피하려면 참조 또는 포인터를 받는다.

```cpp
void InspectItem(const Item& item);
void InspectItem(const Item* item);
```

추상 기반 클래스는 애초에 값 매개변수나 기반 객체를 직접 만들 수 없으므로 참조·포인터 인터페이스를 사용하게 된다.

## 기반 포인터로 delete하려면 기반 소멸자가 가상이어야 한다

파생 객체를 기반 포인터에 저장한 뒤 제거한다.

```cpp
Item* item = new Weapon;
delete item;
```

`Item` 소멸자가 가상이면 실제 객체 타입에 맞춰 `Weapon` 소멸자가 먼저 호출되고 `Item` 소멸자가 이어진다.

```cpp
class Item
{
public:
    virtual ~Item() = default;
};
```

```text
~Weapon() → ~Item()
```

기반 소멸자가 가상이 아닌 상태에서 기반 포인터로 파생 객체를 `delete`하면 동작이 정의되지 않는다. 파생 클래스가 가진 자원이 정리되지 않는 정도로 끝난다고 보장할 수도 없다.

```cpp
class Item
{
public:
    ~Item(); // 가상 소멸자가 아님
};

Item* item = new Weapon;
// delete item; // 정의되지 않은 동작
```

반대로 `Weapon*`로 `Weapon` 객체를 제거하면 정적 타입 자체가 파생 타입이므로 파생 소멸자와 기반 소멸자가 정상적으로 호출된다. 문제가 되는 조건은 파생 객체를 가리키는 기반 포인터를 통해 제거하는 경우다.

## 가상 소멸자는 다형적 기반 클래스의 계약이다

기반 클래스에 다른 가상 함수가 있다는 것은 기반 포인터나 참조를 통해 파생 객체를 사용할 가능성이 높다는 뜻이다. 그 인터페이스를 통해 소유 객체까지 제거할 수 있다면 소멸자도 가상이어야 한다.

```cpp
class Item
{
public:
    virtual ~Item() = default;
    virtual void Use() const = 0;
};
```

소멸자에 `virtual`을 붙이는 목적은 모든 소멸자를 무조건 느리게 만드는 것이 아니라 기반 타입을 통한 제거를 올바르게 지원한다는 계약을 만드는 것이다.

기반 포인터를 통한 제거를 허용하지 않을 설계라면 보호된 비가상 소멸자로 제한하는 방식도 있다. 외부에서 기반 포인터를 소유하고 삭제할 수 있는 공개 인터페이스라면 공개 가상 소멸자를 사용하는 것이 일반적이다.

파생 소멸자에는 `virtual`을 다시 적지 않아도 가상성이 이어진다. 재정의 의도를 명확히 하려면 `override`를 사용할 수 있다.

```cpp
class Weapon : public Item
{
public:
    ~Weapon() override = default;
};
```

## 관련 없는 포인터 타입은 강제로 연결하지 않는다

상속 관계가 없는 `Knight*`와 `Item*` 사이에는 일반적인 객체 관계가 없다.

```cpp
Knight* knight = new Knight;
// Item* item = (Item*)knight;
```

캐스트가 주소의 비트 값을 전달할 수 있더라도 그 주소에 `Item` 객체가 생기는 것은 아니다. 변환된 포인터로 `Item` 멤버를 사용하면 존재하지 않는 객체를 해당 타입으로 접근하게 된다.

두 시스템이 데이터를 주고받아야 한다면 명시적인 변환 함수나 별도의 데이터 타입을 설계한다. 객체 주소를 관련 없는 포인터 타입으로 강제 변환해 클래스 관계를 대신하지 않는다.

## 객체 배열과 포인터 배열은 전혀 다른 구조다

`Item`이 추상 클래스가 아닌 원본 형태라고 가정할 때 다음 배열은 `Item` 객체 100개를 배열 안에 직접 포함한다.

```cpp
Item items[100];
```

다음 배열은 `Item*` 포인터 100개만 포함하며 실제 아이템 객체를 생성하지 않는다.

```cpp
Item* itemPointers[100]{};
```

포인터 배열의 각 요소가 동적 객체를 소유한다면 모든 요소를 정확히 한 번씩 해제해야 한다. 중간에 할당이 실패하거나 함수가 일찍 끝나는 경우까지 직접 처리해야 한다.

```cpp
for (int i = 0; i < 100; ++i)
{
    delete itemPointers[i];
}
```

`delete nullptr`는 안전하지만 각 포인터가 유효한 단일 객체를 소유한다는 조건은 여전히 필요하다. 실제 코드에서는 `std::vector<std::unique_ptr<Item>>`처럼 컨테이너와 스마트 포인터를 조합하면 배열과 각 객체의 수명을 자동으로 관리할 수 있다.

## 전체 구현

기반 포인터를 통해 서로 다른 아이템의 가상 함수를 호출하고 안전하게 제거하는 예제다.

```cpp
#include <cassert>
#include <iostream>

class Item
{
public:
    Item()
    {
        ++aliveCount_;
        std::cout << "Item()\n";
    }

    Item(const Item&) = delete;
    Item& operator=(const Item&) = delete;

    virtual ~Item()
    {
        --aliveCount_;
        std::cout << "~Item()\n";
    }

    virtual void Describe() const = 0;

    static int AliveCount()
    {
        return aliveCount_;
    }

private:
    inline static int aliveCount_ = 0;
};

class Weapon final : public Item
{
public:
    explicit Weapon(int damage) : damage_(damage)
    {
        std::cout << "Weapon()\n";
    }

    ~Weapon() override
    {
        std::cout << "~Weapon()\n";
    }

    void Describe() const override
    {
        std::cout << "Weapon damage: " << damage_ << '\n';
    }

private:
    int damage_;
};

class Armor final : public Item
{
public:
    explicit Armor(int defense) : defense_(defense)
    {
        std::cout << "Armor()\n";
    }

    ~Armor() override
    {
        std::cout << "~Armor()\n";
    }

    void Describe() const override
    {
        std::cout << "Armor defense: " << defense_ << '\n';
    }

private:
    int defense_;
};

void InspectItem(const Item& item)
{
    item.Describe();
}

void VerifyWeapon()
{
    Item* item = new Weapon{35};
    assert(Item::AliveCount() == 1);

    InspectItem(*item);
    delete item;
    item = nullptr;

    assert(Item::AliveCount() == 0);
}

void VerifyArmor()
{
    Item* item = new Armor{12};
    assert(Item::AliveCount() == 1);

    InspectItem(*item);
    delete item;
    item = nullptr;

    assert(Item::AliveCount() == 0);
}

int main()
{
    VerifyWeapon();
    VerifyArmor();
}
```

실행 결과는 다음과 같다.

```text
Item()
Weapon()
Weapon damage: 35
~Weapon()
~Item()
Item()
Armor()
Armor defense: 12
~Armor()
~Item()
```

`item`의 정적 타입은 두 함수 모두 `Item*`이지만 `Describe`는 실제 객체에 맞는 함수를 선택한다. `delete item`도 가상 소멸자를 통해 파생 소멸자와 기반 소멸자를 차례대로 호출한다.

검증이 끝날 때마다 살아 있는 `Item` 기반 부분의 수가 0인지 확인해 기반 포인터를 통한 소멸이 완료됐음을 확인한다.

## 상속 포인터를 검토할 때 확인할 기준

1. 포인터 변환과 객체 값 복사를 구분하는가?
2. 파생 타입에서 기반 타입으로 가는 공개 업캐스팅인가?
3. 다운캐스팅하려는 실제 객체 타입을 확실히 검증할 수 있는가?
4. 파생 타입별 행동을 가상 함수로 옮겨 캐스트를 제거할 수 있는가?
5. 타입 태그와 실제 객체 타입을 중복 관리하고 있지 않은가?
6. 값 매개변수로 다형적 객체를 복사해 슬라이싱을 만들지 않는가?
7. 기반 포인터를 통해 제거할 수 있다면 기반 소멸자가 가상인가?
8. `new[]`로 만든 배열과 객체별 `new`를 담은 포인터 배열을 구분하는가?
9. 관련 없는 클래스 포인터를 주소가 같다는 이유로 강제 변환하지 않는가?

상속 포인터 변환의 핵심은 주소 형식을 억지로 맞추는 것이 아니다. 실제 객체 안에 존재하는 기반 클래스 부분으로 관점을 넓히고, 다시 좁힐 때는 동적 타입이 그 가정을 만족하는지 확인하는 것이다.
