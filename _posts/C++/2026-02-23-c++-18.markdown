앞에서는 함수 호출마다 매개변수와 지역 객체가 독립적으로 존재하고, 그 실행 문맥을 일반적으로 호출 프레임으로 관리한다는 점을 살펴봤다. 여기서 “지역 변수는 블록을 벗어나면 사용할 수 없다”와 “지역 객체는 함수가 끝나면 소멸한다”를 같은 규칙처럼 외우기 쉽다.

하지만 **이름을 사용할 수 있는 범위**, **객체가 살아 있는 기간**, **호출자와 같은 객체인지 여부**는 서로 다른 문제다. 이 차이를 구분해야 `static` 지역 변수, 전역 상태, 댕글링 포인터와 값 전달도 정확히 이해할 수 있다.

## 먼저 네 가지 질문을 분리한다

변수를 볼 때는 다음 질문을 따로 확인한다.

1. 이 이름을 코드의 어느 위치에서 사용할 수 있는가?
2. 이 이름이 가리키는 객체는 언제 생성되고 소멸하는가?
3. 객체의 저장 공간은 어떤 규칙으로 유지되는가?
4. 함수의 매개변수는 호출자의 원본과 같은 객체인가?

각 질문에 대응하는 개념이 다르다.

| 질문 | 중심 개념 |
| :--- | :--- |
| 이름을 어디에서 찾을 수 있는가? | 스코프(Scope) |
| 객체가 언제부터 언제까지 존재하는가? | 수명(Lifetime) |
| 저장 공간이 얼마나 오래 유지되는가? | 저장 기간(Storage duration) |
| 호출자와 같은 객체를 사용하는가? | 값·참조·포인터 전달 방식 |

스코프와 수명이 자주 함께 끝나는 경우가 많지만 항상 같은 것은 아니다.

## 스코프는 이름을 사용할 수 있는 범위다

스코프는 객체가 메모리의 어디에 놓였는지를 설명하지 않는다. 선언한 **이름이 소스 코드의 어느 영역에서 유효한지**를 정한다.

```cpp
int main()
{
    int playerHp = 100;

    if (playerHp > 0)
    {
        int damage = 20;
        playerHp -= damage;
    }

    // damage는 이 위치에서 찾을 수 없다.
}
```

`damage`의 이름은 자신이 선언된 `if` 블록 안에서만 사용할 수 있다. 닫는 중괄호를 지난 뒤 `damage`라는 이름으로 접근하려 하면 컴파일 오류가 발생한다.

반면 `playerHp`는 바깥 블록에 선언됐으므로 내부 `if` 블록에서도 사용할 수 있다.

```text
main 블록: playerHp 사용 가능
┌──────────────────────────────┐
│ if 블록: playerHp, damage    │
│ 사용 가능                    │
└──────────────────────────────┘
if 블록 밖: playerHp만 사용 가능
```

안쪽 스코프는 바깥쪽에 선언된 이름을 찾을 수 있지만, 바깥쪽 스코프는 안쪽 블록에만 선언된 이름을 찾을 수 없다.

## 선언보다 앞에서는 이름을 사용할 수 없다

같은 블록 안에 있다는 사실만으로 모든 위치에서 이름이 보이는 것은 아니다.

```cpp
int main()
{
    // score = 10;
    int score = 0;
    score = 10;
}
```

이름은 선언이 효력을 갖기 시작하는 지점부터 해당 스코프 안에서 사용한다. 선언보다 앞의 코드는 뒤에 나타날 지역 변수 `score`를 미리 알지 못한다.

함수도 호출 위치에서 사용할 수 있는 선언이 보여야 한다는 점에서 같은 원리가 적용된다.

```cpp
int Add(int left, int right);

int main()
{
    int result = Add(10, 20);
}
```

## 매개변수 이름은 함수 몸체에서 사용한다

함수 정의의 매개변수도 이름을 가진다.

```cpp
int CalculateDamage(int attack, int defence)
{
    int damage = attack - defence;
    return damage;
}
```

`attack`과 `defence`는 해당 함수 정의 안에서 사용할 수 있다. `damage`는 함수 몸체에 선언된 지역 이름이다. 다른 함수가 같은 매개변수 이름과 지역 변수 이름을 사용해도 충돌하지 않는다.

```cpp
int CalculateHeal(int amount)
{
    int result = amount * 2;
    return result;
}

int CalculateReward(int amount)
{
    int result = amount + 100;
    return result;
}
```

두 `amount`와 두 `result`는 각각의 함수에 속한 별개의 이름이다.

## 안쪽 선언은 바깥쪽 이름을 가릴 수 있다

안쪽 스코프에서 바깥쪽과 같은 이름을 다시 선언하면 가까운 선언이 선택된다. 이를 이름 가림(Name hiding) 또는 섀도잉(Shadowing)이라고 한다.

```cpp
#include <iostream>

int main()
{
    int score = 100;

    if (score > 0)
    {
        int score = 20;
        std::cout << "Inner score: " << score << '\n';
    }

    std::cout << "Outer score: " << score << '\n';
}
```

안쪽 출력은 내부 `score`인 20을 사용하고, 블록 밖 출력은 외부 `score`인 100을 사용한다. 두 객체는 서로 독립적이므로 내부 값을 변경해도 외부 값은 변하지 않는다.

문법적으로 허용되더라도 가까운 범위에 같은 이름이 반복되면 어느 객체를 수정하는지 놓치기 쉽다. 의도적인 가림이 아니라면 역할이 드러나는 다른 이름을 사용하는 편이 좋다.

```cpp
int totalScore = 100;
int roundScore = 20;
```

## 수명은 객체가 존재하는 기간이다

수명은 이름이 보이는지보다 객체 자체가 존재하는지를 설명한다. 객체의 수명이 시작되면 그 객체의 상태를 사용할 수 있고, 수명이 끝나면 해당 객체를 더 이상 사용해서는 안 된다.

일반적인 지역 객체는 선언이 실행될 때 수명이 시작되고 블록을 빠져나갈 때 수명이 끝난다.

```cpp
void RunTurn(bool hasTarget)
{
    int turn = 1;

    if (hasTarget)
    {
        int damage = 20;
    }
}
```

호출 흐름을 기준으로 보면 다음과 같다.

```text
RunTurn 진입
  └─ turn 생성
       └─ if 블록 진입 시 damage 생성
       └─ if 블록 종료 시 damage 소멸
  └─ RunTurn 종료 시 turn 소멸
```

`hasTarget`이 `false`라면 `damage`의 선언이 실행되지 않으므로 그 호출에서는 `damage` 객체가 생성되지 않는다.

## 블록을 나가는 모든 경로에서 지역 객체가 정리된다

지역 객체의 블록을 빠져나가는 경로는 닫는 중괄호만이 아니다. `return`이나 예외로 블록을 벗어날 때도 이미 생성된 자동 저장 기간 객체는 규칙에 따라 소멸한다.

```cpp
#include <string>

int GetNameLength(bool valid)
{
    std::string name = "Player";

    if (!valid)
    {
        return 0;
    }

    return static_cast<int>(name.size());
}
```

`valid`가 `false`여도 `return 0;`으로 함수를 빠져나가는 과정에서 `name`의 소멸자가 호출된다. 이 규칙 덕분에 `std::string`, `std::vector`와 같은 객체가 관리하는 자원을 블록 경계에 맞춰 정리할 수 있다.

이처럼 객체의 수명에 자원 관리를 결합하는 C++ 설계를 RAII(Resource Acquisition Is Initialization)라고 한다.

## 저장 기간은 객체의 저장 공간이 유지되는 방식을 분류한다

저장 기간은 객체를 위한 저장 공간이 얼마나 오래 유지되는지를 설명한다. 입문 단계에서 주로 만나는 분류는 다음과 같다.

| 저장 기간 | 대표적인 예 | 일반적인 유지 범위 |
| :--- | :--- | :--- |
| 자동 저장 기간 | 일반 지역 변수, 값 매개변수 | 선언이 실행된 블록 또는 함수 호출 동안 |
| 정적 저장 기간 | 네임스페이스 스코프 변수, `static` 지역 변수 | 프로그램 실행 기간 |
| 동적 저장 기간 | 동적 할당으로 만든 객체 | 명시된 해제 또는 소유 객체의 관리가 끝날 때까지 |
| 스레드 저장 기간 | `thread_local` 객체 | 각 스레드의 실행 기간 |

저장 기간은 물리적인 메모리 영역 이름과 동일하지 않다. 예를 들어 자동 저장 기간 객체를 흔히 “스택 변수”라고 부르지만, 최적화된 코드에서는 레지스터에만 존재하거나 저장 공간 자체가 제거될 수 있다.

C++ 규칙상 중요한 것은 객체의 수명과 관찰 가능한 동작이지, 모든 지역 변수가 반드시 특정 스택 주소를 가진다는 보장이 아니다.

## 일반 지역 변수는 호출마다 새로 만들어진다

일반 지역 변수와 값 매개변수는 보통 자동 저장 기간을 가진다.

```cpp
int NextLevel(int currentLevel)
{
    int nextLevel = currentLevel + 1;
    return nextLevel;
}
```

`NextLevel`을 호출할 때마다 그 호출에 속한 `currentLevel`과 `nextLevel`이 존재한다. 함수가 반환되면 해당 호출에 속한 객체의 수명이 끝난다.

```cpp
int first = NextLevel(1);
int second = NextLevel(10);
```

첫 번째 호출의 `nextLevel`과 두 번째 호출의 `nextLevel`은 같은 이름을 사용하지만 서로 다른 객체다. 앞에서 살펴본 호출 프레임은 이 독립된 실행 상태를 구현하는 대표적인 방식이다.

## `static` 지역 변수는 스코프와 수명이 다르게 움직인다

함수 안에 `static` 지역 변수를 선언할 수 있다.

```cpp
int GetNextId()
{
    static int nextId = 1;
    return nextId++;
}
```

`nextId`라는 이름은 `GetNextId` 함수 안에서만 사용할 수 있다. 하지만 객체는 호출이 끝나도 소멸하지 않고 프로그램 실행 동안 유지된다.

```cpp
int first = GetNextId();
int second = GetNextId();
```

첫 호출은 1을, 두 번째 호출은 2를 반환한다. 두 호출이 같은 `nextId` 객체의 상태를 공유하기 때문이다.

| 항목 | `nextId`의 특성 |
| :--- | :--- |
| 스코프 | `GetNextId` 함수 내부 |
| 저장 기간 | 정적 저장 기간 |
| 초기화 | 한 번만 수행되며 첫 호출에서 값을 사용하기 전에는 완료됨 |
| 호출 간 상태 | 이전 호출의 값을 유지 |

이 사례만으로도 스코프와 수명이 같은 개념이 아니라는 점을 확인할 수 있다.

상수 초기화가 가능한 정적 객체는 첫 함수 호출보다 일찍 초기화될 수 있고, 실행 중 계산이 필요한 동적 초기화는 처음 선언 지점에 도달할 때 수행된다. C++11부터 함수 지역 정적 객체의 동적 초기화는 여러 스레드가 동시에 처음 접근하더라도 한 번만 완료되도록 보장된다. 그러나 초기화 이후 `nextId++` 같은 상태 변경 자체가 자동으로 스레드 안전해지는 것은 아니다.

## 네임스페이스 스코프 변수도 어디서나 자동으로 보이지는 않는다

함수 밖, 네임스페이스 영역에 선언한 변수를 흔히 전역 변수라고 부른다.

```cpp
int PlayerCount = 0;

void AddPlayer()
{
    ++PlayerCount;
}
```

`PlayerCount`는 정적 저장 기간을 가지므로 프로그램 실행 동안 저장 공간이 유지된다. 하지만 “전역 변수는 프로그램의 모든 파일과 모든 위치에서 자동으로 접근할 수 있다”는 설명은 정확하지 않다.

다른 소스 파일에서 같은 객체를 사용하려면 적절한 선언과 연결(Linkage) 규칙이 필요하다. 이름이 보이는 범위와 여러 번역 단위에서 같은 대상을 가리키는지는 별개의 문제다.

```cpp
// GameState.h
#pragma once

extern int PlayerCount;
```

```cpp
// GameState.cpp
#include "GameState.h"

int PlayerCount = 0;
```

```cpp
// Main.cpp
#include "GameState.h"

void AddPlayer()
{
    ++PlayerCount;
}
```

`extern` 선언은 다른 곳에 정의된 객체를 이 번역 단위에서 사용할 수 있도록 알린다. 헤더에 일반 전역 변수 정의를 그대로 두면 여러 번역 단위에서 중복 정의 문제가 생길 수 있으므로 선언과 정의의 위치를 구분한다.

## 전역 객체와 `static` 지역 객체는 기본적으로 0 초기화된다

정적 저장 기간을 가진 객체는 명시적인 초기화가 없더라도 정적 초기화 과정에서 0에 해당하는 값으로 초기화된다.

```cpp
int GlobalScore;

int GetVisitCount()
{
    static int visitCount;
    return visitCount;
}
```

이 예제의 `GlobalScore`와 `visitCount`는 0으로 초기화된다.

반면 기본 초기화된 일반 지역 `int`는 자동으로 0이 되지 않는다.

```cpp
void PrintScore()
{
    int score;
    // std::cout << score << '\n';
}
```

`score`는 불확정한 값을 가질 수 있으므로 값을 지정하기 전에 읽어서는 안 된다. 이를 단순히 “쓰레기값이 들어 있다”라고만 외우면 어떤 값이 우연히 출력될 수 있다고 오해하기 쉽다. 초기화되지 않은 값을 읽는 코드는 올바른 결과를 기대할 수 없는 잘못된 코드로 취급한다.

가능하면 선언과 동시에 의미 있는 초기값을 제공한다.

```cpp
int score = 0;
```

## 값 전달은 원본과 별개의 매개변수 객체를 만든다

값 매개변수는 호출자의 인자로 초기화되는 별도 객체다.

```cpp
void IncreaseHp(int hp)
{
    ++hp;
}

int main()
{
    int playerHp = 100;
    IncreaseHp(playerHp);
}
```

함수 안의 `hp`를 101로 변경해도 `main`의 `playerHp`는 100이다.

```text
호출자 객체
playerHp = 100
       │ 값으로 매개변수 초기화
       ▼
매개변수 객체
hp = 100 → 101
```

두 객체는 값이 처음에 같을 뿐 정체성이 다르다. `hp`의 수명은 `IncreaseHp` 호출 동안 유지되고, 함수가 반환되면 끝난다.

여기서 “값 전달은 항상 메모리 스택에 비트를 복사한다”라고 단정하지 않는다. 언어 관점에서는 별도의 매개변수 객체가 핵심이며, 실제 인자 전달은 레지스터, 스택, 인라인 최적화 등 구현에 따라 달라질 수 있다.

## 값 전달의 장점은 호출자의 상태 변경을 제한하는 데 있다

값 매개변수를 사용하면 함수 안의 단순한 대입이 호출자의 객체를 직접 바꾸지 않는다.

```cpp
int ClampHp(int hp, int maxHp)
{
    if (hp < 0)
    {
        hp = 0;
    }

    if (hp > maxHp)
    {
        hp = maxHp;
    }

    return hp;
}
```

호출자는 반환값을 사용할지 직접 결정한다.

```cpp
int playerHp = 120;
int clampedHp = ClampHp(playerHp, 100);
```

`playerHp`는 120으로 유지되고 `clampedHp`는 100이 된다. 원본을 바꾸려면 결과를 명시적으로 다시 대입한다.

```cpp
playerHp = ClampHp(playerHp, 100);
```

호출부에 상태 변경이 드러나므로 데이터 흐름을 추적하기 쉽다.

## 값 전달이 항상 깊은 복사를 뜻하지는 않는다

클래스 객체를 값으로 전달하면 해당 타입의 규칙에 따라 매개변수 객체가 초기화된다. 이 과정에서 복사 생성이나 이동이 일어날 수 있고, 컴파일러가 허용된 생략을 적용할 수도 있다.

또한 객체가 내부적으로 다른 대상을 가리키는 핸들이나 포인터를 가지고 있다면 외부 자원까지 무조건 복제된다고 단정할 수 없다.

```cpp
struct PlayerView
{
    int* hp;
};

void Damage(PlayerView view)
{
    *view.hp -= 10;
}
```

`view` 자체는 값 매개변수지만 그 안의 포인터 값은 호출자가 가진 포인터와 같은 `int` 객체를 가리킬 수 있다. 따라서 `*view.hp`를 수정하면 원본 HP가 변경된다.

값 전달이 보장하는 것은 매개변수 객체 자체가 호출자의 인자 객체와 별개라는 점이다. 그 객체가 소유하거나 가리키는 대상까지 분리되는지는 타입의 복사 의미에 달려 있다.

## 원본을 수정하는 함수는 계약에 그 의도를 드러낸다

함수가 호출자의 객체를 직접 변경해야 한다면 비상수 참조 매개변수를 사용할 수 있다.

```cpp
void ApplyDamage(int& hp, int damage)
{
    hp -= damage;

    if (hp < 0)
    {
        hp = 0;
    }
}
```

```cpp
int playerHp = 100;
ApplyDamage(playerHp, 30);
```

`hp`는 `playerHp`의 다른 이름처럼 동작하므로 함수 안의 변경이 호출자의 객체에 반영된다.

그러나 원본 수정이 가능하다는 이유만으로 모든 매개변수를 참조로 받을 필요는 없다. 함수가 결과를 계산하는 역할이라면 반환값을 사용하는 편이 데이터 흐름을 더 명확하게 만들 수 있다.

```cpp
int CalculateRemainingHp(int hp, int damage)
{
    return hp > damage ? hp - damage : 0;
}
```

값, 참조, 포인터 중 어떤 방식을 선택할지는 객체 크기 하나가 아니라 다음 내용을 함께 보고 판단한다.

- 호출자의 원본을 수정해야 하는가?
- 입력이 없을 수 있다는 상태를 표현해야 하는가?
- 함수가 객체를 소유해야 하는가?
- 복사 또는 이동 비용은 어느 정도인가?
- 호출부에서 변경 가능성이 충분히 드러나는가?

## 지역 객체의 주소를 반환하면 수명이 먼저 끝난다

스코프 밖에서 이름을 사용할 수 없다고 해서 주소나 참조를 통해 객체에 계속 접근할 수 있는 것은 아니다. 객체의 수명이 이미 끝났다면 그 주소는 유효한 객체를 가리키지 않는다.

```cpp
int* CreateScore()
{
    int score = 100;
    return &score;
}
```

`score`는 `CreateScore`가 반환될 때 수명이 끝난다. 반환된 포인터는 더 이상 살아 있는 `score` 객체를 가리키지 않는 댕글링 포인터(Dangling pointer)가 된다. 이를 역참조하면 정의되지 않은 동작이 발생한다.

지역에서 계산한 값 하나를 전달하려면 값으로 반환한다.

```cpp
int CreateScore()
{
    int score = 100;
    return score;
}
```

반환된 결과로 호출자 쪽 객체가 초기화되므로 함수의 지역 객체 수명과 분리된다.

```cpp
int playerScore = CreateScore();
```

“함수가 끝나도 예전 스택 메모리에 숫자 100이 남아 있을 수 있다”는 사실은 객체가 여전히 살아 있다는 뜻이 아니다. C++에서 사용할 수 있는지는 남은 비트 모양이 아니라 객체의 수명 규칙으로 판단한다.

## 동적 객체의 수명은 포인터 이름의 스코프와 다를 수 있다

동적으로 생성한 객체는 객체를 가리키는 지역 포인터와 다른 수명 규칙을 가질 수 있다.

```cpp
void CreateValue()
{
    int* value = new int(10);
}
```

함수가 끝나면 지역 포인터 `value`의 수명은 끝나지만 `new`로 만든 `int` 객체가 자동으로 해제되지는 않는다. 주소를 잃어버렸으므로 메모리 누수가 발생한다.

직접 `new`와 `delete`를 관리하기보다 소유권을 표현하는 RAII 타입을 사용한다.

```cpp
#include <memory>

void CreateValue()
{
    auto value = std::make_unique<int>(10);
}
```

`value`가 블록을 벗어나 소멸할 때 `std::unique_ptr`가 소유한 동적 객체도 정리한다. 포인터 이름의 스코프, 포인터 객체의 수명, 포인터가 소유한 동적 객체의 수명은 구분해야 하지만 RAII를 사용하면 정리 시점을 안전하게 연결할 수 있다.

## 전역 상태는 함수의 실제 입력을 숨긴다

전역 변수는 여러 함수가 쉽게 공유할 수 있지만 함수 선언에 의존성이 나타나지 않는다.

```cpp
int PlayerAttack = 20;
int MonsterDefence = 8;

int CalculateDamage()
{
    return PlayerAttack - MonsterDefence;
}
```

`CalculateDamage()`라는 선언만 보면 결과가 어떤 값으로 결정되는지 알기 어렵다. 다른 코드가 두 전역 값을 변경하면 같은 호출식의 결과도 달라진다.

필요한 상태를 매개변수로 받으면 의존성이 호출부에 드러난다.

```cpp
int CalculateDamage(int attack, int defence)
{
    return attack > defence ? attack - defence : 0;
}
```

```cpp
int damage = CalculateDamage(playerAttack, monsterDefence);
```

명시적인 입력을 사용하면 다음 장점이 있다.

- 함수의 결과를 결정하는 값을 선언에서 확인할 수 있다.
- 다른 입력으로 함수를 재사용하기 쉽다.
- 테스트마다 전역 상태를 준비하고 복구할 필요가 줄어든다.
- 어느 코드가 상태를 변경했는지 추적하기 쉬워진다.

전역 변수가 무조건 금지된다는 뜻은 아니다. 프로그램 전체 설정, 로깅 시스템, 의도적으로 공유하는 서비스처럼 긴 수명이 필요한 대상도 있다. 중요한 것은 긴 수명과 광범위한 접근 권한을 자동으로 같은 설계로 묶지 않는 것이다.

## 전역 상수와 전역 상태도 구분한다

변하지 않는 상수는 수정 가능한 전역 상태와 위험이 다르다.

```cpp
constexpr int MaxPlayerCount = 4;
int CurrentPlayerCount = 0;
```

`MaxPlayerCount`는 실행 중 변경되지 않으므로 호출 순서에 따라 값이 달라지지 않는다. 반면 `CurrentPlayerCount`는 여러 코드가 수정할 수 있다면 현재 값을 만든 경로를 추적해야 한다.

상수를 전역으로 두면 모든 문제가 해결된다는 뜻은 아니다. 이름 충돌, 헤더 정의 방식, 어느 기능이 해당 상수에 의존하는지 같은 설계 문제는 남는다. 필요한 가장 좁은 스코프에 이름을 두고, 여러 위치가 실제로 공유해야 할 때 범위를 넓힌다.

## 전체 예제로 네 가지 규칙을 함께 확인한다

전역 상태 없이 플레이어의 피해 적용 결과를 계산하는 예제다.

```cpp
#include <algorithm>
#include <iostream>

struct PlayerState
{
    int hp;
    int maxHp;
};

int CalculateDamage(int attack, int defence)
{
    return std::max(0, attack - defence);
}

int CalculateRemainingHp(int hp, int damage)
{
    return std::max(0, hp - damage);
}

PlayerState ApplyDamage(PlayerState player, int damage)
{
    player.hp = CalculateRemainingHp(player.hp, damage);
    return player;
}

void PrintPlayerState(const PlayerState& player)
{
    std::cout << "HP: " << player.hp << " / " << player.maxHp << '\n';
}

int main()
{
    constexpr int PlayerAttack = 25;
    constexpr int MonsterDefence = 10;

    PlayerState monster{50, 50};
    int damage = CalculateDamage(PlayerAttack, MonsterDefence);

    {
        int previewHp = CalculateRemainingHp(monster.hp, damage);
        std::cout << "Preview HP: " << previewHp << '\n';
    }

    PrintPlayerState(monster);
    monster = ApplyDamage(monster, damage);
    PrintPlayerState(monster);
}
```

이 코드에서 각 규칙을 따로 확인할 수 있다.

| 코드 | 확인할 규칙 |
| :--- | :--- |
| `previewHp` | 안쪽 블록에서만 이름을 사용할 수 있다. |
| `damage` | `main` 블록의 자동 저장 기간 객체다. |
| `PlayerAttack`, `MonsterDefence` | `main` 안에서만 이름을 사용하며 각 호출에서 값이 바뀌지 않는다. |
| `ApplyDamage`의 `player` | `monster`의 값으로 초기화된 별도 매개변수 객체다. |
| `monster = ApplyDamage(...)` | 반환된 새 상태를 호출자가 명시적으로 반영한다. |
| `PrintPlayerState`의 `player` | 원본을 수정하지 않고 읽기 위해 `const` 참조로 받는다. |

코드 흐름을 따라가면 미리 계산한 HP는 35지만 첫 번째 `PrintPlayerState`가 보는 `monster.hp`는 여전히 50이다. `ApplyDamage`의 반환값을 `monster`에 대입한 뒤에야 두 번째 출력에서 HP가 35가 된다.

여기서 `PlayerState`는 작아서 값 전달 비용이 핵심 문제가 아니다. `ApplyDamage`가 입력 상태를 직접 수정하지 않고 새로운 상태를 반환한다는 계약을 보여주기 위해 값 매개변수를 선택했다. 실제 타입이 크거나 복사하기 어려운 자원을 소유한다면 인터페이스와 성능 요구사항을 다시 검토해야 한다.

## 변수를 이해할 때 확인할 기준

변수와 매개변수를 볼 때 “전역인가, 지역인가?”만 확인하면 중요한 차이를 놓칠 수 있다. 다음 순서로 살펴본다.

1. 이름이 선언된 스코프는 어디인가?
2. 해당 이름은 현재 코드 위치에서 보이는가?
3. 객체의 수명은 언제 시작되고 끝나는가?
4. 저장 기간은 자동, 정적, 동적, 스레드 중 무엇인가?
5. 함수 호출마다 별도 객체가 만들어지는가, 상태를 공유하는가?
6. 값 전달이라면 매개변수 자체와 그 안에서 가리키는 대상을 구분했는가?
7. 포인터나 참조가 대상 객체보다 오래 남아 댕글링 상태가 되지 않는가?
8. 긴 수명의 상태가 함수의 숨은 입력으로 사용되고 있지는 않은가?

스코프는 이름 검색의 규칙이고, 수명은 객체 사용 가능 기간의 규칙이다. 값 전달은 호출자의 객체와 매개변수 객체를 분리하지만, 내부 포인터가 가리키는 대상까지 자동으로 복제하지는 않는다. 이 세 층을 나눠 보면 지역 변수, 전역 변수, `static` 객체와 함수 매개변수의 동작을 하나의 막연한 “메모리 위치” 설명에 의존하지 않고 이해할 수 있다.

## 다음 학습: 선언과 정의가 필요한 시점

이름은 자신의 스코프 안에서도 선언이 효력을 갖기 시작한 뒤에 사용할 수 있다. 객체가 오래 살아 있다고 해서 모든 코드에서 그 이름을 자동으로 찾을 수 있는 것도 아니며, 다른 소스 파일에서 같은 대상을 사용하려면 적절한 선언과 연결 규칙이 필요하다.

다음 글에서는 컴파일러가 호출 위치에서 어떤 함수 선언을 필요로 하는지, 선언과 정의가 각각 컴파일 단계와 링크 단계에서 어떤 역할을 하는지 살펴본다.
