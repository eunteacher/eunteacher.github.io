프로그램이 잘못된 값을 출력하거나 크래시했다고 해서 실행 결과만 보고 원인을 확정할 수는 없다. 초기화되지 않은 값과 배열 범위 초과처럼 동작 자체가 정의되지 않은 오류도 있고, 체력을 0보다 작게 유지해서 사망 조건을 놓치는 논리 오류도 있다.

이번 글에서는 기사 클래스에 발생한 다섯 가지 버그를 `증상 → 확인 과정 → 원인 → 수정 → 검증` 순서로 살펴본다. 단순히 크래시가 사라지는 코드를 찾는 것이 아니라 객체가 지켜야 할 상태와 산술 연산의 전제를 코드에 반영한다.

## 먼저 오류의 종류를 구분한다

비슷한 증상도 C++ 관점에서는 서로 다른 문제일 수 있다.

```text
정의되지 않은 동작  표준이 결과를 규정하지 않음
구현 정의 동작      구현이 선택한 동작을 문서화해야 함
명시되지 않은 동작  허용된 여러 결과 중 하나지만 어떤 것인지 지정하지 않음
논리 오류           프로그램은 정의된 방식으로 실행되지만 요구사항과 결과가 다름
```

초기화되지 않은 값을 읽거나 배열 범위를 벗어난 접근, 부호 있는 정수 오버플로와 정수 0 나누기는 정의되지 않은 동작을 만들 수 있다. “이 컴퓨터에서는 음수가 나왔다”거나 “대부분 크래시한다”는 관찰을 모든 실행의 규칙으로 일반화할 수 없다.

사망 판정을 `hp == 0`으로만 검사해 음수 체력을 놓치는 것은 논리 오류다. 언어가 이상하게 실행된 것이 아니라 프로그램이 작성된 조건대로 잘못된 판정을 수행한 것이다.

## 사례 1: 일부 생성자에서 멤버를 초기화하지 않았다

### 증상

기본 생성한 기사의 공격력은 10인데 체력만 전달해 만든 기사의 공격력은 음수나 큰 값처럼 예상할 수 없는 값으로 보인다.

```cpp
Knight first;
Knight second{200};

first.PrintInfo();
second.PrintInfo();
```

### 확인 과정

`Knight(int)` 생성자에 중단점을 설정하고 생성자 본문 직후 `hp_`와 `attack_`을 확인한다. `hp_`는 200으로 설정됐지만 `attack_`에는 의도한 값을 넣은 코드가 없다.

```cpp
Knight::Knight(int hp) : hp_(hp)
{
}
```

### 원인

`attack_`은 기본 초기화 과정에서 결정된 유효한 값이 없다. 이후 값을 읽어 출력하는 코드가 문제가 된다. 디버그 환경에서 특정 패턴이 보이거나 이전 실행의 값처럼 보여도 사용할 수 있는 기본값이 아니다.

모든 생성자는 객체가 동일한 상태 조건을 만족하도록 끝나야 한다.

```text
hp_ >= 0
attack_ >= 0
```

### 수정

여러 생성자가 공유하는 기본값을 멤버 선언에 둔다.

```cpp
class Knight
{
public:
    Knight() = default;
    explicit Knight(int hp) : hp_(std::max(0, hp))
    {
    }

private:
    int hp_ = 100;
    int attack_ = 10;
};
```

`Knight(int)`가 `hp_`만 별도로 지정해도 `attack_`은 10으로 초기화된다. 생성자마다 같은 기본값을 반복할 필요도 없다.

### 검증

```cpp
Knight first;
Knight second{200};

assert(first.Hp() == 100);
assert(first.Attack() == 10);
assert(second.Hp() == 200);
assert(second.Attack() == 10);
```

출력에서 우연히 정상 값이 나오는지만 확인하지 않고 두 생성 경로의 상태를 직접 검증한다.

## 사례 2: 배열의 마지막 인덱스를 하나 넘었다

### 증상

기사 포인터 10개를 만들고 출력하는 반복문에서 간헐적으로 잘못된 주소를 사용하거나 프로그램이 중단된다.

```cpp
constexpr int KnightCount = 10;
Knight* knights[KnightCount]{};

for (int i = 0; i <= KnightCount; ++i)
{
    knights[i] = new Knight;
}
```

### 확인 과정

반복문 본문에 조건부 중단점 `i == KnightCount`를 설정한다. 중단됐을 때 `i`는 10이지만 배열의 유효한 인덱스는 0부터 9까지다.

```text
요소 개수: 10
유효 인덱스: 0, 1, 2, ..., 9
```

### 원인

조건 `i <= KnightCount`가 10번째 인덱스까지 허용한다. `knights[10]`은 배열 범위를 벗어나며 해당 접근의 동작은 정의되지 않는다.

인접 메모리에 쓰기가 성공한 것처럼 보여도 안전한 실행이 아니다. 다른 지역 변수나 반환 주소와 관련된 데이터를 손상시켜 나중에 전혀 다른 위치에서 증상이 나타날 수 있다.

### 수정

반복 조건을 요소 개수보다 작은 동안으로 제한한다.

```cpp
for (int i = 0; i < KnightCount; ++i)
{
    knights[i] = new Knight;
}
```

더 나은 방법은 인덱스와 수동 동적 할당을 줄이는 것이다.

```cpp
#include <array>

std::array<Knight, 10> knights{};

for (const Knight& knight : knights)
{
    knight.PrintInfo();
}
```

크기가 실행 중 결정된다면 `std::vector<Knight>`를 사용한다. 컨테이너는 요소 수와 저장 공간의 수명을 함께 관리한다.

### 검증

```cpp
assert(knights.size() == 10);

for (const Knight& knight : knights)
{
    assert(knight.Hp() == 100);
}
```

디버그 표준 라이브러리의 범위 검사나 AddressSanitizer 같은 도구도 범위를 벗어난 접근을 찾는 데 도움을 줄 수 있다. 도구의 검출 여부가 코드의 유효성을 대신하지는 않는다.

## 사례 3: 체력이 0을 지나 음수가 됐다

### 증상

체력 100인 기사가 200의 피해를 받았는데 사망 로그가 출력되지 않는다.

```cpp
knight.AddHp(-200);

if (knight.IsDead())
{
    std::cout << "Dead\n";
}
```

### 확인 과정

`AddHp` 실행 전후의 체력을 확인한다.

```text
실행 전 hp_: 100
실행 후 hp_: -100
```

사망 함수는 정확히 0인지 검사한다.

```cpp
bool Knight::IsDead() const
{
    return hp_ == 0;
}
```

### 원인

피해가 현재 체력보다 크면 체력은 0을 지나 음수가 된다. `hp_ == 0`은 음수 체력을 사망으로 판단하지 않는다.

`hp_ <= 0`으로 바꾸면 판정 증상은 고칠 수 있지만 객체가 계속 음수 체력을 보유한다. 체력의 유효 범위가 `0 <= hp_ <= maxHp_`라면 변경 시점에 범위를 유지하는 편이 일관적이다.

### 수정

피해와 회복을 의미가 드러나는 함수로 분리하고 범위를 제한한다.

```cpp
void Knight::TakeDamage(int damage)
{
    if (damage <= 0)
    {
        return;
    }

    hp_ = damage >= hp_ ? 0 : hp_ - damage;
}

bool Knight::IsDead() const
{
    return hp_ == 0;
}
```

이제 체력이 음수가 되지 않는다는 클래스 조건 덕분에 `hp_ == 0`도 올바른 사망 판정이 된다.

### 검증

```cpp
Knight knight;
knight.TakeDamage(200);

assert(knight.Hp() == 0);
assert(knight.IsDead());
```

피해가 0이거나 음수인 경우, 정확히 현재 체력만큼 받는 경우와 초과 피해도 함께 확인한다.

## 사례 4: 부호 있는 정수 오버플로가 발생했다

### 증상

기사에게 큰 체력 값을 반복해서 더했더니 체력이 음수처럼 보이고 사망 판정이 참이 된다.

```cpp
for (int i = 0; i < 1'000'000; ++i)
{
    knight.AddHp(1'000'000);
}
```

수학적으로는 약 1조가 증가하므로 32비트 `int`가 흔히 표현하는 범위를 크게 넘는다.

### 확인 과정

연산 전 값을 조사식으로 확인하고 대상 타입의 최댓값과 비교한다.

```cpp
std::numeric_limits<int>::max()
```

덧셈 전에 다음 조건을 검사할 수 있다.

```cpp
value > 0 && hp_ > std::numeric_limits<int>::max() - value
```

### 원인

부호 있는 정수의 표현 범위를 넘는 산술 오버플로는 정의되지 않은 동작이다. 2의 보수 환경에서 음수로 감싸지는 결과를 관찰할 수 있어도 표준 C++의 보장으로 의존할 수 없다.

원본 수정본은 `hp_`를 `float`로 바꾸는 방안을 제시한다. `float`는 더 큰 크기의 수를 표현할 수 있지만 큰 값에서 모든 정수를 정확하게 구분하지 못한다. 체력처럼 정확한 정수 단위를 요구하는 값의 일반적인 해결책이 아니다.

### 수정

먼저 도메인의 최대 체력을 정의하고 그 범위에서 포화시킨다.

```cpp
void Knight::Heal(std::int64_t amount)
{
    if (amount <= 0)
    {
        return;
    }

    hp_ = amount >= maxHp_ - hp_ ? maxHp_ : hp_ + amount;
}
```

`hp_`와 `maxHp_`는 `std::int64_t`를 사용한다. 하지만 타입을 넓히는 것만으로 무한히 큰 값을 처리할 수 있는 것은 아니다. 계산 전에 `maxHp_ - hp_`와 비교해 허용 범위를 넘는 덧셈 자체를 실행하지 않는다.

요구사항이 최대 체력 100이라면 1조를 저장할 타입을 찾는 것보다 100에서 멈추는 정책이 자연스럽다.

### 검증

```cpp
Knight knight{100};
knight.TakeDamage(50);
knight.Heal(1'000'000'000'000LL);

assert(knight.Hp() == 100);
assert(!knight.IsDead());
```

큰 입력을 받아도 허용 범위 안에서 결과가 결정되는지 검증한다.

## 사례 5: 사망한 객체의 체력으로 나눴다

### 증상

체력 비율에 따라 공격력을 두 배로 만드는 기능을 추가한 뒤, 체력이 0인 기사에게서 공격력을 조회하면 프로그램이 중단된다.

```cpp
int ratio = maxHp_ / hp_;

if (ratio > 2)
{
    damage *= 2;
}
```

### 확인 과정

나눗셈 직전에 중단점을 두고 `hp_`와 `maxHp_`를 확인한다.

```text
hp_: 0
maxHp_: 100
```

분모가 0이라는 직접 원인을 확인할 수 있다. 동시에 이 수식이 “현재 체력이 최대 체력의 50% 이하인가?”라는 요구사항을 정확하게 표현하는지도 검토한다.

### 원인

정수 0으로 나누는 동작은 정의되지 않는다. 특정 환경에서 예외나 크래시가 발생할 수 있지만 항상 같은 증상을 보장하지 않는다.

또한 `maxHp_ / hp_ > 2`는 정수 나눗셈 때문에 경계가 잘못된다.

```text
maxHp = 100, hp = 50 → 100 / 50 = 2 → 2 > 2는 거짓
```

요구사항은 50% 이하에서 두 배이므로 체력 50에서도 발동해야 한다. 단순히 사망 시 조기 반환만 추가해도 경계 논리 오류는 남는다.

### 수정

나눗셈 없이 비교한다.

```cpp
int Knight::AttackDamage() const
{
    if (IsDead())
    {
        return 0;
    }

    if (hp_ <= maxHp_ / 2)
    {
        return attack_ * 2;
    }

    return attack_;
}
```

생성자에서 `maxHp_ >= 1`을 보장하면 최대 체력 자체가 잘못된 상태도 막을 수 있다.

홀수 최대 체력에서 정확히 어떤 값을 50% 이하로 볼 것인지도 정책이 필요하다. 정수 나눗셈의 내림을 피하고 수학적 조건 `2 * hp_ <= maxHp_`를 사용할 수 있지만 왼쪽 곱셈의 오버플로를 고려해야 한다. 현재처럼 작은 게임 능력치 범위가 보장된다면 사용할 수 있고, 일반적인 큰 정수에는 안전한 비교 방법을 별도로 설계한다.

### 검증

경계 양쪽과 사망 상태를 확인한다.

```cpp
Knight knight{100, 10};

knight.TakeDamage(49);
assert(knight.Hp() == 51);
assert(knight.AttackDamage() == 10);

knight.TakeDamage(1);
assert(knight.Hp() == 50);
assert(knight.AttackDamage() == 20);

knight.TakeDamage(50);
assert(knight.Hp() == 0);
assert(knight.AttackDamage() == 0);
```

50% 바로 위, 정확히 50%와 0을 각각 검증해야 경계 조건과 0 나누기 방지를 함께 확인할 수 있다.

## 상태를 직접 공개하면 같은 버그가 여러 경로에서 반복된다

원본 실습은 테스트 편의를 위해 `_hp`, `_maxHp`, `_attack`을 `public`으로 공개한다.

```cpp
knight._hp = -100;
knight._maxHp = 0;
```

이렇게 외부에서 직접 값을 바꿀 수 있으면 생성자와 `Heal`, `TakeDamage`가 범위를 지켜도 객체 상태를 언제든 깨뜨릴 수 있다.

```cpp
class Knight
{
public:
    void TakeDamage(std::int64_t damage);
    void Heal(std::int64_t amount);
    std::int64_t Hp() const;

private:
    std::int64_t hp_;
    std::int64_t maxHp_;
    int attack_;
};
```

데이터를 감추고 의미가 있는 변경 함수만 제공하면 다음 조건을 클래스 내부에서 유지할 수 있다.

```text
1 <= maxHp_
0 <= hp_ <= maxHp_
0 <= attack_
```

각 오류를 개별 조건문으로 막는 것보다 객체가 잘못된 상태를 가질 수 있는 경로 자체를 줄인다.

## 전체 수정 구현

다섯 사례의 상태 규칙과 산술 전제를 하나의 클래스에 반영한다.

```cpp
#include <algorithm>
#include <array>
#include <cassert>
#include <cstdint>
#include <iostream>
#include <limits>

class Knight
{
public:
    Knight() = default;

    explicit Knight(std::int64_t maxHp, std::int64_t attack = 10) : hp_(std::max<std::int64_t>(1, maxHp)), maxHp_(std::max<std::int64_t>(1, maxHp)), attack_(std::max<std::int64_t>(0, attack))
    {
    }

    void TakeDamage(std::int64_t damage)
    {
        if (damage <= 0)
        {
            return;
        }

        hp_ = damage >= hp_ ? 0 : hp_ - damage;
    }

    void Heal(std::int64_t amount)
    {
        if (amount <= 0)
        {
            return;
        }

        hp_ = amount >= maxHp_ - hp_ ? maxHp_ : hp_ + amount;
    }

    bool IsDead() const
    {
        return hp_ == 0;
    }

    std::int64_t AttackDamage() const
    {
        if (IsDead())
        {
            return 0;
        }

        if (hp_ <= maxHp_ / 2)
        {
            const std::int64_t maximum = std::numeric_limits<std::int64_t>::max();
            return attack_ > maximum / 2 ? maximum : attack_ * 2;
        }

        return attack_;
    }

    std::int64_t Hp() const
    {
        return hp_;
    }

    std::int64_t MaxHp() const
    {
        return maxHp_;
    }

    std::int64_t Attack() const
    {
        return attack_;
    }

private:
    std::int64_t hp_ = 100;
    std::int64_t maxHp_ = 100;
    std::int64_t attack_ = 10;
};

void VerifyInitializationAndArray()
{
    Knight first;
    Knight second{200};
    assert(first.Hp() == 100 && first.Attack() == 10);
    assert(second.Hp() == 200 && second.Attack() == 10);

    std::array<Knight, 10> knights{};
    assert(knights.size() == 10);

    for (const Knight& knight : knights)
    {
        assert(knight.Hp() == 100);
    }
}

void VerifyHealthRules()
{
    Knight knight{100, 10};

    knight.TakeDamage(49);
    assert(knight.Hp() == 51);
    assert(knight.AttackDamage() == 10);

    knight.TakeDamage(1);
    assert(knight.Hp() == 50);
    assert(knight.AttackDamage() == 20);

    knight.Heal(1'000'000'000'000LL);
    assert(knight.Hp() == 100);

    knight.TakeDamage(1'000'000'000'000LL);
    assert(knight.Hp() == 0);
    assert(knight.IsDead());
    assert(knight.AttackDamage() == 0);
}

int main()
{
    VerifyInitializationAndArray();
    VerifyHealthRules();
    std::cout << "All checks passed\n";
}
```

실행 결과는 다음과 같다.

```text
All checks passed
```

모든 생성 경로에서 공격력이 초기화되고 배열 순회는 요소 수 안에서만 수행된다. 큰 회복과 피해 입력도 덧셈이나 뺄셈을 먼저 실행하지 않고 경계를 비교해 0부터 최대 체력 사이로 제한한다.

체력 51에서는 기본 공격력, 50에서는 두 배 공격력, 0에서는 공격력 0을 반환하므로 50% 경계와 사망 상태도 나눠 검증된다.

## 정적 분석과 런타임 도구를 함께 사용한다

컴파일러 경고 수준을 높이면 초기화 누락, 위험한 변환과 일부 범위 문제를 조기에 발견할 수 있다. Visual Studio의 코드 분석과 지원되는 Sanitizer는 배열 범위 초과나 잘못된 메모리 접근을 실행 중 발견하는 데 도움을 준다.

하지만 도구가 모든 입력 경로를 실행해 주거나 게임 규칙의 기대값을 이해하는 것은 아니다.

```text
컴파일러 경고   의심스러운 코드 패턴 탐지
정적 분석       실행하지 않고 가능한 오류 경로 분석
Sanitizer       실행한 경로의 잘못된 메모리·산술 동작 탐지
자동 검증       도메인 요구사항과 경계값 확인
디버거          실제 값이 달라지는 시점과 호출 경로 추적
```

한 도구가 문제를 찾지 못했다고 코드가 안전하다고 결론 내리지 않는다. 도구가 찾기 쉬운 오류는 도구에 맡기고 상태 조건과 경계값은 코드와 검증에 명시한다.

## 반복되는 오류를 검토할 때 확인할 기준

1. 모든 생성자가 멤버를 유효한 상태로 초기화하는가?
2. 배열 반복 조건이 `0 <= index < size`를 만족하는가?
3. 컨테이너와 범위 기반 반복문으로 수동 인덱스를 제거할 수 있는가?
4. 피해와 회복 이후에도 `0 <= hp <= maxHp`가 유지되는가?
5. 산술 전에 대상 타입의 표현 범위를 넘는지 검사하는가?
6. 정확한 정수 의미가 필요한 값을 부동소수점으로 우회하지 않는가?
7. 나눗셈 전에 분모가 0이 아님을 보장하는가?
8. 비율 계산 대신 경계의 의미를 직접 비교할 수 있는가?
9. 정확히 경계 바로 아래·경계·바로 위를 모두 검증하는가?
10. 정의되지 않은 동작의 한 실행 결과를 언어 규칙으로 일반화하지 않는가?

이런 버그의 공통 원인은 개별 문법을 몰라서만 생기지 않는다. 객체가 유지해야 할 범위와 연산이 성립하기 위한 전제를 코드에 표현하지 않았기 때문에 같은 문제가 다른 함수에서 반복된다. 오류를 고칠 때는 증상이 나타난 한 줄뿐 아니라 잘못된 상태가 만들어질 수 있는 경로를 함께 닫아야 한다.
