지역 객체는 블록에 들어갈 때 만들어지고 블록을 벗어나면 자동으로 소멸한다. 하지만 필요한 객체 수가 실행 중에 결정되거나 객체의 수명이 현재 함수보다 길어야 하는 상황도 있다.

동적 할당(Dynamic allocation)을 사용하면 실행 중에 저장 공간을 확보하고 객체의 수명이 끝나는 시점을 직접 결정할 수 있다. 자유로운 대신 할당과 해제, 생성과 소멸을 정확하게 짝지어야 한다.

## 저장 위치보다 저장 기간을 먼저 구분한다

지역 변수는 흔히 스택, 동적으로 할당한 객체는 힙에 존재한다고 설명한다.

```cpp
void Spawn()
{
    Monster localMonster;
    Monster* dynamicMonster = new Monster;
    delete dynamicMonster;
}
```

표준 C++ 관점에서는 자동 저장 기간(Automatic storage duration)과 동적 저장 기간(Dynamic storage duration)을 구분하는 편이 정확하다.

```text
localMonster가 가리키는 객체  블록을 벗어나면 자동으로 수명 종료
new로 만든 객체               delete 표현식으로 수명을 종료할 때까지 유지
dynamicMonster 포인터 변수    블록을 벗어나면 자동으로 수명 종료
```

포인터 변수와 포인터가 가리키는 객체는 서로 다른 대상이다. `dynamicMonster`가 함수 종료로 사라져도 `new Monster`로 만든 객체가 자동으로 제거되는 것은 아니다. 주소를 잃어버리면 더 이상 해제할 수 없는 메모리 누수가 된다.

실제 메모리가 물리적인 스택이나 힙에 어떻게 배치되는지는 구현 환경과 최적화에 영향을 받을 수 있다. 언어 차원에서는 객체의 저장 기간과 수명을 기준으로 판단한다.

## new 표현식은 저장 공간 확보와 객체 생성을 함께 수행한다

클래스 객체 하나를 동적으로 만든다.

```cpp
Monster* monster = new Monster{150};
```

개념적으로 `new` 표현식은 다음 작업을 수행한다.

```text
1. Monster 객체에 필요한 저장 공간을 확보한다.
2. 확보한 공간에 Monster 객체를 생성한다.
3. 생성된 객체를 가리키는 Monster*를 반환한다.
```

생성자 인자도 일반 객체 생성처럼 전달할 수 있다.

```cpp
Monster* defaultMonster = new Monster;
Monster* strongMonster = new Monster{300};
```

일반적인 `new` 표현식은 저장 공간 확보에 실패하면 null을 반환하지 않고 `std::bad_alloc` 예외를 던진다. `new (std::nothrow)` 형태는 실패 시 null을 반환하지만 별도의 실패 검사가 필요하다.

## delete 표현식은 소멸과 저장 공간 반환을 함께 수행한다

`new`로 만든 단일 객체는 `delete`로 정리한다.

```cpp
delete monster;
monster = nullptr;
```

`delete` 표현식은 객체의 소멸자를 호출한 뒤 해당 동적 저장 공간을 반환한다. 포인터 변수 자체를 제거하는 것이 아니라 포인터가 가리키던 객체의 수명을 끝낸다.

해제 후에도 포인터에는 이전 주소 값이 남아 있을 수 있다. 그 주소는 더 이상 유효한 객체를 가리키지 않는 댕글링 포인터(Dangling pointer)다.

```cpp
delete monster;
// monster->Attack(); // 해제된 객체 접근: 정의되지 않은 동작
```

같은 포인터를 곧바로 `nullptr`로 바꾸면 해당 변수의 실수로 인한 재사용을 줄일 수 있다. 하지만 같은 객체를 가리키던 다른 포인터까지 자동으로 바뀌지는 않는다.

```cpp
Monster* alias = monster;
delete monster;
monster = nullptr;
// alias는 여전히 해제된 주소를 보유한다.
```

여러 포인터가 소유권을 공유하는 구조에서는 단순한 null 대입만으로 문제를 해결할 수 없다. 누가 객체를 제거할 책임이 있는지 명확해야 한다.

## 배열 할당은 반드시 배열 해제와 짝을 맞춘다

같은 타입의 객체 여러 개를 동적으로 만든다.

```cpp
Monster* monsters = new Monster[3];
```

각 배열 요소가 순서대로 생성된다. 배열 전체를 정리할 때는 `delete[]`를 사용한다.

```cpp
delete[] monsters;
monsters = nullptr;
```

배열 요소의 소멸자는 생성의 반대 순서로 호출된다. `new[]`로 할당한 포인터에 단일 객체용 `delete`를 사용하면 동작이 정의되지 않는다.

```text
new T      ↔ delete
new T[n]   ↔ delete[]
```

배열 중간 요소를 가리키는 포인터를 해제 함수에 전달해서도 안 된다.

```cpp
Monster* monsters = new Monster[3];
Monster* second = monsters + 1;

// delete second;    // 잘못된 해제
// delete[] second;  // 잘못된 해제
delete[] monsters;
```

해제에는 할당 표현식이 반환한 원래 포인터를 사용해야 한다.

## malloc과 new는 같은 방식으로 섞어 사용할 수 없다

`malloc`은 요청한 바이트 수의 저장 공간을 확보하고 `void*`를 반환하는 C 라이브러리 함수다.

```cpp
#include <cstdlib>

void* storage = std::malloc(sizeof(Monster));
```

`malloc`은 `Monster` 생성자를 호출하지 않는다. 반환된 저장 공간만으로 일반적인 `Monster` 초기화가 수행된 것은 아니다. 클래스 객체를 평범하게 생성하려는 C++ 코드에서는 `new` 표현식이 타입과 생성 과정을 함께 다룬다.

```cpp
Monster* monster = new Monster{100};
```

확보한 방식에 맞는 해제 수단을 사용해야 한다.

```text
malloc / calloc / realloc 계열 → free
new                           → delete
new[]                         → delete[]
```

`malloc`으로 받은 저장 공간을 `delete`로 해제하거나 `new`로 만든 객체를 `free`로 해제하면 동작이 정의되지 않는다. 특히 `free`는 C++ 객체의 소멸자를 호출하지 않는다.

`malloc`은 실패하면 null을 반환하므로 사용 전에 확인해야 한다. 저수준 메모리 관리, C API 연동이나 직접적인 객체 수명 제어가 필요한 코드에서는 별도의 규칙에 따라 사용할 수 있지만 단순 클래스 생성에서 `new`와 임의로 섞지 않는다.

## 할당은 운영체제 호출과 항상 일대일로 대응하지 않는다

프로그램의 할당기는 운영체제로부터 큰 메모리 영역을 확보한 뒤 작은 요청에 재사용할 수 있다. 따라서 `new Monster`를 호출할 때마다 커널이 직접 한 객체 크기의 메모리를 새로 제공한다고 단정할 수 없다.

```text
프로그램의 new 표현식
→ 할당 함수와 런타임 할당기
→ 필요할 때 운영체제의 메모리 기능 이용
```

구체적인 할당 경로는 C++ 런타임, 운영체제, 사용자 정의 할당 함수와 메모리 풀 사용 여부에 따라 달라진다. 성능을 판단할 때는 “힙은 무조건 느리다” 같은 문장보다 실제 할당 횟수, 크기와 사용 환경을 측정해야 한다.

## 잘못된 동적 수명 관리는 정의되지 않은 동작을 만든다

대표적인 오류를 구분한다.

### 메모리 누수

할당한 객체를 해제하지 않은 채 마지막 주소를 잃는다.

```cpp
Monster* monster = new Monster;
monster = nullptr; // 원래 객체를 해제할 주소를 잃음
```

객체가 더 이상 필요하지 않아도 저장 공간이 프로그램에 반환되지 않는다. 반복되면 사용 메모리가 계속 증가할 수 있다.

### 이중 해제

같은 동적 객체를 두 번 해제한다.

```cpp
delete monster;
// delete monster; // 정의되지 않은 동작
```

항상 크래시가 발생한다고 보장되지 않는다. 겉으로 정상처럼 보이거나 나중에 다른 위치에서 문제가 드러날 수도 있으므로 결과를 예측할 수 없는 정의되지 않은 동작이다.

### 해제 후 사용

객체의 수명이 끝난 뒤 포인터로 접근한다.

```cpp
delete monster;
// int hp = monster->Hp(); // 정의되지 않은 동작
```

해제된 저장 공간이 아직 덮어써지지 않아 값이 보이는 경우에도 올바른 접근이 아니다.

### 범위를 벗어난 접근

동적 배열의 유효한 인덱스 밖을 읽거나 쓴다.

```cpp
Monster* monsters = new Monster[3];
// monsters[3].Attack(); // 유효 범위는 0, 1, 2
delete[] monsters;
```

힙에 할당됐다는 사실과 관계없이 배열 범위를 벗어난 접근은 정의되지 않은 동작이다.

## 직접 delete를 작성하지 않는 구조를 우선한다

원시 포인터와 직접적인 `new`, `delete`는 객체 소유권을 코드 흐름으로 추적하게 만든다. 함수 중간에 예외가 발생하거나 여러 반환 경로가 생기면 해제를 빠뜨리기 쉽다.

현대 C++에서는 소유 객체 하나에는 `std::unique_ptr`, 공유 소유가 실제로 필요하면 `std::shared_ptr`, 동적 배열에는 `std::vector`처럼 수명을 자동으로 관리하는 타입을 우선 사용한다.

```cpp
#include <memory>

auto monster = std::make_unique<Monster>(150);
```

이 객체는 스마트 포인터의 수명이 끝날 때 자동으로 정리된다. 스마트 포인터와 컨테이너는 이후 글에서 각각 자세히 다룬다.

이번 글의 원시 `new`와 `delete` 예제는 동적 객체의 생성·소멸 규칙을 직접 확인하기 위한 학습 코드다. 실제 코드에서는 자원 관리 객체가 수명을 맡도록 만드는 RAII(Resource Acquisition Is Initialization)를 우선한다.

## 전체 구현

단일 객체와 배열 객체의 생성·소멸 횟수를 확인하는 예제다.

```cpp
#include <algorithm>
#include <cassert>
#include <iostream>

class Monster
{
public:
    Monster() : Monster(100)
    {
    }

    explicit Monster(int hp) : hp_(std::max(0, hp))
    {
        ++aliveCount_;
        std::cout << "Monster constructed, alive: " << aliveCount_ << '\n';
    }

    Monster(const Monster&) = delete;
    Monster& operator=(const Monster&) = delete;

    ~Monster()
    {
        --aliveCount_;
        std::cout << "Monster destroyed, alive: " << aliveCount_ << '\n';
    }

    int Hp() const
    {
        return hp_;
    }

    static int AliveCount()
    {
        return aliveCount_;
    }

private:
    int hp_;
    inline static int aliveCount_ = 0;
};

void VerifySingleObject()
{
    Monster* monster = new Monster{150};
    assert(monster->Hp() == 150);
    assert(Monster::AliveCount() == 1);

    delete monster;
    monster = nullptr;
    assert(Monster::AliveCount() == 0);
}

void VerifyArray()
{
    Monster* monsters = new Monster[3];
    assert(Monster::AliveCount() == 3);

    delete[] monsters;
    monsters = nullptr;
    assert(Monster::AliveCount() == 0);
}

int main()
{
    VerifySingleObject();
    VerifyArray();
}
```

실행 결과는 다음과 같다.

```text
Monster constructed, alive: 1
Monster destroyed, alive: 0
Monster constructed, alive: 1
Monster constructed, alive: 2
Monster constructed, alive: 3
Monster destroyed, alive: 2
Monster destroyed, alive: 1
Monster destroyed, alive: 0
```

단일 객체는 `delete`로 정리되고 배열의 세 요소는 `delete[]`에서 역순으로 소멸한다. 두 검증 함수가 끝났을 때 살아 있는 몬스터 수가 0인지 확인해 예제 범위의 할당과 해제가 대응했음을 검증한다.

## 동적 할당 코드를 검토할 때 확인할 기준

1. 동적 수명이 정말 필요한가, 지역 객체나 컨테이너로 해결할 수 있는가?
2. 포인터 변수의 수명과 동적 객체의 수명을 구분하는가?
3. 모든 할당에 정확히 한 번의 해제가 대응하는가?
4. `new/delete`, `new[]/delete[]`, `malloc/free`의 짝이 맞는가?
5. 해제 후 남아 있는 모든 별칭 포인터를 고려했는가?
6. 배열의 시작 주소와 유효한 인덱스 범위를 유지하는가?
7. 예외와 조기 반환이 발생해도 자원이 정리되는가?
8. 객체 소유권이 코드에서 한눈에 드러나는가?
9. 직접 해제보다 스마트 포인터와 표준 컨테이너를 사용할 수 있는가?

동적 할당의 핵심은 메모리를 얻는 문법이 아니라 객체 수명의 책임이다. `new`를 호출한 순간부터 누가 언제 그 객체를 제거할지 명확해야 하며, 가능하면 그 책임을 RAII 타입에 맡겨 직접 관리해야 할 상태를 줄인다.
