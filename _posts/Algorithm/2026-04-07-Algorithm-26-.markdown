배열은 인덱스를 알고 있으면 $O(1)$에 원소에 접근한다. 하지만 문자열이나 큰 정수 키를 그대로 배열 인덱스로 사용할 수는 없다.

해시 테이블(Hash Table)은 키를 해시 함수에 넣어 정수 해시 값을 만들고, 그 값을 버킷(Bucket) 인덱스로 변환한다.

```text
key
 │
 ▼
hash(key)
 │
 ▼
hash % bucketCount
 │
 ▼
bucket index
```

키가 어느 버킷에 들어갈지 빠르게 계산할 수 있으므로 삽입·검색·삭제의 평균 시간 복잡도는 $O(1)$이다. 하지만 서로 다른 키가 같은 버킷을 선택하는 충돌(Collision)은 피할 수 없다. 평균 성능은 충돌을 어떻게 처리하고 버킷이 얼마나 차 있는지를 어떻게 관리하는지에 달려 있다.

## 해시 함수와 버킷 인덱스는 역할이 다르다

해시 함수는 키를 일정한 크기의 정수 값으로 변환한다.

```cpp
std::size_t hashValue = std::hash<int>{}(key);
```

해시 값 자체는 현재 배열 크기보다 클 수 있다. 버킷 수로 나눈 나머지를 실제 인덱스로 사용한다.

```cpp
std::size_t index = hashValue % bucketCount;
```

```text
bucketCount = 8
hashValue = 37

37 % 8 = 5
→ 5번 버킷
```

해시 함수와 버킷 인덱스 계산을 구분하면 버킷 수가 바뀔 때 같은 해시 값을 새 인덱스로 다시 배치해야 하는 이유를 이해할 수 있다.

## 서로 다른 키의 충돌은 반드시 발생할 수 있다

가능한 키의 개수는 버킷 수보다 훨씬 많다. 비둘기집 원리에 따라 서로 다른 키가 같은 버킷을 선택하는 경우가 생긴다.

```text
bucketCount = 5

12 % 5 = 2
27 % 5 = 2
42 % 5 = 2

12, 27, 42가 모두 2번 버킷에서 충돌
```

좋은 해시 함수는 충돌을 완전히 없애는 함수가 아니다. 실제 입력 키가 특정 버킷에 몰리지 않고 가능한 한 고르게 퍼지도록 만드는 함수다.

해시 값이 다르면 키도 다르지만, 해시 값이 같다고 키가 같은 것은 아니다. 검색에서는 해시나 버킷만 확인하지 않고 최종적으로 키 동등 비교를 해야 한다.

## 같은 키는 반드시 같은 해시 값을 가져야 한다

해시 컨테이너는 해시 함수와 동등 비교를 함께 사용한다.

```text
KeyEqual(a, b) == true
→ Hash(a) == Hash(b)여야 함
```

같다고 판단하는 두 키가 서로 다른 해시 값을 가지면 서로 다른 버킷에 들어가 검색이 실패할 수 있다.

반대 방향은 요구되지 않는다.

```text
Hash(a) == Hash(b)
→ a와 b가 같을 필요는 없음
→ 충돌 처리 뒤 KeyEqual로 구분
```

사용자 정의 키에서 대소문자를 무시해 문자열을 같다고 판단한다면 해시 함수도 같은 대소문자 규칙을 사용해야 한다.

## 체이닝은 버킷마다 키 목록을 둔다

분리 연결법(Separate Chaining)은 각 버킷에 충돌한 원소의 컨테이너를 둔다.

```text
bucket 0: [ ]
bucket 1: [ ]
bucket 2: [12] → [27] → [42]
bucket 3: [8]
bucket 4: [ ]
```

검색은 키의 버킷을 계산하고 그 버킷 안에서 실제 키를 비교한다.

```cpp
bool Contains(int key) const
{
    const std::list<int>& bucket = buckets_[BucketIndex(key)];
    return std::find(bucket.begin(), bucket.end(), key) != bucket.end();
}
```

모든 키가 하나의 버킷에 몰리면 내부 목록을 선형 탐색하므로 $O(N)$이 된다. 평균 $O(1)$은 적절한 해시 분포와 제한된 부하율을 전제로 한다.

## 체이닝 기반 정수 집합을 구현한다

중복 키를 저장하지 않는 간단한 집합을 만든다.

```cpp
class IntHashSet
{
public:
    explicit IntHashSet(std::size_t bucketCount = 8) : buckets_(std::max<std::size_t>(bucketCount, 1))
    {
    }

    bool Contains(int key) const
    {
        const std::list<int>& bucket = buckets_[BucketIndex(key)];
        return std::find(bucket.begin(), bucket.end(), key) != bucket.end();
    }

    bool Insert(int key)
    {
        if (Contains(key))
        {
            return false;
        }

        if (static_cast<float>(size_ + 1) / buckets_.size() > maxLoadFactor_)
        {
            Rehash(buckets_.size() * 2);
        }

        buckets_[BucketIndex(key)].push_back(key);
        ++size_;
        return true;
    }

    bool Erase(int key)
    {
        std::list<int>& bucket = buckets_[BucketIndex(key)];
        auto found = std::find(bucket.begin(), bucket.end(), key);

        if (found == bucket.end())
        {
            return false;
        }

        bucket.erase(found);
        --size_;
        return true;
    }

    std::size_t Size() const noexcept
    {
        return size_;
    }

    float LoadFactor() const noexcept
    {
        return static_cast<float>(size_) / buckets_.size();
    }

private:
    std::size_t BucketIndex(int key) const
    {
        return std::hash<int>{}(key) % buckets_.size();
    }

    void Rehash(std::size_t newBucketCount)
    {
        std::vector<std::list<int>> oldBuckets = std::move(buckets_);
        buckets_.assign(newBucketCount, {});

        for (const std::list<int>& bucket : oldBuckets)
        {
            for (int key : bucket)
            {
                buckets_[BucketIndex(key)].push_back(key);
            }
        }
    }

private:
    std::vector<std::list<int>> buckets_;
    std::size_t size_ = 0;
    float maxLoadFactor_ = 0.75f;
};
```

`Insert`는 중복을 먼저 확인한다. 새 원소를 추가했을 때 부하율 제한을 넘으면 버킷 수를 늘린 뒤 새 인덱스로 모든 키를 다시 배치한다.

`Rehash` 중에는 원소 수가 달라지지 않으므로 `size_`를 다시 증가시키지 않는다.

## 부하율은 버킷 대비 원소 수다

부하율(Load Factor) $\alpha$는 다음과 같이 정의한다.

$$
\alpha = \frac{N}{B}
$$

- $N$: 저장된 원소 수
- $B$: 버킷 수

```text
원소 6개, 버킷 8개
load factor = 6 / 8 = 0.75
```

체이닝에서는 한 버킷에 여러 원소를 저장할 수 있으므로 부하율이 1을 넘을 수 있다. 하지만 부하율이 커질수록 평균 체인 길이가 증가해 검색과 삭제에서 더 많은 키를 비교하게 된다.

최대 부하율을 정하고 그 값을 넘기기 전에 버킷 수를 늘린다.

```cpp
if (nextLoadFactor > maxLoadFactor)
{
    Rehash(newBucketCount);
}
```

낮은 최대 부하율은 충돌 가능성을 줄이는 대신 더 많은 빈 버킷 메모리를 사용한다. 하나의 고정된 값이 모든 데이터와 환경에 최적이라고 볼 수 없다.

## Rehash는 단순히 배열 크기만 바꾸는 작업이 아니다

버킷 인덱스는 해시 값을 버킷 수로 나눈 나머지다.

```text
hash = 13

버킷 8개:  13 % 8  = 5
버킷 16개: 13 % 16 = 13
```

버킷 수가 바뀌면 기존 키의 인덱스도 달라질 수 있다. 새 버킷 배열을 만든 뒤 모든 원소에 대해 인덱스를 다시 계산해야 한다.

Rehash 한 번의 비용은 $O(N)$이다. 하지만 버킷을 보통 두 배처럼 기하급수적으로 늘리면 매 삽입마다 발생하지 않으므로 여러 삽입에 나눈 분할 상환 비용은 평균 $O(1)$로 설명할 수 있다.

```text
대부분의 Insert → O(1) 평균
가끔 Rehash     → O(N)
여러 삽입의 분할 상환 → O(1) 평균
```

실시간 프레임처럼 한 번의 긴 작업도 문제가 되는 환경에서는 평균만 보지 않고 rehash 발생 시점을 제어하거나 충분한 용량을 미리 예약하는 방법을 고려한다.

## 개방 주소법은 같은 배열의 다른 칸을 찾는다

개방 주소법(Open Addressing)은 버킷 내부에 별도 목록을 두지 않는다. 충돌하면 탐사 규칙에 따라 다른 버킷을 확인한다.

### 선형 탐사

```text
index = hash % bucketCount

충돌 시
index, index+1, index+2, ... 순서로 빈칸 검색
```

```text
초기
[ ][12][ ][ ][ ]

17도 1번 인덱스 선택
[ ][12][17][ ][ ]

22도 1번 인덱스 선택
[ ][12][17][22][ ]
```

연속된 군집이 길어지는 Primary Clustering이 발생할 수 있다.

### 이차 탐사와 이중 해싱

이차 탐사는 $1^2$, $2^2$, $3^2$처럼 간격을 늘리고, 이중 해싱은 두 번째 해시 함수로 이동 간격을 정한다. 충돌한 키들이 같은 탐사 경로에 몰리는 문제를 줄일 수 있지만 버킷 수와 탐사식의 조합을 주의해야 한다.

개방 주소법에서는 빈 버킷, 사용 중인 버킷과 삭제된 버킷을 구분해야 한다.

```text
Empty     → 이 위치 뒤에는 해당 탐사 경로의 키가 없음
Occupied  → 키 비교 후 계속 탐사 가능
Deleted   → 삽입에는 재사용 가능하지만 검색은 계속 진행
```

삭제 위치를 즉시 Empty로 바꾸면 그 뒤에 충돌로 저장된 키를 검색하지 못할 수 있다. 삭제 표식인 Tombstone이 필요한 이유다.

## 체이닝과 개방 주소법을 비교한다

| 비교 | Separate Chaining | Open Addressing |
|---|---|---|
| 충돌 처리 | 버킷별 목록 | 다른 버킷 탐사 |
| 부하율 | 1을 넘을 수 있음 | 반드시 1 미만 |
| 추가 메모리 | 노드·컨테이너 오버헤드 | 상태 정보 필요 |
| 데이터 배치 | 분산된 노드일 수 있음 | 배열 안에 연속 저장 |
| 삭제 | 목록에서 제거 | Tombstone 처리 필요 |
| 성능 저하 | 긴 체인 | 긴 탐사 군집 |

개방 주소법은 원소가 배열 안에 있어 캐시 지역성이 좋을 수 있지만 부하율이 1에 가까워질수록 빈칸을 찾는 탐사 길이가 급격히 늘어난다. 체이닝은 삭제가 단순하고 높은 부하율도 표현할 수 있지만 각 체인의 저장 방식에 따른 메모리 비용이 있다.

## 시간 복잡도의 평균과 최악을 구분한다

| 연산 | 평균 | 최악 |
|---|---:|---:|
| 검색 | $O(1)$ | $O(N)$ |
| 삽입 | $O(1)$ 분할 상환 | $O(N)$ |
| 삭제 | $O(1)$ | $O(N)$ |

모든 키가 같은 버킷이나 같은 탐사 경로에 몰리면 선형 탐색과 비슷해진다. 해시 함수가 실제 입력에 대해 고르게 분포하고 부하율이 적절히 관리된다는 전제에서 평균 $O(1)$을 기대한다.

외부 입력이 해시 키를 제어할 수 있는 환경에서는 의도적인 충돌 입력이 성능 문제로 이어질 수도 있다. 보안이 중요한 입력에서는 라이브러리 구현과 해시 정책을 함께 검토해야 한다.

## 사용자 정의 키를 unordered_map에 사용한다

좌표를 키로 사용하는 예를 생각해 보자.

```cpp
struct Pos
{
    int y;
    int x;

    bool operator==(const Pos& other) const
    {
        return y == other.y && x == other.x;
    }
};

struct PosHash
{
    std::size_t operator()(const Pos& pos) const noexcept
    {
        std::size_t yHash = std::hash<int>{}(pos.y);
        std::size_t xHash = std::hash<int>{}(pos.x);
        return yHash ^ (xHash + 0x9e3779b9u + (yHash << 6) + (yHash >> 2));
    }
};
```

```cpp
std::unordered_map<Pos, int, PosHash> distance;
distance[Pos{3, 5}] = 20;
```

좌표가 같으면 `yHash`, `xHash` 조합도 같아야 한다. 단순히 `yHash ^ xHash`만 사용하면 `(y, x)`와 `(x, y)`가 같은 결과를 만드는 등 입력 패턴에 따라 충돌이 늘 수 있어 두 성분의 위치를 구분해 섞는다.

해시 조합 공식 하나가 모든 키 분포에 최적이라는 뜻은 아니다. 실제 키 범위와 패턴을 기준으로 분포를 확인해야 한다.

## unordered_map의 용량을 미리 준비한다

원소 수를 예상할 수 있다면 `reserve`로 필요한 저장 공간을 미리 요청할 수 있다.

```cpp
std::unordered_map<int, Player> players;
players.reserve(expectedPlayerCount);
players.max_load_factor(0.75f);
```

불필요한 rehash 횟수를 줄일 수 있다. 다만 실제 버킷 수는 구현이 선택하며 `reserve(n)`이 정확히 버킷을 `n`개 만든다는 뜻은 아니다.

Rehash는 반복자를 무효화할 수 있으므로 컨테이너를 순회하면서 삽입할 때는 해당 연산의 무효화 규칙을 확인해야 한다.

## 전체 검증 예제

```cpp
#include <algorithm>
#include <cassert>
#include <cstddef>
#include <functional>
#include <list>
#include <utility>
#include <vector>

// IntHashSet 구현은 앞의 코드와 같다.

int main()
{
    IntHashSet values(2);

    assert(values.Insert(12));
    assert(values.Insert(27));
    assert(values.Insert(42));
    assert(!values.Insert(27));
    assert(values.Size() == 3);

    assert(values.Contains(12));
    assert(values.Contains(27));
    assert(values.Contains(42));
    assert(!values.Contains(99));

    assert(values.Erase(27));
    assert(!values.Erase(27));
    assert(!values.Contains(27));
    assert(values.Contains(12));
    assert(values.Contains(42));
}
```

작은 초기 버킷 수를 사용하면 테스트 중 rehash가 발생한다. Rehash 뒤에도 모든 기존 키를 찾을 수 있는지와 원소 수가 유지되는지를 함께 확인한다.

## 해시 테이블을 구현할 때 확인할 기준

1. 같은 키가 항상 같은 해시 값을 만드는가?
2. 해시 값과 키 동등 비교를 구분하는가?
3. 서로 다른 키의 충돌을 정상적인 상황으로 처리하는가?
4. 버킷 수가 0이 되지 않도록 보장하는가?
5. 부하율과 최대 부하율의 의미를 구분하는가?
6. Rehash에서 모든 기존 키의 버킷을 다시 계산하는가?
7. Rehash 중 원소 수를 중복 증가시키지 않는가?
8. 체이닝에서 한 버킷에 몰리는 최악 상황을 고려하는가?
9. 개방 주소법의 삭제에서 Tombstone을 사용하는가?
10. 탐사가 테이블 전체를 순환했을 때 종료하는가?
11. 사용자 정의 해시와 동등 비교가 같은 키 정의를 사용하는가?
12. 반복자와 참조의 무효화 규칙을 확인하는가?
13. 예상 원소 수를 안다면 용량을 미리 준비하는가?
14. 평균 $O(1)$과 최악 $O(N)$을 구분해서 설명하는가?

해시 테이블의 핵심은 키를 배열 인덱스로 바꾸는 공식 하나가 아니다. 충돌은 반드시 발생할 수 있다는 전제에서 실제 키를 다시 비교하고, 부하율이 높아지면 버킷을 늘려 원소를 재배치하며 평균 탐색 길이를 제한하는 전체 구조에 있다.
