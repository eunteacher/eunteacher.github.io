선형 자료구조는 데이터를 한 줄의 순서로 다룬다. 배열, 동적 배열과 연결 리스트는 모두 선형 자료구조지만 데이터를 메모리에 놓는 방법이 다르다. 이 차이가 인덱스 접근, 삽입·삭제, 순회 성능과 참조 안정성을 결정한다.

```text
배열·동적 배열: 요소를 연속된 메모리에 저장
연결 리스트:    떨어진 노드를 포인터로 연결
```

이번 글은 직접 구현하기 전에 세 구조의 비용을 비교하고 선택 기준을 세우는 단계다. 동적 배열과 연결 리스트의 내부 구현은 다음 두 글에서 각각 다룬다.

## 선형이라는 말은 연속 메모리라는 뜻이 아니다

선형 자료구조에서 각 데이터는 논리적으로 이전과 다음 순서를 가진다.

```text
A → B → C → D
```

이 순서가 실제 메모리 주소까지 연속이라는 뜻은 아니다.

```text
배열
주소     1000  1004  1008  1012
데이터   [ A ][ B ][ C ][ D ]

연결 리스트
주소     1000       8400       3200       7100
노드     [ A | • ] → [ B | • ] → [ C | • ] → [ D | null ]
```

배열은 논리적 순서와 물리적 배치가 모두 연속이다. 연결 리스트는 노드의 연결 관계로 순서만 유지하며, 각 노드가 메모리의 어디에 있는지는 연속일 필요가 없다.

## 고정 배열은 크기를 타입에 포함한다

C++의 기본 배열이나 `std::array`는 원소 수가 생성할 때 정해지고 이후 바뀌지 않는다.

```cpp
int scores[4]{10, 20, 30, 40};
std::array<int, 4> levels{1, 2, 3, 4};
```

`std::array<int, 4>`와 `std::array<int, 5>`는 서로 다른 타입이다. 원소는 연속해서 저장되며 컨테이너 자체가 원소를 직접 포함한다.

인덱스 `i`의 주소는 시작 주소에서 원소 크기만큼 건너뛰어 계산할 수 있다.

$$
\text{address}(i) = \text{base address} + i \times \text{sizeof}(T)
$$

따라서 임의 접근(Random Access)은 $O(1)$이다.

```cpp
int value = levels[2];
```

여기서 $O(1)$은 인덱스 값과 관계없이 주소 계산 횟수가 일정하다는 뜻이다. 범위를 벗어난 `operator[]` 접근은 검사되지 않으며 Undefined Behavior가 된다. 범위 검사가 필요하면 `at()`을 사용한다.

```cpp
int value = levels.at(2);
```

고정 배열은 원소 수가 컴파일 시점에 알려져 있거나 상한이 작고 명확할 때 적합하다. 실행 중 원소 수가 계속 변해야 한다면 크기를 억지로 크게 잡기보다 동적 배열을 검토한다.

## 동적 배열은 size와 capacity를 분리한다

`std::vector`도 원소를 연속해서 저장하지만 실행 중 크기를 바꿀 수 있다.

```cpp
std::vector<int> values;
values.push_back(10);
values.push_back(20);
values.push_back(30);
```

이를 가능하게 하려면 현재 원소 수와 확보한 저장 공간을 따로 관리해야 한다.

```text
size:     실제로 생성돼 있는 원소 수
capacity: 재할당 없이 저장할 수 있는 원소 수

size = 3, capacity = 5
[10][20][30][  ][  ]
```

`size()`는 접근할 수 있는 유효 원소 수다. `capacity()`의 남는 공간에는 아직 원소가 존재하지 않으므로 인덱스로 접근할 수 없다.

### 공간이 부족하면 더 큰 메모리로 이동한다

`size == capacity`인 상태에서 원소를 추가하려면 더 큰 연속 공간이 필요하다.

```text
1. 더 큰 메모리 블록 확보
2. 기존 원소를 새 공간으로 이동 또는 복사
3. 새 원소 생성
4. 기존 메모리 해제
```

한 번의 재할당은 기존 원소 수에 비례하므로 $O(N)$이다. 매번 한 칸만 늘리면 추가를 $N$번 하는 전체 비용이 $O(N^2)$까지 커질 수 있다. 그래서 구현은 보통 capacity를 기하급수적으로 늘려 재할당 횟수를 줄인다.

증가 배율은 C++ 표준이 정하지 않는다. 1.5배나 2배는 흔한 구현 전략일 뿐 모든 표준 라이브러리가 같은 값을 사용한다고 가정하면 안 된다.

개별 `push_back`은 재할당 시 $O(N)$이지만 여러 번의 추가 비용을 전체 연산에 나눠 계산하면 평균적인 분할 상환 시간(Amortized Time)은 $O(1)$이다.

### reserve는 size를 늘리지 않는다

추가할 개수를 미리 안다면 `reserve`로 재할당 횟수를 줄일 수 있다.

```cpp
std::vector<int> values;
values.reserve(100);

for (int i = 0; i < 100; ++i)
{
    values.push_back(i);
}
```

`reserve(100)`은 capacity를 최소 100으로 확보하지만 size는 여전히 0이다. 반면 `resize(100)`은 실제 원소를 100개 만든다.

```text
reserve(100): 저장 공간 확보, size 유지
resize(100):  원소 수를 100개로 변경
clear():      모든 원소 제거, 일반적으로 capacity 유지
```

표준은 `clear()`가 capacity를 줄이지 않도록 규정한다. 메모리 축소가 필요하면 `shrink_to_fit()`을 요청할 수 있지만, 이 함수도 반드시 capacity를 줄인다고 보장하지는 않는다.

## 연결 리스트는 노드의 링크로 순서를 만든다

단일 연결 리스트의 노드는 데이터와 다음 노드를 가리키는 포인터를 가진다.

```cpp
template<typename T>
struct Node
{
    T value;
    Node* next = nullptr;
};
```

`std::list`는 앞뒤 방향으로 이동할 수 있는 이중 연결 리스트다. 개념적으로 각 노드에 이전·다음 링크가 필요하다.

```text
null ← [prev | A | next] ⇄ [prev | B | next] ⇄ [prev | C | next] → null
```

노드가 연속될 필요가 없으므로 배열처럼 `시작 주소 + i × 원소 크기`로 $i$번째 원소의 주소를 계산할 수 없다. 처음부터 링크를 $i$번 따라가야 하므로 위치 접근은 $O(N)$이다.

```cpp
std::list<int> values{10, 20, 30};
auto it = values.begin();
std::advance(it, 2);
int value = *it;
```

이 때문에 `std::list`에는 `operator[]`가 없다.

## 리스트의 삽입·삭제가 O(1)이라는 말의 조건

연결 리스트는 삽입할 위치의 이터레이터를 이미 가지고 있다면 주변 링크만 변경하면 된다.

```text
삽입 전: A ⇄ C
삽입 후: A ⇄ B ⇄ C
```

```cpp
auto position = values.begin();
std::advance(position, 1);
values.insert(position, 15);
```

실제 `insert` 자체는 $O(1)$이지만, 위 코드에서 위치를 찾는 `advance`는 $O(N)$일 수 있다. 값 `15`를 찾아 삭제하는 전체 작업도 다음 두 비용으로 나뉜다.

```text
삭제할 값 탐색: O(N)
찾은 노드 제거: O(1)
전체 작업:      O(N)
```

따라서 “수정이 많으면 연결 리스트가 빠르다”라고만 결론 내리면 조건을 놓친다. 수정 위치를 이미 알고 있는지, 순회가 얼마나 많은지와 메모리 사용량까지 함께 봐야 한다.

## 배열도 중간 삽입·삭제는 원소를 이동한다

동적 배열 중간에 원소를 추가하면 뒤쪽 원소를 한 칸씩 이동해야 한다.

```text
삽입 전: [10][20][30][40][  ]
20 앞에 15 삽입
이동:                40 →
                 30 →
             20 →
삽입 후: [10][15][20][30][40]
```

위치를 알고 있어도 이동할 원소 수에 비례하므로 삽입과 삭제는 $O(N)$이다. 하지만 Big-O가 같다고 실제 시간이 항상 같지는 않다. 연속된 원소의 이동은 캐시 지역성이 좋고, 단순 타입은 효율적인 메모리 이동으로 처리될 여지가 있다.

반대로 연결 리스트는 각 노드의 링크와 할당 관리 비용이 들고 노드를 따라갈 때 메모리 접근이 분산된다. 중간 삽입·삭제가 있다는 이유만으로 `std::list`가 `std::vector`보다 빠르다고 단정할 수 없다.

## 순회에서는 연속된 메모리가 유리하다

CPU는 요청한 주소 주변 데이터를 캐시 라인 단위로 가져온다. 배열의 다음 원소는 가까운 주소에 있으므로 순차 접근에서 가져온 데이터를 계속 활용하기 쉽다.

```text
vector: [A][B][C][D]  → 다음 원소가 가까움
list:   [A]──→       [B]──→ [C]       → 다음 노드 주소가 분산될 수 있음
```

연결 리스트는 다음 노드 포인터를 읽어야 다음 주소를 알 수 있고, 그 주소가 캐시에 없으면 대기 비용이 발생한다. 이 차이는 점근적 복잡도 표에는 나타나지 않는다.

성능이 중요한 선택은 “둘 다 $O(N)$”이라는 정보만으로 끝내지 않고 실제 데이터 크기와 접근 패턴으로 측정해야 한다.

## 참조와 이터레이터의 수명도 다르다

자료구조를 선택할 때 기존 원소를 가리키는 포인터, 참조와 이터레이터가 언제 무효화되는지도 중요하다.

### vector

- capacity가 바뀌는 재할당이 발생하면 모든 원소의 주소가 바뀌므로 기존 포인터·참조·이터레이터가 모두 무효화된다.
- 재할당이 없는 삽입에서도 삽입 위치와 그 뒤를 가리키는 이터레이터가 무효화될 수 있다.
- 삭제하면 삭제 위치와 그 뒤의 원소가 앞으로 이동하므로 해당 범위의 이터레이터가 무효화된다.

### list

- 삽입은 기존 노드를 이동시키지 않으므로 기존 원소를 가리키는 이터레이터가 유지된다.
- 삭제한 노드를 가리키는 이터레이터만 무효화된다.

리스트의 안정적인 주소가 필요한 설계도 있지만, 제거된 원소의 이터레이터까지 유효한 것은 아니다.

## 연산 비용 비교

원소가 $N$개일 때 대표적인 비용은 다음과 같다.

| 연산 | 고정 배열 | `std::vector` | `std::list` |
|---|---:|---:|---:|
| 인덱스 접근 | $O(1)$ | $O(1)$ | 지원하지 않음 |
| 값 탐색 | $O(N)$ | $O(N)$ | $O(N)$ |
| 뒤에 삽입 | 크기 변경 불가 | 분할 상환 $O(1)$ | $O(1)$ |
| 중간 위치 탐색 | $O(1)$ 인덱스가 있을 때 | $O(1)$ 인덱스가 있을 때 | $O(N)$ |
| 위치를 안 상태의 중간 삽입 | 크기 변경 불가, 직접 이동 시 $O(N)$ | $O(N)$ | $O(1)$ |
| 위치를 안 상태의 중간 삭제 | 크기 변경 불가, 직접 이동 시 $O(N)$ | $O(N)$ | $O(1)$ |
| 순차 저장 | 연속 | 연속 | 비연속 |
| 원소 외 추가 메모리 | 거의 없음 | 미사용 capacity | 노드 링크와 할당 관리 비용 |

`std::list`의 끝 삽입이 $O(1)$인 것은 컨테이너가 끝 위치를 관리하기 때문이다. 직접 만든 단일 연결 리스트가 꼬리 포인터를 보관하지 않는다면 뒤에 삽입하기 위해 전체를 순회해야 하므로 $O(N)$이 될 수 있다.

## 동적 배열을 직접 구현할 때 필요한 상태

동적 배열을 직접 구현하려면 저장 공간의 주소, 실제 원소 수와 현재 용량을 각각 관리한다.

```cpp
T* data = nullptr;
int vectorSize = 0;
int vectorCapacity = 0;
```

`push_back`은 size와 capacity가 같을 때 기존 capacity의 1.5배를 계산하고, 0에서 증가하지 않는 경우 1을 더한다.

```cpp
if (vectorSize == vectorCapacity)
{
    int newCapacity = static_cast<int>(vectorCapacity * 1.5f);

    if (newCapacity == vectorCapacity)
    {
        ++newCapacity;
    }

    reserve(newCapacity);
}
```

이 세 상태를 사용하면 원소 추가와 재할당 흐름을 직접 표현할 수 있다. 구현 과정에서는 메모리와 객체의 수명도 함께 생각해야 한다.

- 동적으로 확보한 저장 공간은 소유 객체가 사라질 때 해제한다.
- 컨테이너를 복사할 때 저장 공간까지 새로 만들지, 복사를 허용하지 않을지 정책을 정한다.
- capacity는 저장 가능한 공간의 크기이고 size는 실제 원소 수이므로 두 범위의 객체 수명을 구분한다.
- 재할당 도중 예외가 발생해도 기존 데이터와 컨테이너 상태를 유지할 수 있어야 한다.
- `clear`는 원소를 제거해 size를 0으로 만들며, 확보한 capacity는 유지한다.

이 내용은 다음 동적 배열 구현편에서 재할당 과정과 메모리 소유권을 따라가며 자세히 살펴본다.

## 세 자료구조를 직접 사용하는 예제

다음 코드는 고정 배열의 인덱스 접근, 동적 배열의 크기 증가와 연결 리스트의 이터레이터 기반 삽입·삭제를 비교한다.

```cpp
#include <array>
#include <iostream>
#include <list>
#include <vector>

template<typename Container>
void Print(const char* name, const Container& container)
{
    std::cout << name << ':';

    for (int value : container)
    {
        std::cout << ' ' << value;
    }

    std::cout << '\n';
}

int main()
{
    std::array<int, 4> fixed{10, 20, 30, 40};
    std::cout << "array[2]: " << fixed[2] << '\n';

    std::vector<int> dynamic;
    dynamic.reserve(5);

    for (int value : fixed)
    {
        dynamic.push_back(value);
    }

    dynamic.insert(dynamic.begin() + 2, 25);
    Print("vector", dynamic);
    std::cout << "vector size: " << dynamic.size() << '\n';
    std::cout << "capacity covers size: " << std::boolalpha << (dynamic.capacity() >= dynamic.size()) << '\n';

    std::list<int> linked{10, 20, 30, 40};
    auto position = linked.begin();
    ++position;
    ++position;
    auto inserted = linked.insert(position, 25);
    linked.erase(inserted);
    Print("list", linked);
}
```

실행 결과는 다음과 같다.

```text
array[2]: 30
vector: 10 20 25 30 40
vector size: 5
capacity covers size: true
list: 10 20 30 40
```

이 예제는 사용법과 결과를 확인하기 위한 것이며 자료구조의 실제 성능을 비교하는 benchmark는 아니다. 시간 측정 없이 한쪽이 더 빠르다는 결론을 내릴 수는 없다.

## 어떤 구조를 선택할까

### 고정 배열이 자연스러운 경우

- 원소 수가 컴파일 시점에 정해진다.
- 크기가 변하지 않는 작은 테이블이나 방향 벡터를 저장한다.
- 별도 동적 할당 없이 값을 객체 안에 직접 포함하고 싶다.

### vector가 기본 선택이 되기 쉬운 경우

- 원소 수가 실행 중 변한다.
- 인덱스 접근과 전체 순회가 잦다.
- 주로 뒤에 원소를 추가한다.
- 원소의 연속 저장이 필요하다.

추가 개수를 예상할 수 있다면 `reserve`를 함께 검토한다. 다만 기존 원소의 주소를 장기간 보관한다면 재할당에 따른 무효화를 고려해야 한다.

### list를 검토할 수 있는 경우

- 중간 삽입·삭제 위치를 이터레이터로 이미 알고 있다.
- 삽입·삭제 후에도 다른 원소의 이터레이터와 참조가 유지돼야 한다.
- 임의 접근이 필요 없고 노드별 추가 메모리와 낮은 지역성을 감수할 수 있다.

대부분의 데이터를 순회하면서 가끔 삽입·삭제하는 정도라면 `vector`가 더 나을 수도 있다. 자료구조 이름보다 실제 작업의 비율과 데이터 규모를 기준으로 결정한다.

## 선택 전에 확인할 질문

1. 원소 수가 고정인가, 실행 중 변하는가?
2. 인덱스로 임의 접근해야 하는가?
3. 삽입·삭제 위치를 이미 알고 있는가, 먼저 탐색해야 하는가?
4. 삽입·삭제는 앞·중간·뒤 중 어디에서 주로 발생하는가?
5. 전체 원소를 순차적으로 얼마나 자주 읽는가?
6. 원소를 가리키는 포인터·참조·이터레이터가 오래 유지돼야 하는가?
7. 원소당 링크와 개별 할당 비용을 감수할 수 있는가?
8. 최대 개수를 예상해 vector의 capacity를 미리 확보할 수 있는가?

이번 학습의 핵심은 “배열은 조회, 리스트는 수정”이라는 문장을 외우는 것이 아니다. 메모리 배치가 각 연산의 비용을 어떻게 만드는지 이해하고, 위치 탐색부터 실제 수정까지 전체 작업 비용을 계산해야 한다.
