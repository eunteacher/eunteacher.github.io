# 컴퓨터 구조 Day 5 - 입출력과 인터럽트

Day 4에서는 CPU가 데이터를 기다리는 시간을 줄이기 위한 캐시와 메모리 계층을 살펴봤다.

컴퓨터는 계산만 하는 장치가 아니다. 키보드 입력을 받고, 화면에 결과를 보여 주고, 저장장치에서 파일을 읽어야 한다. CPU는 이런 장치들과 어떻게 일을 주고받을까?

오늘의 목표는 **입출력의 의미를 이해하고, 장치의 상태를 반복해서 확인하는 방법과 장치가 알림을 보내는 방법의 차이를 설명할 수 있는 것**이다.

## 입출력은 데이터를 받아들이거나 내보내는 일이다

컴퓨터가 외부에서 데이터를 받아들이는 것을 **입력(Input)**, 처리 결과나 데이터를 외부로 내보내는 것을 **출력(Output)**이라고 한다. 둘을 합쳐 **입출력(I/O, Input/Output)**이라고 부른다.

| 구분 | 예시 |
|---|---|
| 입력 | 키보드의 키를 누르거나 마우스를 움직임 |
| 출력 | 화면에 그림을 표시하거나 스피커로 소리를 냄 |

저장장치도 데이터를 주고받는 대상이다. CPU와 메모리에서 실행되는 프로그램을 기준으로 보면, 파일을 읽어 들이는 작업은 입력이고 파일을 기록하는 작업은 출력이다.

```text
파일 읽기: 저장장치 → 메모리 쪽으로 데이터가 들어옴
파일 쓰기: 메모리 쪽의 데이터 → 저장장치에 기록
```

즉, 입력과 출력은 키보드와 모니터에만 해당하는 말이 아니다.

## CPU는 장치에 작업을 요청하고 상태를 확인한다

CPU가 직접 키보드의 물리적인 키를 감지하거나 SSD의 내부 동작을 하나씩 수행하는 것은 아니다.

장치 쪽에는 명령을 받아 장치를 동작시키고 상태를 관리하는 하드웨어가 있다. 이를 **장치 제어기 또는 장치 컨트롤러(Device Controller)**라고 한다.

운영체제에는 장치의 사용 방법에 맞춰 제어기와 통신하는 소프트웨어도 있다. 이것을 **장치 드라이버(Device Driver)**라고 한다.

| 구분 | 역할 |
|---|---|
| 장치 제어기 | 장치를 제어하고 상태를 관리하는 하드웨어 |
| 장치 드라이버 | 운영체제에서 장치를 사용하도록 돕는 소프트웨어 |

저장장치에서 파일을 읽는 상황을 단순화하면 다음과 같다.

```text
CPU가 드라이버의 명령어를 실행해 읽기 작업 요청
    ↓
장치 제어기가 장치의 읽기 작업 진행
    ↓
작업 완료 여부 확인
    ↓
읽은 데이터를 프로그램에서 사용
```

운영체제는 프로그램 실행과 장치 사용 같은 컴퓨터의 자원을 관리하는 기본 소프트웨어다. 오늘은 드라이버의 구현보다 **장치와 작업을 주고받는 중간 역할이 있다**는 점만 알아두자.

## 폴링: 상태를 반복해서 확인한다

장치의 작업이 끝났는지 알아내는 가장 직접적인 방법은 상태를 반복해서 읽는 것이다. 이런 방식을 **폴링(Polling)**이라고 한다.

```text
CPU: 작업이 끝났는가? → 아직 안 끝남
CPU: 작업이 끝났는가? → 아직 안 끝남
CPU: 작업이 끝났는가? → 완료
CPU: 결과 처리
```

일상생활에서는 주문한 음료가 나왔는지 카운터를 여러 번 확인하는 상황과 비슷하다.

폴링에서는 **확인하는 쪽이 상태를 물어본다.** 장치가 작업 중인 동안 계속 확인하는 방식이라면 CPU가 같은 확인 작업에 시간을 쓰게 된다.

다만 폴링이 언제나 쉬지 않고 확인하는 것만을 뜻하지는 않는다. 일정한 간격으로 확인하거나 다른 작업 사이에 확인할 수도 있다.

## 인터럽트: 처리가 필요하다는 알림을 보낸다

반대로 장치 쪽에서 CPU에 처리가 필요하다는 신호를 보낼 수도 있다. 이런 알림을 통해 CPU가 현재의 실행 흐름을 잠시 바꾸어 필요한 처리를 하도록 하는 것이 **인터럽트(Interrupt)**다.

오늘은 입출력 장치가 보내는 하드웨어 인터럽트를 중심으로 살펴본다.

```text
CPU: 장치에 작업 요청
    ↓
CPU: 다른 명령어 실행
장치: 요청받은 작업 진행
    ↓
장치 쪽에서 작업 완료 인터럽트 요청
    ↓
CPU: 인터럽트를 받아 관련 처리 실행
```

음료가 준비되면 진동벨로 알려 주는 상황과 비슷하다. 주문한 사람이 계속 카운터를 확인하지 않아도 준비됐다는 사실을 알 수 있다.

입출력 인터럽트는 작업 완료뿐 아니라 입력 데이터 도착 등 여러 사건을 알리는 데 사용된다.

**인터럽트는 장치의 작업 자체를 빠르게 만드는 기능이 아니다. CPU가 상태를 계속 확인할 필요를 줄여 주는 방법이다.**

## 인터럽트를 받으면 관련 처리 코드를 실행한다

인터럽트를 처리하려면 어떤 알림인지 확인하고 필요한 일을 수행하는 코드가 있어야 한다. 이 코드를 **인터럽트 처리 루틴 또는 인터럽트 핸들러(Interrupt Handler)**라고 한다.

처리의 기본 흐름은 다음과 같다.

1. 장치 쪽에서 인터럽트 요청을 보낸다.
2. CPU가 인터럽트를 받아들일 수 있는 시점에 요청을 받아들인다.
3. 실행을 이어가는 데 필요한 위치와 상태를 보존한다.
4. 해당 인터럽트의 처리 코드를 실행한다.
5. 처리를 마친 뒤 보존한 상태를 바탕으로 실행을 이어갈 수 있다.

```text
원래 실행:  작업 A 진행 ──┐                 ┌── 작업 A 이어서 진행
                         ↓                 ↑
인터럽트 처리:           알림 확인 → 필요한 처리
```

인터럽트 요청이 도착했다고 모든 상황에서 즉시 처리되는 것은 아니다. CPU의 상태나 우선순위에 따라 처리가 늦춰질 수 있다.

그림은 기본 원리를 설명하기 위해 원래 작업으로 돌아가는 경우를 보여 준다. 실제로 어떤 작업을 이어서 실행할지는 운영체제의 판단도 관여하며, 자세한 내용은 운영체제에서 다룬다.

## 키보드 입력으로 연결해 보기

게임에서 이동 키를 누르는 상황을 단순화해 보자.

```text
사용자가 키를 누름
    ↓
입력 장치 쪽에서 입력을 감지
    ↓
인터럽트를 통해 입력 관련 처리가 필요함을 알림
    ↓
운영체제와 드라이버가 입력 정보를 처리
    ↓
게임이 전달받거나 조회한 입력 정보를 이용
    ↓
게임의 이동 코드 실행
```

키보드 인터럽트를 받았다는 이유만으로 CPU가 곧바로 게임의 캐릭터 이동 함수를 실행하는 것은 아니다. 운영체제와 입력 처리 과정을 거쳐 게임에서 사용할 정보로 이어진다.

실제 연결 방식에 따라 세부 과정은 다르다. 여기서는 **입력 감지, 알림, 입력 처리, 게임 로직 실행이 구분되는 단계**라는 점을 이해하면 된다.

## 폴링과 인터럽트 비교하기

| 구분 | 폴링 | 인터럽트 |
|---|---|---|
| 상태를 아는 방법 | 확인하는 쪽이 상태를 반복해서 읽음 | 장치 쪽에서 처리 요청을 알림 |
| 대기 중 CPU 사용 | 확인 작업에 CPU 시간을 사용 | 계속 확인하는 대신 다른 일을 할 기회가 생김 |
| 필요한 처리 | 상태 확인과 결과 처리 | 인터럽트 요청을 받아 관련 처리 실행 |
| 비유 | 음료가 나왔는지 여러 번 확인 | 준비되면 진동벨로 알림 |

인터럽트도 실행 상태를 보존하고 처리 코드를 실행하는 비용이 있다. 따라서 인터럽트가 언제나 폴링보다 빠르다고 단정할 수는 없다. 작업의 빈도나 대기 시간에 따라 적합한 방식이 달라진다.

또한 게임 코드가 매 프레임 입력 상태를 조회하는 것과, 하드웨어 수준에서 운영체제가 입력을 전달받는 방식은 구분해야 한다. **서로 다른 단계에서 폴링과 인터럽트를 함께 사용할 수도 있다.**

## 핵심 정리

- **입출력:** 컴퓨터가 장치와 데이터를 받아들이거나 내보내는 일
- **장치 제어기:** 장치의 동작과 상태를 관리하는 하드웨어
- **장치 드라이버:** 운영체제에서 장치를 사용하도록 돕는 소프트웨어
- **폴링:** 확인하는 쪽이 상태를 반복해서 읽는 방식
- **인터럽트:** 처리가 필요한 사건을 알려 CPU가 관련 처리를 하도록 하는 방식
- **인터럽트 핸들러:** 인터럽트에 대응하는 처리 코드

**폴링은 상태를 확인하러 가는 방식이고, 인터럽트는 알림을 받아 처리하는 방식이다.**

CPU는 입출력 장치와 역할을 나누고, 인터럽트를 활용해 장치의 상태를 계속 확인하는 부담을 줄일 수 있다.
