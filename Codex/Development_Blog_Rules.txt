개발 블로그 개편 Codex 작업 규칙
================================

이 문서는 개발 블로그 글을 개편할 때 Codex가 지켜야 할 규칙을 정의한다.
영어 및 태국어 글은 현재 개편 대상에서 제외한다.


1. 기존 글과 사용자 작업 보호
------------------------------

1. 영어·태국어 글은 수정하지 않는다.
2. 개발 글이라도 현재 작업 범위에 포함된 글만 수정한다.
3. 사용자가 작성 중인 변경사항은 덮어쓰거나 되돌리지 않는다.
4. 이미지와 코드 예제 등 기존 자료는 명확한 이유 없이 제거하지 않는다.
5. 한글이 터미널에서 깨져 보여도 실제 파일이 손상됐다고 단정하지 않는다.
6. 모든 Markdown 파일은 UTF-8을 유지한다.
7. 텍스트 수정은 인코딩이 안전한 방식으로 수행한다.


2. 실제 내용에 근거해서 작성
-----------------------------

1. 글 제목만 보고 내용을 추측하지 않는다.
2. 기존 본문, 코드, 이미지, 학습 순서를 먼저 확인한다.
3. Unreal 프로젝트와 직접 관련된 글은 가능하면 실제 SmileShooter 코드와 구조를 확인한다.
4. 존재하지 않는 함수, 클래스, 실행 결과 또는 개발 과정을 만들어내지 않는다.
5. 확인하지 못한 내용을 실제 검증이 끝난 사실처럼 표현하지 않는다.
6. 이론적 설명과 프로젝트에서 실제로 사용한 방식을 구분한다.
7. 과거에 맞았던 내용도 현재 코드와 다르면 현재 상태를 기준으로 쓴다.
8. 오류 해결 글은 반드시 `증상 → 확인 과정 → 원인 → 해결 → 검증 결과`를 구분한다.


3. 고정 포맷을 강제하지 않기
-----------------------------

모든 개발 글에 똑같은 목차를 적용하지 않는다.
글의 성격을 먼저 판단하고 그에 맞는 구조를 선택한다.

- 개념 설명: 문제의식 → 핵심 개념 → 동작 원리 → 예제 → 정리
- 코드 실습: 목표 → 구현 과정 → 코드 → 실행 결과 → 개선점
- 자료구조·알고리즘: 문제 → 원리 → 구현 → 복잡도 → 한계와 활용
- 오류 해결: 증상 → 원인 추적 → 근본 원인 → 수정 → 검증
- 아키텍처: 요구사항 → 책임 분리 → 데이터 흐름 → 설계 이유 → 트레이드오프
- Unreal 기능 구현: 목표 → 관련 객체의 역할 → 호출 흐름 → 구현 → 에디터 설정 → 멀티플레이 검증
- 학습 기록: 오늘 이해한 것 → 헷갈렸던 부분 → 직접 확인한 내용 → 다음 학습
- 비교 글: 비교 기준 → 방식별 특징 → 실제 차이 → 선택 기준

핵심 규칙은 “포맷을 먼저 정하고 내용을 끼워 맞추지 않는다”이다.


4. 글의 목적과 독자를 먼저 정의
---------------------------------

각 글을 수정하기 전에 내부적으로 다음을 판단한다.

1. 이 글은 무엇을 설명하려는가?
2. 독자가 글을 읽고 무엇을 이해해야 하는가?
3. 글의 중심이 개념, 구현, 문제 해결, 프로젝트 기록 중 무엇인가?
4. 코드 전체가 필요한가, 핵심 코드만 필요한가?
5. 이 글만 읽어도 되는가, 이전 글을 먼저 읽어야 하는가?

글마다 이 판단을 한 뒤 목차를 구성한다.


5. 코드 사용 규칙
-----------------

1. 글의 핵심과 관계없는 전체 소스 코드는 싣지 않는다.
2. 핵심 흐름을 설명하는 부분만 우선 제시한다.
3. 긴 코드는 역할별로 나눠 설명한다.
4. 코드가 무엇을 하는지만 반복해서 번역하지 않는다.
5. “왜 이렇게 작성했는지”와 “다른 선택지는 무엇인지”를 설명한다.
6. 예제 코드와 실제 프로젝트 코드를 명확하게 구분한다.
7. 생략한 코드가 있다면 생략 사실을 표시한다.
8. 코드의 결과를 주장하려면 실제로 확인된 결과인지 구분한다.
9. 기존 코드의 오류를 발견해도 몰래 고쳐서 정상적인 코드였던 것처럼 쓰지 않는다.
10. C++ 및 Unreal 코드의 이름과 동작은 실제 정의를 확인한다.
11. 코드 줄바꿈은 최대한 줄인다. 한 줄로 충분히 읽을 수 있는 변수 선언, 대입, 함수 선언·정의, 함수 호출, 출력문은 한 줄로 작성한다.
12. 임의의 짧은 글자 수 제한에 맞추기 위해 코드를 기계적으로 여러 줄로 나누지 않는다.
13. 여러 줄로 나누는 것은 한 줄이 실제로 지나치게 길거나, 복잡한 조건·여러 인자·연속 호출의 구조를 구분할 필요가 있을 때로 제한한다.
14. 단순한 스트림 출력은 `<<` 연산자마다 줄을 바꾸지 않는다.

코드 줄바꿈 예시
~~~~~~~~~~~~~~~~~~

다음처럼 한 줄로 충분히 읽을 수 있는 코드는 그대로 한 줄에 둔다.

    unsigned int value = std::numeric_limits<unsigned int>::max();
    std::cout << "checked quotient: " << quotient << '\n';
    bool NearlyEqual(double a, double b, double absoluteTolerance, double relativeTolerance)

다음과 같이 특별한 이유 없이 선언이나 출력식을 나누지 않는다.

    unsigned int value =
        std::numeric_limits<unsigned int>::max();

    std::cout << "checked quotient: "
              << quotient << '\n';

    bool NearlyEqual(double a, double b,
                     double absoluteTolerance,
                     double relativeTolerance)

핵심 기준은 “짧게 보이도록 줄 수를 늘리는 것”이 아니라, 실제 코드를 자연스럽게 읽을 수 있도록 작성하는 것이다.


6. 설명과 문체
--------------

1. 코드에서 명확히 보이는 내용을 장황하게 반복하지 않는다.
2. 설명은 동작보다 목적과 이유에 집중한다.
3. 불필요하게 긴 서론과 AI 특유의 과장된 결론을 피한다.
4. 모든 글에 억지로 “종합 의견”, “핵심 요약”, “Tip”을 붙이지 않는다.
5. 실제로 주의할 사항이 없으면 주의사항 절을 만들지 않는다.
6. 개인 학습 기록이라는 성격을 유지한다.
7. 모르는 내용을 전문가처럼 단정하지 않는다.
8. 용어는 글 안에서 일관되게 사용한다.
9. 한국어 설명을 중심으로 하되 필요한 원문 기술 용어를 함께 표기한다.
10. 제목과 본문 첫 제목이 같은 내용을 중복하지 않도록 한다.


7. 사실성과 깊이
----------------

1. 단순 문법 설명에 불필요한 “최적화” 표현을 붙이지 않는다.
2. 성능 차이를 말할 때는 조건이나 근거를 제시한다.
3. 구현의 장점만 나열하지 말고 한계와 전제도 설명한다.
4. C++ 표준의 동작과 Visual Studio/MSVC의 동작을 구분한다.
5. Undefined Behavior, implementation-defined behavior 등을 정확히 구분한다.
6. Unreal의 서버·클라이언트 동작은 실행 주체와 권한을 명시한다.
7. 블루프린트 또는 DataAsset 설정이 필요한 경우 C++ 구현과 분리해서 안내한다.
8. 프로젝트 고유 설계와 Unreal 일반 원칙을 혼동하지 않는다.


8. 이미지와 실행 결과
---------------------

1. 이미지가 본문 이해에 기여하는지 확인한다.
2. 이미지가 설명하는 시점과 현재 코드가 일치하는지 확인한다.
3. 실행 결과가 없다면 만들어내지 않는다.
4. 이미지 캡션에는 무엇을 봐야 하는지 짧게 설명한다.
5. 깨졌거나 존재하지 않는 이미지 경로를 확인한다.
6. 코드 실행 결과와 에디터 설정 결과를 구분한다.


9. 메타데이터와 시리즈 일관성
-----------------------------

1. 파일명 날짜와 front matter의 `date`를 일치시킨다.
2. 제목의 시리즈 번호를 빠뜨리지 않는다.
3. `categories`는 정해진 계층을 유지한다.
4. 태그의 대소문자와 표기를 통일한다.
5. 같은 시리즈의 제목 규칙을 통일한다.
6. 선행·후속 글이 있으면 자연스럽게 연결한다.
7. 글 순서를 바꾸면 번호와 링크도 함께 확인한다.
8. 기존 URL을 바꿀 가능성이 있는 파일명·제목 수정은 별도로 검토한다.

Chirpy의 permalink가 `:title`을 사용하므로 기존 게시물 제목을 바꾸면 URL과 외부 링크에 영향을 줄 수 있다.
제목을 전면 수정할 때는 리다이렉트 방침부터 정한다.


10. 작업 진행 절차
------------------

1. 수정 전에 해당 시리즈 전체를 읽는다.
2. Git 상태와 사용자 변경사항을 확인한다.
3. 먼저 글별 문제점과 수정 방향을 보여준다.
4. 사용자가 동의한 범위만 수정한다.
5. 한 번에 개발 글 전체를 고치지 않는다.
6. 시리즈 하나 또는 소수의 샘플 글부터 수정한다.
7. 샘플을 사용자가 확인한 뒤 나머지 글에 적용한다.
8. 수정 후 실제 diff를 검토한다.
9. Markdown, front matter, 코드 블록, 내부 링크를 검사한다.
10. Jekyll 빌드를 실행할지는 사용자와 합의한다.
11. 완료된 글과 아직 수정하지 않은 글을 명확히 구분한다.
12. 문서에 적힌 다음 작업을 자동으로 이어서 진행하지 않는다.


11. Codex의 행동 권한
---------------------

- “분석해줘”는 분석만 한다.
- “예시 보여줘”는 예시만 작성하고 파일은 수정하지 않는다.
- “계획 세워줘”는 계획만 만든다.
- 사용자가 명확히 수정 또는 구현을 요청했을 때만 파일을 변경한다.
- 수정 범위가 큰 경우 먼저 대상 글과 예상 구조를 보여주고 동의를 받는다.
- Git commit이나 push는 별도 요청 없이 수행하지 않는다.


핵심 규칙 요약
--------------

1. 내용에 포맷을 맞추고, 포맷에 내용을 끼워 맞추지 않는다.
2. 실제 코드와 프로젝트 상태를 확인하고 작성한다.
3. 확인하지 않은 결과나 개발 과정을 만들어내지 않는다.
4. 설명은 “무엇”보다 “왜”와 흐름에 집중한다.
5. 기존 글의 내용과 사용자 변경사항을 안전하게 보존한다.
6. 시리즈별 샘플을 먼저 합의한 후 단계적으로 수정한다.
7. 분석·제안·수정의 권한을 명확히 구분한다.
